# candidates_presented失効時の能動通知 要否検討

conversation-state-cleanup.md 6節「今後の課題」に残っていた、`candidates_presented`が
`release_idle_conversations()`で失効した際に「候補をご案内しましたが期限切れになりました」等の
メッセージを能動的に送るべきかを検討する。

## 1. 検討した2案

### 案A: 能動送信する
失効した瞬間(または次回スイープ実行時)に、対象顧客へLINEのプッシュメッセージで
「先ほどご案内した空き枠のご案内は期限切れとなりました。あらためてご希望の日時をお知らせください」
のような文言を送る。

- 長所: 顧客が「返信し忘れた」ことに後から気づいた際、なぜ選べないのか(古い候補一覧のまま
  返信すると特定不能扱いになる)を先回りして説明できる。
- 短所:
  1. LINE Messaging APIのプッシュメッセージは無料枠を超えると通数課金が発生する
     (line-api-pricing.md)。「顧客が能動的に話しかけていないタイミングでの送信」は
     プッシュメッセージ扱いとなり、返信(リプライ)より単価が高い。
  2. 送信タイミングが`release_idle_conversations()`のスイープ実行時(Webhook便乗、
     最大5分間隔で間引き)になるため、顧客が離脱してから最大30分+5分程度後に
     脈絡なく通知が届く形になり、顧客体験として唐突になりうる。
  3. 「候補提示 → 無応答 → 期限切れ通知」の往復が、たまたま数十分返信が遅れただけの顧客にも
     一律発生し、通知過多・不要な違和感につながる可能性がある(escalation-consolidation-logic.md
     で連続エスカレーション通知を集約した際と同種の懸念)。

### 案B: 送らない(現状維持)
何も送らず、次回顧客からメッセージが来た時点で通常の新規会話として自然に再開する
(`present_candidates()`から再度開始)。

- 長所: 追加のプッシュメッセージ課金が発生しない。顧客側も「返信を忘れていた」と自覚して
  再度連絡してきた場合は違和感なく会話が続く。
- 短所: 顧客が「あの時提示された枠はまだ有効なはず」と誤解したまま数日後に返信してきた場合、
  `select_slot_from_reply()`は新規会話として扱われるため「もう一度日時を教えてください」という
  やや意図の掴みにくい返答になる可能性がある(ただし特定不能時の再確認文言と同じトーンで
  自然に案内できる範囲)。

## 2. 結論: 案B(MVPでは能動送信しない)を採用

理由:
- 本サービスの主要な価値は「顧客対応の手間削減」であり、追加のプッシュメッセージ課金
  (かつ顧客体験としても唐突になりうる)を払ってまで解消すべき損失は限定的
  (候補一覧は`present_candidates()`を再度呼べば無料で出し直せるため、顧客が再度連絡すれば
  即座に回復する)。
- 想定顧客ヒアリング(customer-interview-design.md)がまだ実施できていない段階では、
  「候補期限切れの唐突な通知」が実際にどの程度の頻度で起き、顧客がどう感じるかの実測値がない。
  実測値なしにプッシュ課金を伴う機能を追加するより先に、まずは案Bで運用し、ヒアリングまたは
  実運用データが取れた時点で必要性を再評価する。
- 技術的には案Aへの切り替えは小さな変更で済む(3節参照)ため、後から追加する障壁は低い。

## 3. 将来案Aに切り替える場合の実装メモ

- `release_idle_conversations()`の戻り値を`list[str]`(user_idのみ)から
  `list[ReleasedConversation]`(`user_id`と失効時の`stage`を持つdataclass)に変更した
  (2026-08-01 14:00 UTC、prototype/engine.py)。これにより呼び出し側は
  `[r for r in released if r.stage == "candidates_presented"]`で通知対象だけを
  取り出せる(`awaiting_details`の無応答離脱は元々通知しない方針のまま変わらず、
  ReleasedConversationのdocstringにも理由を明記)。
- 状態は失効と同時に`_states`から削除されるため、失効後にstageを引き直すことはできない。
  そのため「stageを結果に含める」形にしてある(削除前のスナップショットを返す)。
- 実際に送信する場合の文言案(仮):
  「先ほどご案内したご予約可能日時のご案内は、ご返信がなかったため一旦期限切れとなりました。
  ご希望の日時があれば、あらためてメッセージをお送りください。」
- 送信要否をオーナー側で切り替えられるようにする場合は、owner-settings-wireframe.mdの
  営業情報設定ページにトグルを追加する形が既存の設計パターン(曜日別営業時間トグル等)と
  整合する。

## 4. 今後の課題

  「候補期限切れの通知が欲しいか」を確認項目に追加できないか検討する
  (現行16問には未収載)。
- 案Bのまま運用した場合の実測値(候補提示後どの程度の割合・どの程度の時間差で顧客が
  再度連絡してくるか)は、実LLM呼び出し・実運用開始後でないと取得できない。
