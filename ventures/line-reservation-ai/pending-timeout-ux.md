# 保留タイムアウトのユーザー体験(待機メッセージ文言設計)

double-booking-prevention.md で設計した「仮押さえ(pending)→確定」の2段階方式のうち、
仮押さえ中に顧客へどう伝えるか、タイムアウトが発生した場合にどう案内するかの会話文言を設計する。

## 前提
- 仮押さえのタイムアウトは5分(double-booking-prevention.md の仮設定)。
- 仮押さえ中に必要なのは主に「氏名確認」で、通常は数十秒〜1分程度で完了する見込み。
- 5分間丸ごと顧客を待たせるのではなく、氏名確認の返信が来ない場合の「催促」を挟んでから解放する2段階運用にする。

## 会話文言案

### 1. 仮押さえ直後(氏名確認を依頼する時点)
```
AI: 8/9(土) 15:30〜 カットで仮押さえいたしました。
    お名前を教えていただけますか?(5分以内にご返信いただけますと確実にご予約いただけます)
```
- 「仮押さえ」という言葉を明示し、確定ではないことを顧客に伝える(誤解によるトラブル防止)。
- タイムアウトの目安(5分)を先に伝えることで、返信を促す。

### 2. 一定時間(例: 3分)返信がない場合の催促メッセージ
```
AI: 先ほどの8/9(土) 15:30〜のご予約枠、残り2分ほどで保留時間が終了します。
    お名前だけで結構ですので、よろしければご返信ください!
```
- (2026-11-01 18:00 UTC時点の検討〈フェーズ続き362〉により「あと少しで」から「残り2分ほどで」に
  修正済み。厳密な秒数ではなく分単位の概算表現にすることで、曖昧さによる不安と機械的な印象の
  両方を避ける。経緯・判断理由は本ファイル「2026-11-01 18:00 UTC時点の検討」節を参照。)
- 催促は1回のみとし、しつこい印象を与えない。

### 3. タイムアウトで枠を解放した場合
```
AI: すみません、5分以内にご返信いただけなかったため、8/9(土) 15:30〜の仮押さえを解除いたしました。
    まだご希望でしたら、あらためて空き状況をご案内しますので教えてください!
```
- 顧客側の落ち度を強調しすぎない(「すみません」から始め、店側からのお詫び口調にする)。
- 再度の空き確認へ自然に誘導し、離脱を防ぐ。

### 4. 保留取得に失敗した場合(他の顧客が先に確定・仮押さえ済み)
```
AI: 大変申し訳ございません、ちょうどそちらの枠が埋まってしまいました。
    近い時間ですと 8/9(土) 17:00 / 8/10(日) 14:00 が空いております。いかがでしょうか?
```
- double-booking-prevention.md の「競合時のリカバリー」で定義済みの挙動に、実際の文言を当てた。

## 設計メモ
- 「仮押さえ」「保留」という業界寄りの言葉を顧客向け文言でも維持するか迷ったが、
  誤解防止(確定と誤認させない)を優先し、あえて平易な言い換えはせず明示することにした。
- 催促メッセージのタイミング(3分時点)は暫定値。実運用データが取れたら、
  氏名確認にかかる実際の平均時間を見て調整する。

## 未検証の仮説(要検証)
- 「あと少しで」のような曖昧な残り時間表現が、顧客にとって不安・不親切に感じられないか
- 催促を1回に絞る運用で、タイムアウトによる機会損失(枠が解放されて他の顧客に取られる)がどの程度発生するか

### 仮説1(曖昧な残り時間表現)への対応: 文言修正

一般に、チャット文面では「具体的な数値を短く示す」方が「曖昧な定性表現」よりも
受け手の不安を減らしやすい(残り時間が分からないことそのものが不安要因になりうるため)。
一方で、厳密な秒数提示(「あと187秒」等)は機械的な印象を与え、本サービス全体の
tone-and-manner-guideline.mdが掲げる「事務的になりすぎない」方針にも合わない。
この両者のバランスとして、「あと少しで」を「残り2分ほどで」という分単位の目安表現に
修正する(厳密な秒数ではなく概算であることを示す「ほど」を残すことで、過度な厳密さの
印象を避けつつ曖昧さを減らす)。催促送信タイミング(仮押さえから3分後、タイムアウト
5分後)から逆算すると「残り2分ほど」は実際の残り時間とも一致する。

```
AI: 先ほどの8/9(土) 15:30〜のご予約枠、残り2分ほどで保留時間が終了します。
    お名前だけで結構ですので、よろしければご返信ください!
```

### 仮説2(機会損失)への対応: 設計変更は不要、既存の緩和策で十分と判断

催促を2回以上に増やす案も検討したが、以下の理由で見送り、現行の「催促1回のみ」を維持する。
- 前提(「前提」節)より、氏名確認は通常数十秒〜1分で完了する見込みであり、3分時点の
  催促後さらに2分の余裕がある現行設計は大半のケースをカバーできると見込まれる。
- 催促を増やすほど「しつこい」という逆効果のリスクが上がる一方、本venture側の対策として
  有効なのはタイムアウト発生「後」の体験であり、これは既に本ファイル3項・4項
  (お詫びしつつ即座に空き状況を再案内し、そのまま別候補への誘導を行う設計)で
  実装方針が確定している。つまり機会損失のリスクは「タイムアウトを減らす」方向ではなく
  「タイムアウト発生後の離脱を防ぐ」方向で既に緩和されており、追加の設計変更は不要と判断する。
- 実運用開始後、実際のタイムアウト発生率・催促後の返信率が計測可能になった時点
  (Firestore接続・実店舗運用開始後)で、催促タイミング(3分時点)や回数を再検討する
  運用上の見直し余地として記録しておく(前倒しの再検討トリガー)。

### 結論

仮説1は文言修正(「あと少しで」→「残り2分ほどで」)により対応済みとする。仮説2は
現行設計(催促1回+タイムアウト後の即時再案内)で十分と判断し、設計変更は行わない。
いずれも実店舗での実測はまだ行えていないため、「未検証の仮説」は「机上判断により対応
