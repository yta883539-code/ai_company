# 連続エスカレーション通知の集約ロジック(時間窓・件数)設計

作成日: 2026-07-31

## 目的
escalation-notification-templates.mdの「未検討・要検討事項」に残っていた
「短時間の連続エスカレーションを1通にまとめる」の具体的な時間窓・実装方法を設計する。
同ファイルでは「目安5分以内」「具体的な集約ロジックは実装時に検討」とだけ記載されていたため、
今回は方針をもう一段具体化する(実装・動作検証は未着手)。

## 課題の整理
厳守事項6・10のエスカレーションは即時通知が原則(escalation-notification-templates.md)。
一方で、同一顧客が短時間に複数回問い合わせを重ねるケース
(例:医療相談のあと立て続けに料金相談も送ってくる等)では、
即時性を優先してすべて個別に通知すると、オーナーへの通知が連投され
かえって見落とし・対応の後回しにつながるおそれがある。
「即時性」と「通知過多の防止」を両立させる設計が必要。

## 採用方式: 初回即時 + 追加分は時間窓でまとめて1通

no-show-handling.mdの「翌朝ダイジェスト」方式(全件を遅延集約)はここでは採用しない。
医療相談等の初動遅延リスクが大きいため、初回だけは必ず即時通知する2段階方式とする。

1. **初回発生時**: 現行のテンプレート通り即時に個別通知を送信する。
   同時にその顧客に対して長さ5分の「集約ウィンドウ」を開始する。
2. **ウィンドウ中(5分以内)に同一顧客から追加のエスカレーションが発生した場合**:
   即時送信はせず、ウィンドウ用のバッファに追記する(通知は送らない)。
3. **ウィンドウ終了時(初回発生から5分後)**:
   バッファに1件以上溜まっていれば、まとめ通知を1通だけ送信する。
   バッファが空(追加発生なし)であれば何も送らない。
4. **ウィンドウ終了後に新たなエスカレーションが発生した場合**:
   それを新しい「初回」として扱い、即時通知+新しいウィンドウを開始する(1に戻る)。

時間窓の長さは、escalation-notification-templates.mdに既出の「目安5分以内」を踏襲し
300秒に固定する(可変にする必要が生じた場合のみ将来検討)。

## 件数による文面の出し分け

ウィンドウ終了時のまとめ通知は、バッファ件数に応じて末尾の一文を変える。

- 1〜2件: 通常のまとめ通知のみ。
- 3件以上: 「多数のお問い合わせが続いています」旨を追記し、オーナーが優先的に確認するよう促す
  (同一顧客からの連続エスカレーションは、通常の問い合わせより緊急度が高い可能性があるため)。

## 通知文面案(まとめ通知)

```
【追加報告】[顧客名]様より、直近5分以内にさらに{件数}件のお問い合わせがありました。
内訳: {種別1}、{種別2}...
対応: 最初のご連絡と合わせてご確認・ご連絡をお願いします。
```

3件以上の場合、末尾に以下を追加:
```
※短時間に複数回のお問い合わせが続いています。優先的なご確認を推奨します。
```

## 種別をまたぐ場合の扱い

厳守事項6-a〜d・10のいずれであっても、同一顧客であれば種別を問わずまとめて1つのウィンドウで扱う
(種別ごとに別ウィンドウを立てると通知数が減らず、集約の目的を果たせないため)。
ただしまとめ通知の「内訳」には、faq_segmentsのtopicラベル対応表(escalation-notification-templates.md)と
同様に、種別ごとの日本語ラベルを列挙する。

## 実装方式に関するメモ(概念設計のみ、実装は未着手)

- 顧客ID(LINEのuser ID)単位で `(window_start_at, buffered_events[])` を一時的に保持する必要がある。
- ウィンドウ終了処理(5分後に「バッファを確認してまとめ通知を送るか判断する」処理)は、
  即座に実行されるものではなく遅延実行が必要なため、遅延キュー/ジョブスケジューラ
  (実装時にDB上のタイムスタンプをポーリングする方式か、専用の遅延キューサービスを使うか要検討)が要る。
- 上記は実装時の技術選定が絡むため、本ファイルでは「何を・いつ・どうまとめるか」という
  ロジック仕様の確定にとどめ、技術選定はtech-stack.md側の更新時に改めて検討する。

## 医療相談(6-a)の例外的即時通知の要否 (2026-07-31追記)

**結論: 例外は設けず、医療相談(6-a)もウィンドウ中は他種別と同じくまとめ扱いとする。**

理由:
- そもそも初回発生時点で種別を問わず即時に個別通知しているため、
  最も初動が重要な「最初の医療相談」自体は既に即時到達している。
  例外が効いてくるのは「ウィンドウ中に2件目以降として医療相談が来た」場合のみであり、
  この場合も遅延は最大5分に限られる。
- 医療相談かどうかの種別判定はLLMの分類(厳守事項6-aへの振り分け)に依存するため、
  「医療相談だけ即時」という例外ルールを追加すると誤分類時に例外が発火しない
  (=結局まとめ扱いになる)リスクがあり、例外を作ってもLINE即時性を保証できない。
  そのため「例外を作らずウィンドウ方式を一律適用する」方が、
  誤分類時の挙動も含めて予測可能でシンプルになる。
- 3件以上の場合に付与している「優先的なご確認を推奨します」の一文が、
  医療相談を含むケースでも実質的に緊急度をオーナーに伝える役割を果たす。

以上より、種別による分岐は導入しない。ただし将来、実店舗ヒアリング等で
「医療相談は1件でも即時に知りたい」という声が強ければ、種別ごとの
ウィンドウ有無(6-aのみウィンドウなし=常に即時)への変更を再検討する
(現時点では仮説段階のため見送り)。

## 集約ウィンドウ再発火時の上限ルール (2026-07-31追記)

**結論: 同一「初回」から数えて再発火が3回目(まとめ通知3通目)に達した時点で、
以降はウィンドウを止めて全件即時個別通知に切り替える。**

具体的な挙動:
1. 初回即時通知 → ウィンドウ1回目のまとめ通知(再発火1回目)
2. ウィンドウ2回目のまとめ通知(再発火2回目)
3. ウィンドウ3回目のまとめ通知が発生するタイミングで、そのまとめ通知の末尾に
   以下の一文を追加する:
   ```
   ※短時間のお問い合わせが継続しています。以降のお問い合わせは個別に都度通知します。
     お電話等での直接のご連絡もご検討ください。
   ```
4. 以降(4回目以降の再発火に相当する期間)は集約を行わず、
   発生ごとに即時個別通知に戻す(=通常のエスカレーション同様、都度通知)。
5. この顧客からのエスカレーションが一定時間(目安30分)途絶えたら、
   次回発生時は再び「初回」としてウィンドウ方式からやり直す。

理由:
- 再発火が続く=通知件数そのものが増えている状況でまとめ通知を続けると、
  かえって1通あたりの情報量が増えて確認しづらくなる。
  上限に達した時点で都度通知に切り替え、店舗側に電話等の別手段を促すことで
  「通知が多い=何かおかしい」という状況をオーナーに気づかせやすくする。
- 30秒や1分単位の細かいクールダウンではなく「30分途絶えたらリセット」という
  粗い基準にしたのは、MVP実装をシンプルにするため。実測データが取れた後に調整する。

## 未検討・要検討事項
- 上記の「再発火3回で都度通知に切り替え」「30分途絶えでリセット」の閾値は
  いずれも仮の目安であり、実際の利用データ(1顧客あたりのエスカレーション頻度)が
  取れるまでは机上の値である。
