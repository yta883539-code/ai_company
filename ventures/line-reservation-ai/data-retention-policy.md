# 個人情報の保存期間・削除方針

作成日: 2026-08-03

## 目的

confirmed-state-archival.mdの「今後の課題」およびfirestore-data-model.mdの「残課題」で
いずれも本文書の範囲外として先送りされていた、永続データストア(firestore-data-model.mdの
各コレクション、およびMVP初期のtech-stack.mdが想定するスプレッドシート運用)側に蓄積される
個人情報(顧客の会話履歴・予約履歴・通知ログ)の保存期間・削除方針を整理する。

本文書は個人情報保護法の一般的な考え方を踏まえた設計方針の整理であり、法的助言そのものでは
ない。最終的な妥当性の確認は引き続き法律専門家への確認が必要な事項として残す
(legal-notices-draft.mdと同様の位置づけ)。

## 前提の整理: 「会話メモリのアーカイブ」と「保存期間ポリシー」は別レイヤーの話

confirmed-state-archival.mdが設計した`archive_completed_conversations()`は、あくまで
`ConversationFlowStateMachine._states`という「進行中の会話を追跡するための一時メモリ」を
間引く処理であり、`archivedAt`フラグを立てるだけでレコード自体は削除しない。
一方、本文書が扱うのは「そのレコードを最終的にいつ・どういう条件で削除するか」という、
一段上のデータガバナンスの論点である。両者は別レイヤーであり、後者が定まって初めて
「archivedAt後どれくらいで実削除するか」を決められる関係にある。

## 個人情報保護法の観点からの整理(一般的傾向、法的助言ではない)

- 個人情報保護法は、保存期間の絶対的な上限を一律に定めてはいないが、利用目的の達成に
  必要な範囲を超えて個人データを保有し続けないよう努めることが求められる(努力義務としての
  「正確性の確保等」「消去の努力義務」の考え方)。
- 一方で、以下のような正当な業務上の必要性がある限り、一定期間の保有には合理性がある。
  - no-show-handling.md: 無断キャンセル履歴に基づく事前確認強化(累計予約数・無断キャンセル
    確定数の顧客ごとの参照)。
  - reminder-timing-and-resend-rules.md: 直近の予約状況を踏まえた運用上の参照。
  - 顧客からの問い合わせ対応(「前回いつ予約したか」等の確認)。
  - トラブル発生時の経緯確認(役務提供に関する記録としての事業者側の合理的な保存)。
- したがって「無期限に保有し続けない」ことと「業務上必要な期間は保有する」ことのバランスを
  取る設計とし、明確な期間の上限を設けたうえで、必要であれば延長を検討できる仕組みとする。

## 保存期間ポリシー(案)

firestore-data-model.mdのコレクション構成に対応付けて整理する。

| データ種別 | 対応コレクション | 保存期間(案) | 理由 |
|---|---|---|---|
| 進行中〜直近の会話状態 | `conversations`(`archivedAt`未設定) | 来店日+1日でアーカイブ(既存方針どおり) | confirmed-state-archival.mdで確定済み |
| アーカイブ済み会話状態 | `conversations`(`archivedAt`設定済み) | `archivedAt`から**1年**で削除 | 直近の予約傾向・トラブル経緯確認に使う期間として1年を目安とし、それ以降は下記の「予約実績サマリ」に集約済みという想定 |
| 予約枠(pending) | `bookingSlots`(`status == "pending"`) | 既存のTTL方針(`HOLD_TIMEOUT`超過で失効・削除)を踏襲、変更なし | firestore-data-model.md既定どおり |
| 予約枠(confirmed、来店実績) | `bookingSlots`(`status == "confirmed"`) | **3年** | no-show履歴・リピート顧客判定など中期的な業務利用を想定した目安。飲食店・美容室等の一般的な顧客台帳運用の慣行を参考にした暫定値であり、実運用開始後にオーナーの実感値で見直す |
| 通知ログ生ログ | `notificationLogEntries` | **6か月** | 未解決FAQ・未実装機能問い合わせの傾向把握が主目的で、個々のやり取り自体を長期に参照する必要性は低いため会話履歴より短く設定 |
| 通知ログのユニーク化用エントリ | `notificationLogUniqueTopics` | 生ログと同じ**6か月** | 生ログの集計補助データのため対応させる |
| エスカレーション集約窓 | `escalationWindows` | 既存の時間窓方式で自然に陳腐化(30分無応答等でリセット)、長期保存の対象外 | escalation-consolidation-logic.mdの既定どおり |
| 店舗レコード(オーナー向け設定・課金状態) | `stores/{storeId}` | 休止モード4通目の再通知(移行から90日後)から**さらに1年**、無反応・無操作が続いた場合に削除候補として洗い出す | dormant-mode-renotification-design.mdで新たに認識された残課題への対応。詳細は次項参照 |

いずれの期間も「これを超えたら直ちに機能的な問題が起きる」という技術的制約ではなく、
個人情報保護の観点からの運用ガードレールとして設定する暫定値であり、業種・オーナーの
希望によって調整可能なパラメータとして設計する(店舗ごとの`stores/{storeId}`設定に
将来組み込む余地を残す。MVP段階ではシステム全体の固定値でよい)。

## 店舗レコード(`stores/{storeId}`)の保存期間の考え方

dormant-mode-renotification-design.mdで、休止モードの再通知を90日後の4通目で打ち切った
あとの「店舗レコード自体をいつまで保持するか」が本文書の対象コレクション一覧に含まれて
いない残課題として指摘されていた。これに対応する。

- `stores/{storeId}`は、上記の会話履歴・予約枠・通知ログと異なり「サービス利用者(店舗
  オーナー)自身」に関する記録であり、契約関係(トライアル中・有料プラン中・休止モード中)が
  続く限りは利用目的の範囲内として保有し続けることに合理性がある。休止モードは
  「新規予約受付停止・既存確定予約とリマインドのみ継続」する状態であり、オーナーが
  いつでもプラン選択に戻れることを前提としている(dormant-mode-renotification-design.md)ため、
  再通知の打ち切り(90日)だけをもって即座にレコードを削除するのは、復帰の機会を不当に
  奪うことになり適切でない。
- 一方で無期限の保有は「利用目的の達成に必要な範囲を超えて保有しない」という本文書冒頭の
  基本方針に反するため、明確な上限を設ける。4通目の再通知(移行から90日後)からさらに
  **1年間**、オーナーからの反応(プラン選択・返信・トークルームでの操作等)が一切ない場合に、
  削除候補として洗い出す運用とする。1年という値は、アーカイブ済み会話履歴の保存期間
  (1年)と揃えた暫定値であり、実測データに基づくものではない。
- 削除候補として洗い出した後も即座には削除せず、「顧客からの開示・削除依頼への対応」節と
  同様、オーナーが実在し連絡可能な事業者である以上は、削除前にオーナー(またはその連絡先)へ
  最終確認を試みることが望ましい。

### 最終確認の連絡経路(通知チャネルがブロックされている場合の代替手段)

- 主経路はowner-notification-channel-design.mdが定めるLINE公式アカウントからの
  `owner_user_id`宛push送信とする。休止モードの4回の再通知(dormant-mode-renotification-design.md)
  自体が同じ経路を使っているため、削除候補化時点で「直近4回とも`line_push_failed`が記録されて
  いる(ブロック等で送達できていない)」状態であることが多いと想定される。
- 代替経路として、onboarding-guide.md手順1でオーナー登録時に取得済みの「連絡先メール
  アドレス」を用いる。LINEチャネルが直近の再通知で継続的に失敗している場合に限り、この
  メールアドレス宛の最終確認連絡を代替手段として位置づける。ただし実際のメール送信には
  送信用サービス(SendGrid等)のアカウント作成が別途必要であり、これは「アカウント作成」に
  該当するためオーナー承認待ちの範囲として残る(現時点では「どの宛先を使うか」の方針決定に
  とどめる)。
- 連絡先メールアドレス自体が古いオンボーディング(本項目の方針決定より前)で未収集だった場合、
  またはメール送信サービス未接続のままLINEチャネルもブロックされている場合は、いずれの経路
  でも最終確認ができない「連絡不能」ケースとなる。この場合は自動削除には進まず、削除候補
  リストに「連絡不能」フラグを付けたまま保持し、オーナー(本リポジトリの運営者)が対話
  セッションで個別に削除可否を判断する運用とする(pending-approval.mdと同様、機械的な
  自動実行はしないという本リポジトリ全体の方針に合わせる)。
- 予約実績(`bookingSlots`のconfirmed、3年)や顧客の会話履歴(アーカイブ後1年)は店舗レコード
  より短い・同等の期間で削除されうるため、実際には店舗レコードより先に消える想定である。

### サブコレクションとの削除順序

- firestore-data-model.mdのコレクション構成上、`stores/{storeId}`直下には
  `bookingSlots`・`conversations`・`notificationLogEntries`・`notificationLogUniqueTopics`・
  `escalationWindows`の5つのサブコレクションがぶら下がる。Firestoreは親ドキュメントを
  削除してもサブコレクションのドキュメントを自動的には削除しない(孤立したまま残る)ため、
  削除順序を明示的に設計する必要がある。
- 採用方針: **子(5サブコレクション)を先に全件削除し、最後に親(`stores/{storeId}`本体の
  ドキュメント)を削除する**。逆順(親を先に消す)にすると、削除処理が途中で失敗した場合に
  「オーナー向け設定・課金状態が消えたのにサブコレクションだけ残る」という中途半端な状態に
  なり、以降のバッチが対象店舗を特定できなくなる(`storeId`の手がかりを失う)ため避ける。
  子から先に消す順序であれば、途中で中断しても`stores/{storeId}`本体が残っている限り
  再実行で対象を特定でき、冪等に再試行できる。
- 実装上の留意点: 本ventureのホスティング基盤(hosting-platform-selection.md)はPython製
  Cloud Functionsのため、Node.js Admin SDKが提供する`recursiveDelete()`のような組み込みの
  再帰削除ヘルパーは利用できない。5つのサブコレクションそれぞれに対し、
  `collection.list_documents()`等でページングしながらバッチ削除(`WriteBatch`、
  上限500件/バッチ)する実装が必要になる見込み。この実装自体はidle-conversation-trigger-design.md
  やdormant-mode-renotification-design.mdと同様、実際のFirestore接続後(オーナー承認待ち)の
  課題として残す。

## 削除の実行方法(MVP)

- MVPでは専用の削除バッチジョブは実装せず、idle-conversation-trigger-design.mdと同様の
  「低頻度実行で足りる」性質を踏まえ、実際のホスティング基盤(hosting-platform-selection.md)
  確定後にCloud Schedulerによる日次〜週次バッチとして実装する方針とする(実装自体は
  GCPプロジェクト作成後、オーナー承認待ちの範囲に含まれる)。
- MVPのごく初期(スプレッドシート運用段階、tech-stack.md参照)では、上記期間を超えた行を
  手動またはスプレッドシート関数(日付条件でのフィルタ)で洗い出し、オーナーが確認のうえ
  手動削除する運用で代替してよい。

## 顧客からの開示・削除依頼への対応(方針のみ)

- 個人情報保護法上、本人からの保有個人データの開示・利用停止等の請求に対応できる体制を
  整えておくことが望ましい。MVP規模では、LINEの`sessionId`(userId)を手がかりにオーナーが
  該当レコードを検索・削除できれば足りる想定で、専用の自動化機能(顧客向けセルフサービス
  削除画面等)はスコープ外とする。
- legal-notices-draft.mdのプライバシーポリシー草案に、本方針の要旨(保存期間の目安、
  開示・削除請求への対応窓口がオーナーであること)を反映することを今後の課題とする。
