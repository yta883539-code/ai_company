# 有料プラン移行時のLINE案内文言・決済ページ遷移フロー設計

作成日: 2026-08-14

## 背景

trial-to-paid-billing-flow-consistency-check.md の「残る検討事項」に、有料プラン選択時の
カード登録フロー(LINE上でどう案内し、Stripe Billing等の決済ページへどう遷移させるか)が
UI設計として未着手のまま残っていた。pricing-plan.md / subscription-billing-cost-estimate.md
で確定した「トライアル終了時は自動課金せず、利用実績レポート提示→オーナーの能動的な選択→
その時点で初めてカード登録」という順序を、実際のLINEメッセージ文言・画面遷移として具体化する。

## 全体フロー

```
[トライアル終了(14日 or 予約20件到達)]
        │
        ▼
[Cloud Function C相当: 利用実績レポートをLINEで送信]
        │
        ▼
[オーナーが「有料プランを見る」を選択 or 無視(自動課金なし)]
        │  ※選択しない場合はスタータープラン相当の機能制限モードに移行(下記「未選択時の挙動」参照)
        ▼
[LINEから決済ページ(外部ブラウザ)へ遷移]
        │
        ▼
[決済ページでプラン選択→カード登録]
        │
        ▼
[Webhook経由で決済代行サービスから決済完了通知を受信]
        │
        ▼
[LINEで契約開始完了メッセージを送信]
```

## 1. 利用実績レポート+プラン案内メッセージ(トライアル終了時)

owner-notification-channel-design.md で確定済みのオーナー向け配信経路(LINE公式アカウントの
オーナー用トークルーム)を使う。message-tone-variants.md の店舗設定トーン(formal/standard/
casual)を適用する。

standardトーン文言例:

```
【予約とれる君】無料トライアル終了のお知らせ

14日間の無料トライアルが終了しました。この間の利用実績は以下の通りです。

・処理した予約件数: 32件
・自動対応できたお問い合わせ: 18件
・概算の削減対応時間: 約4時間

引き続きご利用いただく場合は、下記からプランをお選びください。
ご登録いただくまでは自動課金されませんのでご安心ください。

▼ プランを見る・登録する
{決済ページURL}

ご不明点はこのトークルームにご返信ください。
```

- 「利用実績」の3項目は notification-log-classification-labels.md / booking-record-store-design.md
  で既に集計可能な値(確定予約件数、9a/10エスカレーション以外で自動完結した件数、
  1予約あたりの目安対応時間×件数)を流用する。目安対応時間の根拠値は今後の課題として残す
  (現状は「1件あたり約7〜8分の手作業を代替」という一般的な仮定値を置いている)。
- casualトーンは絵文字許容(message-tone-variants.md準拠)、formalトーンは「ご登録」→
  「ご契約手続き」など敬語をやや強める程度の差分とし、内容構成は3トーン共通とする。

## 2. 決済ページへの遷移方式

- LINEのトークルーム内では決済フォーム(カード番号入力等)を直接扱わず、LIFF
  (LINE Front-end Framework)経由 or 通常の外部リンクで決済代行サービス(Stripe Billing
  Customer Portal等を想定)のホスト型決済ページへ遷移させる方式を採用する。
- 理由: カード情報をLINEのトーク上でやり取りする設計は運用者側のPCI DSS対応負荷が大きく、
  MVP規模では現実的でない。ホスト型ページに決済処理自体を委任することで、本サービス側は
  カード情報を一切保持しない構成にできる。
- 決済ページURLには店舗を一意に識別するトークン(既存のセッションID設計
  channel-agnostic-session-id.mdのLINE用識別子を流用)をクエリパラメータとして埋め込み、
  決済完了Webhookと店舗レコードを突き合わせられるようにする。

## 3. 決済完了後のメッセージ

```
【予約とれる君】ご登録ありがとうございます

スタンダードプランへのご登録が完了しました。
本日より正式にご利用いただけます。

・次回請求日: 2026-09-14
・ご登録内容の確認・変更: {決済ページURL}(マイページ)

引き続きよろしくお願いいたします。
```

- 次回請求日は決済代行サービスのWebhookペイロードに含まれる値をそのまま転記する想定
  (Stripe Billingであれば `current_period_end` 相当)。実装時の項目名確定は決済代行サービス
  選定後の課題として残す。

## 4. 未選択時の挙動(新規検討事項)

trial-to-paid-billing-flow-consistency-check.mdでは「継続利用を希望する場合のみ選択する」
とだけ定められており、選択しなかった場合にサービスをどう扱うかが未定義だったため、以下の
方針を新たに定める。

- トライアル終了後、有料プラン未選択のままの店舗は、新規予約の受付を停止し
  (顧客からのメッセージには「現在予約受付を一時停止しています」という定型文で自動応答)、
  既存の確定済み予約・前日リマインドのみ継続する「休止モード」に移行する。
  データを即座に削除せず、オーナーがいつでもプラン選択に戻れる状態を保つ。
- 休止モード移行時・移行後の再通知(7日毎等)の頻度・文言は本ドキュメントのスコープ外とし、
  次の検討事項として残す。

## 未検証の仮説(要検証)

- LIFF経由の遷移とブラウザ外部リンクのどちらがオーナー(非エンジニア)にとって迷いが
  少ないか(LIFFはLINEアプリ内ブラウザで完結するがStripe Billing側の対応状況を要確認)。
- 「利用実績レポート」の3項目がオーナーの継続判断材料として十分か、追加すべき指標
  (例: 対応した顧客数のユニーク数)があるか。
- 休止モードの再通知頻度が督促として煩わしく感じられないか。

## 次のステップ候補

- 実際の決済代行サービス(Stripe Billing等)の選定・契約自体はオーナー承認が必要な
  アクションのため、本ドキュメントの設計はあくまで契約前のUI・文言整理にとどまる
  (pending-approval.md参照)。
- 休止モードへの移行ロジック・再通知設計の詳細化。
