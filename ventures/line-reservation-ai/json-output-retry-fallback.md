# 構造化出力(JSON)フォーマット崩れ時のリトライ・フォールバック設計(2026-07-30時点)

llm-system-prompt-draft.md の「未検証・要検討事項」および「次のステップ候補」で
挙げていた、LLM応答の構造化出力(intent/name/menu/datetime_candidate/confirmed/needs_owner_check)が
毎回安定した形式で返らない場合のリトライ・フォールバック方針を設計する。
実装未着手・動作未検証。

## 想定される崩れ方
1. JSONとして構文的に不正(カンマ抜け、閉じ括弧なし、自然文の説明が前後に混入 等)
2. 構文は正しいがキーが不足/余分(例: `confirmed`キーが無い、想定外の`note`キーが追加されている)
3. 値の型・列挙値が想定外(例: `intent`が定義済み6種以外の値、`confirmed`が文字列"true")
4. 顧客向け自然文とJSONの内容が矛盾(例: 自然文では確定を伝えているのに`confirmed: false`)

## リトライ方針
- 上記1〜3(パース失敗・スキーマ不一致)を検知した場合、まず「同一入力で1回だけ」
  再生成をリクエストする。再生成時のプロンプトには、直前の出力の何が不正だったか
  (パースエラー内容またはスキーマ違反箇所)を短く添えて再提示し、修正を促す。
- 再生成後も不正な場合はリトライを打ち切り、フォールバック処理(下記)に進む。
  無限リトライやユーザー待たせ時間の増大を避けるため、リトライ上限は1回のみとする。
- 4(自然文とJSONの矛盾)はパース自体は成功するため機械的なリトライ対象にしにくい。
  `confirmed`または`needs_owner_check`の一方でも真の場合は「確定/要確認」側を優先する
  安全側判定とし、機械的な補正では対応せず後述のフォールバック(3.確定/要確認関連)として扱う。

## フォールバック方針(リトライでも解消しない場合)
- 顧客への返信: 構造化出力の生成に失敗した場合でも、顧客向け自然文の生成自体は
  別枠で確保する(自然文生成に失敗した場合のみ、定型の待機メッセージ
  「只今混み合っております。少々お待ちください」を送る)。
- バックエンド処理: 構造化データが最終的に得られない/信頼できない場合は、
  intentの種類にかかわらず一律で `needs_owner_check: true` 相当として扱い、
  会話ログをそのままオーナー通知に転送する(no-show-handling.mdの通知設計と同じ経路)。
  楽観的に「予約なし」「変更なし」とみなして処理を進めることは絶対にしない
  (システムプロンプトの厳守事項3・6「確定的な返答をしない/オーナーへおつなぐ」の思想を
  フォーマット崩れ時にも適用する)。
- `confirmed: true` の判定は、リトライ後も構造化出力が安定して得られた場合に限る。
  フォールバック経路に落ちた会話は `confirmed` を常に false 扱いとし、
  誤って二重予約防止ロジック(double-booking-prevention.md)の確定枠を動かさないようにする。

## ログ・監視
- パース失敗/スキーマ不一致/矛盾検知の発生を件数としてカウントし、
  日次で一定件数(要検討: 暫定で1日5件など)を超えた場合はシステムプロンプト側の
  改善(出力形式の指示強化、few-shot例の追加等)を検討するトリガーとする。
- どのケース(1〜4)で落ちたかを分類してログに残し、実装フェーズでの
  プロンプトチューニングの材料にする。

## 未検証・要検討事項
- リトライ1回・矛盾時は安全側判定という方針が、実際のLLM応答傾向(モデル・バージョン)に
  対して十分か、実装後に複数の会話サンプルで検証が必要。
- 日次の許容失敗件数の具体的な閾値は仮置きであり、実運用データが無い現時点では暫定値。

## 次のステップ候補
- エスカレーション(no-show-handling.mdの通知設計)発生時のオーナー通知文面の具体化
- 会話サンプル(複数パターン)を用いたプロンプトテスト設計(正常系・崩れ系の両方を含む)

## 追記(2026-07-31時点): 複合FAQ用の任意フィールド`faq_segments`への対応
json-schema-multi-intent-extension.mdで設計した任意フィールド`faq_segments`(複合FAQ質問時のみ付与)も、
本ドキュメントのスキーマ不一致判定(上記「2. キー不足/余分」)の対象に含める。
`faq_segments`が配列でない、または各要素に`topic`/`resolved`が欠けている場合は、
新しい分岐を設けず既存のリトライ(1回)→フォールバック(`needs_owner_check: true`一律、
`confirmed: false`)にそのまま乗せる。
