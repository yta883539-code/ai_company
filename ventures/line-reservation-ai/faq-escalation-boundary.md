# 厳守事項9(FAQ/雑談)と6(予約以外の相談→エスカレーション)の境界線整理(2026-07-30 18:58 UTC)

llm-system-prompt-draft.md の「未検証・要検討事項」で指摘されていた、
厳守事項9(`intent: "faq"`)と6(予約以外の相談のエスカレーション)の境界が
未整理だった問題への対応。「営業時間は何時までですか」のような単純な質問が
どちらに分類されるべきか曖昧だったため、判定基準を明文化する。

## 問題の所在

厳守事項9は元々「挨拶のみ・雑談・スパム」など"予約に関係しない入力全般"を
短い定型文で受け流す想定だった。一方、厳守事項6は「予約以外の相談」を
すべてオーナーへエスカレーションする設計だった。
しかし「営業時間」「アクセス」「駐車場の有無」のような単純な事実確認は
予約そのものではないが、雑談でもなく、店舗が回答を持っている情報であり、
9番(定型挨拶で受け流す)にも6番(オーナーに丸投げ)にも綺麗に当てはまらない。

## 判定基準(3分類に整理)

入力を受けたら、以下の優先順位で分類する。

1. **新規予約・キャンセル・変更の意図が明確** → 既存の会話フロー(厳守事項1〜5・8)に従う。
2. **店舗が事前登録した静的情報で答えられる質問**
   (例: 営業時間、定休日、住所・アクセス、駐車場の有無、支払い方法、
   メニュー内容・料金表、予約可能な曜日など、owner-settings-wireframe.md の
   オーナー設定画面に入力済みの項目に限る)
   → `intent: "faq"` とし、登録済み情報をそのまま案内する自然文を返す。
   `confirmed: false`、`needs_owner_check: false`。
   9番の対象に含めるが、「定型挨拶で受け流す」ケースとは区別し、
   ここでは実際の店舗情報を回答してよい。
3. **挨拶のみ・雑談・URLのみ/意味不明な文字列などのスパム的入力**
   → 従来通り9番。短い定型挨拶または「ご用件をお知らせください」の一言のみ返す。
   `intent: "faq"`、`confirmed: false`、`needs_owner_check: false`。
4. **上記のいずれにも当てはまらない相談**
   (医療・健康相談、料金交渉、クレーム、店舗未登録情報についての質問、
   個別事情の判断が必要な相談など)
   → 6番の対象としてオーナーへエスカレーション。断定回答はしない。
5. **未実装機能(前払い・デポジット決済等)の問い合わせ**
   → 従来通り10番(6番に準じたエスカレーション)。

判定のポイントは「店舗設定画面に登録済みの固定情報かどうか」。
登録済みなら2番(AIが直接回答してよいFAQ)、未登録・個別事情が絡むなら
4番(6番のエスカレーション)に振り分ける。この線引きにより、
AIが独自判断で回答してよい範囲を「店舗が明示的に許可した情報」に限定でき、
誤った断定回答のリスクを抑えられる。

## システムプロンプトへの反映方針

厳守事項9を「9a. 店舗登録済みの静的情報に基づくFAQへの回答」と
「9b. 挨拶・雑談・スパムへの定型応答」の2つに分割し、9aは
owner-settings-wireframe.md で管理する店舗情報を参照して回答する、
という一文を追記する形を想定。実際のプロンプト文言修正は次回以降に反映する
(本ドキュメントでは判定基準の整理までとし、プロンプト本体の書き換えは
影響範囲確認のため次のステップに切り出す)。
