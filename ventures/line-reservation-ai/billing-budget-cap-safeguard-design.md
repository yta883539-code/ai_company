# 実GCPプロジェクト作成の承認ハードルを下げるための請求額上限(Billing Budget)安全策

## 背景
pending-approval.md(2026-10-23 12:00 UTC記載)に記録した「実GCPプロジェクトの作成(課金設定を
含む)・Firestoreデータベースの新規作成」の承認依頼は、本時刻(2026-11-11 04:00 UTC)時点で
約19日間オーナーからの回答が無いまま保留が続いている。他venture5件の同種依頼(最古は
aircon-pasha等で約1ヶ月超)も同様に保留中であり、「課金設定を含む」という表現が、実際の
想定コスト(unit-economics-estimate.md参照、無料枠を使い切った最悪ケースでも1店舗あたり
月間0.1〜2.6円程度)に比べて重く響き、承認判断を先送りさせる一因になっている可能性がある。
本ドキュメントは、実行(アカウント作成・課金設定)そのものは行わず、承認依頼のリスクを
技術的に小さく・見積もり可能にするための設計のみを行う。

## 今回新たに確認した事実(WebSearch、2026-11-11時点)
- Firestore(Sparkプラン=無料プラン)自体は、支払い情報の登録(クレジットカード登録・
  Blazeプランへの課金アップグレード)なしで利用を開始できる。無料枠(読み取り5万回/日・
  書き込み2万回/日等)を超えた場合はエラーで止まる仕様で、超過課金は発生しない。
- 一方、本venture(hosting-platform-selection.md)が採用したCloud Run functions(旧Cloud
  Functions 2nd gen)は、内部でCloud Build・Artifact Registry等Sparkプランの対象外サービスに
  依存するため、Blazeプラン(課金設定・クレジットカード登録)への切り替えが実質必須である
  (Firestore単体の制約ではなく、サーバーレス関数実行環境側の制約)。したがって「Firestoreは
  無料だがCloud Run functionsを使うなら課金設定が要る」という切り分けを明確にできた。
- 2026年2月3日以降、Cloud Storageのバケット作成・維持にも課金設定(Blazeプラン)が必須に
  なったことを確認したが、本ventureはCloud Storageを利用しない設計(firestore-data-model.md
  のみ)のため本件は影響しない(念のため記録)。

## 提案: Billing Budget(予算アラート)+ 閾値到達時の自動停止による上限保証
Blazeプラン自体は課金設定(クレジットカード登録)を伴うが、「上限なく課金されうる」ことと
「課金設定が必要であること」は別の論点であり、Google Cloudの標準機能である
Cloud Billing Budgets & alertsを使えば、想定外課金のダウンサイドを承認前に確定額へ
限定できる。

1. GCPプロジェクト作成・Blazeプランへのアップグレード直後に、請求先アカウント単位で
   Billing Budgetを作成する(例: 月間500円を予算額とし、50%・90%・100%到達時にオーナー
   宛メール通知)。500円はunit-economics-estimate.mdの最悪ケース試算(プロプラン相当・
   店舗数が仮に100店舗規模まで増えても原価は無視できる水準)に対し十分な安全マージンを
   持つ値として暫定設定する(実際の店舗数が想定を超えて伸びた場合は、オーナー確認の上で
   引き上げる前提)。
2. さらに、Google Cloud公式のサンプルパターン(予算アラートをPub/SubトピックへルーティングしCloud
   Functionで受信、閾値到達時に請求先アカウントをプロジェクトから自動的にデタッチ=
   課金を強制停止する構成)を参考に、`budget-cap-auto-disable`用のCloud Functionを
   deployment-runbook.mdのデプロイ手順に追加候補として記録する。これにより、想定外の
   無限ループ・設計ミス等が発生しても、実際の課金総額が設定した上限(例: 500円)を
   超える前に自動的に止まる(バグにより「気づかないまま数万円課金され続ける」事態を
   機械的に防ぐ)。
3. 自動停止は「請求先アカウントのデタッチ」であり、Firestoreデータ自体の削除は伴わない
   (Blaze→Spark相当への縮退に近い)ため、復旧時はオーナー確認の上で請求先アカウントを
   再アタッチするだけで済む設計とする(データ損失リスクを増やさない)。

## 承認依頼への反映方針
本ドキュメントは設計のみであり、実行(GCPプロジェクト作成・課金設定・Budget作成)は
依然オーナー承認が必要なアクションのため一切行わない。pending-approval.md既存エントリ
(2026-10-23 12:00 UTC記載)自体の文面は履行記録としてそのまま保持し、新規の承認依頼
エントリも追加しない(承認を求めるアクションの実体は変わらないため)。ただし、次回
承認依頼の検討・提示時には、本ドキュメントが示す「月間500円上限のBilling Budget+
自動停止」を添えて提示することで、オーナーが判断しやすい形にすることを次回候補とする。

  実際の閾値確定・通知先メールアドレスの指定はオーナー自身の判断に委ねる。
- `budget-cap-auto-disable`用Cloud Functionの実コード化は、実GCPプロジェクト作成後の
  課題として残す(現時点では構成方針のみ)。
- 他5venture(aircon-pasha・course-set-pasha・forklift-pasha・kura-pasha・
