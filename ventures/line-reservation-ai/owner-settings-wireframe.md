# オーナー向け簡易設定画面ワイヤーフレーム(初回メモ)

README.md / tech-stack.md の「次にやること」候補のうち、
オーナー向け設定画面のワイヤーフレームを検討する。

## 設計方針
- MVP段階ではスプレッドシート直編集でも代替可能という前提だが、
  非エンジニアのオーナーがスマホから迷わず設定できるよう、
  「スプレッドシートの延長」くらいの簡潔さを目指す(多機能な管理画面は作らない)。
- 画面は最小3ページ(営業情報・メニュー・予約一覧)に絞る。

## 画面構成(テキストワイヤーフレーム)

### 1. 営業情報設定ページ
```
┌─────────────────────────────┐
│ 予約とれる君 - 店舗設定         │
├─────────────────────────────┤
│ 店舗名: [___________________] │
│                             │
│ 営業曜日:                    │
│  [月]✓ [火]✓ [水]✓ [木]✓     │
│  [金]✓ [土]✓ [日]☐(定休日)    │
│                             │
│ 営業時間: [10:00]〜[19:00]    │
│  + 休憩時間を追加             │
│                             │
│ ☐ 曜日ごとに営業時間を変える   │
│  (ON時のみ以下を展開表示)      │
│  [月] [10:00]〜[19:00]        │
│  [火] [10:00]〜[19:00]        │
│  [水] [10:00]〜[19:00]        │
│  [木] [10:00]〜[19:00]        │
│  [金] [10:00]〜[19:00]        │
│  [土] [10:00]〜[15:00]        │
│  [日] (定休日のため入力不可)    │
│                             │
│ 予約枠の間隔: [30分 ▼]        │
│  (例: 30分単位で枠を区切る)     │
│                             │
│ 同時受付可能数: [1 ▼]         │
│  (例: 施術台が1台なら1)        │
│                             │
│        [保存する]            │
│                             │
│  > エスカレーション集計を見る   │
└─────────────────────────────┘
```
- 「店舗FAQ情報」欄(本ファイル内「追記: 店舗FAQ情報の入力欄」参照)と
  「通知ログ集計画面」への導線(本ファイル内「追記: 通知ログ集計画面のワイヤーフレーム」参照)は、
  いずれもこの営業情報設定ページ本体に属する要素であり、別ページを増やさない方針を反映して
  上記の主要ワイヤーフレーム図にも明記した(2026-07-31 10:59 UTC追記、これまで追記セクションのみに
  記載され本体図には未反映だった差分を解消)。
- 「曜日ごとに営業時間を変える」トグルを追加(2026-08-01 09:00 UTC追記)。OFF(既定)なら
  従来通り単一の営業時間欄のみで足り、ONにした時だけ曜日ごとの営業時間欄を展開表示する。
  定休日(営業曜日チェックボックスでOFFの曜日)は曜日別営業時間の入力自体を不可とし、
  定休日設定と曜日別営業時間設定が矛盾しないようにする方針(詳細・実装は
  weekday-specific-business-hours.md参照)。
- 「+ 休憩時間を追加」リンクを追加(2026-08-01 10:00 UTC追記)。押すと営業時間欄が
  午前/午後の2区間表示に分割され、昼休憩などを挟む営業時間(例: 9:00-12:00, 15:00-19:00)を
  設定できる。3区間以上への対応や曜日別営業時間との組み合わせ時のレイアウトは未確定
  (詳細・実装はbusiness-hours-lunch-break.md参照)。

### 2. メニュー設定ページ
```
┌─────────────────────────────┐
│ メニュー一覧                  │
├─────────────────────────────┤
│ ・カット       ¥4,000 / 60分  [編集][削除]│
│ ・カラー       ¥8,000 / 120分 [編集][削除]│
│ ・トリートメント ¥3,000 / 30分 [編集][削除]│
│                             │
│        [+ メニューを追加]      │
└─────────────────────────────┘
```
- 追加/編集時の入力項目: メニュー名・料金(任意表示)・所要時間のみ。
- 所要時間は予約枠の自動ブロック計算に使う(例: 120分メニューなら枠を2つ連続で保留)。

### 3. 予約一覧ページ(確認用・読み取り専用が基本)
```
┌─────────────────────────────┐
│ 予約一覧(直近7日間)            │
├─────────────────────────────┤
│ 8/1(木) 11:00 田中様 カット     │
│ 8/1(木) 16:00 佐藤様 カラー     │
│ 8/2(金) 13:00 鈴木様 カット     │
│                             │
│ [今週分をCSVで書き出す]        │
└─────────────────────────────┘
```
- MVPでは編集操作(手動キャンセル等)は「LINEでオーナーに通知→オーナーがAIとの
  トークで指示」の運用とし、この画面自体からの直接編集機能は後回しにする
  (画面の実装コストを最小化するため)。

## 実装メモ
- MVP段階ではNo-codeフォームツール(例: Googleフォーム+スプレッドシート連携、
  またはノーコードDB系サービスの管理画面機能)を流用し、専用フロントエンド開発を
  避けることでゼロ初期投資に近づける方針とする。
- 本格版が必要になった段階で、tech-stack.mdの構成に沿った専用の管理画面(軽量Webアプリ)
  に置き換える。

## 追記: 顧客詳細ページ ワイヤーフレーム(2026-07-30)

no-show-handling.md の設計を受け、予約一覧ページから顧客名をタップすると開く「顧客詳細ページ」を追加する。
既存の3ページ構成(営業情報・メニュー・予約一覧)に対する追加ページという位置づけで、常設のメニューには出さない
(予約一覧からの導線のみとし、画面数を増やしすぎない方針を維持)。

```
┌─────────────────────────────┐
│ 顧客詳細: 田中様               │
├─────────────────────────────┤
│ 累計予約数: 8件                │
│ 無断キャンセル確定数: 1件        │
│ 直近の無断キャンセル: 7/12(日)   │
│ 前回リマインドへの返信: なし      │
│                             │
│ 予約履歴(直近5件)               │
│  7/28 カット   来店済み          │
│  7/12 カラー   無断キャンセル確定  │
│  6/30 カット   来店済み          │
│  …                          │
│                             │
│ (この履歴は顧客本人には表示されません) │
└─────────────────────────────┘
```
- 表示専用ページとし、このページ自体からの編集操作は設けない(来店済み/キャンセルの確定は引き続き予約一覧側で行う)。
- 無断キャンセル確定数が一定件数(仮: 2件)以上の顧客には、ページ上部に「事前確認強化の検討対象」の目印(バッジ等)を出す案があるが、
  対応の要否・具体的な運用はprecheck-strengthening.mdで検討中のため、本ワイヤーフレームでは表示位置の確保のみにとどめる。

## 追記: 店舗FAQ情報の入力欄(2026-07-30)

faq-escalation-boundary.md の残課題で指摘されていた「9a(店舗登録済み静的情報によるFAQ回答)向けの
入力欄が存在するか」を確認した結果、既存の「1. 営業情報設定ページ」には営業曜日・営業時間のみで、
アクセス・駐車場・支払い方法等の項目がなかったため、同ページに項目を追加する。
画面数を増やさず既存の営業情報設定ページの延長として扱い、専用のFAQページは設けない方針とする。

```
┌─────────────────────────────┐
│ 予約とれる君 - 店舗設定         │
├─────────────────────────────┤
│ (既存項目: 店舗名/営業曜日/営業時間/予約枠間隔/同時受付可能数)│
│                             │
│ ── 店舗FAQ情報(AIが自動回答に使用)──│
│ 住所・アクセス: [___________] │
│  (例: ○○駅から徒歩5分)         │
│                             │
│ 駐車場: [○あり ▼] 台数[___]台  │
│  (なし/近隣コインパーキング案内 等)│
│                             │
│ 支払い方法: [現金]✓[クレジット]✓ │
│  [電子マネー]☐ [QRコード決済]☐  │
│                             │
│        [保存する]            │
└─────────────────────────────┘
```
- この欄に入力された項目のみが、システムプロンプトの厳守事項9a(faq-escalation-boundary.md参照)で
  AIが直接回答してよい情報の範囲となる。未入力の項目についての質問は9aの対象外とし、
  厳守事項6(オーナーへのエスカレーション)に振り分ける(=空欄は「未登録」として扱う)。
- 「駐車場: あり」の場合のみ台数入力欄を表示する条件分岐とし、入力の手間を最小化する。
- 支払い方法はチェックボックス形式とし、自由記述欄は設けない(AIの回答が店舗の実態と乖離するリスクを避けるため)。

## 追記: 通知ログ集計画面のワイヤーフレーム(2026-07-31)

escalation-notification-templates.md・escalation-consolidation-logic.mdで設計した、厳守事項6(相談エスカレーション)・
9b(未登録FAQ)・10(未実装機能問い合わせ)発生時のオーナー通知は個別チャット通知のみで、
「どの種類の問い合わせがどれだけ溜まっているか」をオーナーが後から俯瞰する手段がなかったため、
集計専用の画面を追加する。常設メニューには出さず、既存3ページの一角(1. 営業情報設定ページ末尾)に
「エスカレーション集計を見る」リンクを置き、そこからの導線のみとする(画面数を増やしすぎない方針を維持)。

```
┌─────────────────────────────┐
│ 通知ログ集計(直近30日間)         │
├─────────────────────────────┤
│ 未登録FAQ相談: 12件             │
│  内訳: 支払い方法 5 / 駐車場 4 /   │
│       アクセス 3                │
│                             │
│ 未実装機能の問い合わせ: 3件       │
│  内訳: デポジット決済 2 /         │
│       複数店舗一括予約 1          │
│                             │
│ その他エスカレーション(6番): 7件  │
│                             │
│ システム内部イベント: 1件         │
│  内訳: 予約確定時の競合 1          │
│                             │
│ [CSVで書き出す]                │
└─────────────────────────────┘
```

- 表示専用ページとし、この画面からの回答・返信操作は設けない(あくまで傾向把握用)。
- 「未登録FAQ相談」の内訳項目名は、faq-escalation-boundary.mdの9a/9b振り分けで使われる
  項目ラベル(住所・アクセス/駐車場/支払い方法)と揃え、件数が多い項目から店舗FAQ情報欄
  (本ファイル内「店舗FAQ情報の入力欄」参照)への登録をオーナーに促す運用を想定する。
- 「未実装機能の問い合わせ」の内訳は自由記述の要約(LLMが分類ラベルを付与)となるため、
  厳密なカテゴリ一致ではなく参考値である旨を画面上に注記する。
- 「システム内部イベント」は、顧客からの相談ではなく予約枠の競合・候補選択の特定不能など
  技術的な理由でオーナー通知が発火したものを別枠にした欄(notification-log-classification-labels.md
  「システム内部イベントの扱い」参照、2026-08-01追加)。「その他エスカレーション(6番)」は
  人的な相談件数の参考値として意味を持たせるため、この欄を混入させない。
- 実装メモ: MVP段階では専用集計バックエンドを作らず、通知ログを蓄積するスプレッドシートの
  シートに対してCOUNTIF/ピボットテーブルで集計する方式とし、ゼロ初期投資の方針を維持する。
