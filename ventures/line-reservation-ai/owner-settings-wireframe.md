# オーナー向け簡易設定画面ワイヤーフレーム(初回メモ)

README.md / tech-stack.md の「次にやること」候補のうち、
オーナー向け設定画面のワイヤーフレームを検討する。

## 設計方針
- MVP段階ではスプレッドシート直編集でも代替可能という前提だが、
  非エンジニアのオーナーがスマホから迷わず設定できるよう、
  「スプレッドシートの延長」くらいの簡潔さを目指す(多機能な管理画面は作らない)。
- 画面は最小3ページ(営業情報・メニュー・予約一覧)に絞る。

## 画面構成(テキストワイヤーフレーム)

### 1. 営業情報設定ページ
```
┌─────────────────────────────┐
│ 予約とれる君 - 店舗設定         │
├─────────────────────────────┤
│ 店舗名: [___________________] │
│                             │
│ 営業曜日:                    │
│  [月]✓ [火]✓ [水]✓ [木]✓     │
│  [金]✓ [土]✓ [日]☐(定休日)    │
│                             │
│ 営業時間: [10:00]〜[19:00]    │
│  + 休憩時間を追加             │
│                             │
│ ☐ 曜日ごとに営業時間を変える   │
│  (ON時のみ以下を展開表示)      │
│  [月] [10:00]〜[19:00]        │
│  [火] [10:00]〜[19:00]        │
│  [水] [10:00]〜[19:00]        │
│  [木] [10:00]〜[19:00]        │
│  [金] [10:00]〜[19:00]        │
│  [土] [10:00]〜[15:00]        │
│  [日] (定休日のため入力不可)    │
│                             │
│ 臨時休業日:                   │
│  [2026-08-11] [×]            │
│  [2026-09-22] [×]            │
│  + 休業日を追加(日付を選択)     │
│  (祝日・臨時休業など単発の休業日) │
│                             │
│ 予約枠の間隔: [30分 ▼]        │
│  (例: 30分単位で枠を区切る)     │
│                             │
│ 同時受付可能数: [1 ▼]         │
│  (例: 施術台が1台なら1)        │
│                             │
│ メッセージトーン: [standard ▼] │
│  (カジュアル/standard/フォーマル) │
│                             │
│ 常連客とみなす来店回数: [3回 ▼] │
│  (この回数以上の来店実績がある    │
│   顧客は、無断キャンセル確定歴が  │
│   なければ予約確認メッセージを    │
│   簡略化します)                │
│                             │
│        [保存する]            │
│                             │
│  > エスカレーション集計を見る   │
└─────────────────────────────┘
```
- 「店舗FAQ情報」欄(本ファイル内「追記: 店舗FAQ情報の入力欄」参照)と
  「通知ログ集計画面」への導線(本ファイル内「追記: 通知ログ集計画面のワイヤーフレーム」参照)は、
  いずれもこの営業情報設定ページ本体に属する要素であり、別ページを増やさない方針を反映して
  上記の主要ワイヤーフレーム図にも明記した(2026-07-31 10:59 UTC追記、これまで追記セクションのみに
  記載され本体図には未反映だった差分を解消)。
- 「曜日ごとに営業時間を変える」トグルを追加(2026-08-01 09:00 UTC追記)。OFF(既定)なら
  従来通り単一の営業時間欄のみで足り、ONにした時だけ曜日ごとの営業時間欄を展開表示する。
  定休日(営業曜日チェックボックスでOFFの曜日)は曜日別営業時間の入力自体を不可とし、
  定休日設定と曜日別営業時間設定が矛盾しないようにする方針(詳細・実装は
  weekday-specific-business-hours.md参照)。
- 「+ 休憩時間を追加」リンクを追加(2026-08-01 10:00 UTC追記)。押すと営業時間欄が
  午前/午後の2区間表示に分割され、昼休憩などを挟む営業時間(例: 9:00-12:00, 15:00-19:00)を
  設定できる。3区間以上への対応や曜日別営業時間との組み合わせ時のレイアウトは未確定
  (詳細・実装はbusiness-hours-lunch-break.md参照)。
- 「メッセージトーン」選択欄を追加(2026-08-01 15:00 UTC追記)。既定はstandard。
  カジュアル/フォーマルへの変更で確定メッセージ・前日リマインド・FAQ回答等の顧客向け文言の
  語尾・絵文字・感嘆符の使用ルールが一括で切り替わる(詳細な出し分けルールは
  message-tone-variants.md参照)。店舗全体で1つのトーンを選ぶシンプルな設計とし、
  メッセージ種別ごとの個別設定は将来課題とする。
- 「臨時休業日」欄を追加(2026-08-03 00:00 UTC追記)。ad-hoc-closed-dates-support.mdの残課題
  だった入力UIで、`AvailabilitySearcher`/`reminder_scheduler.py`の`closed_dates`に対応する。
  カレンダーUIではなく、日付を1件ずつ追加・削除できるシンプルなリスト入力とした(MVP方針に
  合わせ、祝日データとの自動連携は行わず店舗オーナーが個別に登録する運用)。定休日(曜日単位、
  営業曜日チェックボックス)とは別枠の設定項目として扱い、両者は併用可能(実装上もOR条件で
  両方の休業日を除外する設計、詳細はad-hoc-closed-dates-support.md参照)。過去日付や重複日付の
  入力バリデーションは今回のワイヤーフレームでは未検討のまま残す。
- 「常連客とみなす来店回数」欄を追加(2026-08-04 07:00 UTC追記)。precheck-strengthening.mdで
  MVP採用した案A(無断キャンセル歴のない常連客への確認メッセージ簡略化)を実際に動かすには、
  「常連客」をどの閾値で判定するかを店舗側で設定できる場所が必要だったが、これまで本ワイヤーフレーム
  には対応欄がなかったため新設した(precheck-strengthening.mdの次のステップ候補への対応)。
  - 判定に使う「来店回数」は、本ファイル内「顧客詳細ページ」の「累計予約数」と同じ集計値
    (来店済みとして確定した予約の件数、無断キャンセル確定分は含めない)を流用し、新たな集計ロジックは
    追加しない。
  - 既定値は3回とするが、customer-interview-design.mdのF.(Q17)で指摘した通り業種によって
    「常連客」の感覚(来店頻度・回数)が異なるため、メッセージトーンと同様に店舗ごとに変更できる
    設定項目とし、コード側にハードコードしない。
  - 実際に3回が妥当な既定値かどうかはヒアリング結果(Q17の回答)が得られるまで未確定であり、
    ここでの「3回」はあくまで暫定のプレースホルダーである。ヒアリング結果が出揃い次第、
    業種ごとの既定値を分けるべきかどうかも含めて見直す。
  - 「無断キャンセル確定歴がなければ」の判定は、顧客詳細ページの「無断キャンセル確定数」が
    0件であることを条件とする(1件でもあれば来店回数に関わらず簡略化の対象外とし、
    通常の確認メッセージを送る)。この閾値自体(0件で足りるか)もヒアリング結果を踏まえて
    見直す余地を残す。
- 「臨時休業日」入力欄の過去日付・重複日付バリデーション設計を追加(2026-08-03 01:00 UTC追記)。
  `AvailabilitySearcher`/`reminder_scheduler.py`側は`closed_dates`を`frozenset[date]`として
  受け取るため、重複値はデータ構造上自動的に吸収され、過去日付が混入しても未来日の候補生成には
  影響しない(functionalなバグにはならない)。したがって本バリデーションは「入力ミスに気づかせる
  ためのUX上のガード」という位置づけで設計する。
  - 重複日付: 「+ 休業日を追加」で既に一覧にある日付を再度選択した場合、追加を行わずその場で
    「この日付はすでに追加されています」とインライン表示する(一覧に同じ日付が2行並ぶ状態を防ぐ)。
  - 過去日付: 追加しようとした日付が本日より前の場合、追加を行わずその場で「過去の日付は追加できません」
    とインライン表示する(年の打ち間違い等の入力ミスに気づかせる目的。営業への影響はないため
    ブロックは行わず、あくまで入力時点の即時フィードバックに留める)。
  - 経過後の扱い: 一覧に登録済みの日付が日々の経過で過去日付になった場合は自動削除・自動非表示には
    しない(オーナーが後から「何月何日を休業にしたか」を振り返れる方が、リストが勝手に消えるより
    直感的なスプレッドシート感覚に近いと判断)。MVPはNo-codeフォームツール流用が前提のため、この
    ガードはツール側のフォームバリデーション機能(入力規則)で代替する想定とし、専用コードの実装は
    本格版移行時まで不要と判断する。

### 2. メニュー設定ページ
```
┌─────────────────────────────┐
│ メニュー一覧                  │
├─────────────────────────────┤
│ ・カット       ¥4,000 / 60分  [編集][削除]│
│ ・カラー       ¥8,000 / 120分 [編集][削除]│
│ ・トリートメント ¥3,000 / 30分 [編集][削除]│
│                             │
│        [+ メニューを追加]      │
└─────────────────────────────┘
```
- 追加/編集時の入力項目: メニュー名・料金(任意表示)・所要時間のみ。
- 所要時間は予約枠の自動ブロック計算に使う(例: 120分メニューなら枠を2つ連続で保留)。

### 3. 予約一覧ページ(確認用・読み取り専用が基本)
```
┌─────────────────────────────┐
│ 予約一覧(直近7日間)            │
├─────────────────────────────┤
│ 8/1(木) 11:00 田中様 カット     │
│ 8/1(木) 16:00 佐藤様 カラー     │
│ 8/2(金) 13:00 鈴木様 カット     │
│                             │
│ [今週分をCSVで書き出す]        │
└─────────────────────────────┘
```
- MVPでは編集操作(手動キャンセル等)は「LINEでオーナーに通知→オーナーがAIとの
  トークで指示」の運用とし、この画面自体からの直接編集機能は後回しにする
  (画面の実装コストを最小化するため)。

## 実装メモ
- MVP段階ではNo-codeフォームツール(例: Googleフォーム+スプレッドシート連携、
  またはノーコードDB系サービスの管理画面機能)を流用し、専用フロントエンド開発を
  避けることでゼロ初期投資に近づける方針とする。
- 本格版が必要になった段階で、tech-stack.mdの構成に沿った専用の管理画面(軽量Webアプリ)
  に置き換える。

no-show-handling.md の設計を受け、予約一覧ページから顧客名をタップすると開く「顧客詳細ページ」を追加する。
既存の3ページ構成(営業情報・メニュー・予約一覧)に対する追加ページという位置づけで、常設のメニューには出さない
(予約一覧からの導線のみとし、画面数を増やしすぎない方針を維持)。

```
┌─────────────────────────────┐
│ 顧客詳細: 田中様               │
├─────────────────────────────┤
│ 累計予約数: 8件                │
│ 無断キャンセル確定数: 1件        │
│ 直近の無断キャンセル: 7/12(日)   │
│ 前回リマインドへの返信: なし      │
│                             │
│ 予約履歴(直近5件)               │
│  7/28 カット   来店済み          │
│  7/12 カラー   無断キャンセル確定  │
│  6/30 カット   来店済み          │
│  …                          │
│                             │
│ (この履歴は顧客本人には表示されません) │
└─────────────────────────────┘
```
- 表示専用ページとし、このページ自体からの編集操作は設けない(来店済み/キャンセルの確定は引き続き予約一覧側で行う)。
- 無断キャンセル確定数が一定件数(仮: 2件)以上の顧客には、ページ上部に「事前確認強化の検討対象」の目印(バッジ等)を出す
  (precheck-strengthening.md案Bとして採用済み。閾値判定ロジックはprototype/engine.pyの
  `build_customer_detail_view()`が`precheck_strengthening_flag`として算出する。バッジの具体的な
  表示位置・デザインは未定のため、本ワイヤーフレームでは表示位置の確保のみにとどめる)。
- 上記の各表示項目(累計予約数・無断キャンセル確定数・直近の無断キャンセル日・前回リマインドへの
  返信・予約履歴直近5件)は、外部の永続ストレージ(スプレッドシート等)側で保持される顧客ごとの
  過去予約記録から`build_customer_detail_view()`が組み立てる想定(2026-08-08 19:00 UTC追記)。
  実際にそのストレージから記録一覧を取得する配線はホスティング基盤接続後の課題として残る。

## 追記: 店舗FAQ情報の入力欄(2026-07-30)

faq-escalation-boundary.md の残課題で指摘されていた「9a(店舗登録済み静的情報によるFAQ回答)向けの
入力欄が存在するか」を確認した結果、既存の「1. 営業情報設定ページ」には営業曜日・営業時間のみで、
アクセス・駐車場・支払い方法等の項目がなかったため、同ページに項目を追加する。
画面数を増やさず既存の営業情報設定ページの延長として扱い、専用のFAQページは設けない方針とする。

```
┌─────────────────────────────┐
│ 予約とれる君 - 店舗設定         │
├─────────────────────────────┤
│ (既存項目: 店舗名/営業曜日/営業時間/予約枠間隔/同時受付可能数)│
│                             │
│ ── 店舗FAQ情報(AIが自動回答に使用)──│
│ 住所・アクセス: [___________] │
│  (例: ○○駅から徒歩5分)         │
│                             │
│ 駐車場: [○あり ▼] 台数[___]台  │
│  (なし/近隣コインパーキング案内 等)│
│                             │
│ 支払い方法: [現金]✓[クレジット]✓ │
│  [電子マネー]☐ [QRコード決済]☐  │
│                             │
│        [保存する]            │
└─────────────────────────────┘
```
- この欄に入力された項目のみが、システムプロンプトの厳守事項9a(faq-escalation-boundary.md参照)で
  AIが直接回答してよい情報の範囲となる。未入力の項目についての質問は9aの対象外とし、
  厳守事項6(オーナーへのエスカレーション)に振り分ける(=空欄は「未登録」として扱う)。
- 「駐車場: あり」の場合のみ台数入力欄を表示する条件分岐とし、入力の手間を最小化する。
- 支払い方法はチェックボックス形式とし、自由記述欄は設けない(AIの回答が店舗の実態と乖離するリスクを避けるため)。

## 追記: 通知ログ集計画面のワイヤーフレーム(2026-07-31)

escalation-notification-templates.md・escalation-consolidation-logic.mdで設計した、厳守事項6(相談エスカレーション)・
9b(未登録FAQ)・10(未実装機能問い合わせ)発生時のオーナー通知は個別チャット通知のみで、
「どの種類の問い合わせがどれだけ溜まっているか」をオーナーが後から俯瞰する手段がなかったため、
集計専用の画面を追加する。常設メニューには出さず、既存3ページの一角(1. 営業情報設定ページ末尾)に
「エスカレーション集計を見る」リンクを置き、そこからの導線のみとする(画面数を増やしすぎない方針を維持)。

```
┌─────────────────────────────┐
│ 通知ログ集計(直近30日間)         │
├─────────────────────────────┤
│ 未登録FAQ相談: 12件             │
│  内訳: 支払い方法 5 / 駐車場 4 /   │
│       アクセス 3                │
│                             │
│ 未実装機能の問い合わせ: 3件       │
│  内訳: デポジット決済 2 /         │
│       複数店舗一括予約 1          │
│                             │
│ その他エスカレーション(6番): 7件  │
│                             │
│ システム内部イベント: 1件         │
│  内訳: 予約確定時の競合 1          │
│                             │
│ [CSVで書き出す]                │
└─────────────────────────────┘
```

- システム内部イベントの内訳には、予約確定時の競合(`booking_conflict`)・候補選択の特定不能
  (`candidate_selection_unresolved`)等に加え、LLM API呼び出し自体の失敗(`llm_unavailable`)・
  LINE Push API送信自体の失敗(`line_push_failed`)も表示対象に含める(api-call-failure-handling.md、
  2026-08-04追加)。後者2件はオーナーが「顧客に自動通知が届いていない可能性がある」ことに
  気づく唯一の手段になるため、件数が1件でも見落とされないよう他のシステム内部イベントと同じ
  即時通知(集約ウィンドウを待たない)の扱いとする。

- 表示専用ページとし、この画面からの回答・返信操作は設けない(あくまで傾向把握用)。
- 「未登録FAQ相談」の内訳項目名は、faq-escalation-boundary.mdの9a/9b振り分けで使われる
  項目ラベル(住所・アクセス/駐車場/支払い方法)と揃え、件数が多い項目から店舗FAQ情報欄
  (本ファイル内「店舗FAQ情報の入力欄」参照)への登録をオーナーに促す運用を想定する。
- 「未実装機能の問い合わせ」の内訳は自由記述の要約(LLMが分類ラベルを付与)となるため、
  厳密なカテゴリ一致ではなく参考値である旨を画面上に注記する。
- 「システム内部イベント」は、顧客からの相談ではなく予約枠の競合・候補選択の特定不能など
  技術的な理由でオーナー通知が発火したものを別枠にした欄(notification-log-classification-labels.md
  「システム内部イベントの扱い」参照、2026-08-01追加)。「その他エスカレーション(6番)」は
  人的な相談件数の参考値として意味を持たせるため、この欄を混入させない。
- 実装メモ: MVP段階では専用集計バックエンドを作らず、通知ログを蓄積するスプレッドシートの
  シートに対してCOUNTIF/ピボットテーブルで集計する方式とし、ゼロ初期投資の方針を維持する。

### 未検討事項
- 通知ログにカテゴリラベルを自動付与する処理(LLMによる分類)の精度検証は未着手。

### 集計期間(直近30日固定)の変更可否(2026-08-07 03:00 UTC結論化)

- 検討した選択肢
  1. **専用の期間セレクタUIを追加する**: 「直近7日/30日/90日」等を切り替えるプルダウンを
     この画面に新設する案。利用者体験としては最も分かりやすいが、MVPが前提とする
     「専用集計バックエンドを作らずスプレッドシートのCOUNTIF/ピボットテーブルで代替する」
     方式(本ファイル上記「実装メモ」参照)とは別に、期間選択の状態をどこかに保持し
     ピボットの絞り込み条件を動的に切り替える仕組みが必要になり、ゼロ初期投資の方針から外れる。
  2. **直近30日固定のまま、期間変更が必要な場合はオーナー自身がスプレッドシート側の
     ピボットテーブルの日付フィルタを直接編集する(採用)**: 専用UIは設けず、

- 採用方針: MVPでは選択肢2を採用し、直近30日固定のまま専用UIは追加しない。

## 追記: 曜日別営業時間×複数休憩区間のレイアウト(2026-08-07)

business-hours-lunch-break.mdの残課題だった、(1)休憩区間を3つ以上(朝・昼・夜の3部制等)に
増やせるようにする対応、(2)「曜日ごとに営業時間を変える」ON時に曜日ごとの行へ毎回
「+ 休憩時間を追加」を並べるとスマホ画面で縦に伸びすぎる問題、の2点をあわせて設計した。

### (1) 休憩区間を3つ以上に増やせるようにする

- 「+ 休憩時間を追加」リンクは1回だけでなく、押すたびに区間がもう1つ増える設計に変更する
  (エンジン側`_normalize_business_hour_ranges`は区間数を制限していないため、UI側の
  「1回押すと2区間になり、それ以上は増やせない」という暗黙の制限を外すだけでよい)。
- 区間が3つ以上になったら、各区間の右側に「− 削除」リンクを表示し、増やしすぎた場合に
  戻せるようにする(削除して1区間のみになった状態が「休憩なし」の初期状態と同義)。
```
│ 営業時間: [09:00]〜[12:00] [−]  │
│          [13:00]〜[15:00] [−]  │  ← 2つ目以降の区間には削除リンクを表示
│          [16:00]〜[19:00] [−]  │
│  + 休憩時間を追加             │
```

### (2) 曜日別営業時間ON時のレイアウト(アコーディオン方式)

- 「曜日ごとに営業時間を変える」ONの各曜日行は、既定で「折りたたみ表示(サマリー1行)」
  とし、休憩区間の追加・編集はその行をタップして展開した時だけ行えるようにする。
  一覧性(全曜日の営業時間をざっと見渡せること)と編集のしやすさ(タップした曜日だけ
  「+ 休憩時間を追加」等の操作UIを出すことで画面を縦に伸ばさないこと)を両立する狙い。
- 展開前(折りたたみ状態)は「開始〜終了」を区間の数だけ「/」区切りでサマリー表示する
  (例: `10:00〜19:00` または区間が複数なら`09:00〜12:00 / 15:00〜19:00`)。
- 定休日の曜日(営業曜日チェックボックスでOFF)は展開自体できない行として表示する
  (weekday-specific-business-hours.mdの既存方針どおり、定休日設定と曜日別営業時間設定が
  矛盾しないようにする扱いを踏襲)。
```
│ ☑ 曜日ごとに営業時間を変える   │
│  [月] 10:00〜19:00        [▼] │  ← 折りたたみ状態(サマリー1行)。[▼]タップで展開
│  [火] 09:00〜12:00/15:00〜19:00[▲]│  ← 展開状態の例(火曜のみ展開中)
│    営業時間: [09:00]〜[12:00][−]│
│             [15:00]〜[19:00][−]│
│     + 休憩時間を追加          │
│  [水] 10:00〜19:00        [▼] │
│  [木] 10:00〜19:00        [▼] │
│  [金] 10:00〜19:00        [▼] │
│  [土] 10:00〜15:00        [▼] │
│  [日] (定休日のため入力不可)     │
```
- 「曜日ごとに営業時間を変える」がOFFの場合は、従来どおり単一の営業時間欄1つに
  「+ 休憩時間を追加」を付ける表示のみで、アコーディオンは不要(曜日別ONの場合のみ発生する
  レイアウト課題のため)。

### 実装への影響
- エンジン側(`AvailabilitySearcher`・`_normalize_business_hour_ranges`)は区間数・曜日別の
  組み合わせのいずれも既に対応済みのため、コード変更は不要でUI(ワイヤーフレーム)側の
  表示方法の追加のみで対応できる。

  (`weekday_business_hours`の各値)には影響しない。

### 残課題
- 実際のUI実装(HTML/CSS、アコーディオンの開閉インタラクション)は「公開」に該当する
  範囲まで含めると着手できないため、本追記はテキストワイヤーフレームでの方針確定に留める。
- (訂正 2026-08-07 01:00 UTC: 本節に以前あった「定休日(0分間トグル)と曜日別営業時間の
  二重表現問題は本件でも引き続き未着手のまま残っている」という記載は誤りだったため削除した。

### トライアル終了条件の表示ロジック(2026-08-15追記、フェーズ続き104)

pricing-plan.mdのトライアル終了条件(14日間 または 予約20件到達のいずれか早い方)は
単位が異なる(日数 vs 件数)ため単純比較できない。どちらか一方だけを選んで表示すると、
選ばれなかった条件が先に到達した際にオーナーが気づかないまま突然トライアルが終了する
リスクがある(例: 開始3日目で予約が急に18件入った場合、「あと11日」表示のみでは
「あと2件」で終了することに気づけない)。

- 採用方針: 優先順位をつけて片方だけ選ぶのではなく、**常に2条件とも表示する**
  (「あと5日 / 予約はあと3件」のように1画面に併記)。limit-approaching-notification-design.md
  (aircon-pasha、course-set-pasha等の姉妹venture)が採用している「複数の閾値が近い場合は
  片方に絞らず両方通知する」という考え方と同じ方向性。
- 表示順は常に「日数→件数」の固定順とし、値によって順序を入れ替える動的ロジックは
  導入しない(実装をシンプルに保つため。どちらが先に到達しそうかの強調表示が必要になった
  場合は、残り日数・残り件数それぞれの残り割合(経過日数/14、予約件数/20)が大きい方に
  太字・警告色を付ける案を将来の拡張候補として残す)。
- ワイヤーフレーム(上記4節)の該当行を以下のように修正する(「または」による二者択一表現を
  廃止し、常時併記に変更):

```
│ トライアル終了まで: あと5日 / 予約はあと3件 │
```

- 実装への影響: 新規のデータ項目・バックエンドロジックは発生しない(pricing-plan.mdの
  既存2条件の残り値をそのまま2行として並べるだけ)。強調表示(将来の拡張候補)を実装する
  場合のみ、両条件の進捗割合を比較する軽微なロジックが追加で必要になる。

### 強調表示(進捗割合ベース)の詳細設計(2026-08-16追記、フェーズ続き105)

上記「将来の拡張候補」として残していた、経過日数/14・予約件数/20の進捗割合を比較して
どちらが先に到達しそうかを太字・警告色で強調表示する案を詳細化した。

- **閾値**: 進捗割合が**70%以上**(経過10日目以降、または予約14件以降)に達した条件のみを
  強調表示の対象とする。70%未満のうちは両条件とも通常表示のままとし、トライアル開始直後から
  常に片方が強調されて見える(視覚的なノイズになる)状態を避ける。この「早すぎる段階では
  騒がず、実際に近づいてから知らせる」考え方は、course-set-pasha/aircon-pashaの
  limit-approaching-notification-design.mdが採る「残り一定数を切ってから通知する」設計と
  同じ方向性。
- **強調ルール**:
  - 70%以上の条件が1つだけ → その行のみ太字+警告色(オレンジ等、既存の通知色と統一)。
  - 70%以上の条件が2つとも → 両方とも太字+警告色(「どちらも近い」ことが一目でわかる状態を
    優先し、片方だけを選ばない。上記「常に2条件とも表示する」方針との整合を保つ)。
  - どちらも70%未満 → 強調表示なし(通常表示のまま2条件併記)。
  - 進捗割合が同値の場合(理論上まれ)も、両方70%以上なら両方強調・両方70%未満ならどちらも
    強調しないという同じルールで扱われるため、同値専用の分岐は不要。
- **表示順への影響なし**: 強調表示を導入しても「日数→件数」の固定表示順(フェーズ続き104で
  確定済み)は変更しない。強調は色・太さのみで表現し、行の並び替えは行わない。

```
│ トライアル終了まで: あと3日 / 予約はあと8件 │   ← 日数のみ70%以上(経過11/14日)の例
│              ^^^^^ 太字+警告色              │
```

- **実装への影響**: `progress_days = elapsed_days / 14`・`progress_bookings = booking_count / 20`
  の2値を算出し、各値が0.7以上かを判定するだけの軽微なロジックで実現できる(新規データ項目は
  不要、既存2条件の残り値から算出可能)。バックエンド側で強調フラグを2つ(`highlight_days`・
  `highlight_bookings`)算出して返す設計とし、色・太さの実際の表現方法(CSS等)はMVPが
  No-codeツールの管理画面機能を使う想定のため、採用するツールの制約に応じて実装時に決定する。
- **残課題**: 70%という閾値は机上の仮の目安であり、実際のトライアル利用データ(日数・件数の
  進み方の分布)が得られていない段階での暫定値。実データが取れた段階で、早すぎる/遅すぎるの
  検証・調整が必要(aircon-pashaのlimit-approaching-notification-design.mdが「残り5回」の
  閾値について残している課題と同種)。実装自体は決済代行サービス選定・実際のホスティング
  基盤接続(いずれもオーナー承認待ち)後の着手となる。

## 4節への`suspension_reason`分岐の反映(2026-08-16追記)

payment-failure-dunning-design.md 5節・dormant-mode-renotification-design.md 4.1で
残課題として挙げられていた、`suspension_reason`(なし/`trial_unselected`/`payment_failed`)の
値に応じたステータス表示の出し分けを4節のワイヤーフレームに反映する。従来の4節は
「トライアル中 / スタンダードプラン / 休止モード」の3状態のみを想定しており、
payment-failure-dunning-design.mdで新設された「猶予期間」「制限モード」(いずれも
決済失敗起因)が表示に含まれていなかった。

### 状態遷移とステータス表示の対応表

| `suspension_reason` | 新規予約受付 | ステータス表示 | バッジ色の方向性 |
|---|---|---|---|
| なし・トライアル中 | 継続 | トライアル中 | 通常 |
| なし・決済成功中 | 継続 | スタンダードプラン(次回請求日: {日付}) | 通常 |
| `payment_failed`(猶予期間中、payment-failure-dunning-design.md 3節段階2) | 継続 | お支払い確認中(猶予期間、あと{残り日数}日) | 警告色(オレンジ等) |
| `payment_suspended`(制限モード、同3節段階3) | 停止 | 新規予約受付を一時停止中(お支払い未確認) | 強い警告色(赤等) |
| `trial_unselected`(休止モード) | 停止 | 休止モード(新規予約受付を停止しています) | 強い警告色(赤等) |

- payment-failure-dunning-design.md 3節の状態名(`payment_failed`=猶予期間・
  `payment_suspended`=制限モード)をそのまま`suspension_reason`の値として採用する。
  同ドキュメント3節時点では制限モードの値が明記されていなかったため、休止モードの
  `trial_unselected`と対称になるよう本ワイヤーフレームで`payment_suspended`と命名した
  (`payment_failed`は猶予期間中でまだ新規予約受付を停止していない状態であり、
  制限モードとは新規予約受付の可否が異なるため別値として区別する必要がある)。
- 「猶予期間中」「制限モード」の2状態は見た目のバッジ色を休止モードより弱め(猶予期間中は
  まだ新規予約受付を止めていないため)/同等(制限モードは休止モードと同じく新規予約受付を
  止めているため)に分ける。トライアル終了条件の強調表示(上記「強調表示(進捗割合ベース)の
  詳細設計」節)と同じく、色は既存の通知色体系(警告=オレンジ、停止=赤)を流用し新規の
  配色ルールは起こさない。
- [プランを見る・登録する]ボタンは、`payment_failed`・`payment_suspended`いずれの場合も
  payment-failure-dunning-design.md 4節の各通知文言と同じ決済ページURL
  ({決済ページURL})に遷移させ、休止モード・トライアル中の遷移先(スタンダードプラン契約導線)
  とは別の「お支払い方法の確認・更新」導線であることが分かるよう、ボタン文言を
  [お支払い方法を確認する]に差し替える(既存のスタンダードプラン中の
  [お支払い方法の確認・変更]ボタンと同じ遷移先を再利用できる想定)。

### ワイヤーフレーム(猶予期間中の例)

```
┌─────────────────────────────┐
│ プラン・お支払い状況            │
├─────────────────────────────┤
│ ⚠ お支払い確認中(あと4日)       │
│ お支払い手続きが完了できませんでした。│
│ 期限までにご確認いただけない場合、  │
│ 新規のご予約受付を停止します。     │
│                             │
│ [お支払い方法を確認する]         │
└─────────────────────────────┘
```

- 「あと{残り日数}日」は、payment-failure-dunning-design.md 3節の猶予期間7日と決済失敗検知
  日時から算出する(新規のデータ項目は不要、検知日時+7日−現在日時で導出可能)。
- 制限モード(`payment_suspended`)時の文言は、休止モードのバッジ文言
  (「休止モード(新規予約受付を停止しています)」)と同じ「停止中」であることを明示する
  形式を踏襲しつつ、原因が決済失敗であることが分かるよう
  「新規予約受付を一時停止中(お支払い未確認)」と表示し、休止モードの文言
  (原因はトライアル未選択)と混同されないようにする。
