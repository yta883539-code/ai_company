# LLM API利用コスト試算(1ターンあたりの原価 vs 月額プラン実質単価)

作成日: 2026-09-11

## 背景

unit-economics-estimate.md(GCP/Firestore原価)・payment-gateway-fee-estimate.mdで
決済手数料を試算したが、原価構造のもう一つの主要素であるLLM API呼び出し自体のコスト
(Claude API利用料)は本ventureでは未試算だった。course-set-pasha・kura-pasha・
aircon-pashaは既に同種の試算(llm-api-cost-estimate.md)を行っており、本venture
のみ「専用ファイルが無い」状態がllm-turn-context-design.md「残る課題」に記載漏れの
ような形で残っていた(実際は当初から未着手であり、記載漏れではなく単純未着手)。
claude-apiスキル記載の公開料金表(2026年9月時点)を使用した机上試算であり、実LLM API
呼び出し自体は行わない(オーナー承認待ちの範囲)。

## 他venture(パシャッと系)との前提の違い

course-set-pasha・kura-pasha・aircon-pashaは「メモ1件→下書き3点をまとめて1回で生成」
という単方向バッチ処理のため、生成1回あたりのコストがそのまま課金対象(従量単価40〜60円/回)
と直接比較できた。本ventureは双方向の会話型で、1件の予約確定までに複数ターンのLLM呼び出しが
発生する点、また課金体系が「生成1回ごとの従量課金」ではなく「月額固定+予約件数上限」
(pricing-plan.md)である点が異なるため、(1)1ターンあたりのコスト、(2)1予約(複数ターン)
あたりのコスト、の両方を試算し、(2)をpricing-plan.mdの実質単価(月額÷件数上限)と比較する。

## 前提(1ターンあたりの入出力トークン数の概算)

llm-turn-context-design.mdで採用した設計(案2: サーバー側の構造的引き継ぎ)により、
turn2・turn3でも過去の会話履歴をLLMに渡さない(会話が進んでも入力トークン数が線形に
増えない)方式のため、1ターンあたりの入力は「システムプロンプト+スキーマ(ほぼ固定)+
その時点の顧客メッセージ1件」のみで済む。

- **入力(1)システムプロンプト+構造化出力スキーマ**: llm-system-prompt-draft.md
  (21,097文字)・schema/booking_output.schema.json(3,919文字)の現行ドラフト合計
  約25,016文字。他venture同様、実際にAPIへ送信するシステムプロンプトは設計根拠の
  説明等のメタ記述を除いた凝縮版になる見込みが高いため、以下2シナリオで幅を持たせる。
  - シナリオA(圧縮後の想定・保守的な小規模プロンプト): 2,000トークン
  - シナリオB(現行ドラフトの文字数からの概算・上限側): 日本語・英語混在のMarkdownを
    1トークン≒2文字と仮定し、約12,500トークン
- **入力(2)顧客の当該ターンのメッセージ**: conversation-flow.mdのサンプルの通り
  「来週の土曜の午後空いてますか?カットお願いしたいです」「15:30で」「田中です」
  等、1ターンあたり数文字〜数十文字程度。日本語1文字≒1トークンと概算し、50トークン
  (シナリオA/B共通)。
- **出力(構造化出力JSON 1件)**: intent・name・menu・datetime_candidate・confirmed・
  needs_owner_check等を含むbooking_output.schema.json準拠のJSON 1件分。下書き文章
  3点セットを出力する他ventureと異なり値が数個のフィールドのみのため小さく、
  シナリオAは100トークン、シナリオBは150トークンを採用。

正確なトークン数は、実LLM接続後に`count_tokens`(無料・課金なしの計測専用エンドポイント)
で確認する必要がある(接続自体はオーナー承認待ちのため未実施)。本試算は上記の概算値に
基づく机上の見積もりである。

## 1予約あたりのコスト試算(新規予約フロー=3ターン基準)

conversation-flow.mdの新規予約フロー(1. 候補提示→2. 候補選択→3. 氏名確認・確定)は
LLM呼び出し3回で構成される(FAQ単発応答やキャンセル・変更フローはターン数が異なるため
本試算では代表ケースとして新規予約フローを採用)。

| シナリオ | キャッシュなし(3ターン合計) |
|---|---|
| A | 約3.44円 |
| B | 約17.96円 |

### プロンプトキャッシュ適用時の試算(シナリオB、Sonnet 5)

システムプロンプト+スキーマ(約12,500トークン)は店舗・顧客・ターンによらず共通の
固定部分のため、プロンプトキャッシュ(cache_control)の対象にできる。既に稼働中で
十分な頻度でリクエストが発生している定常状態(キャッシュ読み取り単価=通常の約0.1倍が
毎回効く前提)を仮定すると:

- システムプロンプト部分(キャッシュ読み取り): 12,500トークン × $3/100万 × 0.1 × 150円
  ≒ 0.5625円/ターン
- 顧客メッセージ(キャッシュ対象外): 50トークン × $3/100万 × 150円 ≒ 0.0225円/ターン
- 出力: 150トークン × $15/100万 × 150円 ≒ 0.3375円/ターン
- 合計: 約0.92円/ターン → 1予約(3ターン)あたり約2.77円
  (キャッシュなしの約17.96円から約85%削減)

キャッシュの初回書き込みコスト(約1.25倍の割増)は、aircon-pashaのllm-api-cost-
estimate.mdと同様、全契約店舗・全顧客で共有される固定部分のため、稼働中の店舗数が
一定数を超えれば実質無視できる水準まで償却される見込みだが、正確な損益分岐点の算出には
実際のリクエスト間隔の実測が必要(オーナー承認待ちの範囲、次項に残課題として記録)。

## pricing-plan.mdの実質単価との比較

pricing-plan.mdは従量課金ではなく「月額固定+予約件数上限」のため、月額を件数上限で
割った実質単価と比較する。

| プラン | 月額 | 予約件数上限目安 | 実質単価(月額÷件数上限) |
|---|---|---|---|
| スタータープラン | 2,980円 | 〜50件/月 | 約59.6円/件 |
| スタンダードプラン | 5,980円 | 〜150件/月 | 約39.9円/件 |
| プロプラン | 9,800円 | 〜300件/月 | 約32.7円/件 |

| 比較 | 1予約あたりLLMコスト | 実質単価に対する比率(スタータープラン/スタンダードプラン/プロプラン) |
|---|---|---|
| シナリオB・キャッシュなし | 約17.96円 | 約30.1% / 約45.0% / 約54.9% |
| シナリオB・キャッシュ適用(定常状態) | 約2.77円 | 約4.6% / 約6.9% / 約8.5% |

キャッシュなしの場合、特にプロプラン(実質単価が最も低い)ではLLM原価だけで実質単価の
過半を占めうる水準であり、unit-economics-estimate.mdが結論づけた「GCP/Firestore原価は
無視できる水準」「Stripe手数料が主要コスト要因」という整理に、本venture固有の事情として
「プロンプトキャッシュの導入有無がLLM原価の重みを大きく左右する」という論点を追加する
必要がある。キャッシュ適用時は他venture(aircon-pasha試算で約4〜7%)と近い水準に収まり、
Stripe手数料(月額の約3.6%、payment-gateway-fee-estimate.md)と合算しても粗利を大きく
圧迫しない見込みとなる。

## 結論・次のステップ候補

- 本venture(双方向会話・月額固定+件数上限プラン)は、パシャッと系(単方向バッチ・
  従量課金)と比べてプロンプトキャッシュ導入の重要性が高い。実LLM接続時の実装優先事項
  とする。
- 1予約あたりのターン数は新規予約フロー(3ターン)を代表ケースとしたが、FAQ単発応答
  (1ターン)・キャンセル/変更フロー(オーナー確認を挟むため別ターン構成)は未試算。
  実LLM接続後、conversation-samples-test-cases.mdの各フロー別に実測ターン数の分布を
  取ってから精緻化するのが望ましい。
- 正確なトークン数は`count_tokens`エンドポイント(無料)で実測できるため、実LLM接続の
  承認が得られた際は、まずcount_tokensのみで正確な入出力トークン数を確認し、本試算の
  シナリオA/Bのどちらに近いかを特定してから実際の生成呼び出しに進む順序が望ましい
  (aircon-pashaのllm-api-cost-estimate.mdと同じ順序を踏襲)。
- プロンプトキャッシュの損益分岐点(5分TTLで十分か、1時間TTLが必要か)は、全契約店舗
  合算でのリクエスト間隔の実測データが無いと確定できない(aircon-pashaのプロンプト
  キャッシュ関連の残課題と同種)。実LLM接続後の実測課題として残す。
- 実際のLLM API呼び出し・APIキー取得はオーナー承認が必要なアクションであり、本ドキュメント
  はあくまで契約前の判断材料整理にとどまる(pending-approval.md記載の既存の承認待ち事項の
  範囲内)。
