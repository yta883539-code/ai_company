# 休止モード移行時・移行後の再通知頻度・文言設計

作成日: 2026-08-14

## 背景

billing-upgrade-flow-design.md の「4. 未選択時の挙動」で、トライアル終了後に有料プラン
未選択のままの店舗が移行する「休止モード」(新規予約受付停止・既存確定予約とリマインドのみ
継続)を新たに定義したが、休止モード移行時・移行後の再通知の頻度・文言は同ドキュメントの
スコープ外として次の検討事項に持ち越されていた。本ドキュメントでこれを具体化する。

data-retention-policy.md の保存期間方針(データは即座に削除せず一定期間保持)、
pending-timeout-ux.md の「催促は1回のみとし、しつこい印象を与えない」という基本姿勢、
message-tone-variants.md の3トーン出し分けルールを踏まえて設計する。

## 1. 休止モードへの移行タイミング(猶予期間)

billing-upgrade-flow-design.md の記述だけでは「利用実績レポート送信直後に無反応=即休止」
とも読めてしまうが、オーナーがレポート確認・検討する時間を考慮せず即座に新規予約を止める
のは店舗側の不利益が大きい。以下の猶予期間を新たに設ける。

- 利用実績レポート送信(トライアル終了時)から**3日間**は現状のまま新規予約受付を継続する。
- 3日間の猶予期間終了時点で有料プラン未選択の場合に、休止モードへ移行し1通目の通知を送る。
- 3日間という値は、他の類似判断(pending-timeout-ux.mdの仮押さえタイムアウト5分・催促1回)
  と異なりオーナー(非エンジニア、日常業務多忙)が対象であるため、顧客向けより大幅に長い
  期間を仮置きした暫定値。実測データはまだ無い。

## 2. 休止モード移行後の再通知頻度

「督促として煩わしく感じられないか」という billing-upgrade-flow-design.md の未検証の
仮説を踏まえ、頻度を漸減させたうえで上限を設けて打ち切る方式を採用する
(pending-timeout-ux.mdの「催促は1回のみ」の精神を、単発の催促ではなく状態通知が続く
休止モードに合わせて「回数上限を設けて必ず終わらせる」という形で踏襲する)。

| 通知回数 | タイミング | 目的 |
|---|---|---|
| 1通目 | 休止モード移行時(猶予期間終了時点) | 移行した事実と現状(新規予約停止・既存予約は継続)を伝える |
| 2通目 | 移行から7日後 | プラン選択への軽い再案内 |
| 3通目 | 移行から30日後 | プラン選択への再案内、データ保持期間の目安を伝える |
| 4通目(最終) | 移行から90日後 | 最終案内。以降は再通知しない旨を明示する |

- 4通目以降は再通知を行わない。理由: 無期限の定期通知は「督促が煩わしい」リスクを高め、
  LINE公式アカウントのブロックによる将来の再開機会喪失にもつながりうるため
  (reminder-timing-and-resend-rules.mdが顧客向けリマインドの再送を1回に限定する理由と
  同じ考え方)。
- 4回で打ち切った後も、休止モード自体(新規予約停止・既存確定予約とリマインドの継続)は
  解除されない。オーナーがいつでも決済ページからプラン選択に戻れる状態は維持される
  (再通知の有無とサービスの利用可否は別レイヤー)。
- データの削除タイミングは本ドキュメントでは新たに定めず、data-retention-policy.mdの
  既存の保存期間方針(店舗レコード自体は同ポリシーの対象外のため、別途整理が必要な残課題
  として下記「未検証の仮説」に記載)に従う。

## 3. 通知文言(standardトーン)

owner-notification-channel-design.md で確定済みのオーナー向け配信経路(LINE公式アカウントの
オーナー用トークルーム)を使う。message-tone-variants.mdの規則により、フォーマル/カジュアル
トーンは同表の語尾・絵文字・感嘆符ルールをそのまま適用して機械的に変換できるため、以下は
standardトーンのみ示す。

### 1通目(休止モード移行時)

```
【予約とれる君】休止モードへの移行について

無料トライアルの利用実績レポートからプランのご選択がなかったため、
本日より休止モードへ移行しました。

・新規のご予約受付を停止しました(お客様には自動で受付停止中の旨をご案内します)
・すでに確定済みのご予約と前日リマインドは引き続き通常通り対応します
・データは削除されませんので、いつでもプランをお選びいただければ再開できます

▼ プランを見る・登録する
{決済ページURL}

ご不明点はこのトークルームにご返信ください。
```

### 2通目(移行から7日後)

```
【予約とれる君】休止モードが継続しています

休止モードへの移行から1週間が経過しました。
現在も新規のご予約受付を停止した状態です。

再開をご希望の場合は、下記からいつでもプランをお選びいただけます。

▼ プランを見る・登録する
{決済ページURL}
```

### 3通目(移行から30日後)

```
【予約とれる君】休止モードが継続しています(30日経過)

休止モードへの移行から1か月が経過しました。
確定済みのご予約・前日リマインドは引き続き通常通り対応していますが、
新規のご予約受付は停止したままです。

再開をご希望の場合は、下記からいつでもプランをお選びいただけます。
{決済ページURL}
```

### 4通目・最終(移行から90日後)

```
【予約とれる君】休止モードのご案内(最終)

休止モードへの移行から3か月が経過しました。
これ以降、休止モードに関する定期のご案内はお送りしません。

このままご利用にならない場合も、確定済みのご予約・前日リマインドの対応は継続します。
再開をご希望になった際は、いつでも下記からプランをお選びいただけます。

▼ プランを見る・登録する
{決済ページURL}
```

- 1〜3通目は「催促」ではなく「状態のお知らせ」というトーンを基本とし(billing-upgrade-flow-
  design.mdの利用実績レポートのような能動的な勧誘要素は薄める)、4通目のみ「最終」であることを
  明示して以降通知が来ないことへの不安(見落としたのではという誤解)を防ぐ。
- 顧客向けの自動応答文言(「現在予約受付を一時停止しています」)はbilling-upgrade-flow-design.md
  で定義済みのため変更しない。本ドキュメントはオーナー向け通知のみを扱う。

## 4. 休止モードからの復旧通知(プラン選択完了時)

payment-failure-dunning-design.md 5節「残課題」で、休止モード(`trial_unselected`)からの
復旧通知文言がbilling-upgrade-flow-design.md・本ドキュメントのいずれにも未定義であることが
判明していた(決済失敗〈`payment_failed`〉からの復旧通知は同ドキュメント4節で定義済み)。
本節で対になる文言を新規に定義し、この欠落を解消する。

### 4.1 既存の2メッセージとの違い・使い分け

Webhook受信時点の店舗の状態(`suspension_reason`の値)で送るメッセージを分岐する。

| `suspension_reason`の状態 | 該当ケース | 送るメッセージ |
|---|---|---|
| なし(休止モード未経由) | トライアル中〜終了直後に初めてプランを選んだ場合 | billing-upgrade-flow-design.md 3節「決済完了後のメッセージ」(既存) |
| `trial_unselected` | 休止モードから復帰した場合 | 本節4.2(新規) |
| `payment_failed` | 決済失敗による制限モードから復帰した場合 | payment-failure-dunning-design.md 4節「決済成功による復旧時」(既存) |

billing-upgrade-flow-design.md 3節のメッセージは「本日より正式にご利用いただけます」という
初回開始のトーンであり、休止モード中に発生していた「新規予約受付停止」という状態変化を告知する
一文を持たない。休止モードは最短でも移行から復帰まで数日〜90日超に及びうる(本ドキュメント2節)
ため、初回登録メッセージをそのまま流用すると「新規予約受付を再開した」という最重要事項が
オーナーに伝わらない欠落が生じる。この欠落を埋めるのが本節の目的。

### 4.2 通知文言(standardトーン)

```
【予約とれる君】新規予約受付を再開しました

プランのご登録が完了しました。ご不便をおかけしました。
本日より新規のご予約受付を再開しました。

休止期間中に確定していたご予約・前日リマインドはそのまま引き続き対応しています。

・次回請求日: {決済代行サービスWebhookペイロードの値}
・ご登録内容の確認・変更: {決済ページURL}(マイページ)

引き続きよろしくお願いいたします。
```

- 「次回請求日」の項目はbilling-upgrade-flow-design.md 3節を、「ご不便をおかけしました」の
  詫びの表現はpayment-failure-dunning-design.md 4節をそれぞれ踏襲し、初回登録・決済失敗復旧・
  休止モード復旧の3メッセージ間でトーンの一貫性を保った。
- 「休止期間中に確定していたご予約」の一文は、休止モード中も既存確定予約・前日リマインドは
  継続していた(billing-upgrade-flow-design.md「4. 未選択時の挙動」、本ドキュメント1節の前提)
  ことを再確認してもらう目的で追加した。決済失敗時の復旧メッセージには同様の一文が無いが、
  決済失敗時は猶予期間+制限モードが最短でも7日程度と短いのに対し、休止モードは90日を超えて
  継続しうるため、より長い空白期間後の安心材料として明記する価値が高いと判断した。

### 4.3 顧客向け自動応答の切り替え

休止モード中、顧客には「現在予約受付を一時停止しています」という定型文で自動応答していた
(billing-upgrade-flow-design.md「4. 未選択時の挙動」)。復旧通知(4.2)と同時にこの自動応答
フラグを解除し、通常の予約受付フローに戻す。休止モード移行時に顧客への個別通知を行っていない
のと対称に、復旧時も顧客への能動的な通知は送らない(次回の問い合わせ時から自動的に通常の
応答に戻る)。

## 5. 送信要否の判定(2026-08-29 フェーズ続き145で追加)

trial-end-scheduler-design.md 5節に残っていた「レポート送信後、3日間の猶予期間中に
プラン選択が完了した場合の`trialEndReportSentAt`と`suspensionReason`の整合」を解消する。

`prototype/dormant_mode_scheduler.py`の`compute_dormant_schedule()`はイベントの予定表
(1〜4通目の予定時刻)を算出するのみで、「実際に今その店舗へ送るべきか」は別途判定が
必要だった。この判定を`select_due_dormant_events()`として実装した。

- `trial_end_report_sent_at`時点では`suspension_reason`はまだ`"trial_unselected"`に
  書き換わっていない(1通目送信時に初めて書き換わる、4節の`cloud_function_subscription_
  activated_webhook.py`参照)ため、`suspension_reason`だけでは猶予期間中の決済完了を
  判定できない。かわりに`stripeCustomerId`(`checkout.session.completed`受信時に
  Webhookが設定、firestore-data-model.md参照)の有無を「有効な契約が成立したか」の
  代理指標として使う。1通目未送信のうちに`stripeCustomerId`が設定されれば、休止モード
  自体に一度も入らず通常運用へ戻る(1通目を送らず、`dormant_transitioned_at`も書き込まない)。
- 冪等性フラグとして`dormant_transitioned_at`(1通目送信済み時刻)・
  `dormant_renotify_count`(2〜4通目のうち何通送信済みか、0〜3)の2フィールドを新設する
  (firestore-data-model.mdに反映)。
- 2〜4通目(renotify)は、1通目送信後に`subscription_activated`Webhook経由で
  `suspension_reason`が解除(`None`へ)されていれば対象外とする(4節の復旧通知が
  既にそちらで送信済みのため)。`dormant_renotify_count`が3に達した後は2節の
  「4回で打ち切り」方針どおり以降何も返さない。
- `suspension_reason == "payment_failed"`の店舗は対象外とする(決済失敗からの猶予期間・
  制限モードはdunning_notification_scheduler.pyの担当、1節の前提どおり)。

テスト9件追加(test_dormant_mode_scheduler.py `SelectDueDormantEventsTests`)、
line-reservation-ai配下計383件全件パス・schema検証25件パスを確認した。承認不要な設計・
実装・テスト追加のみで、外部サービスへの公開・アカウント作成・支払い等は発生していない
ためpending-approval.mdへの追記なし。実際のCloud Schedulerからの呼び出し配線・
Firestoreからの候補読み取りクエリ組み立ては、実ホスティング基盤接続時の課題として残る。

## 6. 送信配線の実装(2026-08-29 13:00 UTC定例更新)

5節で残っていた「`select_due_dormant_events()`とLINE Push送信を実際につなぐ配線」を、
`dunning_notification_scheduler.py`に対する`cloud_function_send_dunning_notifications.py`
と同じ役割分担で、`prototype/cloud_function_send_dormant_notifications.py`として実装した。

- `select_due_dormant_events()`は1店舗につき最大1件のイベントしか返さない設計のため、
  `send_dormant_notifications()`も1回の起動につき各店舗最大1件のみ送信する(複数回分の
  未送信が溜まっている場合は次回以降の起動で1件ずつ追いつく、既存の`select_due_
  dormant_events()`の設計をそのまま踏襲)。
- 5節の docstring が前提としていた「1通目(`transitioned`)送信時に初めて`suspension_
  reason`が`trial_unselected`に書き換わる」処理を、本モジュールの送信成功時の状態更新と
  して実際に実装した(これを実装しないと、`select_due_dormant_events()`の2〜4通目判定
  〈`state.suspension_reason != "trial_unselected"`〉が常に不成立になり2通目以降が
  永久に送信されないバグになることをテストで発見・修正した)。
- 送信失敗時は状態(`dormant_transitioned_at`/`dormant_renotify_count`/`suspension_
  reason`)を一切書き込まず、次回起動時に同じイベントが再度送信対象になる設計とした
  (`send_dunning_notifications()`と同じ「送信成功時のみ状態を書き込む」方針)。
- 復旧通知(`render_dormant_recovery_message()`)は決済代行サービスのWebhook
  (`subscription_activated`)を直接トリガーとする別経路の担当のため、本モジュールの
  スコープ外(4節参照)。

テスト9件追加(`test_cloud_function_send_dormant_notifications.py`
`SendDormantNotificationsTests`)、line-reservation-ai配下計392件全件パス・
schema検証25件パスを確認した。承認不要な設計・実装・テスト追加のみで、外部サービスへの
公開・アカウント作成・支払い等は今回発生していないためpending-approval.mdへの追記なし。
実際のCloud Schedulerからの定期呼び出し配線・Firestoreからの候補読み取りクエリ組み立ては、
引き続き実ホスティング基盤接続時(オーナー承認待ち)の課題として残る。

## 未検証の仮説(要検証)

- 猶予期間3日・再通知タイミング(7/30/90日)・4回打ち切りは、いずれも実測データの無い
  暫定値。実運用開始後、休止モードからの復帰率・ブロック率等の実データを見て見直す。
- 4.1の3分岐(`suspension_reason`なし/`trial_unselected`/`payment_failed`)が、実際の
  決済代行サービスのWebhookペイロードから正しく判定できるかは、サービス選定後の実装時に
  確認が必要な残課題として残る。
- (解消済み 2026-08-14 17:00 UTC: 90日打ち切り後にデータをいつまで保持するか〈店舗レコード
  自体の保存期間〉をdata-retention-policy.mdに新設した「店舗レコード(stores/{storeId})の
  保存期間の考え方」節で整理した。4通目の再通知〈90日後〉からさらに1年間オーナーからの
  反応がなければ削除候補として洗い出す方針とし、削除前のオーナーへの最終確認・サブ
  コレクションとの削除順序は新たな残課題として残した)
- 「1通目は移行日当日、以降7/30/90日」という間隔がオーナーにとって唐突すぎないか
  (例えば2通目を3日後にすべきか等)は、実際のオーナーの反応を見ないと判断できない。
