# 決済失敗(カード継続課金エラー)時の再試行・案内設計

作成日: 2026-08-16

## 背景

billing-upgrade-flow-design.md・dormant-mode-renotification-design.mdは、いずれも
「トライアル終了時に有料プランを未選択のまま放置した場合」の休止モード移行を扱っている。
一方、いったんスタンダードプランへ加入し継続課金が始まった後に、**カード期限切れ・利用限度額
超過・カード停止等で毎月の自動課金自体が失敗するケース**(いわゆるdunning対応)は
どのドキュメントにも定義がなく、未検討のまま残っていたため本ドキュメントで整理する。

決済代行サービス自体の契約・実装配線は引き続きオーナー承認待ち(pending-approval.md参照)
のため、本ドキュメントは机上の設計のみを行い、実装・実際の課金は行わない。

## 1. 「未選択」と「決済失敗」の違い

| | 休止モード(既存) | 決済失敗(本ドキュメント) |
|---|---|---|
| 発生条件 | トライアル終了時に一度もプラン選択していない | 既にプラン選択済みで、毎月の継続課金が失敗した |
| 新規予約受付 | 停止 | 継続(即停止しない。理由は後述) |
| オーナーの心理的状態 | 検討中・未決断 | 「払っているつもり」の場合が多く、通知を見落とすと不満につながりやすい |

決済失敗は「意図的な未加入」ではなく、大半はカード更新のし忘れ等の事務的な理由と想定され、
即座に休止モード相当の制限をかけると、既に対価を払う意思のあるオーナーに不利益が大きい。
そのためdormant-mode-renotification-design.mdの4段階通知方式をそのまま流用せず、
猶予期間を設けたうえで独立したフローとして設計する。

## 2. 再試行(リトライ)方針

- 決済代行サービス側の自動リトライ機能(Stripe Billing等の一般的なdunning機能)に委ねる
  想定とし、自前でリトライスケジュールを実装しない。理由: unit-economics-estimate.mdで
  確認済みの通り自前インフラの原価は極小のため、リトライロジックの独自実装コストに
  見合うメリットが薄く、決済代行サービス側の実績あるロジックを流用する方が安全。
- 自前で持つのは「決済失敗イベントをWebhookで受け取り、店舗の状態を`payment_failed`に
  更新し、オーナーへLINE通知する」部分のみ。リトライの成否もWebhookイベントとして
  受け取り、成功すれば状態を`active`に戻す。

## 3. 猶予期間と新規予約受付の扱い

決済失敗検知後、即座に新規予約受付を止めない。以下の3段階とする。

| 段階 | タイミング | 新規予約受付 | 既存確定予約・リマインド |
|---|---|---|---|
| 1. 通常運用 | 決済成功中 | 継続 | 継続 |
| 2. 猶予期間(`payment_failed`) | 決済失敗検知〜7日間 | 継続 | 継続 |
| 3. 制限モード(`payment_suspended`) | 猶予期間終了後も未解消 | 停止(休止モードと同じ制御を再利用) | 継続 |

- 猶予期間を7日間としたのは、dormant-mode-renotification-design.mdの休止モード猶予期間
  (3日間、意思決定を待つ性質)より長い。決済失敗はオーナーの能動的な判断待ちではなく
  「カード会社への問い合わせ・カード再登録」という事務作業待ちであり、カード会社からの
  再発行郵送等を考慮すると3日では短すぎると判断したための暫定値(実測データなし)。
- 段階3(制限モード)は、新規予約受付停止という制御そのものは休止モードと同一のため、
  既存のフラグ機構を流用し`suspension_reason`(`trial_unselected` / `payment_failed`)を
  区別する属性として追加する設計とする(新規のON/OFF制御を二重実装しない)。
- (2026-08-16追記: owner-settings-wireframe.mdへの反映時に、段階2(猶予期間)と段階3
  (制限モード)は新規予約受付の可否が異なるため`suspension_reason`の値としても区別が
  必要と判明し、段階3の値を`payment_suspended`と命名した。段階2は引き続き`payment_failed`
  のままとする。本節の表・5節はこの命名を前提に更新していないため、値の呼称は
  owner-settings-wireframe.md「4節への`suspension_reason`分岐の反映」節を正とする)

## 4. 通知文言(standardトーン、message-tone-variants.md準拠)

### 決済失敗検知時(猶予期間開始)

```
【予約とれる君】お支払いの確認をお願いします

いつもご利用ありがとうございます。
今回のお支払い手続きが完了できませんでした
(カードの有効期限切れ・利用限度額等が考えられます)。

現在、サービスは通常通りご利用いただけます。
7日以内にお支払い方法をご確認・更新いただけますようお願いします。

▼ お支払い方法を確認する
{決済ページURL}
```

### 猶予期間終了直前(3日前リマインド)

```
【予約とれる君】お支払い確認のお願い(再送)

お支払い手続きが未完了のままです。
このままですと3日後に新規のご予約受付を一時停止いたします
(すでに確定済みのご予約・前日リマインドには影響しません)。

▼ お支払い方法を確認する
{決済ページURL}
```

### 猶予期間中間地点の状況確認((b)14日構成のみ、6.2節)

```
【予約とれる君】お支払い確認の状況をご案内します

お支払い手続きがまだ完了していないようです。
検知から{経過日数}日が経過しました。猶予期間は残り{残り日数}日です。
お手数ですが、お支払い方法のご確認・更新をお願いします。

▼ お支払い方法を確認する
{決済ページURL}
```

(2026-08-17追記・フェーズ続き112: `prototype/dunning_notification_scheduler.py`実装時に
本ドキュメントへの記載漏れが判明し新規に書き下した文面。(a)7日構成では送信されない
(6.2節参照)。他の4文言と同じくstandardトーン・tone-and-manner-guideline.md準拠とし、
経過日数・残り日数を明示する内容とした。)

### 制限モード移行時(段階3)

```
【予約とれる君】新規予約受付を一時停止しました

お支払い手続きが確認できないため、新規のご予約受付を停止しました。
すでに確定済みのご予約と前日リマインドは引き続き通常通り対応します。

お支払い方法をご確認いただければ、確認完了後に自動で新規受付を再開します。

▼ お支払い方法を確認する
{決済ページURL}
```

### 決済成功による復旧時

```
【予約とれる君】お支払いを確認しました

お支払い手続きが完了しました。ご不便をおかけしました。
新規のご予約受付を再開しましたので、引き続きよろしくお願いします。
```

- 猶予期間終了直前リマインドは1回のみとし、pending-timeout-ux.mdの「催促は1回のみ」の
  方針を踏襲する。
- 決済成功による復旧の通知は、Webhookの`payment_succeeded`(またはリトライ成功)イベントを
  トリガーとし、`suspension_reason`が`payment_failed`の場合のみ送る
  (`trial_unselected`起因の休止モード解除とは別文言のため、既存の休止モード解除通知
  〈billing-upgrade-flow-design.mdでは未定義、こちらも次のステップ候補に記載〉と混同しない)。
  - (2026-08-18 17:00 UTC・フェーズ続き115で修正)上の「`payment_failed`の場合のみ」だけでは、
    猶予期間中(検知通知は届いているがまだ制限モードに入っていない)に決済が成功したケースで
    通知が一切送られず、検知通知を受け取ったオーナーが解決したか分からないまま放置される。
    かといって上の復旧文言をそのまま流用すると「新規のご予約受付を再開しました」となり、
    実際には一度も止まっていない受付が止まっていたかのような誤解を与える。そのため猶予期間中
    専用の文言(下記)を新設し、決済成功時の分岐を3通りに整理した。
    1. `suspension_reason == "payment_failed"` → 上の復旧文言(受付再開を伝える)
    2. 猶予期間中かつdunning通知を1通以上送信済み → 猶予期間中用の完了通知(下記)
    3. 猶予期間中だがdunning通知は未送信 → オーナーは決済失敗自体を知らないため通知しない
       (状態のリセットのみ)
    dunning中でない店舗の`payment_succeeded`(毎月の正常な課金成功)も通知しない。

### 猶予期間中(制限モード移行前)の決済成功時

```
【予約とれる君】お支払いを確認しました

お支払い手続きが完了しました。お手数をおかけしました。
ご予約の受付はこれまでどおり続いています。引き続きよろしくお願いします。
```

## 5. 残課題・未検証の仮説

- 猶予期間7日・リマインド1回のみという値は、いずれも実測データの無い暫定値。
- (解消済み 2026-08-17 11:00 UTC: 決済代行サービスをStripe Billingと仮定した場合の
  スマートリトライ標準スケジュールをWeb調査で確認した。デフォルト推奨設定は「2週間で
  最大8回」、Stripe推奨のカスタム設定でも「3〜4週間で3〜4回」が目安であり、いずれも
  本ドキュメントの猶予期間7日より長い。カスタムスケジュール(Billingベースプランは
  最大3回・Billing Scaleプランは最大8回、間隔1・3・5・7日から選択)を使えば7日以内に
  収めることも可能だが、その場合はStripe標準のML最適化(成功確率が高いタイミングを
  推定して再試行する仕組み)より試行回数が絞られ回収率が下がるトレードオフがある。
  したがって「猶予期間7日」を維持する場合は(a)カスタムスケジュール(1・3・5・7日、
  最大3〜4回)を選び猶予期間内にリトライを収める、または(b)標準のスマートリトライ
  (最大2週間)を使い猶予期間を14日程度に延ばす、のいずれかを決済代行サービス選定時に
  選ぶ必要があることが判明した。回収率とオーナー体験(猶予期間の長さ)のどちらを優先
  するかの選択はサービス選定・契約自体を伴うためオーナー承認待ちとし、本ドキュメントでは
  上記(a)(b)の二択と各トレードオフを整理するにとどめる。
  出典: https://docs.stripe.com/billing/revenue-recovery/smart-retries 、
  https://stripe.com/blog/how-we-built-it-smart-retries)
- (解消済み 2026-08-16 18:59 UTC: 休止モード〈trial_unselected〉からの復旧通知文言は
  dormant-mode-renotification-design.md 4節で新規設計した。決済失敗からの復旧通知(本
  ドキュメント4節)と合わせ、`suspension_reason`の値〈なし/`trial_unselected`/
  `payment_failed`〉に応じた復旧メッセージ3種の使い分けが出揃った)
- (解消済み 2026-08-16 23:59 UTC: `suspension_reason`属性の追加をowner-settings-wireframe.mdの
  「4. プラン・お支払い状況ページ」の表示分岐に反映した。休止モード・猶予期間・制限モードの
  3状態それぞれのステータス文言・バッジ色・ボタン遷移先を対応表として整理した。詳細は
  owner-settings-wireframe.md「4節への`suspension_reason`分岐の反映」節参照)
- 実際のWebhook受信・状態更新の実装、決済代行サービスとの契約は、引き続きオーナー承認待ち

## 6. 猶予期間の値による通知文言・リマインドタイミングへの影響(二択A/Bの事前整理)

5節で判明した二択(a: 猶予期間7日を維持しカスタムスケジュールで収める/b: 標準スマート
リトライを使い猶予期間を14日程度に延ばす)は、決済代行サービス選定・契約自体を伴うため
どちらを選ぶかはオーナー承認待ちのまま(引き続き未確定)。ただし、4節の通知文言は現状
「7日以内」「3日後」を固定の文言として書き下しており、(b)が選ばれた場合に文言の書き直し
が発生する。契約自体は待つとしても、実装着手時にすぐ差し替えられるよう、猶予期間の値に
連動する部分をあらかじめ整理しておく。

### 6.1 文言のパラメータ化

4節の文言のうち、猶予期間の日数に依存する箇所を固定文字列ではなく変数として扱う設計とする。

| 変数名 | 決済失敗検知時の文言中の用途 | (a)7日の場合 | (b)14日の場合 |
|---|---|---|---|
| `{猶予日数}` | 「{猶予日数}以内にお支払い方法をご確認・更新いただけますよう」 | 7日 | 14日 |
| `{リマインド送付日数前}` | 「このままですと{リマインド送付日数前}後に新規のご予約受付を一時停止いたします」(逆算表現) | 3日 | 後述6.2参照 |

### 6.2 リマインド回数・タイミングの見直し

現行(3節・4節)は猶予期間7日を前提に「猶予期間終了3日前(検知から4日後)に1回だけ
リマインド」という設計だった。(b)で猶予期間が14日に伸びる場合、1回だけのリマインドでは
検知から終了までの間隔が空きすぎ、pending-timeout-ux.mdが「催促は1回のみ」とした前提
(猶予期間3〜7日程度の短さを想定した設計)から外れる懸念がある。そのため(b)を選ぶ場合は
以下のようにリマインド回数を1回から2回に見直す案を追加で用意しておく。

- (a)7日のまま: 現行どおり検知時1通+終了3日前(検知から4日後)に1通の計2通構成
  (4節の記載を「1回のみ」としていたのは終了直前リマインドの回数であり、検知時通知と
  合わせると元々2通構成だった。この点は表現の混同であり、以下(b)の追加で整理する)。
- (b)14日の場合: 検知時1通+中間地点(検知から7日後、Stripeスマートリトライのデフォルト
  期間と重なるタイミング)の状況確認1通+終了3日前(検知から11日後)の1通の計3通構成とし、
  期間の長さに応じてリマインド頻度も増やす。

いずれの構成でも、決済成功による復旧通知(4節末尾)とWebhookトリガーの実装方針は
変わらないため、この部分は(a)(b)どちらが選ばれても再設計不要。

### 6.3 実装への反映方針

上記のとおり、猶予日数・リマインド回数・リマインドタイミングはすべて設定値として
切り出し、通知文言テンプレート側はプレースホルダーで参照する形にすることで、決済代行
サービス選定時に(a)(b)いずれが選ばれても、設定値の変更のみで対応できる状態にしておく。
実際のテンプレートエンジン実装・Webhook配線自体は、他の項目と同様に決済代行サービスとの
契約を伴うためオーナー承認待ち(pending-approval.md参照)。
