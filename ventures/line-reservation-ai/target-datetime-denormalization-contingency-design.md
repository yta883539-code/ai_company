# target_datetime denormalization 移行コンティンジェンシー設計(フェーズ続き201)

## 位置づけ

reminder-scheduler-composite-index-design.md(フェーズ続き199)「残る課題」に、
「将来的に確定予約数が増加し『全confirmed予約をメモリに読み込んでからインメモリ判定する』
方式がコスト・レイテンシ上ボトルネックになった場合、`target_datetime`をFirestore側にも
保持してクエリ条件に含める再設計が必要になる可能性がある」という先送り事項が残っていた。
現時点(想定顧客数:数十〜百店舗規模)では対応不要と結論済みだが、実測が取れるのは実運用
開始後であり、その時点で初めて設計を始めると切り替えに時間がかかる。本ドキュメントは
「いつ・何をトリガーに切り替えるか」「切り替え自体の設計」を今のうちに具体化し、実測待ちの
状態でも即座に着手できるようにする。

## 1. 切り替えを判断するトリガー(閾値の具体化)

firestore-traffic-cost-estimate.mdの試算はコレクション全体の読み書き課金が対象で、
Cloud Function C固有の「1回の定期実行で読み込むconfirmed予約の総件数」を直接の指標として
明記していなかった。本設計では以下をトリガー条件とする。

- Cloud Function Cの1回の実行(1時間ごと想定、reminder-scheduler-design.md)で
  `stage == "confirmed" AND archivedAt == null`のクエリが返す件数が概ね1,000件を
  超える状態が継続する場合。Firestoreクエリ結果1,000件は「1回のクエリで返せる上限が
  実質的な問題にならない」目安として一般に扱われる件数であり、これを超えるとインメモリ
  判定のCPU時間・関数のメモリ使用量が無視できなくなり始める閾値として採用する。
- 上記件数は「未来の予約すべて」が対象になる(予約日を過ぎてもarchive処理
  〈archive_completed_conversations()〉が走るまでは`archivedAt == null`のまま残る)ため、
  店舗数だけでなく「予約が完了してからarchive処理が走るまでの遅延」も件数に効いてくる
  点に注意する。archive処理の遅延自体が原因で件数が膨らんでいる場合は、本設計の対象外
  (archive処理側の頻度見直しで対応すべき別問題)として切り分ける。

## 2. 切り替え後のデータモデル

`conversations`ドキュメントに`target_datetime`(次に送るべきリマインド種別の発火時刻、
`select_due_initial_reminders()`/`select_due_resends()`が算出するのと同じ値)を
非正規化フィールドとして追加する。

- 書き込みタイミング: 予約確定時(`stage`が`confirmed`になる遷移)、および前日リマインド
  送信直後(次は当日リマインドの`target_datetime`に更新)、当日リマインド送信直後
  (`customer_replied_at`が無ければ再送用の`target_datetime`に更新、あれば`null`に
  クリアしてクエリ対象から外す)の3箇所。既存の`select_due_initial_reminders()`/
  `select_due_resends()`が持つ判定ロジック(いつ発火すべきかの算出式)自体は変更せず、
  算出結果をFirestoreへ書き戻すだけにとどめる(ロジックの二重実装を避ける)。
- クエリ条件を`stage == "confirmed" AND archivedAt == null AND target_datetime <= now`に
  変更する。複合インデックス(#5)の定義に`target_datetime` ASCを追加する必要がある
  (既存の#5は`stage` ASC, `archivedAt` ASCの2フィールドのみ)。

## 3. 移行時の互換性(既存データの扱い)

切り替え時点で既に存在する`confirmed`な予約は`target_datetime`フィールドを持たないため、
クエリが新条件に切り替わった瞬間にリマインドが飛ばなくなる(フィールド欠落はクエリの
比較演算子に一致しないため)。これを避けるため、切り替えは以下の順序で行う。

1. 新規/更新される予約から`target_datetime`の書き込みを開始する(クエリ条件はまだ旧のまま)。
2. 移行用の一括更新(バックフィル)処理で、既存の`confirmed`予約全件に対して
   `select_due_initial_reminders()`/`select_due_resends()`と同じ算出式で
   `target_datetime`を計算し書き込む。
3. バックフィル完了を確認してから、Cloud Function Cのクエリ条件を新条件に切り替える。

このバックフィル処理自体は実Firestore接続後にのみ実行可能なため、設計のみを本フェーズで
固め、実装・実行は該当トリガーに達した時点で着手する。

## 4. 現時点での結論

トリガー条件(1,000件目安)に達するまでは、reminder-scheduler-composite-index-design.mdの
結論(インメモリ判定で十分)を維持する。本ドキュメントにより「閾値」「切り替え後の
データモデル」「移行手順」が事前に固まったため、実測データが得られた際に設計からやり直す
必要はなく、閾値超過の確認後すぐに実装(書き込み処理3箇所の追加、バックフィルスクリプト、
インデックス#5への`target_datetime`追加)に着手できる状態になった。

## 残る課題

- 実装・実測はいずれも実Firestore接続(GCPプロジェクト作成、オーナー承認待ち)後の課題。
- 1,000件という閾値は一般的な目安からの仮置きであり、実測でのクエリレイテンシ・
  関数メモリ使用量の実測値が得られ次第、具体的な数値に見直す。
