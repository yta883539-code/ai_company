# LLM呼び出し失敗時の処理方針(フェーズ111)

result-display-page-generation-request-design.md(フェーズ102)4節・result-display-
wireframe.md(フェーズ110)4節から持ち越されていた「LLM呼び出し失敗時(タイムアウト・
Structured Outputs不整合等)のリトライ・ユーザー表示方針」に対応する。

## 1. 「技術的失敗」と`status`分岐の区別

schema/output.schema.jsonの`status`(`generated`/`out_of_scope`/`insufficient_input`)は、
LLMが構造化出力として**正常に応答できた**場合の業務上の分岐であり、いずれも
`llm_client.generate()`が値を返したことを前提にしている。これに対し、タイムアウト・
ネットワーク断・Structured Outputs側のパース失敗(スキーマに合致しない応答)は、
`generate()`自体が値を返せない「技術的失敗」であり、`status`のいずれの値にも当てはまらない。
この2種類を混同しないよう、本フェーズでは技術的失敗を`GenerationHttpResult`の
`status_code=502`・`error="llm_generation_failed"`という、`status`分岐とは別のHTTP層の
エラーとして扱うことに決めた(generation_request_handler.pyの`LlmGenerationClientProtocol`は
元々「リトライ・エラーハンドリングの詳細は未設計」としていたため、本フェーズで初めて実装する)。

タイムアウト・ネットワーク断・Structured Outputs不整合のいずれであるかを呼び出し元
(フロント側)が区別して表示する必要は無いと判断した(いずれも利用者にとっては「結果が
出なかった」という同じ事象であり、原因の技術的な違いを案内しても対応行動は変わらないため)。
したがって`receive_generation_request()`では`llm_client.generate()`を広く`except Exception`
で捕捉し、原因種別によらず単一のエラーコードに正規化する。

## 2. リトライは行わない(本関数内では1回で打ち切り)

本フェーズでは関数内部での自動リトライは実装しない。理由は以下の2点。

1. `llm_client.generate()`の実際の実装(タイムアウト秒数、どの例外がリトライ可能かの判定)は
   実LLM接続時にしか確定できず、現段階でリトライ回数・バックオフ間隔を決め打ちすると、
   実接続後に手戻りになる可能性が高い。
2. 都度プラン(`one_time_pass`)は1回の決済に対して1回のアクセストークンしか発行されない
   ため、関数内でサーバー側が自動でリトライして二重にLLM APIコストを消費するより、
   利用者の「もう一度試す」操作に委ねる方が、意図しないコスト超過を避けやすい(aircon-pasha
   等の他ventureでも、サーバー側自動リトライは採用せず利用者操作起点としている既存方針と
   整合させた)。

したがって「リトライ」は本関数の責務ではなく、3節のUI側で「もう一度試す」ボタンを提供する
ことで、利用者操作起点の再試行として実現する。

## 3. 失敗時に消費させないものの確定

- 月額フリーパス(`fan_pass`): 失敗時は`generation_log.record()`を呼ばない。
  generation-count-design.mdの月次カウントを、結果が出なかった試行でも消費させてしまうと、
  利用者から見て「失敗したのに上限を1回損した」という不満につながるため。
- 都度プラン(`one_time_pass`): 失敗時は`one_time_pass_store.mark_consumed()`を呼ばない。
  既存コード(フェーズ107)が「生成成功を確認してから消費済みにする」順序を既に採用していた
  ため、`try`ブロックの配置自体でこの要件は自然に満たされる(本フェーズで明文化・テスト化)。
  この結果、都度プラン購入者は同一`access_token`で追加決済なしに再試行できる
  (one-time-plan-access-token-design.mdの「1決済=1回」という前提を、技術的失敗のケースに
  限り「1決済=結果が出るまで」に緩和する格好になるが、利用者に不利益が生じる方向の変更では
  ないため、追加のオーナー承認対象には当たらないと判断した)。

## 4. UI表示方針(result-display-wireframe.mdへの追加分)

tone-and-manner-guideline.mdの基本方針(ですます調・絵文字不使用・断定しない・不安を
煽らない)を踏襲し、原因の技術的な詳細(タイムアウト/パース失敗等)には触れず、以下の
定型文言とする。

```
生成中に時間がかかってしまい、結果を表示できませんでした。
少し時間をおいてから、もう一度お試しください。
[ もう一度試す ]
```

- 「もう一度試す」ボタンは、result-display-wireframe.md状態3の`insufficient_input`分岐
  (フォームを消さず入力内容を保持したまま再表示)と同じ考え方で、入力中の「当選情報メモ」を
  保持したまま再送信する(状態2「送信中」に戻るのみで、状態1の空フォームには戻さない)。
  利用者が同じ内容を入力し直す手間を避けるため。
- 都度プラン利用者に対して「もう一度試しても追加のお支払いは発生しません」等の明示的な
  文言は、本フェーズでは追加しないことにした(実際に追加決済が発生しないことの技術的保証は
  3節で確定済みだが、エラー文言に決済の話を混ぜると逆に不安を誘発しかねないため。もし
  問い合わせが多い場合はowner-faq相当の文書を別途検討する、という形で次回候補に残す)。

## 5. 残る課題

- 本フェーズはテキストでの文言・分岐方針の確定とgeneration_request_handler.pyへの実装に
  留め、result-display-wireframe.mdのASCIIワイヤーフレームへの反映は次回候補とする。
- 実LLM接続後に判明する実際のタイムアウト秒数・リトライ可能な例外種別の精査(本フェーズは
  `except Exception`で広く捕捉する暫定実装)。
- 都度プラン利用者向けFAQ文言(4節で保留した「追加決済は発生しない」旨の案内)の要否検討。
- 実LLM呼び出し・実際のHTML/JS実装・外部サービスへの接続は本フェーズでも行っていない
  (設計検討とプロトタイプ内の分岐コード実装のみ)。承認が必要なアクション(支払い・
  アカウント作成・外部公開・送信等)は本フェーズでは発生していないためpending-approval.md
  への新規追記は不要(既存の承認待ち事項〈Stripe/GCPアカウント開設等〉の範囲内で扱う)。
