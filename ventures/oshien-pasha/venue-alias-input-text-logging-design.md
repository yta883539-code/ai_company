# 会場名表記揺れデータの定量判断移行に向けた生入力記録のスキーマ・プライバシー検討(フェーズ28)

README.mdフェーズ27の次回候補(3)「`generation_log`への入力名称生テキスト記録を将来追加する
場合のスキーマ・プライバシー面の検討(定性判断から定量判断へ移行する際の前提)」に対応する。

## 1. 前提の再確認

- venue-name-normalization-design.md(フェーズ15)で設計した名寄せアルゴリズムは、
  エイリアス辞書一致・部分一致(フォールバック)の判定結果(`venue_matched`等)のみを
  output.schema.jsonの構造化出力として返す設計であり、入力された会場名の生テキスト自体は
  現状どこにも記録されない。
- フェーズ27で確定した`recognition_priority`(`high`/`normal`)の運用は、16会場の定期
  再確認サイクルの都度WebSearchで「旧名称がどの程度言及され続けているか」を定性的に確認する
  方式とした。これは外部情報(ニュース・SNS等の一般的な言及傾向)に基づく代替手段であり、
  自社サービスの実利用者が実際にどの表記で入力しているかという一次データではない。
- 本フェーズでは、実利用開始後に一次データ(利用者自身の入力)で定性判断を補強・置き換える
  ことを検討する前提として、`generation_log`(generation-count-design.md フェーズ8)への
  記録項目追加の要否とリスクを整理する。スキーマファイル(schema/venue-master.json・
  schema/output.schema.json)および実装への反映は行わない(設計検討のみ)。

## 2. 記録対象の絞り込み方針(データ最小化)

- 利用者の入力全文(自由記述欄全体)をそのまま記録することは、(a)入力に同行者名・個人の
  予定等の会場名と無関係な情報が混在する可能性があり個人情報保護の観点でリスクが高い、
  (b)異常検知目的の`generation_log`(フェーズ8)の趣旨(生成回数・会場マッチ状況の把握)を
  超える記録になる、という2点から採用しない。
- 代わりに、名寄せ処理(venue-name-normalization-design.md 3節の正規化・マッチング処理)の
  入力時点で切り出される「会場名らしき部分文字列」のみを記録対象とする。具体的には、
  正規化処理に渡される直前の文字列のうち、マッチング処理が実際に比較対象として扱った
  トークン(ユーザー入力全体ではなく、会場名の記載があると判定された箇所)に限定する。
- この絞り込みにより、同行者名や公演の感想等、会場名と無関係な自由記述部分は記録対象から
  除外される。ただし会場名そのものが稀に個人を特定しうる情報(例:個人宅を会場と誤記した場合)
  を含む可能性は理論上残るため、3節で追加の緩和策を検討する。

## 3. スキーマ案

`generation_log`サブコレクション(フェーズ8で確定済み、フィールド: `requestedAt`・
`venueMatched`・`inputPerformanceCount`)に、以下を追加する案とする(いずれも将来追加の
設計案であり、本フェーズでは未実装)。

- `venueMatchStatus`(string, enum: `exact` / `alias` / `partial_fallback` / `unmatched`):
  venue-name-normalization-design.md 3節のどの段階でマッチしたか(またはしなかったか)を
  記録する。既存の`venueMatched`(boolean)より粒度の細かい情報を持つが、`venueMatched`は
  互換性のため残し、新フィールドとして追加する形にする。
- `unmatchedVenueNameToken`(string, nullable, 上限文字数を設定): `venueMatchStatus`が
  `unmatched`または`partial_fallback`の場合に限り、2節で絞り込んだ「会場名らしき部分文字列」
  を記録する。マッチ済み(`exact`/`alias`)の場合は正式名称に正規化済みであり旧名称の生テキスト
  を保持する意味が薄いため記録しない(記録対象をさらに絞ることでデータ量・リスクを低減)。
- 上限文字数(案: 30〜50文字程度)を設けることで、万一想定外に長い自由記述が切り出し処理を
  すり抜けて混入した場合でも、記録される情報量を制限する安全策とする。

## 4. プライバシー面の検討

- 会場名(施設の固有名称)自体は一般に個人情報には該当しないと考えられるが、3節のスキーマ案
  どおり「マッチしなかった入力」のみを対象とすることで、万一切り出し処理が意図せず会場名
  以外の文字列を含んでしまった場合のリスクは、対象を`unmatched`/`partial_fallback`時のみに
  絞ることで一定抑制できる(マッチ成功時は記録しないため、正常系の入力は影響を受けない)。
- 個人情報保護法上の「個人情報」に該当するか否かの最終判断は、実際の自由記述欄の仕様(入力欄が
  会場名専用か、公演情報と一体の自由記述か)が確定していない現時点では確定できない。
  line-reservation-aiのdata-retention-policy.mdのようなventure単位の保存期間・削除方針は
  oshien-pashaには未整備であることも本検討で判明したため、本記録項目の追加を実装する場合は
  保存期間・削除方針の整備(data-retention-policy.md相当のドキュメント新規作成)を前提条件とする
  ことを残課題として明記する。
- 記録の利用目的は「会場名表記揺れパターンの発見・エイリアス辞書の拡充」に限定し、個人の
  利用履歴の特定・追跡には用いない方針とする(目的外利用の禁止をプライバシーポリシー
  〈legal-notices-draft.md相当、oshien-pashaには未整備〉に明記する必要がある点も残課題とする)。

## 5. 実装タイミング・残課題

- 本フェーズはスキーマ・プライバシー面の検討のみであり、schema/venue-master.json・
  schema/output.schema.jsonの編集、Firestore実装への反映はいずれも行っていない。実装は
  実LLM API・実Firestoreへの接続(オーナー承認が必要なアクション)が可能になった段階で、
  3節のスキーマ案をもとに改めて検討する。
- 4節で判明した保存期間・削除方針(data-retention-policy.md相当)・プライバシーポリシー
  (legal-notices-draft.md相当)がoshien-pashaにまだ存在しないことは、本記録項目追加に限らず
  venture全体の残課題として次回以降に引き継ぐ。
- 上限文字数の具体値(30〜50文字程度、3節)は仮の目安であり、実際の入力フォーム仕様確定後に
  見直す。

実LLM呼び出し・実Firestoreへの接続自体はオーナー承認が必要なアクションに該当するため、本メモは
設計・リスクの検討に留める(コード実装・外部サービスへの接続は一切行っていない)。承認が必要な
アクション(支払い・アカウント作成・外部公開・送信等)は本フェーズでは発生していないため
pending-approval.mdへの新規追記は不要(既存の承認待ち事項〈Firestore/GCPアカウント開設等〉の
範囲内で扱う)。
