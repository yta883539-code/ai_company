## 2. 入力フィールド構成

README.md「概要」節の入力定義、goods-line-participation-input-field-design.mdの
`goods_line_intention`3値方針に基づき、以下の構成とする。他venture同様、構造化
フォーム(別々の入力欄)ではなく1つの自由記述テキストエリア(「当選情報メモ」)に
まとめる方式を踏襲する(llm-system-prompt-draft.mdが自由記述メモからの抽出を前提と
しており、`insufficient_input`判定自体をLLMに委ねる既定方針〈result-display-page-
generation-request-design.md 2節手順4〉と整合させるため)。

```
┌───────────────────────────┐
│ [おしえんパシャっと ロゴ]          │ ← 固定ヘッダー
├───────────────────────────┤
│ 当選情報を教えてください            │  ← H1
│                             │
│ 会場・日時・枚数、予算感、           │  ← 補助テキスト(プレース
│ グッズ購入希望、グッズ列に並ぶ        │    ホルダー内に例文として表示、
│ かどうか、前後の予定を、思いつく       │    ラベル分割はしない)
│ ままメモしてください               │
│                             │
│ ┌─────────────────────┐ │
│ │ 例: ○○公演 △△ホール          │ │  ← 自由記述テキストエリア
│ │ 11/30昼・夜2公演当選、2枚。     │ │    (textarea、複数行、
│ │ 予算は交通込みで3万円くらい。    │ │    プレースホルダーに
│ │ グッズは発売形式次第で買う      │ │    記入例を薄字表示。
│ │ 予定。グッズ列には並びたい。    │ │    入力必須、文字数上限は
│ │ 翌日は仕事で休めない。         │ │    3節参照)              │ │
│ └─────────────────────┘ │
│                             │
│ [ この内容で遠征プランを作る ]     │  ← 送信ボタン
│                             │
│ 入力内容はプラン作成のみに使用し、     │  ← 補足(小文字)
│ 保存・他目的利用は行いません         │
│ (data-retention-policy.md参照)      │
└───────────────────────────┘
```

送信後は送信ボタンを「作成中です…(しばらくお待ちください)」表示に切り替え、二重
送信を防止する(他venture同様のローディング表示方針。具体的なスピナー等の見た目は
次回以降)。

## 3. バリデーション方針

- クライアント側では「空文字列での送信不可」のみをチェックする(送信ボタンを
  非活性化)。入力内容の充足性(会場・日時等の必須項目の有無)はクライアント側で
  事前判定せず、そのままサーバー側`receive_generation_request()`経由でLLMに渡し、
  `status=insufficient_input`の判定をLLMに委ねる(result-display-page-generation-
  request-design.md 2節手順4の既定方針と整合、入力検証ロジックの二重実装を避ける)。
- 文字数上限は2,000文字とする(itinerary_draft生成に必要な情報量に対し十分な余裕を
  持たせつつ、LLM呼び出しコストの異常な増大〈極端に長文を貼り付けられるケース〉を
  防ぐための暫定値。実際のLLM呼び出し運用開始後の実測を踏まえた見直しを次回候補とする)。
  上限到達時はtextarea付近に残り文字数を表示し、送信自体はブロックしない(超過分は
  サーバー側で切り詰めるか警告するかは`_LlmGenerationClientProtocol`側の次回検討課題)。
- `access_token`はURLクエリパラメータではなく、access-token-client-storage-design.md
  (フェーズ101)の方針どおりsessionStorageから取得し、画面上では一切表示・編集不可
  とする(本画面はaccess_token入力欄を持たない)。

## 4. goods_line_intention の入力UI

自由記述メモの一部として扱うか、専用のUIコンポーネント(トグル等)を設けるかを検討した。

- 専用UIコンポーネント(例: 「グッズ列に並ぶ予定がありますか? [並ぶ/並ばない/未定]」の
  3択トグル)を設ける案は、LLMによる自由記述からの抽出精度に依存せず`join`/`skip`/
  未記載を確定できる利点がある一方、入力項目を自由記述1本にまとめた本フォームの設計
  方針(本節冒頭)と矛盾し、「メモで送るだけ」というLP訴求文言(landing-page-copy-
  draft.md)とも不整合になる。
- 本フェーズでは、自由記述メモ内に言及があればLLMが抽出する方式(専用UIなし)を採用
  する。ただし抽出精度の実運用データが無い段階のため、textareaのプレースホルダー
  例文(2節)に「グッズ列には並びたい」という一文を含め、利用者に記載を促す形で
  対応する。LLMでの`join`/`skip`/未記載の抽出精度が実運用上低いと判明した場合に、
  専用UIコンポーネントへの変更を再検討する(次回候補)。
