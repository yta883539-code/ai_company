# 会場名寄せの確信度(match_confidence)設計とエイリアス陳腐化の反映方法

## 背景・経緯

- フェーズ9(venue-name-normalization-design.md)で、会場名寄せを「正規化→完全一致→エイリアス辞書一致→部分一致(留保付き案内)→非該当」の段階的方針として整理した際、`schema/output.schema.json`の`venue_matched`(boolean)では完全一致とエイリアス一致・部分一致の区別が表現できないことを課題として記録し、`match_confidence`のenum型への拡張を将来候補とした(ただし実LLMでの安定生成検証が未済のため、当時はスキーマ本体の変更を見送った)。
- フェーズ10(venue-alias-verification-and-naming-rights-risk.md)で、会場名の多くがネーミングライツ契約に基づき3〜5年周期で改称されるため、静的なエイリアス辞書が契約更新・終了のタイミングで陳腐化するリスクを発見し、`last_verified_date`・`naming_rights_review_due`を会場マスタに持たせる方針を決めた。
- フェーズ12(venue-master-data-structure-design.md)で、これらのフィールドを内部参照データ(会場マスタJSON)側の構造として確定したが、ユーザー向け出力スキーマ(`schema/output.schema.json`)側への反映方法は未検討のまま残していた。

本ドキュメントは、フェーズ13の次回候補(3)「`last_verified_date`・`naming_rights_review_due`フィールドのschema/output.schema.json側への反映方法の検討」に対応する。

## 設計: match_confidenceのenum候補

`venue_matched`(boolean)を次の5値のenumに置き換える案を設計する(現段階では**設計のみ**で、スキーマ本体は未変更。理由は後述)。

| 値 | 意味 | `nearest_station_note`の文言方針 |
|---|---|---|
| `exact` | 会場マスタの`canonical_name`と完全一致 | マスタ記載の最寄り駅・徒歩目安をそのまま記載 |
| `alias_fresh` | エイリアス辞書と一致し、かつ`naming_rights_review_due`が未到来(または命名権なしで`null`) | マスタ記載の情報を記載。現名称との対応関係(例: 旧名称◯◯=現名称△△)を一言添える |
| `alias_stale` | エイリアス辞書と一致したが、`naming_rights_review_due`が現在日付を過ぎている | マスタ記載の情報は「参考情報」として記載しつつ、「命名権契約の更新・終了により名称が変わっている可能性があるため最新情報をご確認ください」という留保文を必ず付す |
| `partial_unconfirmed` | 部分一致(編集距離等の緩い一致)のみで、別施設との混同リスクが排除できない | フェーズ9の方針を踏襲し、会場を確定情報として案内せず「候補の一つとして」留保付きで案内する一言に留める |
| `unmatched` | マスタに該当なし | 従来の`false`時と同じ「一般的な調べ方を案内する」文言 |

- `alias_stale`を新設する狙いは、フェーズ10で発見した「陳腐化したエイリアス辞書をユーザーが鮮度不明のまま信じてしまう」リスクを、出力側の文言分岐で緩和することにある。`last_verified_date`自体はユーザー向け出力には含めず(裏側の内部管理情報であり、ユーザーに提示しても意味のある文脈情報にならないため)、`naming_rights_review_due`の経過判定結果のみを`alias_stale`というenum値に変換して反映する、という設計判断とした。
- `exact`と`alias_fresh`を分けている理由は、現状の運用(venue-master-draft.mdの会場マスタは`canonical_name`のみを収録し、エイリアス辞書は別建て)を踏まえ、将来的にエイリアス一致の方が誤りの蓋然性がわずかに高いという前提を出力側でも区別可能にしておくためだが、実際の文言を変える必要があるかどうかは実データでの検証課題として残す。

## 既存スキーマへの影響(未実施の理由)

フェーズ9の判断を踏襲し、**`schema/output.schema.json`本体の編集は今回も見送る**。理由は次の2点で変わっていない。

1. enum値を5つに増やすことで、実LLM(Claude API等)が各値の判定基準(特に`alias_fresh`と`alias_stale`の日付境界判定)を安定して守れるかが机上検証では確認できない。
2. 会場マスタのJSON化自体(フェーズ12の設計)がまだ実ファイルとして存在せず、`naming_rights_review_due`の実データが1件(エディオンアリーナ大阪、2028年8月)しか裏取りできていない段階でenum本体を確定させるのは早計と判断した。

このため、本ドキュメントは次の実装フェーズ(オーナー承認後、実API接続時)で使う設計メモとして位置づけ、`validate_test_cases.py`相当のテストケース(line-reservation-ai等の既存ventureを参照)を用意する際の判定ロジック仕様として再利用する想定とする。コード実装・外部サービス接続は一切行っていない。

## 次回候補

1. 会場マスタJSON(フェーズ12設計)の実ファイル化と、エディオンアリーナ大阪以外の主要会場(東京ドーム・さいたまスーパーアリーナ等)の`naming_rights_review_due`裏取り(WebSearchでの命名権契約状況確認)。
2. 都度プラン⇔月額フリーパスの短期間内連続切替時の初回割引の再検討(実利用データ観察後)。
3. 異常検知(bot的利用)の閾値・対応方針の検討(実利用データ観察後)。
4. `alias_stale`判定時のユーザー向け留保文言について、他の「パシャっと」系ventureが漏えい対応等で使っている「不確実性の明示」表現パターンとの整合を確認。
