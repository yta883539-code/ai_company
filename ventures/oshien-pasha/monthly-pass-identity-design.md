# 月額フリーパス利用者の識別方法の検討(フェーズ7)

tech-stack.md「6. 月額フリーパス利用者の識別(新規の検討課題)」で未解決としていた、会員登録
なし方針(README.md)と両立する形での月額フリーパス利用者識別方法を検討する。forklift-pasha
のaccess-token-reissue-design.mdが確立した「ログインID/パスワードを発行せず、推測不能な
アクセストークンを配布・保持する」パターンを本venture固有の制約(都度プランとの共存、Web
単体・LINE非依存)に合わせて適用する。

## 1. 前提の整理

- 都度プラン(`mode=payment`)は決済1回=利用1回で完結し、利用者を横断的に識別する必要が
  ない(event-komiguai-pashaのone-time-checkout-no-account-design.mdと同型。識別方法の
  検討対象外)。
- 月額フリーパス(`mode=subscription`)のみ、「同一利用者が今月すでに契約済みか」を次回
  利用時に判定する識別手段が必要。
- 他6venture(LINE前提)はLINEユーザーIDを識別子として使えるが、本ventureはpayment-method-
  design.md(フェーズ5)で確定した「Web単体(LINE非依存)」方針のため使えない。
- forklift-pashaのように専用の設定ページ・日次点検メモ送信のような継続操作を会員登録代替の
  アクセストークンで束ねる構成が参考になるが、本ventureは「当落発表後の短期間に集中する
  都度利用」が基本であり、forklift-pashaほど頻繁な継続アクセスは発生しない点が異なる。

## 2. 識別方法の方針

forklift-pashaの設計(ドキュメントIDとアクセストークンを分離し、推測不能なランダム文字列を
`accessToken`として発行する)を踏襲し、以下の方式を採用する。

1. 月額フリーパスのStripe Checkout Session(`mode=subscription`)完了時、Webhook
   (`checkout.session.completed`)でFirestore `monthly_pass/{internal_id}`(自動生成ID)
   ドキュメントを新規作成し、`stripeCustomerId`・`stripeSubscriptionId`・`email`
   (Stripe Checkoutが標準で収集する購入者メールアドレス)・`accessToken`(サーバー側で
   ランダム発行)・`currentPeriodEnd`・`subscriptionStatus`を記録する。
2. 決済完了直後は、Stripe Checkoutの`return_url`(`{CHECKOUT_SESSION_ID}`プレースホルダー
   付き)で遷移する結果ページ上で、サーバー側がCheckout Session IDから該当ドキュメントを
   特定し、アクセスURL(`https://<ドメイン>/m/{accessToken}`)をその場で画面表示する。
   forklift-pashaはアクセスURLの初回配布を「メール送信」に依存しているが、本ventureは
   決済完了直後に利用者が同一ブラウザへリダイレクトされる構成のため、**初回配布はメール
   送信に依存せず画面表示のみで完結できる**という差分がある(他ventureのメール送信運用
   方針〈送信直前のオーナー確認〉への依存を初回配布では避けられる)。
3. 以降の利用(同月内の2回目以降の生成)は、利用者が保存したアクセスURL
   (`https://<ドメイン>/m/{accessToken}`)に再訪問することで、`accessToken`から
   `monthly_pass`ドキュメントを特定し、`subscriptionStatus`が有効であれば生成回数を
   無制限に許可する。会員登録・ログインは発生しない。

## 3. アクセストークンを失った場合の再発行(クロスデバイス対応)

決済直後の画面表示で得たアクセスURLをブックマークし忘れた、別の端末から利用したい、といった
ケースは、画面表示のみでは解決できないため、forklift-pashaと同型の「メールアドレスを入力して
アクセスURLを再送してもらう」再発行フローを設ける。

1. 「アクセスURLを再送する」ページ(会員登録とは異なる、メールアドレス入力1項目のみの
   軽量フォーム)を用意する。
2. サーバー側でStripe APIの顧客検索(`customers.list(email=...)`)により該当顧客を特定し、
   有効な月額フリーパスのサブスクリプションを保持しているか確認する。
3. 確認できた場合、該当`monthly_pass`ドキュメントの`accessToken`を新しい値で上書きし
   (forklift-pashaの「漏洩時再発行」と同じ操作。旧トークンは即時失効する)、新しいアクセス
   URLを入力されたメールアドレス宛に送信する。
4. この送信は決済直後の即時画面表示とは異なり、利用者が離脱した後の非同期送信のため、
   他venture共通の運用方針(メール連携接続後、送信直前に毎回オーナー確認を得てからのみ送信)
   に従う。実際のメール送信実装・接続自体は現時点では行わない。

## 4. 有効期限方針

forklift-pashaの「5. 有効期限方針の決定」(操作自体が会員登録の代替であるため無期限とする
判断)の理由は本ventureにも当てはまるが、一点差分がある。forklift-pashaは契約が続く限り
同一`accessToken`が有効であればよいが、本ventureはStripeサブスクリプションが解約・
支払い失敗等で無効化された場合、`accessToken`自体は無効化せず(再契約時に同じURLで
再度有効化できるようにするため)、`subscriptionStatus`の判定のみで利用可否を切り替える
方針とする(トークンのライフサイクルとサブスクリプションのライフサイクルを分離する)。
これにより、解約後に再度月額フリーパスを契約し直した利用者が、同じアクセスURLをそのまま
使い続けられる(新しいトークンの再発行・再送が不要)という利点がある。

## 5. 都度プランとの関係

都度プラン利用者がその後月額フリーパスに加入した場合、都度プラン側は`accessToken`を
発行しないため(2節参照)、両者の間に識別子の引き継ぎは発生しない。月額フリーパス加入時に
新規`monthly_pass`ドキュメントが作られるのみで、過去の都度プラン利用履歴との統合は行わない
(pricing-plan.mdが未検証事項として残した「都度プラン⇔月額フリーパスのプラン変更時の扱い」
のうち、少なくとも識別子設計の観点では追加の設計を必要としないことを確認した)。

## 6. 残課題

- 生成回数カウント(tech-stack.md「7. 月額フリーパスの生成回数カウント」)の実装方針
  (course-set-pashaの`UsageCounterProtocol`相当)は、本フェーズで`internal_id`が確定した
  ため、次回以降`monthly_pass/{internal_id}`配下のサブコレクションまたはフィールドとして
  設計できる状態になった。
- venue-master-draft.mdの各会場のアクセス情報精査(WebSearchでの裏取り)は未着手のまま。
- 会場名表記揺れの名寄せ方法の検討は未着手のまま。
- 都度プラン⇔月額フリーパスのプラン変更時の「残存クレジットの有無」等、課金面の扱いは
  本フェーズの範囲外(5節は識別子設計の観点のみ確認)。

実LLM呼び出し・Stripe等決済代行サービスとの実接続、実際のFirestore・GCPプロジェクト作成・
メール送信実装自体はオーナー承認が必要なアクションに該当するため、本メモは設計・仮説の検討に
留める(コード実装・外部サービスへの接続は一切行っていない)。承認が必要なアクション
(支払い・アカウント作成・外部公開・送信等)は本フェーズでは発生していないため
pending-approval.mdへの新規追記は不要(既存の承認待ち事項〈Stripe/GCPアカウント開設等〉の
範囲内で扱う)。
