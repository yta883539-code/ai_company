# 会場名表記揺れの名寄せ方法検討

README.mdフェーズ8の次回候補(3)「会場名表記揺れの名寄せ方法の検討」に対応する。
schema/output.schema.jsonの`venue_matched`は現段階で「venue-master-draft.mdの会場マスタと
完全一致した場合のみtrue」という暫定方針を採用しているが、実際の入力では旧名称・略称・
表記ゆれが混在すると想定されるため、完全一致以外のマッチ手法を段階的に整理する。

## 表記揺れのパターン分類

venue-master-draft.mdに掲載した会場名を例に、想定される表記揺れを4種類に分類した。

| パターン | 例(入力想定) | 正式名称(venue-master-draft.md) |
|---|---|---|
| (a) 旧名称⇔現名称 | ナゴヤドーム | バンテリンドーム ナゴヤ |
| (a) 旧名称⇔現名称 | 大阪府立体育会館 | エディオンアリーナ大阪 |
| (b) 略称 | さいスタ/さいたまスーパーA | さいたまスーパーアリーナ |
| (b) 略称 | Kアリーナ | Kアリーナ横浜 |
| (c) 表記ゆれ(全角半角・スペース・中点) | ｴﾃﾞｲｵﾝｱﾘｰﾈ、さいたま　スーパーアリーナ | エディオンアリーナ大阪、さいたまスーパーアリーナ |
| (d) 通称・俗称 | 横浜アリーナ(と誤記されやすいがKアリーナ横浜とは別施設) | (誤記であり名寄せ対象外、別会場として扱う必要がある例) |
| (d) 通称・俗称 | 日本ガイシホール/NGKスポーツプラザ(いずれも名古屋市総合体育館の愛称。愛知県施設の愛知県体育館〈通称ドルフィンズアリーナ〉とは別施設だが、入力者が「日本ガイシ」繋がりで愛知県体育館と取り違えるおそれがある) | (誤記であり名寄せ対象外、別会場として扱う必要がある例。README.mdフェーズ15で発見、フェーズ18で対象施設の取り違えを是正) |

(d)のように「別施設との混同」は名寄せで吸収すべきではなく、むしろ誤認識として
venue_matched=falseのまま一般的な確認を促す方が安全という判断も必要になる
(名寄せの精度を上げすぎると誤った会場情報を提示するリスクがあるため)。

## 段階的マッチングのアルゴリズム案

1. **正規化**: 入力文字列から前後の空白除去、全角スペース→半角統一、カタカナの長音・中点の
   表記ゆれを統一(NFKC正規化相当)。括弧内の補足(例:「(旧ナゴヤドーム)」)は正規化後に
   別途エイリアス抽出の対象として扱う。
2. **完全一致**: 正規化後の文字列がvenue-master-draft.mdの会場名(正式名称)と完全一致 →
   `venue_matched=true`(現行方針どおり)。
3. **エイリアス辞書一致**: 完全一致しない場合、会場ごとに保持するエイリアス辞書(旧名称・
   略称・通称のリスト)と一致するか確認 → 一致すれば`venue_matched=true`とし、
   `nearest_station_note`等は正式名称側の情報を参照する。
4. **部分一致(フォールバック)**: エイリアス辞書にも一致しない場合、入力文字列が
   正式名称またはエイリアスの部分文字列として含まれるか(例:「ナゴヤドーム前」のような
   駅名寄りの入力)を確認する。部分一致はエイリアス辞書より誤判定リスクが高いため、
   現段階では`venue_matched`をtrueにはせず、`nearest_station_note`に「◯◯会場かもしれませんが
   断定できません」という留保付きの案内文を返す設計とする(上記(d)のような誤認混同リスクを
   踏まえた保守的な方針)。
5. **非該当**: いずれにも該当しない場合は現行どおり`venue_matched=false`。

編集距離(レーベンシュタイン距離)によるスペルミス吸収は、(d)のような別施設との誤混同を
誘発しやすいため今回は採用しない方針とした(入力ミスの吸収よりも誤認防止を優先)。

## エイリアス辞書の初期ドラフト(東京・大阪・名古屋圏、抜粋)

| 正式名称(canonical) | エイリアス例 |
|---|---|
| バンテリンドーム ナゴヤ | ナゴヤドーム、バンテリンドームナゴヤ |
| エディオンアリーナ大阪 | 大阪府立体育会館、大阪府立体育館 |
| さいたまスーパーアリーナ | さいスタ、さいたまスーパーA |
| Kアリーナ横浜 | Kアリーナ |
| 東京ガーデンシアター | ガーデンシアター |

本辞書はvenue-master-draft.mdと同様、一般に知られている旧名称・略称のみを基にした一次
ドラフトであり、各会場の正式な改称履歴・略称の実際の使用頻度はWebSearchでの裏取りを
別途行う必要がある(venue-master-draft.md既出の検討課題と合わせて次回以降に実施)。

## 「別施設との混同」(d)パターンの明示的な警告リストについて(README.mdフェーズ15対応)

フェーズ15の会場マスタ実ファイル化(schema/venue-master.json)作業時点では、「日本ガイシ
ホール」を愛知県体育館の命名権付き愛称として記録し、別施設である名古屋市総合体育館
(2026年4月1日付で愛称が『NGKスポーツプラザ』に変更予定)との間にKアリーナ横浜/横浜
アリーナと同種の「別施設との混同」リスクがあると整理していたが、これ自体が誤りだった
(フェーズ18で是正、venue-master-data-structure-design.mdおよびschema/venue-master.json
参照)。「日本ガイシホール」は実際には愛知県体育館の愛称ではなく、名古屋市総合体育館
(名古屋市南区)内のホール(旧称レインボーホール)の愛称であり、愛知県体育館(名古屋市中区、
通称ドルフィンズアリーナ)とは最初から無関係の別施設である。したがって真の混同リスクは
「日本ガイシホール⇔名古屋市総合体育館」(同一施設の新旧名称、混同ではなく正しい対応関係)
ではなく、「愛知県体育館(ドルフィンズアリーナ)⇔名古屋市総合体育館(日本ガイシホール→
クロコくんホール)」という、ともに名古屋市内にあり命名権絡みの通称を持つ2つの別施設の
取り違えである。この(d)パターンは上記の段階的マッチング手順3〜5(エイリアス辞書一致→
部分一致フォールバック→非該当)だけでは十分に対処できない。たとえば入力が
「日本ガイシアリーナ」のように両施設のどちらとも紛らわしい名称だった場合、現行の
手順ではエイリアス辞書にも正式名称にも一致せず単純に`venue_matched=false`(非該当)
となるだけで、「別施設の可能性があるため確認してください」という具体的な注意喚起は
出力されない。

このため、段階的マッチングの手順3(エイリアス辞書一致)と手順4(部分一致フォールバック)
の間に、新たな手順として「**混同注意リスト**」照合を挟む設計とする。

- 混同注意リストは`{ambiguous_input_pattern, candidate_venues[], note}`の形式を持つ小さな
  テーブルとし、venue-master.json本体とは別管理する(各会場エントリに持たせると、
  混同相手が未登録の会場〈今回の名古屋市総合体育館のように、まだvenue-master.jsonに
  独立したエントリを持たない施設〉の場合に参照が壊れるため)。
- 今回の例では`ambiguous_input_pattern`に「日本ガイシ」を含む曖昧な入力(正式名称
  完全一致・既存エイリアス一致のいずれにも該当しないもの)を置き、`candidate_venues`に
  「愛知県体育館(ドルフィンズアリーナ)」「名古屋市総合体育館(日本ガイシスポーツプラザ→
  2026年4月1日付NGKスポーツプラザ)」の2件を列挙し、`note`に両施設は別物であり
  入力者本人への会場名再確認を促す文言を保持する(フェーズ18で対象施設の取り違えを是正)。
- この混同注意リストに一致した場合、`venue_matched`はfalseのまま、
  `nearest_station_note`等の出力に「日本ガイシホールは愛知県体育館の愛称ではなく、
  別施設である名古屋市総合体育館内ホールの愛称のため、正式な会場名をチケット・
  当選メールでご確認ください」という留保付きの案内を返す設計とする(Kアリーナ横浜/
  横浜アリーナの組も同じ仕組みで扱える)。
- 名古屋市総合体育館はフェーズ18でvenue-master.jsonに独立エントリを追加したため、
  本混同注意リストの2件とも`registered_in_venue_master=true`に更新した(フェーズ16
  設計時点では未登録だったため、混同注意リストはvenue-master.json登録状況に依存しない
  設計としていたが、結果的に両方を登録する運びとなった)。

## schema/output.schema.jsonへの反映について

今回は設計メモに留め、schema本体の変更は行っていない。将来的に部分一致(フォールバック)を
実装する場合、現行のboolean型`venue_matched`では「エイリアス一致」と「部分一致(留保付き)」
の区別が表現できないため、`match_confidence`(`exact`/`alias`/`partial`/`none`)のような
enum型フィールドへの拡張が候補になる。ただし実LLMでの安定生成検証(course-set-pashaの
schema-structured-output-compat-check.md相当)を本venture側でまだ行っていないため、
スキーマ拡張は次回以降、実装着手の判断と合わせて検討する。

## 「休館中だが愛称は契約上適用済み」パターン(フェーズ22・25対応、GMOアリーナさいたま特有)

README.mdフェーズ22・25の次回候補「段階的マッチング手順に『休館中だが愛称は契約上適用済み』
というさいたまスーパーアリーナ特有のパターン(旧名称での入力頻度が当面高いことを踏まえた
エイリアス優先度)を反映する設計」に対応する。

### 論点1: 既存のclosedテンプレ文言が前提とする「後継施設への機能移転」とは性質が異なる

venue-operational-status-output-reflection-design.md(フェーズ20)が設計した
`venue_operational_status_note`のclosed時テンプレ文言は「この会場名は現在イベント会場として
稼働していない可能性があります(後継施設: {後継施設名})」という、愛知県体育館→IGアリーナの
ような**恒久的閉館・別施設への機能移転**を前提にした文面である。これをGMOアリーナさいたま
(旧さいたまスーパーアリーナ)にそのまま適用すると、「2026年1月13日からの改修工事による
一時休館(2027年4月リニューアルオープン予定、施設自体は存続)」という事実に反して、あたかも
同施設が廃止され別の後継施設に置き換わったかのような誤解を招く。両者は`operational_status`
としてはいずれも`closed`だが、ユーザーに伝えるべき案内文の性質が異なる。

このため、closedをさらに2種類に細分化する設計案を記録する(スキーマ本体の変更は
venue-operational-status-output-reflection-design.mdと同じ理由〈実LLM安定生成未検証〉で
今回も見送り、設計メモに留める)。

| 細分類(案) | 想定ケース | 案内文の方向性 |
|---|---|---|
| `closed_permanent` | 愛知県体育館(老朽化・後継施設へ機能移転) | 後継施設名を案内し、そちらでの開催可能性を示唆 |
| `closed_temporary` | GMOアリーナさいたま(改修工事による一時休館) | 「○年○月頃リニューアルオープン予定」という再開時期を案内し、後継施設の示唆はしない(同一施設が再開する旨を明示) |

会場マスタ側(`schema/venue-master.json`)にはフェーズ22時点で`verification_note`に再開予定日
(2027年4月)を自然文で記録済みのため、将来この細分類を実装する際は`reopening_date_note`
のような構造化フィールドへ切り出す案が候補になる(今回は設計メモのみ、JSON未変更)。

### 論点2: エイリアス優先度(旧名称の当面の認知度の高さをどう出力に反映するか)

段階的マッチング手順3(エイリアス辞書一致)は現状「一致すればvenue_matched=true、会場情報は
正式名称側を参照する」という設計だが、これだけだと出力文面上は常に`GMOアリーナさいたま`
とだけ案内されることになり、「さいたまスーパーアリーナ」で検索・入力したファンが「本当に
自分の当選会場と同じ施設のことを言っているのか」を確認しづらい。特に本件は改称と休館が
同時発生した直後で旧名称の認知度が当面高く残る点がフェーズ22で指摘済みの論点である。

対応案として、エイリアス辞書の各エントリに`recognition_priority`(`high`/`normal`、デフォルト
`normal`)という注釈を追加する設計とする。これはマッチング可否の判定ロジック(venue_matched/
将来のmatch_confidence)には一切影響させず、出力文面生成時にのみ参照する:

- `recognition_priority: high`のエイリアスで一致した場合、案内文の会場名表記を
  「GMOアリーナさいたま(旧称:さいたまスーパーアリーナ)」のように正式名称と入力名称を
  併記する(入力に使われた側の名称をそのまま文中に残すことで、ファン自身の記憶と結びつけ
  やすくする)。
- `recognition_priority: normal`(通常の略称・旧名称)では、現行方針どおり正式名称のみを
  案内すれば足りるとする(例: 「エディオンアリーナ大阪」への「大阪府立体育会館」入力は、
  改称から年数が経ち旧名称への言及頻度が本件ほど高くないと見込まれるため)。
- `recognition_priority`は会場マスタ側`naming_rights`が`true`かつ改称後1〜2年程度の期間
  (目安、厳密な年数基準は今回設けない)に限り`high`とし、期間経過後は`normal`へ引き下げる
  運用を想定するが、具体的な切り替えタイミングの判定方法(日付計算か手動レビューか)は
  次回以降の検討課題とする。

### 両論点を組み合わせた案内文イメージ(自然文、実装前のイメージ案)

「ご入力いただいた『さいたまスーパーアリーナ』は、現在の正式名称では『GMOアリーナさいたま』
(2026年4月改称)です。この会場は大規模改修工事のため2026年1月13日から休館中で、
2027年4月頃のリニューアルオープンが予定されています。当選公演の実際の開催会場・日程は
主催者発表で改めてご確認ください。」

closed_permanent(愛知県体育館型)とclosed_temporary(本件)とで後半の文面を出し分ける
必要があるのは論点1、前半で入力名称と正式名称を併記する必要があるのは論点2、という
2つの独立した設計判断の組み合わせで本文面が構成される。

## 残課題

- 混同注意リストの実データ化(今回は日本ガイシホール/NGKスポーツプラザの1組のみ設計例として
  記述。Kアリーナ横浜/横浜アリーナの組も含め、実ファイル〈schema配下のJSON等〉への反映は
  次回以降に行う)。
- エイリアス辞書の会場別裏取り(WebSearchでの旧名称・略称の実在確認)。
- 会場マスタの対象範囲拡大(地方のライブハウス・ホールまで含めるか)に伴うエイリアス辞書の
  メンテナンス方法(件数が増えた場合、Markdown管理では限界が来る可能性)。
- 部分一致(フォールバック)時の案内文の具体的な文例(status=generatedとの整合、
  schema拡張の判断とセットで検討)。
- `closed_permanent`/`closed_temporary`細分類・`recognition_priority`注釈の両方とも、
  `match_confidence`拡張・`venue_operational_status_note`追加と合わせて実API接続後の
  結合実装フェーズで具体化する(いずれも今回は設計メモのみ、schema/venue-master.json・
  schema/output.schema.jsonの編集は行っていない)。
- `recognition_priority`の`high`→`normal`切り替えタイミングの具体的な判定方法(改称からの
  経過期間の自動計算か、定期レビュー時の手動判断か)の検討。

コード実装・外部サービス接続は一切行っていない。承認が必要なアクション(支払い・
アカウント作成・外部公開・送信等)は本フェーズでは発生していないためpending-approval.mdへの
新規追記は不要(既存の承認待ち事項の範囲内で扱う)。
