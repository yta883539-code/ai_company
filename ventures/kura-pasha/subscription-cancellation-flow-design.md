# 解約・ダウングレード時のLINE案内文言・処理フロー設計

作成日: 2026-09-07(フェーズ23)

## 背景

フェーズ22で、llm-system-prompt-draft.mdの前提(「継続課金・解約フローが無い」)が
pricing-plan.md(月額サブスク+月間生成回数上限)・data-retention-policy.md
(`user_profile`が決済ID等を保持)と矛盾していたことを発見し、course-set-pashaの
厳守事項7a(解約意図検知)を参考に本venture向けの厳守事項7aを新設して前提を訂正した。
ただし厳守事項7aは「解約意図の検知」自体を扱うのみで、検知後の具体的な案内文言・
処理フロー(course-set-pasha/subscription-cancellation-flow-design.md相当)は
フェーズ22時点で未着手のまま次の課題として残されていた。本ファイルはその課題に対応する。

## 前提

- 決済方式は他venture(aircon-pasha/course-set-pasha/line-reservation-ai)と同様、
  Stripe Billing優先を想定する(実接続はオーナー承認待ち、pending-approval.md参照)。
- 本ventureは「メモ送信→3種類のテキスト生成(受注内容整理・納品案内・お手入れ案内)→
  返信」という単方向バッチ処理であり、line-reservation-aiのような予約枠の状態管理・
  進行中の会話が存在しない点はcourse-set-pashaと共通。そのため解約時の複雑な移行処理は
  不要で、course-set-pashaの設計をほぼそのまま踏襲できる。
- 本venture固有の論点: pricing-plan.mdの「複数職人プラン」は複数の職人が共同で1契約を
  利用する形態であり、他venture(1事業者=1契約が前提)には無い「誰が解約操作を行える
  権限を持つか」という論点が新たに生じる。

## 解約フロー

```
[契約者がLINEで「解約したい」等の解約意図を示すメッセージを送信]
        │
        ▼
[llm-system-prompt-draft.md 厳守事項7aの意図判定で検知]
        │
        ▼
[解約案内メッセージを送信(下記1.)]
        │
        ▼
[契約者が決済ページ(Stripeカスタマーポータル)で解約を確定]
        │
        ▼
[Webhook経由でStripeから解約確定通知(customer.subscription.deleted等)を受信]
        │
        ▼
[LINEで解約完了メッセージを送信(下記2.)]
        │
        ▼
[当月の生成回数カウントは維持したまま、次回生成リクエスト時は無料プラン相当(生成不可)として扱う]
```

## 1. 解約意図検知時の案内メッセージ(例)

```
【鞍パシャッと】解約についてのご案内

解約をご希望とのことで承知しました。以下の点をご確認のうえ、下記リンクから
お手続きください。

・現在のご契約: スタンダードプラン(月8回まで/月額1,980円)
・解約手続き完了後も、今回のご請求サイクルの終了日(◯月◯日)まではサービスを
  引き続きご利用いただけます。
・日割りでの返金は行っておりません(Stripeカスタマーポータルの表示に従います)。
・解約後、再開をご希望の場合はいつでも新規契約と同じ手順で再度お申し込みいただけます。

▼ 解約手続きはこちら
{Stripeカスタマーポータル URL}

このまま継続をご希望の場合は、このメッセージへの返信は不要です。
```

## 2. 解約確定Webhook受信時の案内メッセージ

```
【鞍パシャッと】解約手続きが完了しました

ご契約は◯月◯日をもって終了となります。それまでは引き続きご利用いただけます。
またのご利用をお待ちしております。
```

## 複数職人プラン固有の論点: 解約操作の権限(仮決め)

- 複数職人プランは複数の職人が共同で1契約を利用する形態のため、「共同利用者の誰もが
  解約操作を行える」設計は、他の職人が意図せずサービスを失うリスクがあり不適切と
  判断する。
- 仮決め方針: 契約(Stripeサブスクリプション)の名義人となった申込者本人のみが
  解約・ダウングレード操作を行える、というシンプルな権限モデルを採用する。
  他の共同利用者からの解約意図表明は、厳守事項7aの検知対象とはせず「契約者様に
  ご確認ください」という趣旨の案内に留める(誤って第三者が解約を進めてしまう事態を防ぐ)。
- 未確定事項: 「誰が契約者本人か」を判定する仕組み自体(本venture未設計、user_id
  紐付けの方式含め他venture(line-user-id-linking-design.md相当)を参照する必要が
  ある)は本venture未着手であり、複数職人プランの共同利用機能自体の実装設計と
  合わせて次の課題とする。

## ダウングレード(プラン変更)フロー

course-set-pasha/subscription-cancellation-flow-design.mdの確定方式をそのまま踏襲する
(本venture固有に異なる理由がないため)。

- タイミング: Stripeのプロレーション機能を用い、変更申込み時点で日割り差額を精算する
  (即時変更)。
- 当月の生成回数上限の適用方法(確定): ダウングレード申込み時点で本venture固有の
  `usage_counter`(pricing-plan.md想定、month・countのみ保持する設計)の当月`count`は
  リセットせずそのまま維持し、上限判定にのみ新プラン(下位プラン)の上限値を即時適用する。
  course-set-pashaがStripe公式ドキュメント調査(Prorations/Update a subscription)に
  基づき確定した結論(`billing_cycle_anchor`はダウングレード操作では途切れない)を
  本venture固有の`usage_counter`にもそのまま当てはめられると判断し、独自の再調査は
  行わなかった。
- 複数職人プランからライト/スタンダードプランへのダウングレードは、共同利用機能自体が
  失われる(複数職人プランのみの機能)ため、上記の生成回数上限の話に加えて「共同利用者の
  扱い」という論点が生じるが、共同利用機能自体が未設計のため本ファイルでは扱わず
  次の課題とする。
- 案内メッセージ: 解約案内と同様にStripeカスタマーポータルへ誘導し、プラン変更自体は
  ポータル内のUIに委ねる。
