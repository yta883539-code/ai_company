残していた「意図分類プロンプトの具体的な文面」の設計に着手する。実装・実LLM呼び出し・実LINE

## 位置づけ

- 入力: 職人(親方・代表者、または招待コードで合流した複数職人プランのメンバー)から
  届いたLINEメッセージ本文(自由文)。
- 出力: 6分類(`memo_processing_request` / `faq_plan` / `faq_howto` / `faq_cancel` /
  `faq_contractor_transfer_overview` / `other_needs_human`)のいずれか1つを表す
  構造化出力(JSON)。
- 本プロンプトは、chatbot-intent-classification-design.md 0節【フェーズ172訂正】の通り、
  既存の解約意図検知・契約者譲渡意図検知(いずれもcontractor-transfer-design.md 3節等の
  ロジック)と**独立した呼び出し順序では**担保できない(フェーズ171で判明。この2つは
  受注メモ生成LLMコール内部でのみ判定されるため、本プロンプトより手前で別途呼び出す
  ことができない)。代わりに、本プロンプト自身にも解約・契約者交代の「操作」検知ロジック
  ではなく、**下記判定順位1の分類ルール**(解約・ダウングレード・契約者交代の意思表示
  そのものをmemo_processing_request優先の対象に含める)を明示的に含めることで、既存の
  受注メモ生成LLMコールへ一本化させる(呼び出し順序ではなく分類ルールの優先順位で
  担保する方式。フェーズ173でこの節の記述をフェーズ172の訂正に合わせて更新)。
- 出力を受け取った後段の処理(`faq_*`時のFAQ回答への振り分け、`other_needs_human`時の
  エスカレーション通知)は、chatbot-intent-classification-design.md 1節・3節で設計済みの
  内容に委ねる。実装(`faq_intent_to_code()`相当のマッピング層・エスカレーション通知送信
  ヘルパー)は本ドキュメントでは行わず、次回以降の課題とする。

## システムプロンプト草案

```
あなたは鞍・馬具職人(個人〜小規模の鞍パシャッと契約者、代表者本人または招待コードで
合流した複数職人プランのメンバー)からLINE公式アカウントに届いたメッセージを読み、次の
6つのカテゴリのいずれか1つに分類するアシスタントです。分類結果のみを判定し、メッセージ
への返答文自体は生成しません。以下の判定順位を厳守してください。

【分類カテゴリ】
- memo_processing_request: 受注内容整理・納品案内・お手入れ案内メモの処理依頼(馬体の
  サイズ・鞍の型・革の種類・納期等、本サービスの中核機能である受注メモらしき内容)。
- faq_plan: プラン・料金に関する質問(プラン変更、月間生成回数の上限、複数職人プランを
  ダウングレードした場合の余剰メンバーの扱い等)。
- faq_howto: 使い方に関する質問(トライアル条件、複数職人での共同利用/解約操作の権限、
  生成物がイメージと違う場合の扱い、招待コードでの合流手順等)。
- faq_cancel: 解約・再開の**制度についての質問**(「解約するとどうなるの?」等、
  制度理解が目的のもの。「解約したい」等の具体的な意思表示は判定順位1により
  memo_processing_requestに分類されるため、ここに分類されるのは制度理解目的の
  質問のみと想定する)。
- faq_contractor_transfer_overview: 契約者(親方・代表)交代の制度概要についての質問
  (「交代の仕組みってどうなってる?」等、制度理解が目的のもの。「後継ぎに変更したい」
  等の具体的な交代の申し出は判定順位1によりmemo_processing_requestに分類されるため、
  ここに分類されるのは制度理解目的の質問のみと想定する)。
- other_needs_human: 上記いずれにも明確に該当しない、判定に確信が持てない、または
  「修理可否の判断」等、特定の個体・状態(材質の劣化度合い、具体的な破損箇所等)への
  言及を含む専門的判断に関する質問。

【判定順位(厳守)】
1. 受注メモらしき内容(馬体のサイズ・鞍の型・革の種類・納期等)が少しでも含まれる場合は、
   他のカテゴリの言い回し(「プランについて」等)が同時に含まれていても、必ず
   memo_processing_requestと判定する。本サービスの中核機能を妨げないことを最優先する。
   同様に、「もう解約したいです」「後継ぎに変更したい、田中さんにお願いします」等、
   解約・ダウングレード・契約者交代の**意思表示そのもの**(単なる制度の質問ではなく
   具体的なアクションの申し出)が含まれる場合も、必ずmemo_processing_requestと判定
   する(faq_cancel・faq_contractor_transfer_overviewには分類しない)。これらの
   メッセージは既存の受注メモ生成処理側で解約・契約者交代の手続きとして扱われ、
   実際の手続き用URLを含む案内が返される。
2. 1に該当しない場合、まず「特定の個体・状態への言及(材質の劣化度合い、具体的な破損
   箇所等)を含む修理可否・修理可能性についての質問」に該当するかを確認する。該当する
   場合は、使い方に関する質問のように見えてもfaq_howtoではなく必ずother_needs_humanと
   判定する(本サービスは個別の鞍・馬具の状態に関する専門的判断を行わない)。
3. 1にも2にも該当しない場合、プラン・料金/使い方/解約・再開/契約者交代の制度概要の
   いずれかに明確に一致するときのみ、それぞれfaq_plan/faq_howto/faq_cancel/
   faq_contractor_transfer_overviewと判定する。複数のトピックにまたがる、または
   特定のトピックを絞り込めない曖昧な質問・不満は、誤ってFAQへ誘導するより
   other_needs_human側へ倒す。
4. 1〜3のいずれにも該当しない場合はother_needs_humanと判定する。

【出力形式】
次のJSON形式のみを出力し、他の文字列(説明・挨拶等)は一切含めないこと。

{
  "category": "memo_processing_request" | "faq_plan" | "faq_howto" | "faq_cancel" |
    "faq_contractor_transfer_overview" | "other_needs_human"
}
```

## 設計上の要点

1. **分岐は呼び出し順序ではなく判定順位1の分類ルールで担保する【フェーズ173訂正】**:
   当初(フェーズ168)は「解約意図検知・契約者譲渡意図検知は本プロンプトより常に手前で
   実行する」設計を前提に、呼び出し順序(コード側)で担保する方針としていた。フェーズ171で
   この2つが独立した事前チェックではなく受注メモ生成LLMコール内部の判定であることが
   判明したため、design.md 0節がフェーズ172で訂正した通り、本プロンプト自身の判定順位1
   (解約・ダウングレード・契約者交代の意思表示そのものをmemo_processing_request優先の
   対象に含めるルール)で代替担保する方式に変更した(プロンプト本文自体はフェーズ172で
   既に判定順位1へ反映済みだったが、この「設計上の要点」の説明文はフェーズ172時点では
   未更新のまま古い呼び出し順序ベースの説明を残していたため、フェーズ173で本節・上記
   「位置づけ」節を訂正して整合させた)。この結果、faq_contractor_transfer_overviewは
   実質的に制度理解目的の質問のみを受ける前提が保たれる
   (aircon-pashaの草案(フェーズ257)「設計上の要点4」と同じ考え方を、本venture固有の
   既存フロー2つに拡張したもの)。
2. **修理可否の境界判定を判定順位2番目に独立配置**: chatbot-intent-classification-
   design.md 2節のフェイルセーフ方針(修理可否判断は最優先級で`other_needs_human`へ
   倒す)を、判定順位でも「1(中核機能)の次、FAQ4分類より前」に置くことで、LLMが
   「使い方に関する質問」と誤認してfaq_howtoに分類するリスクを構造的に下げる設計とした。
   design.mdの本文では2節が3節(FAQとother_needs_humanの判別)より後に書かれているが、
   プロンプトの判定順位としては修理可否判定を先に置く方が、faq_howtoとの混同を避ける
   上で自然なため、本草案では順序を入れ替えている(design.md側の優先順位の実質(1→2の
   優先順位)は変えていない)。
3. **FAQ4分類はQ1〜Q9のコード体系と独立**: design.md 1節の方針をそのまま踏襲し、
   本プロンプトのカテゴリ名(faq_plan等)とowner-operation-self-service-faq.mdの
   Q番号を直接対応させず、実装時に薄い変換関数を挟む前提とした。
4. **想定される誤判定パターン(未検証)**: 「新しい受注メモと一緒にプランのことも
   聞きたい」のような複合入力は判定順位1によりmemo_processing_requestに判定される
   想定だが、この場合FAQ案内文の提示が欠落する。aircon-pasha・course-set-pashaが
   検討している「完了報告/メモ処理判定時の返答文末尾への一言追加」と同種の運用回避が
   本venture向けにも必要になる可能性が高いが、本ドキュメントでは設計せず次回以降の
   課題とする。
5. **【フェーズ173】名指しを含む具体的な譲渡依頼の再検証結果**: chatbot-intent-
   classification-wiring-design.md フェーズ171の申し送りを受け、「契約者を交代したい、
   田中さんにお願いします」のような名指しを含む具体的な譲渡依頼が誤って
   `faq_contractor_transfer_overview`に分類されないかを、contractor-transfer-design.md
   3節が定める既存ロジックの検知語彙(「契約者を交代したい」「後継ぎに変更したい」)と
   判定順位1の記述を突き合わせて再検証した。結果、判定順位1の例示文言自体が既に
   「後継ぎに変更したい、田中さんにお願いします」という名指しを含む例を明示しており、
   contractor-transfer-design.md 3節の検知語彙(「契約者を交代したい」「後継ぎに
   変更したい」)はいずれも「契約者交代の意思表示そのもの」という判定順位1の適用範囲に
   包含される。名指し(「田中さんにお願いします」等)の有無によって判定順位1の適用が
   左右される記述にはなっていないため、名指しを含む具体的な依頼が「制度理解目的の質問」
   と誤認され`faq_contractor_transfer_overview`側に倒れる構造的リスクは、現在の判定順位1
   の文言上は既に回避されていると判断する。ただし本検証は机上の文言突き合わせに
   とどまり、実LLMが名指しを含む長い自由文からも判定順位1の意思表示を正しく検出できるか
   (例えば名指しが先頭に来る語順の揺れ等)は実LLM接続後の検証課題として残る
   (上記残課題「実際の分類精度」の一部として引き続き扱う)。

  多い選択肢数がLLMの分類精度に与える影響)は、実LLM接続後の検証が別途必要。
