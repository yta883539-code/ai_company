# 外部ベンダー侵害発覚時の自社キー緊急ローテーション手順(設計)

## 1. 背景

ノーコードWeb制作サービス「Studio」(Studio株式会社)は2026年10月16日、クラウド環境内の
脆弱性を悪用した第三者による不正アクセスを公表した(不正アクセス確認期間は2026年9月30日
〜10月1日、同社は10月14日までに脆弱性修正・経路遮断を完了)。対象は全登録顧客のアカウント
情報に加え、各社サイトのフォーム送信内容、**外部サービス連携用のAPIキー**にまで及んだ
(piyolog・internet.watch.impress.co.jp・cybersecurity-jp.com・rocket-boys.co.jp各報道で
確認)。デジタル庁も2026年10月22日、同社サービスを一部ホームページ運営に利用していたことを
理由に問い合わせフォーム最大13,323件の漏えい可能性を公表し、LUUP(21,368件)・Link-U
(7,663件)・ラクスル(6,412件)等、業種を問わず多数の組織に波及した。

本件が他の「パシャっと」系ventureが既に扱う漏えい対応アイデア群(個人情報保護法上の
報告・本人通知義務の一次整理が主題)と異なる点は、漏えいした情報に**個人情報だけでなく
自社が外部サービスと連携するために使っていたAPIキー・復号鍵そのものが含まれる**ケースが
あることである。この場合、個人情報保護法上の対応に加えて、漏えいしたキーを使って
第三者が自社の決済代行・メッセージング・データベース等の外部サービスへ不正アクセス
できる状態が生じている可能性があり、通常の漏えい対応とは別に「自社が保有するキー群を
総点検し、影響範囲が確定する前に予防的に失効・再発行する」という技術的な緊急対応が
別途必要になる。

本ドキュメントは、kura-pasha自体がこの種の被害を受けた場合に備え、本venture固有の
依存先キー群を洗い出し、緊急ローテーションの手順を設計のみ先行して整理するもの。
実際の不正アクセス発生・キー漏えいは本ventureには生じていない。

## 2. kura-pashaが保有する外部連携キー・シークレットの一覧

tech-stack.md(コンポーネント1〜4)の構成を前提に、本venture固有の依存先を整理する。

| 依存先 | 保有するシークレット | 用途 |
| --- | --- | --- |
| LINE Messaging API | チャネルアクセストークン・チャネルシークレット | Webhook署名検証・返信送信 |
| Stripe | シークレットキー(`sk_live_...`)・Webhook署名シークレット(`whsec_...`) | Checkout Session発行・Webhook受信(stripe-webhook-checkout-completed-design.md) |
| LLM APIプロバイダ | APIキー | 3出力生成(llm-system-prompt-draft.md) |
| GCP(Cloud Run functions・Firestore) | サービスアカウント鍵・Secret Managerアクセス権 | Webhook実行環境・データストア接続 |

いずれも実アカウント開設自体がオーナー承認待ち(pending-approval.md参照、2026-10-23 19:00
UTC記載分)のため、現時点では上記は「開設後に保有することになる」想定の一覧である。
Studio社の事案のように、これらのキーを直接保管するのが上記ベンダー自身ではなく、その先に
利用するさらに別のSaaS(例: 問い合わせフォーム埋め込み用の第三者ウィジェット等)である
場合、依存の層が一段深くなる点にも注意する(本venture現行設計では該当する第三者SaaSの
利用は想定していないが、将来LPにフォーム埋め込み等を追加する際は本表を更新する)。

## 3. 緊急ローテーション手順(ドラフト)

1. **検知**: 上記いずれかのベンダー(またはそのベンダーがさらに利用する委託先)が
   不正アクセス・情報漏えいを公表し、自社が保有するAPIキー・シークレットが対象に
   含まれる可能性があるとの連絡・報道を確認した時点を起点とする。
2. **一次切断**: 対象ベンダーの管理画面から影響範囲が確定する前に、該当するキー・
   シークレットを予防的に失効させ、新しいキーを再発行する(「疑わしきは即時失効」を
   原則とし、公式な影響範囲の確定を待たない)。
3. **再配線**: 新しいキーをCloud Run functionsの環境変数・Secret Managerへ反映し、
   旧キーでの呼び出しが拒否されることを確認する(例: Stripe Webhook署名検証で旧
   `whsec_...`が失敗することを確認)。
4. **不正利用の痕跡確認**: 各ベンダーの管理画面・Cloud Loggingで、キー失効までの間に
   想定外の呼び出し(決済・メッセージ送信等)が発生していないかを確認する。
5. **個人情報保護法上の対応との併走**: キー漏えい自体とは別に、当該ベンダーが保持して
   いた顧客データ(本venture経由の個人情報)が対象に含まれる場合は、既存の漏えい対応系
   「パシャっと」群と同じ一次整理(報告・本人通知の要否判定)を並行して行う。
