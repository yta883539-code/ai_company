# 依頼者以外の第三者個人情報の誤記載対応方針(設計)

legal-notices-draft.md 2.5節が「新たな検討課題」として残していた、納品案内・お手入れ
案内文に依頼者の氏名・住所等の個人情報を職人が誤ってメモへ記載してしまうケースへの
対応方針(本サービス側でのマスキング要否等)について検討する。本フェーズは方針の設計
のみを行い、llm-system-prompt-draft.md・schema/output.schema.json・
prototype/post_generation_checks.pyへの実際の反映は次回以降の課題とする。

## 1. 対象範囲の整理

mvp-flow-draft.md(1節)の定義を前提に、3出力の宛先を改めて整理する。

- **出力1(受注内容整理メモ)**: 職人自身の備忘・作業記録用であり、依頼者本人へ
  転送されることは想定されていない。したがって出力1に依頼者本人や第三者の個人情報が
  そのまま残っても、新たな「第三者への開示」は発生しない(職人本人が既に知っている
  情報の整理に過ぎない)。ここで生じる唯一のリスクは、入力メモが外部LLM APIへ送信
  される際の取り扱い(legal-notices-draft.md 2.3節で既に整理済みの、委託先LLM API
  プロバイダへの入力内容送信の問題)であり、本フェーズの検討課題とは別問題として
  切り分ける。
- **出力2(納品案内下書き)・出力3(お手入れ案内下書き)**: 職人が依頼者へ実際に
  転送することを前提とした文面である(README.md「実際の…送付は職人本人が行う設計」)。
  したがって、この2出力に**依頼者本人以外の第三者**(例: 同じ乗馬クラブの別の馬主、
  取次を行った関係者等)の氏名・連絡先等が紛れ込み、それが職人によってそのまま依頼者へ
  転送された場合にのみ、「本サービスが下書きした文面を通じて第三者の個人情報が別の
  第三者〈依頼者〉へ開示される」という、本サービス固有の追加リスクが生じる。
- 依頼者本人の氏名等が出力2・3に含まれること自体は、納品案内・お手入れ案内の宛名等
  として想定内の記載であり、問題ではない。したがって本方針が対象とするのは
  「依頼者本人以外の第三者の個人情報」に限定する。

## 2. 自動マスキングは採用しない

aircon-pasha/prototype/post_generation_checks.pyの既存チェック群(厳守事項の逸脱を
話題キーワード+判定語の共起で検出するヒューリスティック方式)を調査したが、氏名・
住所等の個人情報そのものを正規表現等で機械的に検出・マスキングする方式は採用しない
方針とする。理由は次のとおり。

- 日本語の人名・地名は表記の多様性(漢字・かな・ローマ字、姓のみ/フルネーム等)が
  大きく、辞書やパターンマッチでの網羅的な検出は現実的でない。
- 過検出のリスクが高い。依頼者本人の氏名を宛名として使う一般的な記載(「◯◯様」等)を
  誤って第三者情報と判定し削除してしまうと、納品案内・お手入れ案内としての体裁が
  崩れ、厳守事項違反よりもむしろサービス品質上の問題を新たに生む。
- 鞍・馬具という商材の性質上、依頼者が「◯◯さんの馬」等、自分以外の馬の所有者名を
  文脈として言及することが構造的にありうる(乗馬クラブ内の共有設備の話等)。一律の
  マスキングでは、依頼者本人にとって必要な文脈情報まで失われる可能性がある。

## 3. 採用する方針: プロンプト側での明示的な取り扱い指示(厳守事項9案)

自動マスキングの代わりに、llm-system-prompt-draft.mdの厳守事項1〜8・7a〜7cに続く
新規項目(厳守事項9)として、以下の趣旨を追加する案を提示する(文面案・実際の反映は
次回以降)。

```
9. 入力メモに、依頼者本人以外の第三者(他の馬主・関係者等)を特定できる氏名・連絡先等の
   記述が含まれている場合、出力2(納品案内)・出力3(お手入れ案内)の本文にはその
   第三者の氏名・連絡先等をそのまま転記しない。当該記述が発注内容の理解に必要な
   文脈(例: 馬の所有者名としての言及)であれば、第三者を特定しない一般化した表現
   (「所有者様」等)に置き換えて記述する。出力1(受注内容整理メモ)は職人本人の
   備忘用であり本項の対象外とし、入力メモの記載をそのまま転記してよい(mvp-flow-
   draft.md 1節の宛先整理に基づく)。
```

- 既存の厳守事項1(専門判断への不介入)・厳守事項2(修理可否判断への不介入)と同様、
  「入力メモの記載をそのまま転記するのが既定」という本ventureの基本方針に対する
  明示的な例外(出力2・3に限り第三者情報を一般化する)として位置づける。
- 厳守事項7a〜7cのように状況(d)内の分岐ではなく、通常の受注メモ生成(状況(a))に
  対する追加ルールという位置づけのため、既存の番号体系(1〜8)の延長である「9」として
  追加するのが自然と判断した(aircon-pashaが原状回復の費用負担区分チェックを「厳守
  事項9」として新設した際の位置づけ〈通常の完了報告生成に対する追加ルール〉と同種)。

## 4. 機械チェック(post_generation_checks.py拡張)の考え方

厳守事項1(冷媒・電気系統の専門的評価語の検出)と同じ「話題キーワード+判定語の共起」
方式は、氏名という自由文字列には適用できないため、以下の限定的な突き合わせ方式を
次回実装時の案として提示する。

- 入力メモ側の`requester_name`(依頼者名、既存フィールドを想定)以外に、メモ本文の
  自由記述欄(備考等)から抽出された人名らしき文字列がLLM側の構造化出力に含まれて
  いる場合にのみ、出力2・3の本文にその文字列がそのまま出現していないかを確認する
  ヒューリスティックとする。
- ただし「人名らしき文字列の抽出」自体が信頼できる技術ではない(厳守事項7cの
  `specified_member_name`抽出と同種の限界がある)ため、このチェックはあくまで
  「明らかな見落としを拾う補助的な網」の位置づけとし、厳守事項9の実効性の主体は
  プロンプト側の指示に置く。
- 上記は設計方針の提示のみであり、実際の`schema/output.schema.json`フィールド追加・
  `prototype/post_generation_checks.py`への関数追加・テストケース追加は次回以降の
  実装フェーズで行う。
