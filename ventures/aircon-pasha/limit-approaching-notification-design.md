# 月間生成回数の上限接近時通知 設計

tech-stack.md「次のステップ候補」1点目にあった、本venture固有の季節性(繁忙期は施工件数が
閑散期の2〜3倍)を踏まえた上限接近時の事前通知設計を検討する。
course-set-pasha/limit-approaching-notification-design.mdをベースとしつつ、本venture固有の
利用ペース(pricing-plan.mdより1日3〜5件・月60〜100件、course-set-pasha比で一桁多い)を
踏まえて再検討する。

## 1. course-set-pashaの設計をそのまま流用できない理由

course-set-pasha/limit-approaching-notification-design.mdは「プラン上限 − 現在count == 2」に
なった生成完了時に1回だけ通知する設計だった。しかしcourse-set-pashaの想定利用ペースは月8〜30回
(1日あたり多くて1〜2件程度)であるのに対し、本ventureはmarket-research.mdより1日3〜5件、
繁忙期はさらに増える可能性がある。この利用ペースの差により、「残り2回」の通知を出した時点から
上限到達・従量課金発生までの猶予がcourse-set-pashaでは数日単位だが、本ventureでは早ければ
当日中(繁忙期は半日程度)に上限へ到達しうる。「残り2回」通知が届いた時点で既にその日の訪問
予定を消化中というケースが起こりやすく、通知の実効性(気づいてから対応を検討する時間)が
course-set-pashaより薄いと考えられる。そのため閾値・タイミングをそのまま踏襲せず、
本venture固有のペースに合わせて再設計する。

## 2. 通知トリガー・閾値の再設計

- **閾値を「残り2回」から「残り1日分の想定最大件数」相当に変更する。**
  pricing-plan.mdの前提(1日3〜5件)より、いずれのプランでも「残り5回」に達した生成完了時点で
  1回通知することとする。5回は3プラン共通の閾値とし、日次件数の上振れ(繁忙期含む)を
  カバーできる最大値(5件)を採用することで、少なくとも「その日のうちに上限へ到達しうる」
  状態になったことをその日のうち、できれば前日までに伝えられる設計とする。
  - スモールプラン(月40回): 残り5回=35回目の生成完了時点で通知。
  - スタンダードプラン(月90回): 残り5回=85回目の生成完了時点で通知。
  - 繁忙期対応プラン(月150回): 残り5回=145回目の生成完了時点で通知。
- **course-set-pashaと同様、通知は1回のみとする。**
  生成のたびに毎回通知が挟まると本来の返信(completion_report/care_guide/history_row)の
  可読性を損なう点はcourse-set-pashaと同じ課題のため、「残り5回」到達時の1回のみとし、
  実際に上限を超えた場合は超過時点の返信メッセージ自体に従量課金が発生する旨を1文添える
  方式(4節)でカバーする方針を踏襲する。
- **繁忙期(6〜8月)固有の追加検討は見送る。**
  当初、繁忙期は「残り5回」到達から上限到達までの実時間がさらに短くなる(2〜3倍のペース)
  ため、繁忙期のみ「残り10回」等の早めの閾値に切り替える案も検討した。しかし本venture・
  course-set-pashaいずれも月をまたいだ実利用データが無く、繁忙期の閾値だけを分けても
  妥当性を検証する材料が無い。閾値を分けるとロジック・通知文言(4節)の分岐も増えるため、
  MVP段階では固定閾値(残り5回)のみとし、実際の繁忙期利用データが得られた段階で
  「残り5回では早すぎる/遅すぎる」の検証・見直しを行う方針とする(6節)。
- **送信方法はcourse-set-pashaを踏襲する。**
  新規のプッシュメッセージは送らず、残り5回目の生成完了時の返信メッセージ(通常のreply API
  応答)に追記する形で実現し、追加のAPI呼び出し・課金を発生させない。

## 3. カウントの対象・タイミング・月の区切り

course-set-pashaと同じ方針を踏襲する(本venture固有の差異は無い)。

- カウント対象は`status == "generated"`の場合のみ(`out_of_scope`・`insufficient_input`・
  検証失敗フォールバックは対象外)。
- インクリメントのタイミングは`process_visit_memo_event()`(cloud_function_webhook.pyの
  イベント処理関数)内で返信本文を組み立てた直後(`generated`の分岐が確定した時点)。
- 月の区切りはJST基準の暦月(`YYYY-MM`)。market-research.mdの対象が日本国内の個人事業主で
  あるため、course-set-pashaと同じ理由でJST基準を採用する。

## 4. 通知文言案(仮)

生成完了時の通常の返信メッセージ末尾に、該当条件のときのみ以下を追記する。

- 残り5回に達した時点(プランごとに35回目/85回目/145回目の生成完了時):
  「※今月の生成回数は残り5回です(上限到達後は1回あたり[単価]円の追加料金がかかります)」
- 上限を超えて従量課金が発生した回(超過1回目以降)の返信メッセージ末尾:
  「※今月の無料生成回数の上限を超えたため、本回は追加料金[単価]円が発生します」

いずれも1文の定型文言とし、course-set-pashaと同様post_generation_checks.pyの機械チェック
対象(厳守事項の違反検知)には含めない(課金案内であり、厳守事項1〜4等が対象とする
「作業完了報告・お手入れ案内の内容そのもの」とは性質が異なる運用メッセージのため)。

## 5. 実装への影響メモ(設計のみ、実装は次回以降)

- course-set-pashaと同じく、`process_visit_memo_event()`のシグネチャに月間カウントの
  読み書きを行うインターフェース(仮称`usage_counter: UsageCounterProtocol`、
  `get_count(user_id, month) -> int` / `increment(user_id, month) -> int`の2メソッド)を
  新規に1つ追加する想定。tech-stack.mdコンポーネント5で既に同名のProtocolを想定済みのため、
  本設計は「残り5回」判定ロジックをこのProtocolの上に乗せる形になる。
- テスト(prototype/test_cloud_function_webhook.py)では、course-set-pashaの
  `InMemoryUsageCounter`と同様のdictベースのスタブを用意し、3プランそれぞれの境界値
  (35/85/145回目、および各上限到達・超過)をユニットテストで検証する方針とする。
- 実際のFirestore接続(プロジェクト作成・課金設定)はオーナー承認待ちの範囲であり、
  本フェーズでは設計とスタブ実装の方針整理のみに留める。

## 6. 今後の課題

- 「残り5回」という固定閾値の妥当性は机上の想定(1日3〜5件)に基づく仮説であり、実LLM接続・
  実運用データが取れた段階で、特に繁忙期(2〜3倍ペース)において閾値が早すぎる/遅すぎる
  ケースがないか再検証する必要がある。
- 2節で見送った「繁忙期のみ閾値を分ける」案は、実データにより「残り5回」では繁忙期に
  猶予が不足すると分かった場合の代替案として、次回以降に再検討する。
- 決済代行サービス側の都度課金対応可否確認(pricing-plan.md未確定事項)が完了した段階で、
  4節の「追加料金[単価]円」の具体的な請求タイミング(即時課金か翌月合算請求か)を通知文言に
  反映する。
- course-set-pashaと同様、Firestore導入に伴う読み書き課金は
  subscription-billing-cost-estimate.mdの原価試算にまだ反映されていない
  (tech-stack.md・README.md「次にやること」既知の課題として別途残っている)。
