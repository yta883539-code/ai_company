# 繁忙期対応プランにおける「複数職人を抱える小規模法人」利用実現方式の検討・明確化(フェーズ204)

作成日: 2026-09-11(フェーズ204)

## 背景・気づいたギャップ

course-set-pashaのmulti-setter-shared-usage-design.md(フェーズ204、2026-09-11)で、
「セッター複数プラン」の想定顧客像に含まれる「複数店舗を運営する事業者」という文言が、
実装(`user_profile/{user_id}`を単位とし「1つのuser_id = 1契約」が前提)では複数の異なる
LINEアカウントでの共同利用をサポートしていない、というギャップが発見された。本venture
(aircon-pasha)のpricing-plan.mdにも同種の文言が存在するか確認したところ、同じパターンの
ギャップが見つかった。

pricing-plan.mdのプラン表で、繁忙期対応プランの想定顧客像を「繁忙期(梅雨〜夏)に施工件数が
大きく増える事業者、複数職人を抱える小規模法人」と記載している。このうち「複数職人を抱える
小規模法人」を文言どおりに読むと、法人に所属する複数の職人がそれぞれ自分のLINEアカウントで
現場から作業完了メモを送信し、1つの契約(サブスクリプション)の生成回数枠を共有するケースを
連想させる。

しかし実装(user-account-linking-design.mdの設計・`prototype/user_id_linking.py`)は
`user_profile/{user_id}`(LINEのuser_id単位)に`current_plan_id`・課金状態を保持しており、
`usage_counter/{user_id}`(tech-stack.md既存設計)も同じuser_id単位でカウントする。
「1つのuser_id = 1契約」が前提であり、複数の異なるuser_idが1つの契約・利用枠を共有する
仕組みは存在しない。つまり「複数職人を抱える小規模法人」の職人各自が自分のLINEアカウントから
独立して送信したい場合、現行設計ではサポートできない(職人ごとに別々の契約が必要になって
しまう)。

## 検討: 複数user_id対応が必要か

course-set-pashaフェーズ204と同じ結論に至る。本venture固有の事情を踏まえても、MVP範囲では
複数user_id対応を見送り、運用でカバーする方が適切と判断する。

- 本ventureも単方向バッチ処理(1件の訪問施工完了メモ受信→依頼者向け報告・お手入れ案内・
  履歴記録の3種類のテキスト生成→即返信)であり、mvp-flow-draft.mdの想定どおり生成される
  報告文・案内文の宛先は依頼者(顧客)であって、送信した職人個人を宛てた文面ではない。
  「誰が送ったか」を区別する業務要件は存在しない点はcourse-set-pashaと同じ。
- 複数職人を抱える小規模法人であっても、実務上は「事業所で1台の業務用スマートフォンを
  職人が現場ごとに持ち出し、作業完了時にその場でメモを送る」運用、または「事業所に戻ってから
  事業所の公式LINEアカウントでまとめて送る」運用が小規模事業者では一般的と考えられる
  (course-set-pasha・line-reservation-ai等の他ventureでも同様の想定を採用済み)。1つの
  LINEアカウント(=1つのuser_id)を法人内の複数職人で共有利用する形で「複数職人を抱える
  小規模法人」というニーズを満たせると考えられる。
- 複数の異なるuser_idを1契約に束ねる設計は、kura-pashaのworkshop型設計
  (craftsman-account-linking-design.md・contractor-transfer-design.md)のような抽象化・
  招待コードフロー・契約者概念の追加が必要になり、単方向バッチ処理という本ventureの
  単純さを損なう。実需要が確認できていない段階での先行実装はオーバーエンジニアリングに
  あたる。

## 結論・スコープ確定

- MVPでは「複数職人を抱える小規模法人」の利用を「1つのLINEアカウント(1 user_id)を法人内の
  複数職人で共有して使う」運用と定義する。技術的な追加実装は不要(既存の
  `user_profile/{user_id}`単位の設計のまま)。
- pricing-plan.mdの想定顧客像の記載はミスリーディングになり得るため、前提を明記する訂正を
  行った(本フェーズで対応済み。下記「対応した内容」参照)。
- 将来、複数の異なるLINEアカウントでの共同利用の実需要が顧客ヒアリング等で確認された場合は、
  kura-pashaのworkshop型設計を参考に横展開を検討する。

## 対応した内容(本フェーズ)

- pricing-plan.mdの繁忙期対応プラン行の想定顧客像を「繁忙期(梅雨〜夏)に施工件数が大きく
  増える事業者、複数職人を抱える小規模法人(1つのLINEアカウントを事業所内で複数職人が
  共有運用する前提。詳細はmulti-technician-shared-usage-design.md参照)」に更新した。
