# 依頼者以外の第三者個人情報の誤記載対応方針(設計)

kura-pasha/requester-personal-info-inclusion-handling-design.md(フェーズ181〜184で
厳守事項9として実装完了)と同種の論点が本ventureにも未検討のまま残っていたかを棚卸しした。
業者が作業後メモに、依頼者本人以外の第三者(例: 集合住宅の管理会社担当者名、隣室の入居者、
立会いに来た家族以外の関係者等)を特定できる氏名等を記載してしまい、それが依頼者・管理
会社へ転送される文面にそのまま紛れ込むケースへの対応方針を検討する。

## 1. kura-pashaとの前提の違い: 出力1が既に依頼者(または管理会社)向けである

kura-pashaのdesign.md 1節は、出力1(order_summary、受注内容整理メモ)が職人本人の備忘用で
あり依頼者へ転送されないことを前提に、出力1を厳守事項9の対象外としていた。

本ventureはこの前提が成立しない。README.md・mvp-flow-draft.mdの整理によれば、

- **出力1(completion_report、作業完了報告メッセージ下書き)**: 依頼者(recipient=tenantの
  場合)または管理会社・オーナー(recipient=management_companyの場合、厳守事項9〈2026-09-14
  新設〉対応)へ実際に転送される前提の文面である。
- **出力2(care_guide、お手入れ案内下書き)**: recipientの値にかかわらず依頼者本人向けに
  転送される前提の文面である(厳守事項9、care_guideはrecipientによる翻案を行わない方針)。
- **出力3(history_rows、簡易な作業履歴記録)**: 号数・機種系統・汚れ状況・追加施工の有無・
  次回推奨時期という定型フィールドのみで構成される表形式データであり、自由記述欄
  (kura-pashaのremarksに相当する項目)が存在しない。人名等の自由記述が入り込む余地が
  構造的に無いため、本方針の対象外とする。

したがって本ventureには「職人本人の備忘用で依頼者へ転送されない出力」が存在せず、
completion_report・care_guideの両方が最終的に依頼者または管理会社という受け手へ渡る。
本方針はこの2出力の両方を対象とする(kura-pashaが出力1を対象外としたのとは異なる整理)。

## 2. 自動マスキングは採用しない

kura-pashaのdesign.md 2節と同じ理由により、氏名・住所等を正規表現等で機械的に検出・
マスキングする方式は採用しない。

- 日本語人名の表記多様性(漢字・かな・ローマ字、姓のみ/フルネーム等)から網羅的検出は
  現実的でない。
- 過検出により依頼者本人・管理会社担当者の宛名表記(「◯◯様」等)を誤って削除すると、
  作業完了報告・お手入れ案内としての体裁が崩れる。
- 集合住宅の管理会社・オーナー名(recipient=management_companyのケース)は、そもそも
  「依頼者」の定義がテナント本人ではなく管理会社側に移るため、第三者の範囲の判定自体が
  recipientの値に依存する(3節参照)。

## 3. 採用する方針: プロンプト側での明示的な取り扱い指示(厳守事項10案)

llm-system-prompt-draft.mdの厳守事項1〜9(6a・6bのサブ項目含む)に続く新規項目
(厳守事項10、9は2026-09-14に使用済みのため新規に10番を付与)として、以下の趣旨を
追加する案を提示する(文面案・実際の反映は次回以降)。

```
10. 入力メモに、依頼者(recipient=management_companyの場合は管理会社・オーナー)以外の
    第三者(同じ集合住宅の別の入居者、管理会社の特定の担当者個人、立会いに来た依頼者以外の
    家族・関係者等)を特定できる氏名・連絡先等の記述が含まれている場合、出力1(作業完了
    報告メッセージ)・出力2(お手入れ案内)の本文にはその第三者の氏名・連絡先等をそのまま
    転記しない。当該記述が作業内容の理解に必要な文脈(例: 立会者としての言及)であれば、
    第三者を特定しない一般化した表現(「ご家族の方」「管理会社ご担当者様」等)に置き換えて
    記述する。recipient=management_companyの場合、管理会社・オーナー自身の担当者名が
    宛名として文面に含まれること自体は想定内の記載であり第三者情報には当たらない
    (本項が対象とするのは受け手以外の第三者に限る)。
```

kura-pashaの厳守事項9本文と同じ考え方(「依頼者本人にとって必要な宛名等は対象外、それ
以外の第三者のみが対象」)を踏襲しつつ、recipientによって「誰が受け手本人か」が変わる
本venture固有の分岐(management_companyのとき、受け手はテナントではなく管理会社・
オーナー自身になる)を明記した。

## 4. 機械チェックの補助フィールド案

kura-pashaのorder_summary.third_party_namesと同じ位置づけで、completion_reportに
`third_party_names`(入力メモから抽出された、受け手以外の第三者を特定できる氏名らしき
文字列のリスト、requiredには含めない補助フィールド)を追加し、post_generation_checks.pyに
completion_report.body・care_guide.bodyへの紛れ込みを検出するチェック関数を新設する案とする
(kura-pashaのcheck_no_third_party_name_leak_in_customer_facing_noticesと同じ、キーワード
突き合わせによる補助的な網であり厳守事項10の実効性の主体はプロンプト側指示に置く)。
