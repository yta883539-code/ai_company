# 実GCPプロジェクト作成の承認ハードルを下げるための請求額上限(Billing Budget)安全策

## 背景
pending-approval.md(2026-09-27 09:00 UTC・2026-09-27 10:00 UTC記載)に記録した「実Stripeアカウント
開設・LPの実装公開」「LINE公式アカウント開設・Cloud Scheduler作成(GCPプロジェクトの課金設定を
伴う)」の承認依頼は、本時刻(2026-11-13 01:00 UTC)時点で約1ヶ月半以上オーナーからの回答が
無いまま保留が続いている。line-reservation-aiはフェーズ続き386(2026-11-11 04:00 UTC)で、
「課金設定を含む」という表現が実際の想定コストに比べて重く響き承認判断を先送りさせている
可能性を踏まえ、Billing Budget(予算アラート)+自動停止による請求額上限保証策を設計し、
次回候補として他5venture(本ventureを含む)への横展開を残していた。本ドキュメントは、
その横展開を本venture向けに行うものであり、実行(アカウント作成・課金設定)そのものは
行わず、承認依頼のリスクを技術的に小さく・見積もり可能にするための設計のみを行う。

## line-reservation-aiとの前提差分(本venture固有の確認事項)
line-reservation-aiはFirestore原価・LLM API原価のいずれも無料枠内に収まる想定で、1店舗あたり
最悪ケースでも月間0.1〜2.6円程度という前提のもと、月間500円という予算額を「十分な安全マージン」
として設定した。しかし本venture(unit-economics-estimate.md)はLLM API原価がキャッシュなしで
1回あたり約6.93円と、line-reservation-aiのような無料枠内に収まる前提ではなく、プラン別の
月間LLM API原価(キャッシュなし、繁忙期単価込み)は以下の通り契約者1件あたりでも無視できない
規模になる。

| プラン | 月間利用回数 | LLM API原価(キャッシュなし) |
|---|---|---|
| スモール | 40回 | 約277.2円 |
| スタンダード | 90回 | 約623.7円 |
| 繁忙期対応(超過込み) | 150〜250回 | 約1,039.5円〜1,732.5円 |

この原価は契約業者の月額料金(2,980円〜8,980円)から支払われる正常な事業運営コストであり、
line-reservation-aiのケースと異なり「ゼロに近いはずの原価が想定外に跳ね上がった場合に検知する」
という設計意図だけでは不十分で、契約業者数が増えるほど予算額もそれに比例して増えるのが正常な
姿になる。したがって本venture向けのBilling Budgetは、line-reservation-aiの固定500円をそのまま
流用せず、想定契約業者数に応じて算出する方式とする。なお、Cloud Functions(Cloud Run functions
2nd gen)実行課金自体は既にフェーズ123(2026-08-25、unit-economics-estimate.md「Cloud Functions
実行課金の原価試算」節)で「想定事業規模(数百〜1,000業者程度)では無料枠内に収まる見込みが高い」
と確認済みのため、本ドキュメントではLLM API原価のみを可変要素として扱う。

## 提案: 想定契約業者数に応じたBilling Budget(予算アラート)+ 閾値到達時の自動停止
1. ローンチ直後の想定契約業者数(launch-readiness-checklist.md・customer-interview-design.md
   で想定している初期ヒアリング候補7〜8件規模を踏まえ、当面は最大10業者程度と仮置きする)に、
   最も原価が高い「繁忙期対応(150回、超過含め最大250回)」プランを全業者が選択した場合の
   最悪ケース(約1,732.5円/業者)を掛けた額に、想定外のバグ・無限ループ等によるLLM API
   呼び出し異常増加に対する安全マージンとして3倍を乗じた「約52,000円/月」を暫定の予算上限
   として設定する(10業者×約1,732.5円×3≒約52,000円)。これは「正常運用時の最大想定原価の
   さらに3倍」という水準であり、正常な契約業者数の増加に伴う原価増と、バグによる異常な
   コスト急増を区別できる閾値として設計した。
2. 50%・90%・100%到達時にオーナー宛メール通知を送るCloud Billing Budgets & alertsを、GCP
   プロジェクト作成・Blazeプランへのアップグレード直後に請求先アカウント単位で作成する。
3. line-reservation-aiのbilling-budget-cap-safeguard-design.mdと同様に、Google Cloud公式の
   サンプルパターン(予算アラートをPub/SubトピックへルーティングしCloud Functionで受信、
   閾値到達時に請求先アカウントをプロジェクトから自動的にデタッチ=課金を強制停止する構成)
   を参考に、`budget-cap-auto-disable`用のCloud Functionをdeployment-runbook.mdのデプロイ
   手順に追加候補として記録する。自動停止は請求先アカウントのデタッチであり、Firestoreデータ
   自体の削除は伴わない(Blaze→Spark相当への縮退に近い)ため、復旧時はオーナー確認の上で
   請求先アカウントを再アタッチするだけで済む。
4. 契約業者数が想定(当面10業者)を超えて増えた場合は、正常なコスト増であるにもかかわらず
   固定閾値のままでは誤って自動停止が作動しうるため、契約業者数が8業者(想定上限の8割)に
   達した時点で予算額の見直しをオーナーに提案するプロセスを、次回以降のlaunch-readiness-
   checklist.mdの運用手順候補として残す(本フェーズでは設計のみで、checklistへの反映自体は
   次回候補とする)。

## 承認依頼への反映方針
本ドキュメントは設計のみであり、実行(GCPプロジェクト作成・課金設定・Budget作成)は依然
オーナー承認が必要なアクションのため一切行わない。pending-approval.md既存エントリ
(2026-09-27 09:00 UTC・2026-09-27 10:00 UTC記載)自体の文面は履行記録としてそのまま保持し、
新規の承認依頼エントリも追加しない(承認を求めるアクションの実体は変わらないため)。ただし、
次回承認依頼の検討・提示時には、本ドキュメントが示す「想定契約業者数に応じた約52,000円上限の
Billing Budget+自動停止」を添えて提示することで、オーナーが判断しやすい形にすることを次回
候補とする。
