# LINEテキストメッセージ文字数上限超過時のフォールバック設計(フェーズ102)

first-generation-self-check-design.md「LINE Messaging API のメッセージ数・文字数上限確認
(フェーズ101で解消)」に残っていた残課題、「極端に長い入力メモが送られた場合の文字数
上限(5,000文字、UTF-16コード単位)超過時のフォールバック処理は未設計のまま」に対応する。
実装未着手・動作未検証(実LLM・実LINE API接続はオーナー承認待ちのため)。

## 前提の再確認

- LINE Messaging APIのテキストメッセージ1件あたりの文字数上限は5,000文字、
  UTF-16コード単位でのカウント(フェーズ101、first-generation-self-check-design.md参照)。
- 本ventureの出力のうち`completion_report.body`(作業完了報告)・`care_guide.body`
  (お手入れ案内)は、業者がそのままコピー&ペーストで依頼者(エンドカスタマー)へ転送する
  運用が正規ルート(フェーズ100)。この2つは「依頼者への誤送信事故」に直結する本venture
  固有のリスクがあるため、上限超過時の扱いは特に慎重に設計する必要がある。

## 想定される超過の原因

- 入力メモ自体が極端に長い(コピー&ペースト時の誤操作、無関係な文章の混入等)。
- LLMが指示から逸脱し、通常想定(数百文字程度、mvp-flow-draft.md参照)を大きく超える
  長文を生成してしまうケース(プロンプト崩れ・幻覚的な冗長生成)。
- いずれの原因であっても、送信直前の機械チェックでは原因を区別せず一律に「上限超過」として
  扱う(原因の切り分けはログに残し事後改善の材料とするが、フォールバック処理の分岐条件には
  しない)。

## 設計方針: 切り詰めは行わない

候補として「上限に収まるよう末尾を切り詰めて送信する」案も検討したが、採用しない。

- `completion_report.body`・`care_guide.body`は依頼者へ直接転送される文面であり、
  末尾を機械的に切り詰めると文が不完全な状態(「本日は熱交換器の洗浄まで実施し、防カビ
  コートは」のような尻切れ)のまま依頼者に送られてしまう危険がある。これは
  first-generation-self-check-design.mdで整理した「本venture固有の誤送信事故リスク」を
  悪化させる方向の対応であり、既存の設計思想(厳守事項1「実際の安全確認・専門的判断への
  不介入」、確定的な内容は業者本人の確認に委ねる)とも相容れない。
- よって、上限超過は「切り詰めて送る」のではなく「送らずに生成失敗として扱う」方針とする
  (json-output-retry-fallback.md(line-reservation-ai)の「フォーマット崩れ時は楽観的に
  処理を進めず安全側に倒す」という既存の設計思想を踏襲)。

## 検知・フォールバックのフロー

1. LLM生成後、LINE APIへの送信メッセージ組み立て前に、`completion_report.body`・
   `care_guide.body`それぞれについて文字数チェックを行う(post_generation_checks.pyに
   新規関数`check_message_length_within_line_limit()`として追加する想定)。
2. いずれか一方でも5,000文字(UTF-16コード単位)を超えていた場合、他の項目のチェック結果に
   関わらず「送信失敗」として扱い、通常の`completion_report_message`・`care_guide_message`
   は一切組み立てない(依頼者へ転送されうる文面は、たとえ一部でも生成しない・送信しない)。
3. 代わりに、業者(LINE公式アカウントの発話者本人)向けにのみ、定型のフォールバック通知
   メッセージを1件返す。例:
   「生成結果が長くなりすぎたため、報告文を作成できませんでした。恐れ入りますが、入力
   メモを少し短くして再度お送りください。」
   このメッセージ自体は固定文言(LLM生成物ではない)とし、依頼者へ転送されることを想定しない
   業者向けの操作案内という位置づけを明確にする。
4. 「簡易な作業履歴記録」(history_row相当)については、依頼者へ転送される文面ではなく
   内部記録であるため、上限超過時も切り詰めて保存すること自体は誤送信事故には直結しない。
   ただし一貫性のため、本設計では history_row も含め3つの生成物のいずれかが上限超過した
   時点で今回の生成全体を「失敗」として扱い、部分的な記録の保存(history_rowのみ保存し
   報告文は送らない、等の中途半端な状態)は行わない方針とする。

## UTF-16コード単位カウントの実装上の注意

Python の `len(str)` はUnicodeコードポイント数を返すため、そのままではUTF-16コード単位数と
一致しない場合がある。具体的には、基本多言語面(BMP)外の文字(補助文字面、U+10000以降。
一部の異体字・稀な漢字や絵文字等)はUTF-16では2コード単位(サロゲートペア)としてカウント
されるが、Pythonの`len()`では1文字として数えられる。本ventureの生成文は厳守事項8により
絵文字を使用しない方針だが、稀な人名・地名漢字等が補助文字面に該当する可能性はゼロでは
ないため、正確を期すなら`len(text.encode('utf-16-le')) // 2`でUTF-16コード単位数を算出する
実装とする(単純な`len(text)`での代用は誤って上限判定を見逃す方向のズレのみ生じるため
致命的ではないが、正確なチェックのため上記方式を採用する)。

## 残課題

- フォールバック通知文言の最終確定(トーン&マナーガイドラインとの整合確認)は、
  tone-and-manner-guideline.md相当のドキュメントが本ventureにまだ無いため、
  他venture(line-reservation-ai)のtone-and-manner-guideline.mdを参考にしつつ
  別途整理する。
- 5,000文字という値自体はLINE APIのハード上限であり、実運用上はその手前(例:1,000文字
  程度)で「通常想定を超える長さ」として業者へ注意喚起する、といったソフトな閾値を
  別途設けるかどうかは、実LLM接続後の生成品質検証(llm-quality-verification-plan.md)の
  中で実測データを見ながら検討する。
- `check_message_length_within_line_limit()`のprototype/post_generation_checks.pyへの
  実装・テスト追加、およびcloud_function_webhook.py側でのフォールバック分岐の実配線は、
  実LLM・実LINE API接続自体がオーナー承認待ちのため未着手のまま残す。
