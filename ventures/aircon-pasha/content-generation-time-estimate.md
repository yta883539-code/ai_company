# 「浮いた作業時間の目安」試算(1回あたりの手動作成時間の仮置き)

作成日: 2026-09-05(フェーズ192)

## 背景

trial-end-notification-design.md 3節は「course-set-pashaの『浮いた作業時間の目安』相当の
一文は、本venture向けのcontent-generation-time-estimate.md相当の試算ドキュメントが未作成の
ため今回は含めない(4節の『今後の課題』に切り出す)。生成実績(回数)のみを事実として提示する
にとどめる」としたまま、同ドキュメントの作成自体がフェーズ131以降ずっと未着手のまま
残っていた(README.mdフェーズ190・191の棚卸しでは発見されていなかった、本フェーズ〈192〉で
新たに発見した積み残し)。course-set-pashaのcontent-generation-time-estimate.md(フェーズ109)
と同じ役割を、本venture固有の出力構造に合わせて果たすドキュメントを新設する。

## 前提: 1回の生成で作成される3点セット

schema/output.schema.jsonの通り、1回の生成でAIが作成するのは以下3点セットである。手動作成の
場合、オーナー(エアコンクリーニング業者)自身がこの3点を個別に作成する必要があるという前提で
試算する。

1. 作業完了報告メッセージ下書き(`completion_report.body`) — 分解洗浄の範囲・使用洗浄剤/
   追加施工の有無・前後の状態変化を記述する1本の文章。
2. お手入れ案内下書き(`care_guide.body`) — フィルター自己清掃目安・次回推奨時期・自己分解
   洗浄リスクの注意喚起を記述する1本の文章。
3. 簡易な作業履歴記録(`history_rows`) — 施工日・機種系統/号数・汚れ状況・追加施工の有無・
   次回推奨時期の定型項目を、分解洗浄した台数分(1台=1行)記録する。

course-set-pashaの3点セット(SNS投稿文・LINE/Web告知文・課題入れ替え履歴記録)と異なり、
本ventureの(1)(2)は「エリアごとに区切って列挙する」構成ではなく、同一訪問先で分解洗浄した
台数分をまとめて1本の文章にする構成(mvp-flow-draft.md・market-research.mdが指摘する
「同一訪問先で2台以上を同時に分解洗浄するケースが業界で一般的」を踏まえた仕様)。このため、
台数が増えても(1)(2)は「1台目を書く」ときに支配的な作業(トーン設定・書き出し・全体の
構成検討)を1回で済ませられるが、(3)は台数分の行を書く必要があるため台数に比例して増える。
この非線形/線形の構造はcourse-set-pashaの「エリア」を「台数」に置き換えたものと同じである。

## 試算(仮置き)

market-research.mdが指摘する通り、作業完了報告・お手入れ案内の作成は「作業内容を分かりやすく
言語化する」というライティングスキルを要する作業であり、単純なタイピング速度だけでなく、
言い回しを考える時間・専門用語を避けた表現を選ぶ時間が支配的になると仮定する。

| 作業項目 | 仮置き所要時間(1台のみの場合) | 前提 |
|---|---|---|
| (1) 作業完了報告メッセージ | 5〜7分 | 分解洗浄の範囲・使用洗浄剤・前後の状態変化を、専門用語を避けつつ分かりやすく言語化する時間が中心。 |
| (2) お手入れ案内 | 4〜6分 | フィルター自己清掃目安・次回推奨時期・リスク注意喚起という定型的な内容だが、自己分解洗浄のリスクを煽り過ぎない言い回しの調整が必要。 |
| (3) 作業履歴記録(1台分) | 1〜2分 | 定型項目(施工日・機種系統/号数・汚れ状況・追加施工有無・次回推奨時期)の記録のみでライティング要素が薄いため短時間。 |
| 合計(1台のみ) | 10〜15分(中間値13分) | 各項目の中間値の合計(6+5+1.5≒12.5分)にほぼ一致するため、幅の中央値13分を採用。 |

AIによる生成自体は数秒〜数十秒で完了し、利用者側の作業は生成結果の確認・微修正(1〜2分程度と
仮定、course-set-pashaの試算と同じく削減効果の対象時間からは除外)にとどまるため、削減効果は
上記合計時間にほぼ等しいとみなす。

## 複数台同時分解洗浄時の按分式

上記「前提」節の通り、(1)(2)は台数に対して非線形(1台目が支配的、追加台は差分のみ)、
(3)は台数に対して線形(history_rowsが台数分の行になるため)という性質の違いがある。

### (1)(2): 台数に対して非線形

2台以上の場合も、完成する文章は「(機種名)は(汚れ状況・分解洗浄範囲)」という句をエリアごと
ならぬ台ごとに列挙する形になるが、文章全体のトーン設定・書き出し・締めの言い回しといった
「1台目を書く」ときに支配的な作業(元試算の(1)5〜7分+(2)4〜6分=中間値11分)は1回で済む。
2台目以降は「機種名+汚れ状況」という短い句を追加するだけであり、1台目より短い追加コストと
仮定する。仮置きで追加1台あたり3分(元の(1)(2)中間値11分のおおよそ3分の1、course-set-pasha
の按分〈5分の1〉より台あたりの記述量が多いと見て比率をやや高めに設定)とする。

### (3): 台数に線形

出力3(履歴記録)はhistory_rowsの要素数=分解洗浄台数nに一致する行数が必要なため、元試算の
(3)1〜2分(中間値1.5分)をそのままn倍する。

### 統合式

1回の生成イベント(分解洗浄台数n、n≧1)あたりの「浮いた作業時間」を、

```
minutes(n) = 11(1台目の(1)+(2)) + 3×(n-1)(2台目以降の(1)+(2)追加分) + 1.5×n((3)のn行分)
           = 8 + 4.5n
```

とする。ただし4.5分/台という半端な値は文言・実装上扱いにくいため、`prototype/
trial_end_scheduler.py`の実装では少数第一位を丸めて`minutes(n) = 8 + 5n`(1台あたり5分)を
採用する(n=1のとき13分となり、上記「試算(仮置き)」節の中間値13分と一致する。n=2で18分、
n=3で23分)。

トライアル期間全体では、生成回数g回・分解洗浄台数総数(全生成のhistory_rows要素数の合計)を
Aとすると、合計の浮いた作業時間は`8×g + 5×A`分となる。

## 採用値・実装への反映

- `prototype/trial_end_scheduler.py`に`BASE_MINUTES_PER_GENERATION = 8`・
  `ADDITIONAL_MINUTES_PER_UNIT = 5`・`estimate_trial_minutes_saved(generation_count,
  unit_count)`(=`8×generation_count + 5×unit_count`)・`format_minutes_saved_line()`を
  実装した(フェーズ192)。
- `user_id_linking.UserProfile`に`trial_unit_count`(トライアル期間中の分解洗浄台数累計、
  `trial_generation_count`と対になるフィールド)を追加し、`increment_trial_unit_count()`/
  `get_trial_unit_count()`を`UserProfileStoreProtocol`・`InMemoryUserProfileStore`に実装した。
  `cloud_function_webhook.process_memo_event()`が生成成功のたびに
  `len(instance["history_rows"])`分を加算する。
- 条件A(`cloud_function_webhook.format_trial_end_condition_a_notice()`)・条件B
  (`trial_end_scheduler.build_trial_end_notification_flex_message()`)の両方が
  `format_minutes_saved_line()`を共通で呼ぶことで、trial-end-notification-design.md 3節の
  既存方針(「回数到達だから」「期間到達だから」で文言を分けない)を維持したまま、通知文言に
  「浮いた作業時間の目安: 約○分(1台の分解洗浄につき平均13分、複数台同時分解洗浄時は1台
  追加ごとにさらに約5分と仮定)」の1行を追加した。

## 残課題

- 上記の値はすべて仮置きであり、実ヒアリングによる検証は未実施。customer-interview-design.md
  「A. 現状把握」質問3「報告書・お手入れ案内の作成に、1件あたりどのくらいの時間をかけて
  いますか?繁忙期はその時間をどう捻出していますか?」が本試算の検証観点を既にカバーしている
  ため、質問の新設は不要と判断した。残るのは一次情報(実際のエアコンクリーニング業者への
  実ヒアリング)による検証そのもので、実施可能になった段階(オーナー承認後)で回答を用いて
  検証・再試算する。
- 4.5分/台を5分/台に丸めた点(統合式節)は、course-set-pashaの按分式が整数のみで構成されて
  いたのに対し本venture固有の事情(1台あたり平均所要時間の目安が半端な値になった)による
  ものであり、丸めによる誤差(0.5分/台)は仮置き値の精度を踏まえれば無視して差し支えないと
  判断した。
- landing-page-copy-draft.mdの「時給換算」訴求(course-set-pashaのcontent-generation-
  time-estimate.mdが行ったような、月額料金に対する時給換算表現への展開)は、本venture側では
  未検討のまま残る。本ドキュメントの13分/回(1台あたり)という値を使った試算・訴求コピーへの
  反映は次回以降の課題とする。
- 複数台同時分解洗浄時の按分係数(追加1台あたり3分、course-set-pashaの追加1エリアあたり
  2.5分より高め)も机上の仮定であり、実測データによる検証は上記と同様に未実施。
