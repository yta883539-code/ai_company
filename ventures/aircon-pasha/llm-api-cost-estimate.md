# LLM API利用コスト試算(生成1回あたりの原価 vs 従量単価・基本料実質単価)

作成日: 2026-08-17

## 背景

subscription-billing-cost-estimate.mdでは決済手数料・Firestore読み書き課金を試算したが、
本ventureの原価構造でもう一つ大きい可能性がある要素、LLM API呼び出し自体のコスト
(Claude API利用料)がこれまで試算されていなかった。course-set-pasha・line-reservation-ai
でも同様の試算は行われておらず、本venture固有の課題ではないが、pricing-plan.mdの従量単価
(40〜60円/回)がLLM原価に対して十分な粗利を確保できているかを確認する。

claude-apiスキル記載の公開料金表(2026年8月時点)を使用した机上試算であり、実LLM API呼び出し
自体は行わない(オーナー承認待ちの範囲)。

## 前提(入出力トークン数の概算)

mvp-flow-draft.md・llm-system-prompt-draft.mdの設計に基づく1回の生成あたりの入出力を、
2つのシナリオで概算する。

- **入力(1)システムプロンプト+構造化出力スキーマ**: llm-system-prompt-draft.md(13,481文字)・
  schema/output.schema.json(6,870文字)の現行ドラフト合計約20,350文字。実際にAPIへ送信する
  システムプロンプトは、設計根拠の説明等のメタ的な記述を除いた凝縮版になる見込みが高いため、
  以下2シナリオで幅を持たせる。
  - シナリオA(圧縮後の想定・保守的な小規模プロンプト): 1,750トークン
  - シナリオB(現行ドラフトの文字数からの概算・上限側): 日本語・英語混在のMarkdownを
    1トークン≒2文字と仮定し、約10,000トークン
- **入力(2)業者からのメモ**: 「作業後の簡単なメモ」200〜400文字。日本語1文字≒1トークンと
  概算し、150〜400トークン(シナリオAは300トークン、シナリオBは400トークンを採用)
- **出力(3件の下書き)**: 作業完了報告・お手入れ案内・簡易履歴記録の3出力を構造化出力(JSON)で
  生成、600〜1,000トークン(中間値800トークン/上限1,000トークンをシナリオA/Bでそれぞれ採用)

正確なトークン数は、実LLM接続後に`count_tokens`(無料・課金なしの計測専用エンドポイント)で
確認する必要がある(接続自体はオーナー承認待ちのため未実施)。本試算は上記の概算値に基づく
机上の上限見積もりである。

## プロンプトキャッシュ適用時の試算(シナリオB、Sonnet 5)

システムプロンプト+スキーマ部分(約10,000トークン)は業者ごと・生成ごとに変化しない固定部分の
ため、プロンプトキャッシュ(cache_control)の対象にできる。2回目以降の生成でキャッシュ読み取り
(通常の約0.1倍単価)が効く前提で試算すると:

- システムプロンプト部分: 10,000トークン × $3/100万 × 0.1 × 150円 ≒ 0.45円
- メモ入力部分(キャッシュ対象外): 400トークン × $3/100万 × 150円 ≒ 0.18円
- 出力: 1,000トークン × $15/100万 × 150円 ≒ 2.25円
- 合計: 約2.88円(キャッシュなしの約6.93円から約58%削減)

キャッシュの初回書き込みは約1.25倍の割増料金がかかるが、1業者が月40〜150回(pricing-plan.md)
生成する運用では2回目以降で十分に元が取れる(shared/prompt-caching.mdの損益分岐点の考え方に
準拠)。デフォルトのキャッシュ有効期限(5分)では生成の間隔が空くと再度キャッシュ書き込みが
発生するため、実際の利用間隔次第では1時間TTLの検討も有効(いずれも実LLM接続後の実装課題)。

### 1時間TTLの一次情報確認(2026-08-24追記・フェーズ121)

フェーズ120の申し送りを踏まえ、1時間キャッシュTTLの料金条件をWebSearchで確認した
(Claude Platform Docs「Prompt caching」を含む複数の一次情報系ソースが一致)。

- デフォルトのキャッシュ有効期限は5分で、書き込み単価は通常入力単価の約1.25倍
  (本ファイル既存の前提と一致)。
- `cache_control`に`"ttl": "1h"`(または`{"type": "ephemeral", "ttl": 3600}`)を明示指定すると
  1時間TTLが使え、この場合の書き込み単価は通常入力単価の約2倍(5分TTLの1.25倍よりさらに
  割増)になる。読み取り単価(通常の約0.1倍)はTTLの長さによらず共通。
- 1時間TTLは「呼び出し間隔が10分を超えて空くことが分かっている場合に限り使う」のが目安とされ、
  概ね3回目以降の生成でキャッシュ書き込みコストの増分を回収できる計算になる(1.25倍→2倍への
  差分0.75倍分は、以降の読み取り時0.1倍単価との差額で数回分の利用で相殺される)。
- 本ventureは1業者あたり月40〜150回の生成(pricing-plan.md)だが、1回あたりの生成間隔は
  業者の作業件数次第でばらつくため、営業時間中に立て続けに数件処理するケース(間隔10分未満、
  5分TTLで十分)と、1日1〜2件程度に留まるケース(間隔数時間、1時間TTLが有効)の両方が
  想定される。実LLM接続後、実際の利用間隔の分布を実測してから5分TTL固定・1時間TTL固定・
  間隔に応じた動的切替のいずれを採用するか判断するのが妥当と結論する(机上では優劣を
  確定できない)。

## pricing-plan.mdの従量単価・基本料実質単価との比較

| 比較対象 | 金額(1回あたり) | Sonnet 5・シナリオB・キャッシュ利用時との比率 |
|---|---|---|
| 繁忙期対応プラン従量単価(最安) | 40円 | 約7.2% |
| スタンダードプラン従量単価 | 50円 | 約5.8% |
| スモールプラン従量単価 | 60円 | 約4.8% |
| 繁忙期対応プラン基本料実質単価(8,980円÷150回) | 約59.9円 | 約4.8% |
| スタンダードプラン基本料実質単価(5,980円÷90回) | 約66.4円 | 約4.3% |
| スモールプラン基本料実質単価(2,980円÷40回) | 約74.5円 | 約3.9% |

最も保守的な組み合わせ(Opus 5・シナリオB・キャッシュなし、約11.55円)で比較しても、
最安の従量単価(40円)に対して約29%にとどまり、十分な粗利が残る計算になる。
Sonnet 5・キャッシュ利用時であれば約4〜7%程度とさらに小さく、subscription-billing-
cost-estimate.mdが結論づけた「決済手数料が粗利率を左右する優先コスト項目」という結論を
補強する形で、LLM API原価も同様に事業性を圧迫する主要因にはならないと見込まれる。

## 結論・次のステップ候補

- 本venture(3種類の短い日本語下書きを生成する単方向バッチ処理)の用途であれば、
  Claude Sonnet 5で十分な品質が見込め、Opus 5ほどの高価格帯モデルは必須ではない可能性が
  高い。実LLM接続後、course-set-pasha・line-reservation-aiのllm-system-prompt-draft.mdの
  厳守事項達成度を踏まえたモデル選定の比較検証が必要(output-samples-validation.mdの
  検証観点と合わせて実施)。
- 正確なトークン数は`count_tokens`エンドポイント(無料)で実測できるため、実LLM接続の
  承認が得られた際は、まずcount_tokensのみで正確な入出力トークン数を確認し、本試算の
  シナリオA/Bのどちらに近いかを特定してから実際の生成呼び出しに進む順序が望ましい。
- プロンプトキャッシュの導入(システムプロンプト+スキーマ部分への`cache_control`付与)は、
  コスト削減効果が大きいため実装時の優先事項とする。5分TTLと1時間TTLのどちらを使うかは
  実LLM接続後の利用間隔の実測データを見て判断する(上記「1時間TTLの一次情報確認」参照)。
- 実際のLLM API呼び出し・APIキー取得はオーナー承認が必要なアクションであり、本ドキュメント
  はあくまで契約前の判断材料整理にとどまる(pending-approval.md記載の既存の承認待ち事項の
  範囲内)。
