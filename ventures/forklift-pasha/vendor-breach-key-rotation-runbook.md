# 外部ベンダー侵害発覚時の自社キー緊急ローテーション手順(設計)

## 1. 背景

ノーコードWeb制作サービス「Studio」(Studio株式会社)は2026年10月16日、クラウド環境内の
脆弱性を悪用した第三者による不正アクセスを公表した(不正アクセス確認期間は2026年9月30日
〜10月1日)。対象は全登録顧客のアカウント情報・フォーム送信内容に加え、**外部サービス
連携用のAPIキー**にまで及んだ。これを受け、kura-pasha(フェーズ262、2026-10-24 10:00 UTC)
が本venture群共通の論点として「外部ベンダーが不正アクセスを受け自社キーが漏えい対象に
含まれた場合の緊急ローテーション手順」を設計し、aircon-pasha(フェーズ340)・
course-set-pasha(フェーズ329)・line-reservation-ai(フェーズ続き341)へ横展開済み。
本ドキュメントはkura-pashaフェーズ262の次回候補(1)に対応し、forklift-pashaへ横展開する。

本venture固有の論点は、tech-stack.mdの暫定決定により**入力チャネルをLINE非依存の汎用
Webフォームとした**ことである(倉庫業・運送業・建設業の現場ではLINE公式アカウントの
業務利用率が他venture〈美容室・ジム等の対個人向けサービス業〉と異なり低いと判断したため)。
したがって、他venture(aircon-pasha・course-set-pasha・kura-pasha・line-reservation-ai)が
保有するLINE Messaging APIのチャネルアクセストークン・チャネルシークレットという依存が
本ventureには存在しない点が、横展開にあたって明記すべき差分である。

本ドキュメントは、forklift-pasha自体がこの種の被害を受けた場合に備え、本venture固有の
依存先キー群を洗い出し、緊急ローテーションの手順を設計のみ先行して整理するもの。実際の
不正アクセス発生・キー漏えいは本ventureには生じていない。

## 2. forklift-pashaが保有する外部連携キー・シークレットの一覧

tech-stack.mdの構成(入力チャネル=汎用Webフォーム〈LINE非依存〉・GCP Cloud Functions
2nd gen・Firestore・LLM API・Stripe)を前提に、本venture固有の依存先を整理する。

| 依存先 | 保有するシークレット | 用途 |
| --- | --- | --- |
| Stripe | シークレットキー(`sk_live_...`)・Webhook署名シークレット(`whsec_...`) | Checkout Session発行・サブスクリプションWebhook受信(stripe-checkout-plan-id-design.md・stripe-webhook-entry-point-design.md) |
| LLM APIプロバイダ | APIキー | 点検記録簿整形・リマインド通知文の生成(llm-system-prompt-draft.md) |
| GCP(Cloud Functions 2nd gen・Firestore) | サービスアカウント鍵・Secret Managerアクセス権 | Webhook実行環境・課金・契約単位データストア接続 |
| Webフォームホスティング先 | APIキー・管理用トークン(ホスティング先未確定) | 点検担当者からの入力受付 |

LINE Messaging APIへの依存は無い(本venture固有の差分、1節参照)。いずれも実アカウント
開設自体がオーナー承認待ち(pending-approval.md参照)のため、現時点では上記は「開設後に
保有することになる」想定の一覧である。Webフォームホスティング先は未確定(tech-stack.md
次回候補)のため、確定後に本表を更新する必要がある。

## 3. 緊急ローテーション手順(ドラフト)

1. **検知**: 上記いずれかのベンダー(またはそのベンダーがさらに利用する委託先)が
   不正アクセス・情報漏えいを公表し、自社が保有するAPIキー・シークレットが対象に
   含まれる可能性があるとの連絡・報道を確認した時点を起点とする。
2. **一次切断**: 対象ベンダーの管理画面から影響範囲が確定する前に、該当するキー・
   シークレットを予防的に失効させ、新しいキーを再発行する(「疑わしきは即時失効」を
   原則とし、公式な影響範囲の確定を待たない)。
3. **再配線**: 新しいキーをCloud Functionsの環境変数・Secret Managerへ反映し、旧キーでの
   呼び出しが拒否されることを確認する(例: Stripe Webhook署名検証で旧`whsec_...`が
   失敗することを確認)。
4. **不正利用の痕跡確認**: 各ベンダーの管理画面・Cloud Loggingで、キー失効までの間に
   想定外の呼び出し(決済・点検記録生成等)が発生していないかを確認する。
5. **個人情報保護法上の対応との併走**: キー漏えい自体とは別に、当該ベンダーが保持して
   いた顧客データ(本venture経由の個人情報)が対象に含まれる場合は、既存の漏えい対応系
   「パシャっと」群と同じ一次整理(報告・本人通知の要否判定)を並行して行う。
