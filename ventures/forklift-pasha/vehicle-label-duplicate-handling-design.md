# vehicle_idの発行・重複チェック設計(フェーズ114)

firestore-data-model.md「未確定・残課題」に「実装時の課題として残す」のまま残っていた
「`vehicle_id`の発行・重複チェック(同一事業者内で車両番号表記が重複した場合の扱い)」に
着手する。

## 1. 問題設定

点検メモ(自由記述)に含まれる車両番号表記(`vehicleLabel`)は、mvp-flow-draft.mdの方針
(「点検結果の良否判断・修理要否の判断はしない」=「入力をそのまま扱う」)により表記ゆらぎの
解決自体は範囲外だが、`vehicle`コレクションへの書き込み時に何の基準もなく毎回新規ドキュメントを
作成すると、同一車両が別表記(例: 「2号機」と「２号機」「no.2」)で送られた場合に限らず、
同一表記を単に複数回送っただけでも重複ドキュメントが量産されてしまう。`vehicle`コレクションの
ドキュメント数は`fleet_operator.vehicleCount`(pricing-plan.mdの台数上限プラン判定に使う
フィールド、tech-stack.md「コンポーネント4」)の根拠になり得るため、重複がそのまま保有台数の
過大カウント・不要なプラン超過判定につながるリスクがある。

## 2. vehicle_idの発行方式

access-token-reissue-design.md(フェーズ96)で`fleet_operator`のドキュメントID
(`internal_id`)をFirestore自動生成IDに統一した前例を踏襲し、`vehicle_id`も**Firestore
自動生成ID**とする(ユーザーに配布・表示する識別子ではなく内部参照専用のため、
`fleet_operator`のような「アクセストークンとの分離」は不要で、自動生成IDそのものをそのまま
使ってよい)。

## 3. 重複判定の方針: 完全一致のみ(表記ゆらぎの吸収はしない)

- 判定キー: `(operatorInternalId, vehicleLabel)`の組。
- 正規化は**前後の空白のトリムのみ**を行う。全角/半角統一、かな/カナ正規化、類似表記の
  クラスタリング等は一切行わない。
  - 理由: mvp-flow-draft.mdが明示する「入力をそのまま扱う」方針(点検記録整形自体も人手の
    自由記述を転記するのみで、表記の正誤判断はしない)と一致させる。表記ゆらぎの吸収を
    実装すると「どの表記が正規形か」という本質的に点検者側の運用に属する判断にサービス側が
    踏み込むことになり、範囲外の方針と矛盾する。
  - 結果として、「2号機」と「２号機」は意図的に**別の車両として扱われる**(過大カウントの
    リスクを許容する代わりに、誤った同一視によって異なる車両の点検記録が同じ車両の記録として
    混在するリスクを避ける)。どちらのリスクを取るかの判断は、4節の「超過時に生成を止めない」
    方針と対にして、「過大カウント側に倒れても記録作成自体は止めない」という一貫した安全側
    設計とする。
- 事業者側が表記を統一したい場合の支援(エイリアス登録等のUI)は本フェーズの範囲外とし、
  次回候補に残す。

## 4. 新規メモ受信時のフロー

1. 入力メモから`operatorInternalId`(アクセストークン経由で特定済み)と`vehicleLabel`
   (トリム済み)を得る。
2. `vehicle`コレクションに対し`operatorInternalId == X AND vehicleLabel == Y`で
   クエリする(複合インデックスが必要。firestore-composite-index-plan相当の文書は未作成
   のため次回候補に残す)。
3. **既存ドキュメントが見つかった場合**: 何もしない(再利用。新規作成しない)。
4. **見つからなかった場合**: 新規`vehicle`ドキュメントを作成する。このとき
   `fleet_operator.vehicleCount`を1増やす(後述5節)。
5. いずれの場合も、点検記録の整形自体(`status=generated`の出力)は本判定の結果に関わらず
   常に実行する。**台数超過が判明しても記録生成を止めない**(pricing-plan.md「月間生成回数の
   上限超過時の挙動」が採用した「利用制限ではなく従量課金」という、法令順守上の記録作成自体を
   止めないという既存方針と同じ考え方を台数超過にも適用する)。

## 5. `vehicleCount`フィールドの性質の明確化: 自己申告ではなく実績カウンタ

tech-stack.md「コンポーネント4」の初回設計メモは`vehicleCount`を単に「保有台数(プラン上限
チェック用)」とのみ記載しており、契約時の自己申告値か、実際に送られてきたメモから判明した
distinct車両数かが未確定だった。本フェーズで**実績カウンタ方式**に確定する。

- 契約開始時点では`vehicleCount: 0`で初期化する(自己申告欄は設けない)。
- 以降は4節のフローで新規`vehicle`ドキュメントが作成されるたびに`+1`する(`vehicle`
  コレクションのdistinctドキュメント数と常に一致させる。将来的な車両廃車・統合機能は範囲外
  のため減算は設計しない)。
- 理由: 契約時の自己申告は「実際に何台分の点検メモを送ってくるか」と一致しない可能性が高く
  (当初1台と申告したが後から増車した等)、自己申告をプラン上限判定の根拠にすると実態との
  ズレが生じる。実績ベースにすることで、実際に処理した車両数という事実に基づく判定になり、
  他venture群で繰り返し採用されている「安全側・実態に即したフォールバック」の考え方と一致する。
- `vehicleCount`がプラン上限(ライト1台・スタンダード3台・複数台10台)を超えた状態は
  「プラン超過」を意味するが、4節の通り生成自体は止めない。超過時のアップセル通知
  (他venture群のlimit-approaching-notification-design.md相当)の具体的な設計(通知
  タイミング・文面・通知手段)は、pricing-plan.md「月間生成回数の上限超過時の挙動」が
  既に「通知: 実装時の課題として残す」としている論点と合わせて次回候補とする。
