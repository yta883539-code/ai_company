# 月間生成回数上限接近通知・保有台数プラン超過時アップセル通知 設計(フェーズ115)

firestore-data-model.md(フェーズ114)の`fleet_operator.vehicleCount`フィールド説明に
残っていた「実際のアップセル導線設計は次回候補」、およびpricing-plan.md「月間生成回数の
上限超過時の挙動(仮決め)」の「通知: 上限到達が近づいた時点での事前通知の設計(通知
タイミング・文面・通知手段)は実装時の課題として残す」という2つの未設計課題に、フェーズ114
最終更新時点の次回候補(2)が明示するとおり「生成回数超過通知と合わせた一体設計が望ましい」
という方針で一体着手する。

## 1. 既存シリーズ(kura-pasha等)の設計をそのまま流用できない理由

kura-pasha/limit-approaching-notification-design.mdは「残り1回」(月3〜20回という低頻度利用
を前提)、aircon-pashaは「残り5回」(月60〜100回)、course-set-pashaは「残り2回」(月8〜30回)
という固定回数閾値を採用していたが、いずれも各venture内の3プランの生成回数が同じ桁数に
収まっている前提に立っている。

本ventureのプラン別月間生成回数上限(pricing-plan.md)はライト25回/スタンダード70回/複数台
220回と、最小プランと最大プランの差が約9倍に達する(台数が増えるほど生成回数が線形に増える
構造、pricing-plan.md「前提」)。この差が大きいプラン構成に既存シリーズと同じ「固定回数」の
閾値をそのまま適用すると、以下の不整合が生じる。

- 「残り5回」をそのまま適用した場合、ライトプラン(25回)では利用率80%時点(20回目)で通知
  されるのに対し、複数台プラン(220回)では利用率97.7%時点(215回目)まで通知が届かない。
  プラン間で「どれだけ使い切った頃に知らせるか」の体感が大きくばらつく。
- 「残り1回」(kura-pasha方式)をそのまま適用すると、複数台プラン(220回)では219回目まで
  通知が届かず、超過(従量課金発生)が翌日以降の生成で確定的に起きてしまう現場(daily区分は
  稼働日ごとに発生、mvp-flow-draft.md)では事前の心構えをする余地がほぼ無くなる。

よって本ventureは固定回数ではなく、プラン間で比例する「月間生成回数上限に対する利用率
(パーセンテージ)」を閾値とする方式を独自に採用する。

## 2. 月間生成回数の上限接近通知(利用率方式)

- **閾値: 3プラン共通で「月間生成回数上限の90%に達した生成完了時点」で1回のみ通知する。**
  `count_after_increment >= ceil(monthly_limit * 0.9)`を満たした最初の生成完了時点。
  - ライトプラン(25回): 23回目(90%=22.5→ceil 23)で通知、残り2回。
  - スタンダードプラン(70回): 63回目(90%=63)で通知、残り7回。
  - 複数台プラン(220回): 198回目(90%=198)で通知、残り22回。
- 90%とした理由: 本venture固有の特性(daily区分が稼働日ごとに自動的に生成され、月次・年次
  区分のような「利用者が生成タイミングを選べる」余地が小さい、mvp-flow-draft.md)を踏まえ、
  通知後も数回〜数十回分の猶予(残り2〜22回、プラン規模に比例)を残すことで、daily運用が
  月の後半に差し掛かった時点で急に従量課金に切り替わる驚きを避ける。90%という比率は机上の
  仮説であり、他venture同様に実運用データでの再検証が必要な値として残す(6節)。
- 通知は1回のみ(既存シリーズと同じ理由。daily区分は毎日生成が発生するため、都度通知すると
  通常の返却テキスト〈点検記録簿整形・リマインド下書き〉の可読性を損なう)。実際に上限を
  超えた回(従量課金発生)は、その回の返却テキスト自体に別途1文を追記する(3節)。

## 3. 保有台数プラン超過時のアップセル通知

firestore-data-model.md(フェーズ114)で確定した`vehicleCount`の実績カウンタ方式(`vehicle`
ドキュメント作成時に加算)を前提に、台数超過の検知・通知を設計する。

- **トリガー: `vehicle`ドキュメント作成(新規車両登録)の直後、加算後の`vehicleCount`が
  現在の`planId`の対象台数上限(pricing-plan.md: ライト1台/スタンダード3台/複数台10台)を
  超えた時点。** vehicle-label-duplicate-handling-design.md(フェーズ114)の重複判定を経て
  新規作成と判定された場合のみ加算されるため、同一車両の再登録(重複)では誤って再発火しない。
- **文面(仮)**: 当該車両登録リクエストに対する通常の返却テキスト(整形済み点検記録簿)の
  末尾に、以下いずれかを1文追記する(mvp-flow-draft.mdの既存方針「記録作成自体は止めない」
  を維持し、台数超過を理由に整形結果の返却自体を拒否することはしない)。
  - ライト→スタンダード、スタンダード→複数台への案内が可能な場合(現プランが最上位
    〈複数台〉でない場合):「※保有台数が現在のプラン(ライト/スタンダード)の対象台数
    [1台/3台]を超えました。[スタンダードプラン(2,480円・3台まで)/複数台プラン
    (4,980円・10台まで)]へのプラン変更をご検討ください」
  - 既に複数台プラン(10台まで)でも超過した場合: pricing-plan.md「10台超は『投資・大規模
    につき要相談』領域の個別対応とし、本プランの機械的な上限緩和では対応しない」という
    既存方針を踏まえ、プラン変更の案内ではなく「※保有台数が10台を超えました。10台を超える
    規模のご利用については個別にご相談ください」という個別相談案内に文面を分岐させる
    (機械的な上限緩和を行わないという既存方針を通知文言にも反映)。
- **通知は台数超過が新たに発生した登録1回のみ**とする(例: 1台目→2台目で超過が発生した
  登録時に1回。その後3台目・4台目…と増えても、既に超過状態である限り再通知しない)。
  判定式: `vehicleCount_before <= planLimit[planId] < vehicleCount_after`の場合のみ発火
  (既に超過済みの状態からさらに台数が増えるケースでの重複通知を避ける)。

## 4. 2節・3節の通知が同一リクエストで重複した場合の扱い

2節(生成回数90%接近)と3節(台数超過)は判定条件・トリガーが独立しており(2節は
`usage_counter`の加算後カウント、3節は`vehicle`ドキュメント作成に伴う`vehicleCount`の
加算後カウント)、新規車両登録のリクエストが偶然その月の90%目の生成でもあった場合など、
稀に両方が真になり得る。kura-pasha(フェーズ75「重複を避ける特別な排他処理は設けない」)と
同じ考え方を踏襲し、本ventureも両方の通知文を独立した1文としてそれぞれ返却テキスト末尾に
追記する(排他処理は設けない)。表示順は3節(台数超過、構造的な変更を促す案内)を先、2節
(生成回数接近、当月限りの注意喚起)を後とする(恒久的な対応を要する案内を先に見せる方が
利用者にとって優先順位が分かりやすいと判断した、机上の仮説)。

## 5. 実装方針(次回候補)

- `prototype/`配下は現時点でinspection_record整形・schema検証のテストのみ(README参照)で、
  usage_counter・vehicleドキュメントの読み書きを模した純粋関数はまだ実装されていない
  (他venture〈kura-pasha等〉の`usage_counter_workshop.py`・`cloud_function_webhook.py`
  相当のコードは本ventureには未着手)。したがって本フェーズは設計文書の作成のみに留め、
  `format_usage_limit_notice(count_after_increment, monthly_limit) -> Optional[str]`・
  `format_fleet_overage_notice(vehicle_count_before, vehicle_count_after, plan_id) ->
  Optional[str]`相当の純粋関数としての実装化は次回候補とする。
  **(フェーズ116で`prototype/overage_notifications.py`として実装済み。2節の「1回のみ通知」の
  制御は本関数の責務外とし、呼び出し側がusage_counterの前回値と比較して行う設計のまま。
  実際のFirestore読み書き自体は引き続き未着手。)**
- 実際のGCP/Firestore接続・Stripeプラン変更導線の実装はアカウント作成・外部サービス接続を
  伴うため、着手時にオーナー承認が必要(pending-approval.md参照)。本ファイルは机上の設計
  整理のみ。

  可能、要否は次回検討)を見直す。
