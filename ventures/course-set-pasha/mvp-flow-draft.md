# MVP入出力フォーマット草案

market-research.mdの整理を踏まえ、最小構成(MVP)の入出力フォーマットを草案する。
line-reservation-aiと異なり、双方向の会話(予約フロー)は不要で、
「入力メモ→3種類の下書き生成」という単方向のバッチ処理で成立する点がシステム構成上のシンプルさ。

## 入力フォーマット(オーナー・セッターがLINE/フォームで送る内容)

箇条書きの自由記述を想定。必須項目は無いが、以下の項目があると出力の精度が上がる。

- エリア名/セクション名(例: 「エリアA」「窓側壁」)
- テープ色・グレード帯(例: 「黄色テープ、3級〜1級相当」)
- 本数(例: 「8本新規」)
- ムーブ・特徴のキーワード(例: 「カチ持ち中心」「ダイナミックなランジあり」「初心者向けスラブ多め」)
- 改訂日
- (任意)課題エリアの写真1〜数枚
- 変更のないエリアがあれば「エリアBは変更なし」等の一言(投稿文で誤って触れないようにするため)

## 出力1: SNS投稿文下書き(Instagram/X想定)

- 冒頭でエリア・改訂日を明示し、見どころ(難易度傾向・ムーブの特徴)を1〜2文で紹介。
- 初級者向け/中〜上級者向けなど、対象層が分かる一言を含める。
- 末尾に来店を促す一文+関連ハッシュタグ候補(例: #ボルダリング #クライミングジム #新課題)を添える。
- 写真が送られていれば「写真の課題」に言及する形で文面を組み立て、送られていなければ
  文面のみで完結する(写真が無い旨をAIが指摘することはしない)。

## 出力2: 公式LINE/Web告知文下書き

- SNSより端的に、エリア・本数・改訂日を箇条書きで整理した通知文。
- 「詳しくはSNSをご覧ください」等でSNS投稿と回遊させる一文を含める(SNS投稿文と役割を分ける)。

## 出力3: 課題入れ替え履歴の簡易記録

- 表形式(改訂日/エリア/テープ色・グレード帯/本数/特徴キーワード)で1行追記する形。
- line-reservation-aiのMVPと同様、当面はスプレッドシート等への手動転記を前提とし、
  専用データベースは持たない。

## 会話フロー・技術構成に関する方針(現時点の仮説)

- 予約枠管理・二重予約防止のような状態管理が不要なため、line-reservation-aiのような
  会話状態マシン(ConversationFlowStateMachine)は不要。1メッセージ受信→LLM呼び出し→
  3種類のテキスト生成→返信、という単純な処理で足りる見込み。
- ホスティング基盤はline-reservation-aiで選定済みのGCP Cloud Functions (Python)の知見を
  流用できる可能性が高いが、状態を持たないためFirestore等の永続ストアは不要か、
  履歴記録(出力3)のみ軽量な保存先(スプレッドシート連携等)で足りる可能性がある。
  技術構成の具体化は次回以降の課題とする。
- 実LLM呼び出し・LINE公式アカウントとの接続は、line-reservation-aiと同様に
  APIキー取得・アカウント作成が必要でありオーナー承認待ちの範囲。今回は下書き作成支援の
  設計・フォーマット整理のみに留める。
