# 「新規課題ゼロ・撤去/休止のみ」入力メモのエッジケース机上検証(2026-11-07 16:00 UTC)

## 発見の経緯

mvp-flow-draft.md・llm-system-prompt-draft.mdの入力フォーマット・厳守事項4は、いずれも
「入れ替え」=「新しい課題が追加される」ことを暗黙の前提として設計されている
(出力1の仕様が「見どころ(難易度傾向・ムーブの特徴)を1〜2文で紹介」「来店を促す一文」を
常に要求しており、新規課題が存在しない前提には触れていない)。

一方、market-research.mdの背景整理(課題は定期的に入れ替えられる)・sns-post-example-observation.md
の実例観察はいずれも「新規課題を追加した」投稿のみを対象としており、ボルダリングジムの
運用実態として「改修・ホールドクリーニング・壁面の張り替え等のため一時的に課題を撤去し、
当面新規セットの予定がない」という告知が発生しうるかどうかはWebSearchでも直接の実例を
確認できなかった(関連する実在ジムの投稿例・文例は見つからず)。しかし、header-summary-
edge-case-review.md・multi-area-mixed-case-review.mdが検証してきた「情報が部分的に
欠けるケース」と同様に、本venture固有の前提(改訂があるたびに必ず新規課題が伴う)が
常に成り立つとは限らない、現行設計の未検証の仮定として扱い、机上検証する。

## 現行設計での挙動(問題点)

入力メモが「Aエリアの課題をすべて撤去しました。壁面の張り替え工事のため、次回更新は
未定です。」のような、新規課題の情報(テープ色・グレード帯・特徴キーワード)を一切含まない
撤去・休止のみの内容だった場合、現行の厳守事項・schemaでは以下のいずれかに該当してしまう。

- 厳守事項8(入力不足時の再送依頼)に該当すると解釈すると、`insufficient_input`として
  「エリア名・本数等が不足しています」という再送依頼を返すことになるが、このメモは
  実際には「エリア名(Aエリア)」「理由(壁面の張り替え工事)」「見通し(次回未定)」が
  具体的に書かれており、情報不足ではない。入力メモとして完結しているにもかかわらず
  再送を促す誤った応答になってしまう。
- 無理に`generated`として扱うと、厳守事項4が要求する「見どころ(難易度傾向・ムーブの
  特徴)を1〜2文で紹介」「色・グレード帯の範囲と合計本数の冒頭要約」を生成できる材料が
  入力に無いため、AIが存在しない新規課題の特徴を推測で捏造するか、意味の通らない
  テンプレート崩れの出力になるリスクがある(厳守事項1・8が禁じる「推測で補う」ことに
  抵触しうる)。
- history_rows(出力3)も、tape_color_or_grade_band(必須文字列)・count(本数)に
  該当する新規情報が無いため、無理に「撤去」を色・グレード帯欄に書く、countをnullに
  する等、現行のフィールド説明(『入れ替え』=追加前提)と整合しない記入になる。

## 対応方針

このケースは「変更なし」(厳守事項2・unchanged_areas、エリアに触れる情報自体が無い)とも、
「入力不足」(厳守事項8、本来書かれるべき情報が欠けている)とも異なる第三の類型であり、
「新規追加は無いが、エリアの状態変化(撤去・休止)自体が会員に伝えるべき情報である」
ケースとして扱う必要がある。line-reservation-aiやaircon-pashaのような新規status値
追加(cancellation_intent等)は、このケースが「通常の3出力生成」の対象から外れる
性質のものではなく、むしろ出力1(SNS投稿)・出力2(告知文)・出力3(履歴記録)を
生成すべき対象であるため不要と判断する(subscription_procedure_notice等とは異なり、
会員への告知文自体は従来どおり必要なため)。したがって新しい`status`値やトップレベル
フィールドは追加せず、既存の`generated`の範囲内で以下のとおり厳守事項4・history_rows
関連の文言を具体化する。

1. 入力メモに新規課題の色・グレード帯・特徴キーワードの情報が無く、撤去・休止・
   メンテナンス等の語で「エリアの課題が無くなる/減る」ことのみが書かれている場合、
   厳守事項8の入力不足とは判定せず、`generated`として扱う。
2. この場合の出力1(SNS投稿)は、厳守事項4の冒頭要約(色・グレード帯・本数)および
   「見どころ紹介」を省略し、代わりに(a)どのエリアが対象か、(b)撤去・休止の理由
   (入力に明記されている場合のみ、無理に推測しない)、(c)次回更新の見通し
   (入力に「未定」「◯月予定」等の記載がある場合はそのまま転記、記載が無い場合は
   見通しには触れない)を要約する。「来店を促す一文」は、新規課題が無いため
   「新しい課題が待っています」のような実態に反する表現を避け、「次回更新を
   楽しみにお待ちください」等、撤去後の状態を前提にした表現に置き換える。
   ハッシュタグは(1)一般ハッシュタグのうち「#新課題」等、新規追加を示唆するものは
   使用せず、「#ボルダリング」「#クライミングジム」等、課題内容に依存しないものに
   限定する((2)ジム独自タグ・(3)地域タグは従来どおり)。
3. 出力2(告知文)も同様に、エリア・理由・次回見通しを箇条書きで整理する内容に
   差し替える(本数・グレード帯の箇条書きは対象項目が無いため省略)。
4. 出力3(履歴記録)は、tape_color_or_grade_bandに「(撤去のみ)」等、新規色・グレード帯が
   存在しないことが分かる値を入力メモの文言に基づいて記述し(推測で色名等を捏造しない)、
   countは新規追加本数が0であることを表すため`0`とする(nullは「抽出できなかった」
   場合用であり、今回は「本数が実在しない」ことが明確なため区別してnullではなく0を
   採用する)。feature_keywordsには「撤去」「休止」等、入力メモから読み取れる理由・
   状態を表すキーワードを格納する。これにより、将来「いつ・どのエリアが休止期間だったか」
   を履歴から振り返られる(market-research.mdが課題とした「記録の属人化」防止に資する)。
5. 上記1〜4はいずれも「新規課題の情報が無い」ことが明示的に読み取れる場合に限る。
   単に本数・グレード帯が書かれていないだけで撤去・休止を示す語も無い入力メモは、
   従来どおり厳守事項8(insufficient_input)の対象のままとする(本項のスコープ外)。

## 未検証事項

- 実在ジムでの「撤去のみ告知」の投稿実例はWebSearchで確認できておらず、上記の出力文面
  イメージ(理由・見通しの要約)が実際の告知慣習と合っているかは未検証(将来の顧客
  ヒアリング・実例観察の課題として残す)。
  - 2026-11-08 フェーズ363追記: WebSearchで「ボルダリングジム ホールド撤去 課題
    クリーニング 次回更新 未定」等を再検索したが、「撤去のみ・次回未定」をそのまま
    告知した実例は今回も見つからなかった(未検証のまま)。一方、東京ドームシティ
    「スポドリ!」のホールド替え告知(対象壁・閉鎖期間・利用再開予定日時を明示する形式)
    という部分的に関連する実例を確認でき、本検証が前提とする「対象エリア+期間(または
    見通し)を要約する」という出力方針の骨格(対応方針2・3の(a)(c))自体は、実在ジムの
    告知慣習(対象範囲と日程を示す)と矛盾しないという傍証が得られた。ただし同事例は
    再開日が確定している通常のメンテナンス告知であり、本venture想定の核心である
    「次回更新が未定」という開示パターンそのものの実例ではないため、未検証事項としては
    解消済みとはせず、引き続き残す。
- 本検証はあくまで机上シミュレーション(header-summary-edge-case-review.mdと同じ手法、
  実LLM呼び出しは行わない)であり、実LLMが改訂後の文言通りに「見どころ紹介の省略」
  「代替の来店訴求表現」を安定して生成するかは未確認(オーナー承認後のAPI接続時の
  検証課題として残る)。
- countを0とする設計が、他venture(line-reservation-ai等)のスキーマ設計方針と整合するか
  (null=抽出不可、0=実在する値としてのゼロ、という使い分けの一般化)は本venture内での
  検討に留め、横展開の要否は次回以降の課題とする。
