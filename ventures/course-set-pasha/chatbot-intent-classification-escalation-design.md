# チャットボット一次受付: 意図分類プロンプト・エスカレーション導線 設計

作成日: 2026-09-21(定例更新フェーズ235)

chatbot-first-response-feasibility.md(フェーズ234)「残課題」が次回以降の課題として
残していた2点、(1)意図分類プロンプトの具体的な設計、(2)エスカレーション導線
(FAQ非該当と分類された場合の運営者通知方法)の設計に着手する。実装・実LLM呼び出し・
実LINE接続は行わない、机上の設計のみとする。

## 1. 意図分類カテゴリの定義

chatbot-first-response-feasibility.md 2節で整理した3分類を、そのままLLMへの分類指示の
出力値として採用する。

- `post_generation_request`: 投稿文生成依頼(本サービスの中核機能)。曖昧な場合も含め、
  「メモらしき内容(練習内容・成果の言及等)が含まれる」場合はこちらを優先する
  (下記フェイルセーフ方針を参照)。
- `faq_pricing`: 料金プラン・トライアル条件に関する質問。owner-operation-self-service-
  faq.mdのQ2相当。
- `faq_howto`: 使い方の再質問。同Q1・Q4〜Q6相当。
- `faq_cancel_change`: 解約・プラン変更に関する質問。同Q3相当(既存の
  `cancellation_intent`/`downgrade_intent`会話フローへの誘導文言に帰着させるため、
  他のfaq_*とは別カテゴリとして分離する)。
- `other_needs_human`: 上記いずれにも該当しない、または分類に確信が持てない場合。

`faq_pricing`/`faq_howto`/`faq_cancel_change`の3分類は、owner_faq_router.pyが既に持つ
コード体系(Q1〜Q6)とは独立したカテゴリ体系とする。理由は、意図分類はLLMの自由入力
(表記揺れのある自然文)を受けるのに対し、owner_faq_router.pyのQ1〜Q6は契約者が明示的に
コマンドとして入力する前提の別経路であり、両者を無理に1つのコード体系に統合すると
意図分類側のプロンプトが複雑化するため。実装時は3分類それぞれに対応する
`render_owner_faq_answer_message("Q1")`等、既存の定型回答関数をそのまま呼び出す
マッピング層(`faq_intent_to_code()`のような薄い変換関数)を挟む設計とし、回答文言
自体の二重管理は避ける。

## 2. フェイルセーフ方針: 「迷ったら人的対応(または投稿文生成)に倒す」の具体化

chatbot-first-response-feasibility.md 5節が指摘した最大のリスク(投稿文生成依頼を
FAQ回答と誤判定し中核機能を妨げる)を踏まえ、優先順位を以下のように明文化する。

1. **`post_generation_request`を最優先**: メモらしき内容(種目名・回数・時間・気づき等、
   既存のLLMシステムプロンプトが投稿文生成に使ってきた要素)が少しでも含まれる場合は、
   FAQ的な言い回し(「プランについて」等)が同時に含まれていても`post_generation_request`
   と分類する。理由は、本サービスの主目的を妨げるコストは「多少不要なFAQ相当の言及を
   読み飛ばして投稿文を生成してしまう」コストより明確に大きいため。
2. **FAQ 3分類と`other_needs_human`の判別に迷う場合は`other_needs_human`側へ倒す**:
   料金・使い方・解約のいずれのFAQにも明確に一致しない微妙な言い回し(例: 「なんか
   いつもと違う気がする」等、具体的なFAQトピックを特定できない曖昧な不満・質問)は、
   誤ったFAQ定型文を返すより、エスカレーションして運営者の目に触れる方が顧客体験を
   損なわないと判断し`other_needs_human`とする。
3. 上記1と2が競合する場合(メモらしき内容と曖昧な不満が同時に含まれる場合)は1を優先する。

この優先順位は、LLMへのシステムプロンプト内に「迷った場合の判定順位」として明示的に
記述する想定とし、モデルの暗黙の判断に委ねない(既存のllm-system-prompt-draft.md群が
厳守事項を明文化してきた方針と同じ考え方)。

## 3. エスカレーション導線: `other_needs_human`判定時の運営者通知

payment-suspension-owner-notification-design.mdが確立した「顧客(ボルダリングジム
オーナー)」と「オーナー(course-set-pashaの運営者)」の呼び分け、および
`OWNER_LINE_USER_ID_PLACEHOLDER`による固定送信先の設計をそのまま踏襲する。

- **検知条件**: 意図分類が`other_needs_human`と判定された時点。日次バッチではなく、
  該当メッセージ受信時にリアルタイムで通知する(決済失敗猶予期間のような日数条件が
  存在せず、顧客が今まさに応答を待っている状況のため、即時通知が適切と判断)。
- **冪等性**: 1メッセージにつき1通知。同一顧客からの連続した`other_needs_human`判定は
  それぞれ別メッセージとして都度通知する(payment-suspension-owner-notification-design.md
  の「1回のみ送信」フラグとは異なり、本件は既存の顧客への都度応答〈`_reply_with_retry()`〉
  と同様、メッセージ単位のイベント通知のため、送信済みフラグによる重複排除の仕組みは
  不要と判断する)。
- **通知文言**:

```
[コースセットパシャッと運営] 一次受付チャットボットからのエスカレーション

以下の顧客からのメッセージが、FAQ・投稿文生成のいずれにも自動分類されませんでした。
内容をご確認のうえ、必要に応じて個別にご対応ください。

顧客ID: {user_id}
メッセージ本文: {memo_text}
```

  payment-suspension-owner-notification-design.md 4節の文言パターン(`[サービス名 運営]`
  接頭辞、顧客IDの記載)を踏襲しつつ、本件は状況把握のため顧客のメッセージ本文自体を
  そのまま引用する点が異なる(決済失敗通知は状態〈経過日数〉の通知で足りるが、
  エスカレーションは運営者が「何に困っているか」を読んで判断する必要があるため)。
- **送信経路**: 既存の`_reply_with_retry()`(顧客への返信用)とは別に、
  payment-suspension-owner-notification-design.mdが前提とする固定送信先
  (`OWNER_LINE_USER_ID_PLACEHOLDER`)宛のpush送信ヘルパーを流用する想定とし、
  新規のインフラ・外部サービスアカウントは追加しない。
- **顧客への応答との関係**: `other_needs_human`判定時も、顧客自身には「担当者が
  内容を確認しご連絡します」旨の定型応答を返す(無応答のまま放置しない)。この定型
  応答は`_reply_with_retry()`経由で通常のFAQ・投稿文生成と同じ経路を使う。
