# 月間生成回数の上限接近時通知 設計

pricing-plan.md「月間生成回数の上限超過時の挙動(仮決め)」の「通知」項目に残っていた、
「上限到達が近づいた時点(残り2回等)でLINE等を通じて事前に知らせ、意図しない従量課金発生を
防ぐ通知設計」を検討する。

## 1. 前提の見直し: 月間カウントの保持方法

通知設計に着手する前提として、そもそも「月間生成回数」をどこでカウント・保持するかが
未確定であることに気づいた。tech-stack.md「全体構成イメージ」は

> line-reservation-aiと異なり、予約枠・会話状態を保持する永続データストアは不要。
> 「1メモ受信 → LLM呼び出し → 3種類のテキスト生成 → 返信」の単純なリクエスト/レスポンス型で
> 完結する。

という前提で設計されているが、月をまたいで生成回数を積算する以上、Webhookの1リクエスト内で
完結しない何らかの永続化が必須になる。この前提の一部見直しが必要になったため、まずこの点を
整理する。

### 検討した3案

- **案A: Firestore等の軽量データストアを新規導入**
  line-reservation-aiのFirestore(firestore-data-model.md)と同じ構成に寄せる。ただし
  本ventureはユーザー(オーナー・セッター)ごとに「当月の生成回数」1件を持てば足りるため、
  line-reservation-aiのbooking/conversation-stateのような複雑なドキュメント構造は不要。
- **案B: LINE公式アカウント側の仕組みで代替**
  リッチメニュー・ユーザー属性等、LINE Platform側の機能でカウントを保持できないか検討したが、
  LINE Messaging APIにはBot運営者が任意の数値をユーザーごとに永続保持する機能はなく、
  実現には結局外部データストアが必要になるため案として成立しない。
- **案C: 決済代行サービス側の利用量トラッキングを流用**
  subscription-billing-cost-estimate.mdで検討中の決済代行サービスが利用量ベースの従量課金に
  対応する場合、そのAPI側でカウントを取得できないか検討したが、決済代行サービスの選定自体が
  未着手(pending-approval.md参照、契約行為はオーナー承認が必要)であり、かつ決済代行サービスの
  利用量トラッキングは通常「請求締め時点の集計」であって「送信直前にリアルタイムで残り回数を
  参照する」用途には向かないため見送る。

### 結論: 案Aを採用(tech-stack.mdの前提を部分的に見直す)

月間生成回数カウントは「ユーザー1人=1ドキュメント、フィールドは`month`(例: `2026-08`)と
`count`のみ」という最小構成で足りるため、line-reservation-aiほどの複雑さは持ち込まずに
Firestore(またはCloud Functions運用と親和性の高い同等の軽量KVS)を導入する。
tech-stack.md「全体構成イメージ」の「永続データストアは不要」という記述は、月間カウント管理を
追加する場合に限り例外とする旨を今後tech-stack.md側にも反映する必要がある(本ドキュメントでは
設計のみ行い、tech-stack.md本体の更新は次回以降の課題として残す)。

## 2. カウントの対象・タイミング

- カウント対象は`status == "generated"`の場合のみとする。`out_of_scope`・
  `insufficient_input`・検証失敗フォールバック(webhook-processing-flow-design.md 5節)は
  実質的に「顧客に届く告知文が生成されなかった」ケースであり、ユーザー側の入力ミスや
  スコープ外リクエストで消費を発生させるのは不合理なため対象外とする。
- インクリメントのタイミングは、`process_memo_event()`内で返信本文を組み立てた直後
  (`generated`の分岐が確定した時点)とする。LLM呼び出し前にインクリメントすると、
  検証失敗→フォールバック(non-generated扱い)になった場合に巻き戻しが必要になり実装が
  複雑化するため、確定後の1回インクリメントの方がシンプル。
- 月の区切りはJST基準の暦月(`YYYY-MM`)とする。pricing-plan.mdの料金プランが日本国内の
  個人経営ジムを対象としており、UTC基準よりオーナーの体感に合うため。

## 3. 通知トリガー・閾値

- pricing-plan.md本文の「残り2回等」という仮の表現を踏襲し、**残り2回に達した生成完了時**
  (プラン上限 − 現在count == 2 になった瞬間)に1回だけ通知を送る。
- 「残り1回」「上限到達」の時点でも重ねて通知するかは検討したが、生成のたびに毎回通知が
  挟まると本来の返信(sns_post/line_web_notice/history_rows)の可読性を損なうため、
  **残り2回の1回のみ**とし、実際に上限を超えた場合は超過時点の返信メッセージ自体に
  従量課金が発生する旨を1文添える方式(4節)でカバーする。
- 送信方法は、line-reservation-ai/candidates-expired-notification-design.mdで整理した
  「プッシュメッセージは追加課金・唐突な体験になりやすい」という論点を踏まえ、**新規の
  プッシュメッセージは送らない**。残り2回目の生成完了時の返信メッセージ(通常のreply API
  応答)に追記する形にすることで、追加のAPI呼び出し・課金を発生させずに実現する。

## 4. 通知文言案(仮)

生成完了時の通常の返信メッセージ末尾に、該当条件のときのみ以下を追記する。

- 残り2回に達した時点:
  「※今月の生成回数は残り2回です(上限到達後は1回あたり[単価]円の追加料金がかかります)」
- 上限を超えて従量課金が発生した回(超過1回目以降)の返信メッセージ末尾:
  「※今月の無料生成回数の上限を超えたため、本回は追加料金[単価]円が発生します」

いずれも1文の定型文言とし、post_generation_checks.pyの機械チェック対象(厳守事項の違反検知)
には含めない(課金案内であり、厳守事項が対象とする「告知文の内容そのもの」とは性質が異なる
運用メッセージのため)。

## 5. 実装への影響メモ(設計のみ、実装は次回以降)

- `process_memo_event()`のシグネチャに、月間カウントの読み書きを行うインターフェース
  (line-reservation-aiの`llm_call`・`reply_client`と同様、差し替え可能なProtocol)を
  新規に1つ追加する想定(仮称`usage_counter: UsageCounterProtocol`、
  `get_count(user_id, month) -> int` / `increment(user_id, month) -> int`の2メソッド)。
- テスト(prototype/test_cloud_function_webhook.py)では、line-reservation-aiの
  `InMemoryReplyClient`と同じ発想で`InMemoryUsageCounter`(dictベースのスタブ)を用意し、
  「残り2回到達」「上限超過」の境界値をユニットテストで検証する方針とする。
- 実際のFirestore接続(プロジェクト作成・課金設定)はオーナー承認待ちの範囲であり、
  本フェーズでは設計とスタブ実装の方針整理のみに留める。
