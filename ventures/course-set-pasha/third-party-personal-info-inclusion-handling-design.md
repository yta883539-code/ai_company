# 会員等の第三者個人情報の入力メモ混入対応方針(設計)

kura-pashaがフェーズ181〜184で実装し、aircon-pashaがフェーズ268〜271で横展開した
「依頼者(受け手)以外の第三者の氏名等が、対外的に転送・公開される出力へ誤って
転記されてしまう」という論点を、本venture固有の入出力構造に照らして棚卸しする。
本フェーズは方針の設計のみを行い、llm-system-prompt-draft.md・
schema/output.schema.json・prototype/post_generation_checks.pyへの実際の反映は
次回以降の課題とする。

## 1. 対象範囲の整理・本venture固有の相違点

mvp-flow-draft.mdの定義を前提に、3出力の宛先を改めて整理する。

- **出力1(SNS投稿文下書き)・出力2(公式LINE/Web告知文下書き)**: いずれも
  オーナー・セッターが実際に対外発信することを前提とした文面である
  (README.md「実際の投稿・送信は利用者自身が行う設計」)。ただし、kura-pasha
  (職人→依頼者の一対一の納品案内)・aircon-pasha(施工者→依頼主の一対一の完了報告)と
  異なり、本ventureの出力1・2は**不特定多数(Instagram/X投稿)または会員全体への
  一斉配信(LINE公式アカウントのブロードキャスト・Web告知)**という、対外公開の
  範囲がそもそも広いメディアである点が本venture固有の相違点。したがって、入力メモに
  会員個人や外部関係者を特定できる氏名等が紛れ込み、それがオーナー・セッターに
  よってそのまま出力1・2として発信された場合、他venture以上に広い範囲へ第三者の
  個人情報が開示されてしまうリスクがある。
- **出力3(課題入れ替え履歴の簡易記録)**: mvp-flow-draft.mdの表形式
  (改訂日/エリア/テープ色・グレード帯/本数/特徴キーワード)による、ジム内部の
  運用記録である。line-reservation-aiと同様、当面はスプレッドシート等への手動転記を
  前提とし、外部への転送・公開は想定されていない。したがって、kura-pashaの出力1
  (職人の備忘用メモ、対象外)と同様の位置づけで、本方針の対象外とする。加えて
  schema上もhistory_rowsの各要素は定型フィールド(area・tape_color_or_grade_band等)と
  `feature_keywords`(自由記述ではなく特徴語の配列)のみで、氏名等の自由記述が
  そのまま転記される自由文本文欄を持たない構造上の理由もある。
- legal-notices-draft.md 2.1節は「会員個人を特定する情報は想定しない」設計である旨を
  既に記載しているが、これは入力メモの主目的(課題設定情報)に照らした「想定しない」
  という整理であり、セッターが特徴キーワード等の自由記述箇所に会員や外部関係者
  (大会関係者、常連客等)の氏名に類する記述を書き添えてしまう可能性そのものを
  構造的に排除するものではない。本方針はこの残存リスクへの対応を扱う。

## 2. 自動マスキングは採用しない

kura-pasha・aircon-pashaの既存整理と同じ理由により、氏名・住所等を正規表現等で
機械的に検出・マスキングする方式は本ventureでも採用しない。

- 日本語の人名は表記の多様性(漢字・かな・ローマ字、姓のみ/フルネーム、
  クライミングジムに多いニックネーム表記等)が大きく、網羅的な検出は現実的でない。
- 過検出のリスクが高い。本venture固有の事情として、出力1(SNS投稿文)は
  「エリアA」「窓側壁」等の固有名詞的なエリア名や、ムーブ名・グレード表記
  (「黄色テープ」等)を多用する文面であり、これらを氏名と誤判定して削除すると
  投稿文としての体裁が崩れる。
- ボルダリングジムという業態上、セッターが常連会員の愛称やニックネームを課題の
  背景説明として言及すること自体は自然な発想であり、一律マスキングでは
  投稿文の魅力を損なう可能性がある。

## 3. 採用する方針: プロンプト側での明示的な取り扱い指示(厳守事項10案)

llm-system-prompt-draft.mdの既存厳守事項1〜9に続く新規項目(厳守事項10)として、
以下の趣旨を追加する案を提示する(文面案・実際の反映は次回以降)。

```
10. 入力メモに、会員個人や外部関係者(大会関係者・常連客等)を特定できる氏名や
    ニックネーム等の記述が含まれている場合、出力1(SNS投稿文)・出力2(公式LINE/
    Web告知文)の本文にはその氏名・ニックネーム等をそのまま転記しない。当該記述が
    課題設定の背景として言及する価値がある場合でも、個人を特定しない一般化した
    表現(「常連の会員の方」「大会出場を目指す会員」等)に置き換えて記述する。
    出力3(課題入れ替え履歴の簡易記録)は改訂日・エリア・テープ色/グレード帯・本数・
    特徴キーワードの定型項目のみで自由記述の本文欄を持たないため、本項の対象外と
    する(mvp-flow-draft.md出力3仕様に基づく)。
```

- 既存の厳守事項2(「変更なし」エリアの誤記載防止)と同様、「入力メモの記載を
  もとに文面を組み立てるのが既定」という本venture基本方針に対する明示的な例外
  (出力1・2に限り第三者の氏名・ニックネームを一般化する)として位置づける。
- kura-pashaの厳守事項9・aircon-pashaの厳守事項9と同種の論点だが、本venture固有の
  「出力1・2がいずれも公開・一斉配信メディアである」という前提(1節参照)を明記した
  上で番号を10とした(既存1〜9の延長)。

## 4. 機械チェック(post_generation_checks.py拡張)の考え方

既存のprototype/post_generation_checks.pyは、厳守事項2(`check_unchanged_areas_not_
mentioned_as_new`)・厳守事項7a/7b(`check_subscription_notice_consistency`・
`check_checkout_notice_consistency`)等、いずれも「話題キーワード+判定語の共起」や
構造化フィールド同士の突き合わせによるヒューリスティック方式であり、氏名という
自由文字列そのものを検出する機能は持たない。kura-pasha・aircon-pashaと同じ限定的な
突き合わせ方式を次回実装時の案として提示する。

- schema/output.schema.jsonに、kura-pashaの`third_party_names`・aircon-pashaの
  `completion_report.third_party_names`と同じ位置づけの補助フィールドを追加する案。
  本ventureでは出力1・2の両方が対象のため、`sns_post.third_party_names`・
  `line_web_notice.third_party_names`のように各出力オブジェクト配下に持たせる形が
  自然(kura-pasha・aircon-pashaは対象出力が1つだったため`completion_report`直下に
  持たせていたが、本ventureは2出力とも対象である点が異なる)。
- 入力メモの自由記述箇所(特徴キーワード等)から抽出された人名・ニックネームらしき
  文字列が上記フィールドに含まれる場合にのみ、`sns_post.body`・
  `line_web_notice.body`の本文にその文字列がそのまま出現していないかを確認する
  `check_no_third_party_name_leak_in_public_posts()`(仮称)を新設する案。
- 「人名・ニックネームらしき文字列の抽出」自体が信頼できる技術ではない点は
  kura-pasha・aircon-pashaと同様であり、このチェックはあくまで「明らかな見落としを
  拾う補助的な網」の位置づけとし、厳守事項10の実効性の主体はプロンプト側の指示に
  置く。
- 上記は設計方針の提示のみであり、実際のフィールド追加・チェック関数追加・
  テストケース追加は次回以降の実装フェーズで行う。
