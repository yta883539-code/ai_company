# LINE友だち追加時のuser_id事前紐付け設計(連携コード方式)

作成日: 2026-08-20(フェーズ77)

application-form-submission-flow-design.md 残課題「LINE友だち追加時のuser_id事前紐付け経路が
本venture未設計のため、フォーム側でのuser_id手入力運用の是非(誤入力リスク)は別途検討が必要」に
対応する。

## 1. 問題の再整理

フェーズ76時点の設計は「申込フォームにLINE user_idを本人が手入力する」という暫定運用だった。
検討の結果、これは単なる「誤入力リスク」の問題ではなく、**そもそも一般のLINEユーザーは自分の
user_id(`U`で始まる文字列)をLINEアプリのUI上から確認する手段を持たない**ため、運用として
成立しない設計であることが判明した(トーク画面・プロフィール画面のいずれにもuser_idの表示箇所は
無く、開発者向けのLINE Developersコンソールを経由しないと取得できない)。したがって手入力前提の
設計は根本的に見直す必要がある。

## 2. 設計方針: 連携コード方式

- LINE公式アカウントを友だち追加した時点(`follow`イベント)で、Cloud Function側が
  ランダムな短い**連携コード**(6文字、英数字)を発行し、`pending_links/{code}`ドキュメントに
  `{user_id, issued_at}`を保存したうえで、ウェルカムメッセージの返信本文にそのコードを埋め込んで
  本人へ送る。
- 申込フォームの入力項目を「user_id」から「連携コード」に変更する(onboarding-settings-and-
  self-check-design.md・application-form-submission-flow-design.md 2節のフォーム項目定義を
  併せて更新する必要がある。フォーム自体の実設定はオーナー承認待ちのため、項目名の変更方針のみ
  ここで確定する)。
- GAS Webhookのペイロードは`user_id`ではなく`linking_code`を送るよう変更する:

  ```json
  {
    "linking_code": "7K9XPQ",
    "gym_area_pairs_raw": "クライミングジムA/○○区, ボルダリングジムB/△△市"
  }
  ```

- Cloud Function側で`linking_code`を`user_id`へ解決してから、フェーズ76で実装済みの
  `handle_form_submission()`(user_id版)へ委譲する。既存の正規化・上書きロジックは変更しない。

## 3. コード仕様

- 文字種: 英大文字26種+数字10種から、視認性の低い文字(`0`/`O`、`1`/`I`/`L`)を除いた
  31種のアルファベットを使用する(スマートフォンでの手入力ミスを減らすため)。
- 長さ: 6文字(31^6 ≈ 8.9億通り。同時に有効なコード数はfollow直後のごく短期間に限られるため
  衝突確率は無視できる水準。念のため発行時に既存コードとの重複チェックを行い、衝突時は
  最大5回まで再生成する)。
- 有効期限: 発行から24時間。フォーム提出時にこれを超えていれば無効として扱う。
  **フェーズ389追記(linking-code-reissue-command-design.md 4節で配線完了)**: 期限切れ・
  使用済みの場合は、`message`イベントで「コード再発行」と送信するだけで(`follow`イベントの
  再発火=ブロック→再追加は不要)新しいコードが発行される。旧稿で想定していた「一度このアカウントを
  ブロックのうえ再度『友だち追加』していただく」という案内は、配線完了により不要になった
  ため削除した。
  **フェーズ390訂正**: フェーズ389では「フォーム側のエラーメッセージに『コード再発行』案内を
  表示する想定」としていたが、これはapplication-form-submission-http-entry-point-design.md
  3節の既存設計(フェーズ295)と矛盾する事実誤認だった。同節は「GAS側は本レスポンスのHTTP
  ステータスをログに残すのみで、フォーム回答者への追加のエラー表示は行わない(Googleフォーム
  自体の標準完了画面を変更しない、MVPの割り切り)」と明記しており、期限切れ・使用済みコードで
  400が返っても回答者には標準の完了画面がそのまま表示され、再試行が必要なことはオーナーが
  GAS実行ログを手動確認するまで誰にも見えない。したがって「フォーム側のエラーメッセージ文言」
  自体がMVP設計上存在せず、そこに案内を追記するという次回候補は前提が誤っていたため撤回する。
  これにより、期限切れ・使用済みコードでフォームを提出した利用者は、見た目上は提出が成功した
  かのような完了画面を見るだけで、LINEトーク画面に戻って「コード再発行」を送るべきこと自体に
  気づく手段を持たない、という新たなUXギャップが残る(本稿末尾「残課題」に追記)。
- 使い切り(one-time use): フォーム提出で解決に成功したコードはその場で`pending_links`から
  削除する。同じコードを2回目に使おうとした場合は「見つからない」扱いとなり、再提出には
  新しいコードの再取得(上記の「コード再発行」コマンド)が必要になる。これはline-reservation-ai
  の`booking-slot-manager-design.md`が採用した「使用済み・期限切れの区別をユーザーには
  意識させず、単に無効として扱う」方針を踏襲したもの。

## 4. 未フォロー・再フォロー時の扱い

- ブロック後の再フォロー(`follow`イベントの再発火)では、その都度新しいコードを発行する。
  ブロック前に発行済みで未使用のまま残っていたコードは明示的には削除しない(MVPでは
  `pending_links`のガベージコレクションの仕組みを持たないため)。有効期限(24時間)が
  自然な失効境界として機能するため、実害(古いコードが後から別人に渡ることによる誤紐付け)は
  実質的に発生しない設計とした。

## 5. プロトタイプ実装方針

- `prototype/user_id_linking.py`に、`LinkingCodeStoreProtocol`(`save`/`get`/`delete`)と
  実Firestore接続前の検証用`InMemoryLinkingCodeStore`を新設した
  (application_form_submission_flow.pyの`UserProfileStoreProtocol`と同じ責務分離パターン)。
- `issue_linking_code_on_follow(user_id, store, now, rng)`: コード生成・重複チェック・保存までを
  行い、発行したコード文字列を返す(呼び出し側がこれをウェルカムメッセージに埋め込む)。
- `resolve_linking_code(code, store, now)`: 存在確認・期限切れ判定・使い切り(削除)までを行い、
  `LinkingResolution(ok, user_id, error)`を返す。
- `handle_form_submission_with_linking_code(payload, profile_store, linking_store, now)`:
  上記の解決を行ったうえで、既存の`handle_form_submission()`(application_form_submission_flow.py)
  へ委譲する薄いオーケストレーター。既存モジュールへの変更は行わず、依存を追加するだけとした。

## 6. 全角入力への対応(フェーズ223)

`resolve_linking_code()`は当初、3節で意図した「スマートフォンでの手入力ミスを減らす」ための
アルファベット制限(視認性の低い文字を除いた31種)は反映していたものの、実際の照合は
`code.strip().upper()`のみで、全角入力そのものは想定していなかった。owner-faq-routing-
design.md 6節(フェーズ221)がオーナー向けFAQコマンド(`prototype/owner_faq_router.py`)で
発見したのと同じ問題で、日本語入力の携帯端末はIME既定が全角モードであることが多く、
Googleフォームに連携コードを手入力する際も契約者が「７Ｋ９ＸＰＱ」のように全角で入力する
可能性がある。3節が明示的に「スマートフォンでの手入力ミスを減らすため」とアルファベットを
制限した設計意図に照らすと、全角入力への非対応はこの意図を部分的に損なう未対応論点だった。

対応として、フェーズ221と同じ`unicodedata.normalize("NFKC", code)`による正規化を
`strip().upper()`の前段に追加した(コードのアルファベットが英数字のみのため、NFKC正規化で
仮名文字の濁点結合等が問題になることもない)。owner_faq_router.pyのような専用の
`_normalize_command_text()`ヘルパーへの切り出しは行わず、`resolve_linking_code()`内に
インラインで適用した(本モジュールには正規化を要する入力箇所がこの1箇所のみのため)。

## 残課題

- Googleフォームの項目名変更(「LINE user_id」→「連携コード」)自体はフォーム未作成のため
  今回は反映できず、実設定時(オーナー承認待ち、pending-approval.md参照)に合わせて行う。
- **フェーズ390追記・フェーズ391で(a)案を両メッセージに反映し解消**: 期限切れ・使用済み
  コードでフォームが提出された場合、MVP設計上(application-form-submission-http-entry-point-
  design.md 3節)フォーム回答者には標準の完了画面がそのまま表示され、「コード再発行」が
  必要なことに気づく手段が無いというUXギャップが残っていた。対応候補のうち(a)
  (ウェルカムメッセージ・コード再発行メッセージ自体に「このコードが使えなかった場合は
  このトークで『コード再発行』と送ってください」という事前案内を含める、フォーム側の変更は
  不要)を採用した。ウェルカムメッセージ(`format_welcome_message()`)側は既に反映済みだったが、
  再発行コマンドへの返信文(`render_linking_code_reissue_message()`)側には同種の事前案内が
  未反映のまま残っていたため、フェーズ391でこれを追加し両メッセージの事前案内を揃えた
  (詳細はlinking-code-reissue-command-design.md 残課題参照)。(b)案(GAS側Webhookレスポンスの
  フォーム完了画面への反映)はMVPの割り切りを超える工数のため採用しない。
- `follow`イベント受信時にウェルカムメッセージへコードを埋め込んで実際に返信する処理は、
  実LINE Messaging API接続自体がオーナー承認待ちのため未着手(コード発行ロジック自体は
  実接続なしで検証済み)。
- `pending_links`の期限切れドキュメントのパージについて、掃除ロジック自体は
  `purge_expired_links(store, now)`として実装・検証済み(有効期限24時間超のエントリを削除し
  削除件数を返す。`resolve_linking_code()`側の遅延削除と冪等に共存する)。本番では Firestore
  ネイティブ TTL ポリシーでの自動削除を第一候補とするが、TTL の削除は最大24〜72時間遅延しうる
  ため、スケジューラ発火型の Cloud Function や follow イベント便乗でこの関数を明示的に呼ぶ経路も
  併せて持てる設計とした(line-reservation-ai の `release_idle_conversations()` と同じ、
  「実スケジューラ確定前に掃除ロジックだけ実接続なしで検証しておく」位置づけ)。実 Firestore
  接続・TTL ポリシー設定自体はオーナー承認待ち。
