# 上限接近通知の閾値「残り2回」はプラン間で固定でよいか(検証)

limit-approaching-notification-design.md「6. 今後の課題」に残っていた、「『残り2回』という
閾値がプラン(ライト/スタンダード/セッター複数)によらず固定でよいか」を、実測データを
待たずに机上で検討できる範囲で試算・検討する。

## 1. 前提: 各プランの想定生成間隔

pricing-plan.mdの想定利用頻度と月間上限から、1回あたりの平均生成間隔(暦月30日換算)を
逆算する。

| プラン | 月間上限 | 想定頻度(pricing-plan.md記載) | 平均生成間隔(30日÷上限) | 「残り2回」到達〜上限到達までの目安期間 |
|---|---|---|---|---|
| ライト | 8回 | 週2回相当 | 約3.75日に1回 | 約7.5日 |
| スタンダード | 15回 | 週3〜4回相当 | 約2.0日に1回 | 約4.0日 |
| セッター複数 | 30回 | 複数セッターでの共同利用(頻度の明記なし) | 約1.0日に1回 | 約2.0日 |

ライト・スタンダードは、想定利用頻度がおおむね一定のペースで発生する前提であれば、
「残り2回」時点で4〜7.5日程度の猶予があり、意図しない従量課金を避けるための事前検知
という通知の目的(pricing-plan.md「通知」項目)を妥当に果たせる。

## 2. セッター複数プランで生じる懸念

セッター複数プランは「複数セッターでの共同利用」という設計(pricing-plan.md)のため、
上表の「約1.0日に1回」という平均値は複数人の生成が均等に分散された場合の目安に過ぎない。
実際には以下のような偏りが起こりうる。

- 大型大会前・新規オープン時など、pricing-plan.mdの「月間生成回数の上限超過時の挙動」節が
  従量課金方式を採用する理由として挙げた「月内の生成回数が想定を上回る場面」そのものが、
  このプランでこそ最も起こりやすい(複数セッターが同時期に課題を一斉更新するケース)。
- 複数セッターが同じ日にまとめて生成した場合、「残り2回」から上限到達までが数時間〜1日
  程度に圧縮される可能性があり、通知を見た時点で既に上限到達寸前、というケースが他の2
  プランより起こりやすい。

## 3. 検討した対応案

- **案A: セッター複数プランのみ閾値を「残り3回」に引き上げる**
  上限が30回と大きいため、「残り3回」でも他プランとの相対的な猶予(上限に対する比率)は
  ライト(残り2/8=25%)に対してセッター複数は残り3/30=10%相当に留まり、絶対的な猶予
  日数を厚めに確保しても極端な誘導にはならない。
- **案B: 全プラン一律「残り2回」を維持する**
  実装のシンプルさ(process_memo_event()の閾値判定ロジックを1つの定数で済ませられる)を
  優先し、プランごとの分岐を持ち込まない。
- **案C: 閾値を「回数」ではなく「残り日数換算」に変更する**
  より精緻だが、月初からの経過日数と現在countから「このペースなら残り何日で上限到達か」を
  都度計算する必要があり、4節で採用済みの「返信メッセージへの追記のみ・新規API呼び出し
  なし」というシンプルな実装方針(limit-approaching-notification-design.md 3節)と相性が
  悪く、実装コストに見合わない。

## 4. 結論(暫定)

- 案Cは実装コストが見合わないため見送る。
- 案Aと案Bのどちらを採るかは、セッター複数プランの実際の利用パターン(複数セッターの
  生成タイミングが分散するか、一斉更新が常態化するか)という実測データに依存するため、
  机上検討のみでは確定できない。ただし、2節で整理したとおりセッター複数プランは他の2
  プランよりも「猶予期間が実質的に短くなるリスク」が構造的に高いため、実LLM接続・実運用
  開始後に真っ先に検証すべき対象として優先順位付けする。
- 暫定の実装方針としては、limit-approaching-notification-design.md 5節で設計済みの
  `usage_counter`インターフェースに閾値判定ロジックを外だしする際、定数1つではなく
  「プラン→閾値」のマッピング(初期値は全プラン「残り2回」、Bを暫定採用)として実装して
  おく。これにより、実運用データが取れてセッター複数プランのみ引き上げが必要と判明した
  場合も、コード変更ではなく設定値変更のみで対応できる(案A・案Bのどちらに転んでも
  作り直しにならない設計)。
