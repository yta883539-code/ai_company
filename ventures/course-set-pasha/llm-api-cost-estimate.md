# LLM API利用コスト試算(生成1回あたりの原価 vs 従量単価・基本料実質単価)

作成日: 2026-08-17

## 背景

pricing-plan.mdで料金プラン(月額+従量課金)を仮決めし、subscription-billing-cost-estimate.mdで
決済手数料・Firestore原価を試算したが、原価構造のもう一つの主要素であるLLM API呼び出し自体の
コスト(Claude API利用料)は本ventureでは未試算だった。aircon-pashaが2026-08-17 09:00 UTC付けで
同種の試算(llm-api-cost-estimate.md)を行っており、本フェーズはその構成・前提を踏襲しつつ
本venture固有の入出力規模(llm-system-prompt-draft.md・schema/output.schema.json)に置き換えて
試算する。claude-apiスキル記載の公開料金表(2026年8月時点)を使用した机上試算であり、実LLM API
呼び出し自体は行わない(オーナー承認待ちの範囲)。

## 前提(入出力トークン数の概算)

- **入力(1)システムプロンプト+構造化出力スキーマ**: llm-system-prompt-draft.md(18,036文字)・
  schema/output.schema.json(9,854文字)の現行ドラフト合計約27,890文字。aircon-pashaの試算と同様、
  実際にAPIへ送信するシステムプロンプトは設計根拠の説明等のメタ記述を除いた凝縮版になる見込みが
  高いため、以下2シナリオで幅を持たせる。
  - シナリオA(圧縮後の想定・保守的な小規模プロンプト): 2,300トークン
  - シナリオB(現行ドラフトの文字数からの概算・上限側): 日本語・英語混在のMarkdownを
    1トークン≒2文字と仮定し、約13,950トークン
- **入力(2)課題入れ替え後のメモ**: mvp-flow-draft.mdが想定する「エリア・テープ色・難易度帯・
  本数・ムーブの特徴・改訂日」を含む短いメモで、aircon-pashaの業者メモ(200〜400文字)と近い
  規模と見積もり、日本語1文字≒1トークンで150〜350トークン(シナリオAは250トークン、シナリオBは
  350トークンを採用)。写真添付時は画像有無フラグのみを判定材料とし画像自体をLLMに送らない設計
  (tech-stack.md)のため、画像トークンは試算に含めない。
- **出力(3件の下書き)**: SNS投稿文・LINE/Web告知文・課題入れ替え履歴記録(history_rows配列)の
  3出力を構造化出力(JSON)で生成。aircon-pashaの出力(納品案内・お手入れ案内・制作履歴記録)と
  性質が近く、複数エリア同時更新時はhistory_rowsが複数行になる分だけ増える見込みのため、
  600〜1,100トークン(中間値800トークン/上限1,100トークンをシナリオA/Bでそれぞれ採用)。

正確なトークン数は、実LLM接続後に`count_tokens`(無料・課金なしの計測専用エンドポイント)で
確認する必要がある(接続自体はオーナー承認待ちのため未実施)。本試算は上記の概算値に基づく
机上の上限見積もりである。

## プロンプトキャッシュ適用時の試算(シナリオB、Sonnet 5)

システムプロンプト+スキーマ部分(約13,950トークン)は課題入れ替えの都度変化しない固定部分のため、
プロンプトキャッシュ(cache_control)の対象にできる。2回目以降の生成でキャッシュ読み取り
(通常の約0.1倍単価)が効く前提で試算すると:

- システムプロンプト部分: 13,950トークン × $3/100万 × 0.1 × 150円 ≒ 0.63円
- メモ入力部分(キャッシュ対象外): 350トークン × $3/100万 × 150円 ≒ 0.16円
- 出力: 1,100トークン × $15/100万 × 150円 ≒ 2.48円
- 合計: 約3.26円(キャッシュなしの約8.91円から約63%削減)

キャッシュの初回書き込みは約1.25倍の割増料金がかかるが、1ジム・セッターが月8〜30回
(pricing-plan.md)生成する運用では2回目以降で十分に元が取れる(shared/prompt-caching.mdの
損益分岐点の考え方に準拠)。デフォルトのキャッシュ有効期限(5分)では週2〜3回程度(sns-tone-
research.md)という利用間隔だと生成のたびにキャッシュ書き込みが再発生する見込みが高く、
aircon-pasha・course-set-pashaいずれも1時間TTLの検討が有効(いずれも実LLM接続後の実装課題)。

## pricing-plan.mdの従量単価・基本料実質単価との比較

| 比較対象 | 金額(1回あたり) | Sonnet 5・シナリオB・キャッシュ利用時との比率 |
|---|---|---|
| ライトプラン従量単価(最安) | 150円 | 約2.2% |
| スタンダードプラン従量単価 | 120円 | 約2.7% |
| セッター複数プラン従量単価 | 100円 | 約3.3% |
| ライトプラン基本料実質単価(1,980円÷8回) | 約247.5円 | 約1.3% |
| スタンダードプラン基本料実質単価(3,480円÷15回) | 約232.0円 | 約1.4% |
| セッター複数プラン基本料実質単価(5,980円÷30回) | 約199.3円 | 約1.6% |

最も保守的な組み合わせ(Opus 5・シナリオB・キャッシュなし、約14.85円)で比較しても、
最安の従量単価(100円)に対して約14.9%にとどまり、十分な粗利が残る計算になる。
Sonnet 5・キャッシュ利用時であれば約1〜3%程度とさらに小さい。course-set-pashaは
line-reservation-aiのようなLINE通数消費・aircon-pashaのような繁忙期変動が無い分、基本料
実質単価がaircon-pashaより高め(1回あたり約200〜250円)に設計されており、LLM API原価が
事業性を圧迫する主要因にはならないという結論はaircon-pashaと同様に成り立つ。

## 結論・次のステップ候補

- 本venture(3種類の短い日本語下書きを生成する単方向バッチ処理)の用途であれば、
  aircon-pashaの結論と同様にClaude Sonnet 5で十分な品質が見込め、Opus 5ほどの高価格帯
  モデルは必須ではない可能性が高い。実LLM接続後、post_generation_checks.pyの各種厳守事項
  チェック(厳守事項2・3・4・5・7・9)の通過率を踏まえたモデル選定の比較検証が必要。
- 正確なトークン数は`count_tokens`エンドポイント(無料)で実測できるため、実LLM接続の
  承認が得られた際は、まずcount_tokensのみで正確な入出力トークン数を確認し、本試算の
  シナリオA/Bのどちらに近いかを特定してから実際の生成呼び出しに進む順序が望ましい。
- プロンプトキャッシュの導入(システムプロンプト+スキーマ部分への`cache_control`付与)は
  コスト削減効果が大きいため実装時の優先事項とする。利用間隔(週2〜3回)がデフォルトTTL
  (5分)より長いため、1時間TTLの採用可否をaircon-pashaと合わせて次の課題とする。
- 実際のLLM API呼び出し・APIキー取得はオーナー承認が必要なアクションであり、本ドキュメント
  はあくまで契約前の判断材料整理にとどまる(pending-approval.md記載の既存の承認待ち事項の
  範囲内)。
