# 制限モード中の解約予約受理案内メッセージの文言レビュー(フェーズ210)

## 位置づけ

subscription-cancellation-scheduled-message-suspension-consistency-design.md
(フェーズ157)5節の残課題「制限モード中の解約予約案内メッセージの具体的な文言(お支払い
方法確認と解約予約という2つの手続きが並行して存在する状態の説明)は、実際の顧客からの
問い合わせ実績が無いため、初期案として妥当性を検証する必要がある」に対応する。

この課題は本venture(フェーズ157)が起点であり、aircon-pashaがフェーズ195で本venture向け
文言を翻案したうえで先に机上レビュー(restricted-mode-cancellation-message-copy-review.md)
を作成済みだったが、起点である本venture自身には同種のレビュー文書がこれまで存在しなかった
(README・presentations.mdへの逆流記載漏れとは別の、cross-venture parityの抜け)。本フェーズ
はこのギャップを解消し、本venture自身の実装文言(`subscription_cancellation_notification.py`
`render_subscription_cancellation_scheduled_message()`)を対象に机上レビューを行う。

実顧客からの問い合わせ実績は本フェーズ時点でも引き続き存在しない(LINE公式アカウント・
Stripeアカウントともにオーナー承認待ちで未接続のため)。そのため本ドキュメントも
aircon-pasha版と同様、「実測に基づく検証」ではなく、複数の観点から現行文言を自己点検し、
代替候補案とその採否理由をあらかじめ整理しておく机上レビューに留まる。

## 1. 現行文言(フェーズ157実装、`subscription_cancellation_notification.py`)

`is_currently_suspended=True`の場合に生成される該当行は以下の通り(`{until_phrase}`は
`今回の請求期間の終了日({period_end_date})まで`等に展開される)。

```
・契約自体は{until_phrase}継続しますが、お支払い方法のご確認が必要な状態のため
投稿文の生成は既に一時停止しています(解約予約とは別に、お支払い方法をご確認
いただくまで生成は再開しません)
```

aircon-pasha版との差異は「投稿文の生成」(本venture、SNS投稿文生成が主機能)と
「作業完了報告・お手入れ案内の生成」(aircon-pasha、エアコン修理報告書生成が主機能)の
対象成果物名のみであり、文構造・接続詞・語順は完全に一致する。

## 2. 点検の観点

aircon-pashaフェーズ195と同じ4つの観点で点検する(観点自体をventure間で変える理由が
ないため踏襲)。

1. **状況の理解しやすさ**: 「契約の解約予約」と「決済失敗による生成停止」という独立した
   2つの状態が同時に存在することが、1文で誤解なく伝わるか。
2. **次に取るべき行動の明確さ**: 生成を再開したい場合に何をすればよいかが分かるか
   (本メッセージ単体でお支払い方法確認の導線まで踏み込むべきか)。
3. **不安を煽りすぎない言い回し**: 「一時停止」「終了」等の否定的な語が連続し、
   実際より深刻な状態(例えば既にサービスを打ち切られた)と誤解されないか。
4. **既存の他の通知文言とのトーン一貫性**: トライアル終了案内(trial-end-notification-
   design.md)・支払い失敗案内(payment-failure-dunning-design.md)と同じ「淡々と事実を
   伝え、行動導線は別途用意する」トーンを踏襲できているか。

## 3. 代替候補案

**案A(現行)**: 上記1節の文言。「契約自体は継続」を先に述べてから、生成停止の事実と
その理由(お支払い方法未確認)、解約予約とは別の話であることを補足する順序。

**案B(行動起点)**: 生成停止の事実を先に述べ、契約継続を後段に回す案。
```
・お支払い方法のご確認が必要な状態のため、投稿文の生成は既に一時停止しています
(解約予約とは別の手続きです)
・契約自体は{until_phrase}継続します
```
生成停止という「今困っている」情報を先に提示できる利点はあるが、「契約自体は継続」を
読む前に「もう使えなくなった」と早合点されるリスクが案Aより高いと考えられる。

**案C(2手続きを明示的に列挙)**: 「2つの手続きが並行している」ことを見出し的に強調する案。
```
・現在、以下の2つが並行して発生しています
  (1) 解約予約: {until_phrase}で契約終了予定
  (2) 生成の一時停止: お支払い方法のご確認待ちのため、解約予約とは別に既に停止中
```
構造は明快だが、他の通知文言(トライアル終了案内・支払い失敗案内)がいずれも箇条書き
1段で完結しており、番号付きの入れ子構造を持つ文言は本venture・aircon-pasha・
line-reservation-aiのいずれにも前例がない。1件のみ入れ子構造を導入すると文言全体の
一貫性(4節参照)を崩す懸念がある。

## 4. 結論(暫定)

現行の案Aを維持することを推奨する。理由はaircon-pashaフェーズ195の結論と同一。

- 「契約自体は継続します**が**」という逆接から入ることで、読み手が最初に「サービスは
  終わっていない」という安心材料を得た上で、生成停止という制約事項を読み進められる。
  案Bのように生成停止を先に出すと、契約継続の情報に到達する前に離脱(既読のみで
  ポータルへ確認に来ない)するリスクがある。
- 「(解約予約とは別に、お支払い方法をご確認いただくまで生成は再開しません)」という
  括弧書きの補足が、案Cが目指す「2手続きの独立性の明示」を1文の範囲で既に達成できて
  おり、入れ子構造による一貫性崩れのコストを避けられる。
- 生成再開のための行動導線(お支払い方法の確認方法)は本メッセージには含めない。これは
  design(フェーズ157)時点からの既存方針で、支払い失敗自体の案内・ポータル誘導は
  `payment-failure-dunning-design.md`側の別メッセージが既に担っており、本メッセージで
  重複させると却って「どちらの案内に従えばよいか」を分かりにくくすると判断したため
  (既存方針の再確認であり、本フェーズでの変更ではない)。

この結論はあくまで机上の比較であり、コード変更は行わない(案Aは既に実装済みのため)。

## 5. 残課題

- 本レビューは実顧客の反応データを伴わない机上検討のため、実際にLINE公式アカウント・
  Stripeアカウントが稼働し、制限モード中に解約予約を行う顧客が実際に発生した段階で、
  問い合わせ件数・解約取り消し率等の実測データをもとに再検証する必要がある
  (aircon-pashaフェーズ195の同種課題も未検証のまま残っている)。
- line-reservation-aiは本フェーズ時点でも解約予約受理時点の顧客向け通知自体が制限モード
  との整合性を考慮した設計になっているか未確認であり、cross-venture parityの観点から
  今後の確認候補として残す。
- 実LINE Push Message API・実Stripeアカウント接続はいずれも実アカウント作成
  (オーナー承認待ち)後の課題として引き続き残る。
