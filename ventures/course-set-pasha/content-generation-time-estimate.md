# 「浮いた作業時間の目安」試算(1回あたりの手動作成時間の仮置き)

作成日: 2026-08-24

## 背景

trial-end-notification-design.md 3節のトライアル終了通知メッセージ・pricing-plan.md・
onboarding-guide.mdはいずれも「浮いた作業時間の目安」を利用実績レポートに含める設計だが、
試算値自体が本venture未着手のままプレースホルダ(「約○分」)として残っていた
(README.mdフェーズ105・「次にやること」参照)。sns-tone-research.mdの時点で「個人経営
ジムの投稿作成時間の定量データは公開情報から見当たらず、実ヒアリングでしか検証できない
可能性が高い」と既に結論づけているため、本フェーズでは追加のWebSearch調査は行わず、
一般的な文章作成に要する時間の目安からの仮置き試算にとどめる。line-reservation-ai/
unit-economics-estimate.mdが果たした役割(複数の個別試算を横断して定量化する)と同様、
本ドキュメントは「値そのものが仮置きである」旨を明記した上で、実装(プレースホルダの解消)を
先に進めるための暫定値を提示することを目的とする。

## 前提: 1回の生成で作成される3点セット

llm-api-cost-estimate.md「出力(3件の下書き)」節の通り、1回の生成でAIが作成するのは
以下3点セットである。手動作成の場合、オーナー自身がこの3点を個別に作成する必要がある
という前提で試算する。

1. SNS投稿文(課題入れ替え後の告知、Instagram等)
2. LINE/Web告知文(SNS投稿文と内容は重複するが媒体に応じた文言調整が必要)
3. 課題入れ替え履歴記録(history_rows相当。エリア・テープ色・難易度帯・本数等の記録)

## 試算(仮置き)

market-research.mdが指摘する通り、投稿文の作成は「セット内容を魅力的に言語化する」という
ライティングスキルを要する作業であり、単純なタイピング速度(日本語で1分あたり数十文字〜
100文字程度)だけでなく、言い回しを考える時間・写真とのバランスを検討する時間が支配的になる
と仮定する。

| 作業項目 | 仮置き所要時間 | 前提 |
|---|---|---|
| (1) SNS投稿文 | 7〜10分 | エリア・テープ色・本数・ムーブの特徴を魅力的な文言に言語化する時間が中心。文面の練り直し・絵文字選定を含む。 |
| (2) LINE/Web告知文 | 3〜5分 | (1)からの流用がベースだが、媒体差(文字数制限・フォーマット)に応じた調整が必要。ゼロから書くより短時間と仮定。 |
| (3) 課題入れ替え履歴記録 | 2〜3分 | 定型項目(エリア・テープ色・難易度帯・本数・改訂日)の記録のみでライティング要素が薄いため短時間と仮定。 |
| 合計 | 12〜18分(中間値15分) | 各項目の中間値の合計(8.5+4+2.5≒15分)とほぼ一致するため、幅の中央値15分を採用。 |

AIによる生成自体は数秒〜数十秒で完了し、利用者側の作業は生成結果の確認・微修正
(1〜2分程度と仮定、pricing-plan.md等の既存試算に含まれる「利用実績レポート」の対象時間
からは除外)にとどまるため、削減効果は上記合計時間にほぼ等しいとみなす。

## 結論・採用値

- 1回あたりの「浮いた作業時間」は**15分**(仮置き、幅12〜18分)を採用する。
- トライアル終了通知メッセージ(trial-end-notification-design.md 3節)の「浮いた作業時間の
  目安」は `trial_generation_count × 15分` で算出し、「1回あたり平均15分と仮定」という
  前提を文言内に明記することで、仮置き値であることを利用者にも透明にする
  (courese-set-pashaの既存方針: 試算の前提を隠さない)。

## 複数エリア同時更新時の按分式(フェーズ109)

multi-area-mixed-case-review.mdの採用方針(案1: エリアごとに区切って列挙)を踏まえ、
1回の生成イベントで更新対象エリアがn個(=history_rowsの要素数)の場合の所要時間を、
(1)(2)(3)それぞれの性質の違いに応じて按分する式を設計する。

### (1)(2): エリア数に対して非線形(1エリア目が支配的、追加エリアは差分のみ)

multi-area-mixed-case-review.mdの採用方針により、2エリア以上の場合も冒頭要約は
「(エリア名)は(色・本数)」の形でエリアごとに区切って列挙するだけであり、文章全体の
トーン設定・書き出し・絵文字選定といった「1エリア目を書く」ときに支配的な作業
(元試算の(1)7〜10分+(2)3〜5分=中間値12.5分)は1回で済む。2エリア目以降は
「エリア名+分かる範囲の色・本数」という短い句を追加するだけであり、3エリア以上では
文量調整ルール(「色+本数」程度に簡潔化)がさらに働くため、1エリア目より短い
追加コストと仮定する。仮置きで追加エリア1件あたり2.5分(元の(1)(2)中間値12.5分の
おおよそ5分の1)とする。

### (3): エリア数に線形(history_rowsが要素数=n個の行になるため)

multi-area-mixed-case-review.mdの対応方針により出力3(履歴記録)はエリアごとに1行
生成される(history_rowsの要素数=更新対象エリア数nに一致)。手動作成の場合も定型項目の
記録をエリアの数だけ繰り返す必要があるため、元試算の(3)2〜3分(中間値2.5分)を
そのままn倍する。

### 統合式

1回の生成イベント(更新対象エリア数n、n≧1)あたりの「浮いた作業時間」を、

```
minutes(n) = 12.5(1エリア目の(1)+(2)) + 2.5×(n-1)(2エリア目以降の(1)+(2)追加分) + 2.5×n((3)のn行分)
           = 10 + 5n
```

とする。n=1のとき `minutes(1) = 15`(元のMINUTES_SAVED_PER_GENERATION=15と一致)。
n=2で20分、n=3で25分となる。

トライアル期間全体では、生成回数g回・エリア更新総数(全生成のhistory_rows要素数の合計)を
Aとすると、合計の浮いた作業時間は `10×g + 5×A` 分となる。

### 現状の実装との差分・次の課題

現在のprototype/trial_end_scheduler.py(MINUTES_SAVED_PER_GENERATION=15を生成回数に
単純に掛ける方式)は、n=1(1回のメモで1エリアのみ更新)のケースでは上式と一致するが、
複数エリア同時更新が発生すると実際より少なく見積もる(過小評価する)ことになる。
上式を実装に反映するには、次の対応が必要で本フェーズの範囲を超えるため次の課題として残す。

- usage_counter(UsageCounterProtocol)に、生成回数(trial_generation_count)とは別に
  トライアル期間中のエリア更新総数(トライアル用history_rows要素数の累計、仮称
  trial_area_count)を積み上げる専用カウンタを新設する(increment_trial_generation_countと
  同様、cloud_function_webhook.py側で`len(instance["history_rows"])`を渡して加算する)。
- trial_end_scheduler.pyのformat_trial_end_notification_message()を
  `10 × generation_count + 5 × area_count`で計算する式に置き換え、通知文言の
  「1回あたり平均15分と仮定」という固定文言も、複数エリア更新を考慮した表現
  (例:「1エリアの更新につき平均15分、複数エリア同時更新時は1エリア追加ごとに
  さらに約5分と仮定」)に見直す。
- 上記いずれも、trial_area_countをまだ持たない既存実装との後方互換
  (hasattr()判定、既存フェーズのパターンを踏襲)を維持する必要がある。
