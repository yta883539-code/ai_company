# 申込フォーム統合の方針確定・接続テスト省略時のフォールバック設計

作成日: 2026-08-16

onboarding-guide.mdの「次のステップ候補」に残っていた2点(ステップ3の申込フォーム統合方針、
ステップ4省略時のフォールバック要否)について設計する。

## 1. ジム名・地域名入力: 申込フォーム統合で確定

onboarding-guide.md注記の通り、本ventureの設定項目はジム名・地域名程度と少なく、
line-reservation-aiのowner-settings-wireframe.mdに相当する専用設定画面を別途持つ費用対効果は
低いと判断し、**申込フォーム(ステップ1)の追加項目として統合する**方針で確定する。

- 申込フォーム項目: ジム名(または屋号)・運営形態(任意)に加え、「ジム名・地域名(任意、
  複数可)」を1つの自由記述欄として追加する。
- 複数ジム掛け持ちセッター(未検証の仮説2点目)向けに、カンマ区切りで複数組を入力できる
  形式(例:「クライミングジムA/○○区、ボルダリングジムB/△△市」)を許容する。専用データストアを
  持たないMVPの制約上、入力された文字列をそのまま保持しLLMシステムプロンプトへ渡す設計とし、
  ジムごとに構造化して選択させるUIは持たない(mvp-flow-draft.mdの「専用データベースは持たない」
  方針を踏襲)。
- llm-system-prompt-draft.mdの「ジム独自のブランドタグ」「地域タグ」ロジックには、メモ本文中に
  該当ジム名が言及されていればそのジム名に対応する地域タグを優先的に採用し、言及が無ければ
  先頭に登録された組を既定値として使う、という優先順位ルールを追加する必要がある(実装時の
  課題として残す)。
- 将来、入力項目数が増えて(例: 3ジム以上の掛け持ちが標準的になった等)申込フォームが
  煩雑になった場合は、専用設定ページへの分離を再検討する。現時点ではこの閾値を数値で
  定義せず、customer-interview-design.mdのヒアリングで実際の掛け持ち数の分布を確認した
  段階で判断する。

## 2. 接続テスト(ステップ4)省略時のフォールバック設計

### 背景

line-reservation-aiはfirst-booking-self-check-notification-design.mdで「店舗全体で最初の
予約確定時に1回だけセルフチェック通知を送る」設計を採用した。本ventureにも同様の課題
(オーナー・セッターがステップ4〈接続テスト〉を省略し、ジム名・地域名未設定によるタグ精度
低下や、意図しない出力形式に気づかないまま本番投稿してしまうリスク)がある。

### line-reservation-aiとの構造的な違い

line-reservation-aiの実装は「予約確定」という明確に区別可能なイベント(会話状態機械が
`confirmed`へ遷移する瞬間)を持ち、かつ`ConversationFlowStateMachine`インスタンスが
店舗ごとに継続して存在するため、インスタンス内のブールフラグで「発火済みか」を保持できた。

本ventureは単方向バッチ処理(1メモ入力→1回の生成で完結、tech-stack.mdの通り会話状態を
持たない)であり、かつ「試験生成」と「本番生成」を区別する専用フラグや別エンドポイントを
onboarding-guide.mdは想定していない(ステップ4はステップ5と同じ入力・出力の仕組みをそのまま
使う「試しに送ってみる」行為でしかない)。したがって、システム側は特定の1回を「これは接続
テストだ」と判別する手段を持たない。

### 方針

- line-reservation-aiと同様、判別不能な以上は**そのユーザーにとって最初の生成成功時**を
  暗黙のテストとみなし、通常の3出力(SNS投稿文下書き・LINE/Web告知文下書き・課題入れ替え履歴)に
  加えて、そのレスポンスの末尾にのみ確認案内を1回だけ付記する設計とする。2回目以降の生成では
  付記しない(first-booking-self-check-notification-design.mdの「オーナー通知は必要な時だけ」
  方針を踏襲)。
- 本ventureの`usage_counter`(tech-stack.md、`{month, count}`の最小構成)は永続化された唯一の
  状態であり、`ConversationFlowStateMachine`のようなインメモリの継続インスタンスを持たない
  ため、フラグはこのドキュメントに`first_generation_notice_sent: bool`フィールドを追加する形で
  永続化する必要がある(line-reservation-aiのインメモリフラグでは、サーバーレス関数の
  再起動やインスタンス使い捨てのたびにフラグが失われ、毎回付記されてしまう既知の差異)。
- 確認案内の文面案(3出力の末尾に追記):

  ```
  【ご確認のお願い】これが最初の生成です。ジム名・地域名の表示やハッシュタグが意図通りか、
  この機会にご確認ください。設定を直したい場合は申込内容の変更フォームからどうぞ。
  問題がなければ今後この案内はありません。
  ```

- ジム名・地域名が未入力(上記1.の欄が空)の場合は、上記に加えて「ジム名・地域名が未設定です。
  ハッシュタグ精度を上げたい場合は設定をご検討ください」の一文を続けて付記する
  (onboarding-guide.mdステップ4に既にあった案の具体化)。
- post_generation_checks.pyの機械チェック(厳守事項違反検知)とは責務が別のため、この確認案内は
  同モジュールではなく出力組み立て側(webhook処理の最終ステップ)に実装する想定とし、
  違反検知ロジックとは混在させない(line-reservation-aiがEscalationConsolidator等と混在させ
  なかった判断と同じ理由)。

### 残課題

- `usage_counter`への`first_generation_notice_sent`フィールド追加、および
  `cloud_function_webhook.py`側での実際の配線(生成成功時にフラグを確認・更新し、初回のみ
  案内文を追記する処理)は、実Firestore接続・実LINE API接続自体がオーナー承認待ちのため
  未着手のまま残す。
- ジム名・地域名の複数組入力(カンマ区切り)をLLMシステムプロンプト側でどう構造化して
  優先順位ルールを適用するかの具体的なプロンプト文面は、llm-system-prompt-draft.mdへの
  反映を次の課題とする。
- 「試験生成のつもりで送ったメモが、実は最初の生成ではなく2回目以降だった」というケース
  (例: 誤って本番投稿と勘違いして送った初回メモに気づかず、2回目の試験のつもりの送信で
  案内が出ずそのまま投稿してしまう)は、システム側では区別できない既知の限界として残す。
