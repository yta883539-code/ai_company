# チャットボットによる一次受付自動化の技術的検討

作成日: 2026-09-21

## 背景

support-cost-selfservice-reduction.md(フェーズ233)「残課題」に、「チャットボットによる
一次受付の自動化(FAQ該当質問への自動応答)は、本サービス自体がLLMを用いた投稿文生成
ツールであることを踏まえると技術的親和性は高いと考えられるが、誤回答時の顧客不信・実装
コストとのトレードオフがあり、本フェーズでは検討していない(次回以降の課題)」として
残っていた。本ドキュメントは、この論点について技術構成の選択肢とトレードオフを整理する
(実装・実LLM呼び出し・実LINE接続は行わない、机上の技術検討のみ)。

## 前提: 対象とする問い合わせの範囲

support-cost-estimate.md・support-cost-selfservice-reduction.mdの整理を踏まえ、一次受付
自動化の対象候補は以下の2種類に絞られる。

- 対象にしやすい: 「使い方の再質問」「料金プラン・トライアル条件の説明」等、
  landing-page-copy-draft.mdのFAQ・onboarding-guide.mdで既に文書化済みの定型的な質問。
- 対象にしにくい: 「生成物の修正依頼」(個別の投稿内容に依存し汎用回答が成立しない)、
  「つまずいた場合の個別環境依存トラブル」(LINEアプリ表示崩れ等、定型FAQでは網羅
  しきれない)。support-cost-selfservice-reduction.mdが指摘した通り、これらはチャット
  ボット化になじまない。

## 技術構成の選択肢

本サービスは既にtech-stack.mdの通りLINE公式アカウント⇄GCP Cloud Functions⇄LLM APIという
構成を持つため、一次受付自動化は新規インフラを追加せず、既存のWebhookサーバーに分岐
ロジックを追加する形で実現できる可能性が高い。検討した選択肢は以下の3つ。

1. **キーワードマッチ方式**: 受信メッセージが「解約」「料金」「使い方」等の定型キーワードを
   含む場合、対応するFAQ回答テンプレートをそのまま返す。LLM呼び出しを伴わないため追加の
   API従量課金が発生せず、誤回答リスクも「キーワードが本来の投稿文生成依頼と誤って一致する」
   場合に限定できる。ただし表記揺れ(「やめたい」「解約したい」等の言い換え)への対応が
   弱く、ヒット率が低くなりやすい。
2. **LLMによる意図分類+定型回答方式**: 受信メッセージをまずLLMに渡し、「投稿文生成依頼」
   「FAQ該当質問(料金/使い方/解約等のカテゴリ)」「その他(人的対応が必要)」のいずれかに
   分類させ、FAQ該当と判定された場合のみ事前に用意した定型回答(FAQ本文をそのまま使用し
   LLMに新規生成させない)を返す。分類さえ誤らなければ回答内容自体はFAQ原文のままなので
   「誤った内容を回答する」リスクは低く抑えられるが、「分類自体を誤り、本来必要な人的
   対応をFAQ回答で済ませてしまう」リスクは残る。
3. **LLMによる自由回答方式**: FAQ内容を踏まえてLLMに都度回答文を自由生成させる。表現の
   柔軟性は最も高いが、事実と異なる回答(ハルシネーション)を生成するリスクが最も高く、
   support-cost-selfservice-reduction.mdが懸念した「誤回答時の顧客不信」に最も直結する
   ため、本サービスの主要顧客(運営に不慣れな個人〜小規模セッター)向けには推奨しない。

既存のtech-stack.md構成(出力1〜3をJSON schemaで検証する設計思想)との整合性、および
誤回答リスクの抑制を優先し、選択肢2(LLMによる意図分類+定型回答方式)が最も現実的な
第一候補と考えられる。選択肢1はヒット率の低さ、選択肢3は誤回答リスクの高さがそれぞれ
主要顧客層(LINE操作に不慣れな場合がある個人事業主)には見合わないと判断した。

## トレードオフの整理

- **メリット**: support-cost-selfservice-reduction.mdの試算通り「使い方の再質問」
  「料金・トライアル説明」の一部は既にFAQ化済みであり、意図分類さえ機能すれば追加の
  文書作成コストなしに一次回答を自動化できる。運営者の対応工数削減に直結する。
- **デメリット・リスク**:
  - 意図分類の精度が低い場合、本来の投稿文生成依頼をFAQ回答と誤判定し、顧客の主目的
    (投稿文生成)を妨げる可能性がある(本サービスの中核機能への悪影響という点で、
    単なる問い合わせ対応の失敗より影響が大きい)。
  - 「その他(人的対応が必要)」への分類時のエスカレーション導線(運営者への通知方法)を
    別途設計する必要があり、これ自体は本ドキュメントの範囲外(次回以降の課題)。
  - LLM呼び出しが1件の問い合わせにつき「意図分類」「(投稿文生成依頼の場合)本来の生成
    処理」の最大2回に増える可能性があり、LLM API従量課金がわずかに増加する
    (影響額は未試算)。

## 6. 他ventureへの横展開検討(フェーズ248)

aircon-pasha・kura-pashaのtech-stack.mdを確認したところ、両venture共に本venture
(course-set-pasha)と同一の「LINE公式アカウント⇄Webhookサーバー⇄LLM(3出力生成)⇄
返信メッセージ」という単方向バッチ処理構成であり、双方向の会話状態管理を持たない点も
共通している。両venture向けのsupport-cost-estimate.mdにも「使い方の再質問」「料金・
トライアル説明」等の定型問い合わせが存在することが記載されており、本ドキュメントが
整理した一次受付自動化の対象範囲(対象にしやすい/しにくいの切り分け)・選択肢2
(LLMによる意図分類+定型回答方式)の設計思想は、両venture固有のFAQ内容(Q1〜Q6相当の
質問カテゴリ)を置き換えるだけでそのまま横展開できる可能性が高いと判断した。ただし、
両venture共に既存の`owner_faq_router.py`相当のFAQコード体系・`process_memo_event()`
相当の本文生成フローの実装状況が本ventureと同一ではないため、実際の横展開(設計の
移植・実装)は各venture側のフェーズとして別途着手する必要がある(本フェーズでは
着手せず、可能性の確認のみに留める)。line-reservation-aiは既にLLMによる会話応答・
意図判定(`intent-to-flow-mapping.md`)が中核機能として存在し、双方向の会話状態管理を
前提とする設計であるため、本ドキュメントが想定する「単方向バッチ処理への一次受付分岐
追加」という構成自体が当てはまらず、本ventureの一次受付自動化とは別の検討軸(既存の
意図判定にFAQ系インテントを追加する形)になると考えられる。line-reservation-ai固有の
検討は本フェーズの範囲外とし、同venture側の次回以降の課題として申し送る。
