# LIFFプラン選択UIワイヤーフレーム

作成日: 2026-09-05(フェーズ163)

checkout-session-plan-selection-design.md(フェーズ152)1節で「LIFFフロントエンド側の
プラン選択UI(未実装、実LIFF登録後の課題)」として残っていた画面の設計を、landing-page-
wireframe.mdと同様にテキストベースのワイヤーフレームとして具体化する。実LIFF実装・
実LIFFチャネル登録(LINE Developersでのアカウント作成に相当)はオーナー承認後の課題として
引き続き未着手のままとする。

## 前提・接続する設計

- checkout-session-plan-selection-design.md 1節により、本画面は選択したプラン名
  (`"ライト"`/`"スタンダード"`/`"セッター複数"`、`cloud_function_webhook.PLAN_MONTHLY_LIMITS`の
  キーと同一集合)をcrypto Checkout Session作成エンドポイントへクエリパラメータ`plan`として
  渡す想定になっている。本ワイヤーフレームは、その`plan`値を利用者に選ばせるための画面である。
- pricing-plan.mdの3プラン(ライト1,980円/月8回、スタンダード3,480円/月15回、
  セッター複数5,980円/月30回・複数セッター共同利用)をそのままカード表示する。
- trial-start-anchor-decision.md(フェーズ100)により無料トライアルは「初回生成成功時点」を
  起点とするため、本画面はトライアル開始のためのプラン選択ではなく、(a)トライアル終了後に
  有料プランへ移行する際、および(b)トライアル中でも先に有料プランを選びたい利用者向けの
  画面と位置づける。トライアル自体はプラン選択なしで開始できる前提は変更しない
  (landing-page-wireframe.mdのCTA「14日間無料で試してみる」はプラン選択を経由しない)。
- 実LIFF SDK(`liff.init()`・`liff.getProfile()`等)への接続はLIFFチャネル登録後の課題として
  未着手。本ワイフレームは画面構成・遷移のみを定義し、実装はプレースホルダに留める。

## 遷移・パラメータ設計

1. 利用者がいずれかのカードの「このプランを選ぶ」をタップすると、
   `create_checkout_session()`エンドポイントへ`plan=<プラン名>`をクエリパラメータとして
   付与しリクエストする(checkout-session-plan-selection-design.md 2節の
   `main()`実装済みの`request.args.get("plan")`読み取りにそのまま合致)。
2. `verify_id_token`失敗時(未認証)・`invalid_plan`(400)時の画面上のエラー表示は、
   本ワイヤーフレームでは「プランの選択に失敗しました。もう一度お試しください」という
   汎用エラーメッセージのみを暫定案とする(個別のエラー内容を利用者に詳細開示する
   設計は行わない。checkout-session-endpoint-design.mdのエラーレスポンス設計と対応関係を
   崩さないため)。
3. Checkout Session URLへの遷移後は、Stripeホスト型のCheckout画面(本ventureの管理下外)に
   遷移する想定であり、本ワイヤーフレームの対象外。
4. 決済完了後の戻り先(`success_url`)・キャンセル時の戻り先(`cancel_url`)は
   checkout-session-endpoint-design.mdで既に定義済みのため、本ワイヤーフレームでの
   再定義は行わない。

## 設計判断

- **横スクロールではなく縦積みカードを採用した理由**: LIFFはLINEアプリ内のWebViewとして
  表示され、画面幅がline-reservation-ai/aircon-pashaのLPと同様に狭いモバイル前提となる。
  3プランを横スクロールのカルーセルにすると中間プラン(スタンダード)が初期表示で
  見切れる可能性があり、「人気」バッジを付けた推奨プランを必ず最初のスクロールで
  目にしてもらうため、縦積みで全プランを見渡せる構成を優先した。
- **「現在のご利用状況」表示の要否**: `get_plan()`(checkout-session-plan-selection-
  design.md実装済み)により、画面表示時点で選択済みプランの有無を判定できる。
  未選択(トライアル中)なら残回数・残日数、選択済みなら現在のプラン名を出し分ける設計とし、
  「今何を選ぶべきか」を利用者が迷わないようにした。残回数・残日数の実際の取得元
  (`usage_counter`等)との接続は、フェーズ164・`prototype/liff_usage_status.py`の
  `get_current_usage_status()`で実装した(下記「未確定・今後の課題」参照)。

## 未確定・今後の課題

- 実LIFF SDK接続(`liff.init()`・チャネルID設定)はLIFFチャネル登録(LINE Developersでの
  設定作業に相当)後の課題として未着手。着手にはオーナー承認が必要(pending-approval.md参照)。
- (解消済み フェーズ164、2026-09-05: 「現在のご利用状況」欄が参照する残回数・残日数の
  実際の取得ロジックを`prototype/liff_usage_status.py`の`get_current_usage_status()`として
  実装した。`get_plan()`設定済みなら`PaidUsageStatus`(現在のプラン名・
  `usage_counter.get_count(user_id, current_month)`・`PLAN_MONTHLY_LIMITS`上限)、未設定
  〈トライアル中〉なら`TrialUsageStatus`(`TRIAL_GENERATION_LIMIT -
  get_trial_generation_count()`を0未満に落ちないようクランプした残回数、`trial_start_at`
  未設定〈初回生成前〉なら満額`DEFAULT_TRIAL_PERIOD_DAYS`・設定済みなら経過日数を差し引いた
  残り日数)を返す。`format_usage_status_line()`でワイヤーフレーム文言
  「トライアル残り: ○回 / ○日」「現在のプラン: ○○」への変換も実装した。実LIFF SDK接続・
  実Firestore接続〈`usage_counter`・`user_profile_store`の実体〉は引き続きオーナー承認後の
  課題として残る)
- (解消済み フェーズ165、2026-09-05: プラン変更(アップグレード/ダウングレード)時に
  本画面を再利用するか、専用の変更画面を別途設けるかを検討した。専用画面は新設せず、
  本画面を再利用する方針とした。ただし各プランカードの「このプランを選ぶ」ボタンの
  遷移先を、`prototype/liff_plan_card_action.py`の`resolve_plan_card_action(current_plan,
  card_plan)`で契約状態に応じて分岐させる。(1)未契約(トライアル中)は従来通り
  `create_checkout_session()`へ遷移、(2)契約中で選択カードが現在のプランと同じ場合は
  ボタンを無効化し「ご利用中」ラベルに差し替え、(3)契約中で選択カードが現在のプランと
  異なる場合(アップグレード/ダウングレード)は`create_portal_session()`
  (portal_session.py)へ遷移する。理由は`mode="subscription"`のCheckout Sessionが常に
  新規サブスクリプションを作成するため、契約中のユーザーに使うと二重契約になってしまう
  ことと、subscription-plan-change-design.mdが既に`customer.subscription.updated`
  Webhookからの`plan`自動更新をStripeカスタマーポータル経由のプラン変更を前提に設計
  済みであるため、遷移先をポータルに揃えるのが最小の変更で済むこと。ポータル側の画面
  上でユーザー自身が変更後のプランを選ぶため、本画面から遷移先プランをポータルへ
  パラメータとして渡す必要はない。テスト4件追加。実LIFF SDK接続後、ボタンの表示・
  無効化自体の実装(HTML/JS側)は引き続き未着手のまま残る)
- 実際のビジュアルデザイン(配色・フォント・ボタンのスタイル)の制作は本ワイヤーフレームの
  範囲外。landing-page-wireframe.mdの画像方針と同様、着手時にどのツール・素材を使うかは
  未検討(外部デザインツール利用はアカウント連携が発生する場合オーナー確認が必要)。
