# 3エリア以上・項目の有無が混在する複合ケースの机上検証(2026-08-07 19:00 UTC)

header-summary-edge-case-review.mdの「未検証事項」に残っていた、3エリア以上が同時に
更新対象となり、エリアごとに色・本数・グレード帯の有無がバラバラなケースを机上検証した。
実LLM呼び出しは行わず、現行のプロンプト文面(厳守事項4)をそのまま適用した場合に
生成されるはずの出力を人手でシミュレーションする形の検証。

## 検証したケース

### ケースE: 3エリア更新、情報の充実度がエリアごとに異なる

入力メモ例:「Aエリア、黄・オレンジテープ(4級〜2級)、8本、カチ持ち系ムーブ中心。
Bエリア、赤テープ、5本(グレード表記なし)。Cエリア、ダイナミックムーブを重点強化
(色・本数・グレード表記なし)。2026-08-07改訂」

現行の厳守事項4は「複数エリアのうち一部エリアのみが更新対象で他エリアが『変更なし』の
場合、冒頭要約に対象エリア名を前置きする」としか定めておらず、これは
「更新対象エリア数=1、非更新エリアあり」を想定した文言。ケースEのように
「更新対象エリアが2つ以上、かつエリアごとに情報の充実度が異なる」場合の冒頭要約の
組み立て方は現行文言では未規定と判明した。

想定される問題点:
1. 単純に3エリア分の色・本数を一文に詰め込むと、ケースCで確立した「片方のみ欠けたら
   欠けている項目だけを外す」という部分省略ルールと、複数エリア分の情報をどう
   同じ文に共存させるかの優先順位が矛盾しうる(例: Cエリアは色も本数も無いため
   要約から完全に除外してよいのか、それとも「Cエリアはムーブ紹介のみ」と明示すべきか)。
2. sns-post-example-observation.mdで観察した実例は単一エリア更新の投稿が中心で、
   3エリア同時更新時の冒頭要約の型(1エリアずつ列挙するのか、全エリア合算の総本数を
   出すのか)は公開情報からの裏付けが無い。

### 検討した2案

**案1: エリアごとに区切って列挙**
「Aエリアは黄・オレンジ(4級〜2級)計8本、Bエリアは赤テープ計5本、Cエリアはダイナミック
ムーブを重点強化、の3エリアを更新」のようにエリア単位で区切る。
- 長所: header-summary-edge-case-review.mdのケースB対応(エリア名前置き)と設計思想が
  連続しており、「情報が薄いエリアはそのエリア分だけ簡潔になる」という自然な縮退が起きる。
- 短所: 4エリア以上になると一文が冗長になりやすい。

**案2: 全エリア合算の総本数のみ先に出し、エリアごとの詳細は本文に回す**
「本日は3エリアで新着課題(計13本)を入れ替え」のように総本数だけを冒頭に出し、
エリアごとの内訳は本文の1〜2文紹介パートに委ねる。
- 長所: 冒頭が簡潔になり、エリア数が増えても崩れにくい。
- 短所: グレード帯の無いエリア(C)の課題本数を合算に含めてよいかが曖昧
  (Cは本数も未記入のため合算からも自然に除外されるが、「合算対象に含めたエリアと
  含めなかったエリアがある」ことが読み手に伝わりにくい)。

### 採用方針

mvp-flow-draft.mdの出力1が想定する「1〜2文の紹介」という分量の制約と、
header-summary-edge-case-review.mdで確立済みの「エリア名前置き」ルールとの連続性を
優先し、**案1(エリアごとに区切って列挙)を採用**する。ただし冗長化を避けるため、
「更新対象エリアが3つ以上の場合、各エリアの記述は最も情報量が多いエリアでも
『テープ色(またはグレード帯)+本数』程度の簡潔な句にとどめ、ムーブの特徴等の詳細は
別途本文の紹介文パートに譲る」という文量調整ルールを追加する。

## 反映内容

llm-system-prompt-draft.mdの厳守事項4に、以下を追記する(次コミットで反映)。

- 更新対象エリアが2つ以上ある場合、冒頭要約はエリアごとに「(エリア名)は
  (分かる範囲の色・グレード帯・本数)」の形で区切って列挙する(情報が無いエリアは
  エリア名のみ、または省略)。
- 更新対象エリアが3つ以上になる場合、各エリアの記述は「色(またはグレード帯)+本数」
  程度に簡潔化し、ムーブの特徴等の詳細説明は冒頭要約ではなく本文の紹介文パートに譲る。

## 派生して見つかった論点: 出力3(履歴記録)の1行仕様との不整合

mvp-flow-draft.mdの出力3は「表形式(改訂日/エリア/テープ色・グレード帯/本数/特徴キーワード)
で1行追記する」と定義されているが、これは暗黙に「1回のメモ=1エリア」を前提にした
仕様だったと判明した。ケースEのように1回のメモで3エリアを同時更新する場合、
1行に3エリア分の情報を詰め込むと「エリア」列が単一値である表形式と矛盾する。

→ 対応方針(解消済み 2026-08-07 20:00 UTC、README.mdフェーズ11): 出力3は「1メモにつき1行」
ではなく「1メモにつき、更新対象エリアの数だけ行を生成する」仕様に改めた。
schema/output.schema.jsonの`history_row`(単一オブジェクト)を`history_rows`(配列)に変更し、
1メモ=1エリアの場合は要素数1、複数エリア同時更新の場合は要素数を更新エリア数に一致させる
仕様とした。status=generatedのとき空配列は不可というルールをschema/validate_test_cases.py
のクロスフィールド検証に追加し、3エリア同時更新の期待出力サンプル(G4_multi_area_single_memo)
を新設して全6件パスを確認済み。llm-system-prompt-draft.md内の`history_row`表記も
`history_rows`に合わせて更新した。
