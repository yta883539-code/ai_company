# 新規オーナー・セッター向けオンボーディングガイド(初回メモ)

これまでpricing-plan.md・tech-stack.md・llm-system-prompt-draft.md等で料金プラン・技術構成・
生成ルールは個々に設計してきたが、「申込から実際にLINE公式アカウントで課題入れ替え下書きの
生成が始まるまで、オーナー・セッターは何をどの順番で行うのか」という一連の導入フロー自体は
これまで文書化していなかった。line-reservation-ai/onboarding-guide.mdの構成を踏襲しつつ、
本ventureは双方向の会話・予約状態管理を持たない単方向バッチ処理である点を反映する。

**本ドキュメントは手順の設計のみを行うものであり、実際の申込受付・課金開始・LINE公式アカウントとの
連携等の運用は一切行わない。**

## 前提

- 対象は非エンジニアの個人事業主〜小規模事業者(個人経営ボルダリングジムオーナー、複数ジムを
  掛け持ちするフリーランスセッター)を想定し、専門知識を要する手順を極力減らす設計とする。
- line-reservation-aiと異なり、営業時間・予約枠・メニュー等の複雑な初期設定は不要。
  tech-stack.mdの通りMVPは月間生成回数カウント用の最小データストア以外に永続状態を持たないため、
  オンボーディングで入力してもらう項目自体も最小限で済む。

## オンボーディングの全体フロー(案)

1. **申込・トライアル開始**
   オーナー・セッターがLP経由で申込フォームに入力。pricing-plan.mdの無料トライアル条件
   (14日間 or 生成5回到達のいずれか早い方、クレジットカード登録なし)に従い、この時点では
   課金は発生しない。
   - 入力項目: ジム名(または屋号)・運営形態(個人経営ジムオーナー/複数ジム掛け持ちセッター等、
     candidate-longlist-draft.mdの区分に対応)・連絡先メールアドレス。運営形態は将来的な
     プラン推奨(セッター複数プランの案内等)の出し分けに使う想定で、必須ではなく任意選択とする。

2. **LINE公式アカウントの準備**
   line-reservation-ai/onboarding-guide.mdステップ2と同じ手順(LINE公式アカウント開設・
   チャネルアクセストークン取得)を踏襲する。本ventureは1:1トーク(オーナー・セッター本人が
   使う入力チャネル)であり顧客対応を含まないため、複数店舗展開時の友だち追加導線設計等は
   不要な分、line-reservation-aiよりステップ自体は単純になる見込み。

3. **ジム名・地域名の初期登録(任意)**
   llm-system-prompt-draft.md記載の「ジム独自のブランドタグ」「地域タグ」はジム名・地域名が
   店舗設定にある場合のみ出力に反映される設計のため、未入力でも起動は可能(**MVPの必須項目は
   実質無い**)。ただし入力しておくとSNS投稿文下書き(出力1)のハッシュタグ精度が上がる旨を
   導入時に案内し、任意入力を促す。
   - line-reservation-aiのowner-settings-wireframe.mdに相当する専用設定画面は、本venture固有の
     設定項目がジム名・地域名程度と少ないため、MVPでは申込フォーム(1.)の追加項目として
     まとめる方針で確定した(専用ページを別途作る費用対効果は低いと判断。複数ジム名の
     入力方式も含め、詳細はonboarding-settings-and-self-check-design.md参照)。

4. **接続テスト・試験生成**
   オーナー・セッター自身が、実際の課題入れ替えを模した簡単なメモ(例:「テストエリア、
   黄色テープ、3級相当、5本新規」)を公式LINEアカウントへ送り、mvp-flow-draft.mdの3出力
   (SNS投稿文下書き・LINE/Web告知文下書き・課題入れ替え履歴)が想定通り返ってくるかを
   本番投稿前に確認してもらうステップ。line-reservation-aiの「試験会話」に相当するが、
   本ventureは会話状態を持たないため1往復のみで完結する。
   - この段階でジム名・地域名の入力漏れ(3.が未入力だとタグが付かない)に気づけるよう、
     試験生成の返信に「ジム名・地域名が未設定です。ハッシュタグ精度を上げたい場合は
     設定してください」等の案内を添える設計を次のステップ候補とする。

5. **本番公開**
   オーナー・セッターが試験生成の内容に問題ないと判断したら、実際の課題入れ替え後にメモを
   送信し、返ってきた下書きをそのままSNS(Instagram/X)・LINE公式アカウント・Web等へ
   転記・投稿する運用を開始する。生成された文面をそのまま使うか手直しするかはオーナー・
   セッター自身の判断に委ねる(post_generation_checks.pyによる機械チェックは違反検知のみで
   文面の巧拙自体には関与しない)。

6. **トライアル終了・プラン選択**
   pricing-plan.mdの方針通り、トライアル終了時は自動課金せず、生成回数の実績をLINEで
   レポートし、継続を希望する場合のみ本人が有料プラン(ライト/スタンダード/セッター複数)を
   選択する。line-reservation-aiと異なり予約件数という指標が無いため、レポート内容は
   「生成回数」「(可能であれば)浮いた文章作成時間の目安」を中心に構成する案とする。

## line-reservation-aiとの違い

- 営業時間・予約枠・メニュー設定等の複雑な初期設定が不要なため、ステップ数自体が
  line-reservation-ai(6ステップだが各ステップの入力項目が多い)より軽量。
- 専用の設定画面(owner-settings-wireframe.md相当)を持つかどうかは3.で未確定のまま残した。
  申込フォームへの統合か専用ページかは、実際の入力項目数が増えた場合(例: 複数ジム掛け持ち
  セッターが複数ジム名を登録する必要が生じた場合)に再検討する。

## 未検証の仮説(要検証)

- ステップ3(ジム名・地域名の初期登録)を任意項目のままにした場合、実際にどの程度の
  オーナー・セッターが入力を省略し、ハッシュタグ精度低下を許容するか(customer-interview-design.mdの
  ヒアリングで確認できる可能性がある項目として追加候補)。
- 複数ジムを掛け持ちするフリーランスセッターが、ジムごとに異なるジム名・地域名を
  メモ本文中に都度書き添える運用と、事前登録した複数ジム名から選択する運用のどちらを
  望むか(セッター複数プランの想定顧客像に直結する論点)。
- ステップ4(接続テスト)をオーナー・セッターが実際に自発的に行うか、省略して本番投稿し
  誤ったタグ付けに気づかないまま運用が始まるリスクがあるか(line-reservation-aiの
  first-booking-self-check-notification-design.mdに相当するフォールバック設計の要否は
  次のステップ候補とする)。
