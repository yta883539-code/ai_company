# テキスト+画像が別イベントで届く場合の束ね方設計

webhook-processing-flow-design.md「残課題」に残っていた、同一送信操作でテキストと画像が
別イベントとして届く場合に「同一メモとして束ねる」処理の設計に対応する。

## 前提の整理

LINE Messaging APIでは、ユーザーが1回の送信操作でテキストと画像を両方送っても、
Webhookには「テキストのmessageイベント」と「画像のmessageイベント」が別々に届く
(1メッセージ1イベント)。これらが束ねられずに届いた場合、現状のprocess_memo_event()は
以下のように扱ってしまう。

- 画像イベント単体: `message.type != "text"`のため素通り(何もしない)。
- テキストイベント単体: `hasPhoto=False`として処理される(実際は写真が添付されていても
  それを検知できない)。

この2つが「同一メモ」であることをどう検知するかが本設計の主題。ケースを2つに分ける。

## ケースA: 同一Webhookリクエスト内に両方のイベントが含まれる場合

LINE Platformは、ユーザーが短時間に連続送信したメッセージを1回のWebhook POSTの
`events`配列にまとめて送ってくることがある(未検証・要実接続確認だが、LINE公式ドキュメントの
一般的な仕様として複数イベントが1リクエストにまとまる場合があるとされている)。この場合、
Cloud Function側の1回の呼び出し内で完結するため、**追加の永続化なしで束ねられる**。

処理: リクエストボディの`events`配列を`source.userId`単位でグルーピングし、
「テキストイベントがちょうど1件、画像イベントが0件以上」のグループを1つのメモとして
統合する(画像イベントが1件以上あれば`hasPhoto=True`)。テキストイベントが0件または2件以上の
グループは統合せず、各イベントを個別に(従来通り)処理する(複数メモが1リクエストに
混在するケースは稀と想定し、誤統合による事故を避けるため保守的に倒す)。

## ケースB: 別々のWebhookリクエストに分かれて届く場合

ケースAでカバーしきれない場合(画像とテキストの間隔が空き、別リクエストとして届く場合)。
これを束ねるには、Cloud Functionsのインスタンス間で共有される永続ストレージ
(Firestore等)に「userIdごとの直近未処理イベント」を短いTTL(例: 数十秒〜数分)で
一時保持する仕組みが必要になる。

### 判断: ケースBの実装は現時点で見送る

tech-stack.mdで本ventureは「line-reservation-aiと異なり会話状態マシンを持たない
単発リクエスト/レスポンス型」と明確に設計方針を決めている。ケースBのためだけに
Firestore等の永続ストレージ・TTL管理・複数リクエストにまたがる整合性制御を導入すると、
この設計方針(line-reservation-aiより意図的にシンプルに保つ)と矛盾し、複雑さに見合う
価値があるか(実際にどれだけの頻度で別リクエストに分かれて届くか)が実測データなしには
判断できない。よって:

- 現時点ではケースBは実装せず、現状の挙動(画像単体イベントは素通り、テキスト単体は
  `hasPhoto=False`で処理)を維持する。
- 実LLM・実LINE API接続後(オーナー承認後)に実際の送信パターンを観測し、画像とテキストが
  別リクエストに分かれる頻度が無視できない水準であれば、その時点で最小構成の永続化
  (例: Firestoreに`{userId}_pending_photo`ドキュメント1件、TTL数十秒)を追加検討する。
- 現状の「写真が無ければ文面のみで完結し、写真が無い旨をAIが指摘しない」
  (mvp-flow-draft.md)という設計のおかげで、ケースBを取りこぼしても出力品質が
  大きく損なわれるわけではない(写真言及が抜けるだけで、テキスト側の処理自体は成立する)
  ことも、優先度を下げる根拠とする。

## ケースAの実装

`prototype/cloud_function_webhook.py`に`merge_text_and_photo_events()`を追加した。
LINE Webhookの生の`events`配列を受け取り、`source.userId`ごとにグルーピングして、
テキストイベントがちょうど1件のグループは画像イベントの有無を`hasPhoto`に反映した
単一のメモイベントへ統合する。統合できなかったイベント(テキスト0件または2件以上の
グループ)はそのままの順序で結果リストに含め、呼び出し側(process_memo_eventループ)で
従来通り個別処理させる。

テストは`prototype/test_cloud_function_webhook.py`に追加
(テキスト+画像1件の統合/テキストのみ/画像のみ素通り/別ユーザー混在時の非混同/
同一ユーザーがテキスト2件を送った場合の非統合、の各ケースをカバー)。

## 残課題

- ケースA自体、実LINE Webhook接続後に「1リクエストに複数イベントがまとまるか」を
  実測で確認する必要がある(未接続のため机上の設計にとどまる)。まとまらないことが
  判明した場合、ケースAの実装は事実上使われず、実質的にケースB相当の対応が必要になる。
- ケースBの永続化要否は、実LLM・実LINE API接続後の実測データ待ち(オーナー承認待ち)。
