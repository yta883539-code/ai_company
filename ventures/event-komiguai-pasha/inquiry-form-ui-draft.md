# 問い合わせ用Webフォームのロール・UI草案(フェーズ52)

cross-venture-inquiry-collection-naming-parity-review.md(フェーズ16)の次回候補(3)
「問い合わせフォーム自体のUI草案(他venture発のフォーム系wireframeとの体裁統一検討)」に
対応する。inquiry-handling-design.md(フェーズ15)2節で受付チャネルとして定めた
「結果ページ`/result/{draft_id}`下部・完了メール本文に常設する簡易Webフォーム」の
入力画面を具体化する。机上設計であり実際のフォーム実装・操作感検証は未着手。

## 1. 前提の整理

- web-form-hosting-selection.md(フェーズ49)の決定により、本venture全体の配信は
  Cloud Run(2nd gen)の同一サービス内でGET/POSTを捌く構成。問い合わせフォームも
  追加のGCPプロダクトを増やさず同サービス内の新規ルートとして実装する前提とする。
- 送信先コレクションは`inquiry/{inquiry_id}`(inquiry-handling-design.md 2節で確定)。
  フィールドは`draft_id`・`customer_email`・`category`(4区分)・`detail`・`status`・
  `created_at`。
- 本venture一貫の設計方針(低頻度利用に常時稼働コンポーネントを増やさない)により、
  双方向チャットボットは持たず、送信=蓄積のみで自動一次回答は行わない
  (inquiry-handling-design.md 2節)。UI側もこの「単方向フォーム」という前提に
  合わせ、送信後は「受け付けました」の静的な確認表示のみとし、以降の会話継続画面は
  設けない。

## 2. 2つの入口と`draft_id`の事前入力

問い合わせの入口は結果ページとメール本文の2種類あり、`draft_id`を把握している
状況が異なるため、入力負荷を減らすために入口ごとにURLクエリパラメータでの
事前入力可否を分ける。

1. **結果ページ`/result/{draft_id}`下部のリンク**: 既にブラウザがその`draft_id`の
   ページを表示している状態なので、リンク先を`/inquiry?draft_id={draft_id}`とし、
   フォーム側は`draft_id`をクエリパラメータから読み取って非表示のhiddenフィールドに
   埋め込む(主催者に再入力させない)。画面上には「対象: {draft_id}の生成結果について」
   という確認表示のみ行い、編集不可とする(厳守事項「推測で埋めない」と同様、
   表示中のページと異なる`draft_id`を誤って手入力させる事故を防ぐ)。
2. **完了メール本文のリンク**: メール本文自体に`draft_id`を直接書くと、メール転送時に
   第三者が`draft_id`を知り得てしまう(one-time-checkout-no-account-design.mdで
   `draft_id`はTTL内の結果アクセスキーを兼ねるため、result-page-ttl-access-design.md
   の意図しない共有防止方針と矛盾する)。そのため、メール本文のリンク先は
   `draft_id`なしの`/inquiry`とし、フォーム側で`draft_id`をプレースホルダ付きの
   通常入力欄として表示する(メール本文に記載された注文番号表記〈下4桁等〉を見ながら
   手入力できるよう、メール本文には`draft_id`の下4桁のみ記載する運用とする。
   全桁記載はTTL内のアクセスキー漏えいに直結するため採用しない)。

## 3. 入力画面の構成

1. **問い合わせ区分(`category`)**: ボタン選択4択(メール未着/再送希望/返金希望/
   その他)。自由記述欄への切り替えより先に区分を確定させることで、オーナー側の
   一次仕分け(inquiry-handling-design.md 3節のシナリオ別対応)をフォーム入力の
   時点で済ませる。
   - 「メール未着」「再送希望」はいずれも3節シナリオ1・2(再送系)に対応するため、
     ボタン選択後に補足テキスト「結果ページのTTL〈生成から24時間〉が切れている場合は
     再送ができず、再入力無料または返金のご案内になります」を自動表示する
     (厳守事項相当、result-page-ttl-access-design.mdの既存案内文言を再掲)。
   - 「返金希望」選択時は3節シナリオ3(品質不満)を想定し、自由記述欄のラベルを
     「生成結果のどの点が期待と異なったか」に変化させる(他区分は「お問い合わせ内容」)。
2. **`draft_id`**: 2節の方式により、結果ページ入口ではhidden+確認表示、メール入口では
   通常入力欄(下4桁からの手入力を想定したプレースホルダ「例: a1b2」)。
3. **`customer_email`**: 決済時に入力済みのメールアドレス(ttl-expiry-result-delivery-
   refund-design.md 2節で決済フローに組み込まれている)と同じものを入力する前提の
   通常入力欄。事前入力は行わない(フォーム側にその場で決済時メールアドレスを
   引き継ぐ機構は現時点で未設計のため、主催者本人の手入力に委ねる)。
4. **`detail`**: 自由記述欄(上記1のラベル切り替えあり)。
5. 送信ボタンは1つのみ。`category`・`customer_email`・`detail`が入力され、
   `draft_id`(hidden時は自動、通常入力時は必須)が揃えば送信可能とする。

## 4. 送信後の表示

「お問い合わせを受け付けました。内容を確認のうえ、ご入力いただいたメールアドレス宛に
ご連絡します」という静的な確認文のみを表示する(1節のとおり自動一次回答なし)。
返信までの目安時間は、オーナー側の対応体制(個人運営)を踏まえ具体的な時間を
明記せず「確認のうえ」という表現に留める(未検証の運用実態を確定的に案内しない)。

## 5. 他venture発フォームとの体裁統一の確認

forklift-pashaのweb-form-ui-design.md(フェーズ71)が採用する「区分をボタンで先に
確定させてから自由記述欄のラベル・初期値を切り替える」という設計パターンを、本
ventureの問い合わせフォーム(category選択→detail欄ラベル切り替え)にも踏襲した。
一方、forklift-pashaは点検記録という高頻度入力(タップ数最小化が主眼)に対する設計
であるのに対し、本ventureの問い合わせは低頻度・1回限りの入力であるため、
localStorageによる前回値キャッシュ等の高頻度最適化は不要と判断し採用しなかった
(本venture固有の利用頻度特性に基づく意図的な差異)。
