# 結果ページのTTL失効後の閲覧可否 設計(フェーズ14)

ttl-expiry-result-delivery-refund-design.md(フェーズ12)「4. 未検証・残課題」1点目
「結果ページのTTL後の扱い(閲覧可否)」に対応する。

## 1. 前提の整理

- `one_time_draft/{draft_id}`自体はFirestoreのTTLポリシーにより作成から24時間後を
  目安に削除される(フェーズ12・1節)。
- 結果ページ`/result/{draft_id}`は`one_time_draft`ドキュメントを参照して表示する
  設計(フェーズ12・2節)のため、ドキュメントが削除されると表示に必要なデータ自体が
  失われる。「閲覧可否」を検討する際は、(a)ドキュメントを残して閲覧だけ止めるか、
  (b)ドキュメントの削除タイミング自体を閲覧要件に合わせるか、の2通りの設計があり
  得ることをまず整理する。

## 2. 方針: TTL失効と同時に閲覧不可とする(ドキュメント削除に閲覧制御を委ねる)

- 単発決済モデル(1決済=1生成)という本ventureの前提(フェーズ10)に立ち返ると、
  主催者が結果を受け取るべき場面はイベント開催前の準備作業(配置案・掲示文確認)に
  限られ、イベント当日を過ぎれば結果の参照価値自体が急速に下がる。24時間という
  TTL期間は「決済から当日準備までに一度は確実に参照できる」ことを主眼に設定された
  値であり(フェーズ12設計時の暗黙の前提)、TTL失効後も長期保存して再閲覧可能にする
  ニーズは本ventureの利用シナリオ上は薄いと判断する。
- したがって、(a)のようにドキュメントだけ残して閲覧をアプリケーション側で止める
  個別実装(例: `viewable_until`フィールドを別途持ち、`expires_at`とは別に閲覧制御
  ロジックを実装する)は、低頻度利用に対して実装・保守コストを増やさないという
  設計方針(tech-stack.mdフェーズ7)に反するため不採用とする。
- 結論: 結果ページの閲覧可否はFirestore TTLポリシーによるドキュメント削除にそのまま
  委ねる(b)。`one_time_draft/{draft_id}`が削除された後に`/result/{draft_id}`へ
  アクセスした場合は「ページが見つかりません」ではなく、後述3節の専用の「結果の
  保存期間が終了しました」案内を表示する(ドキュメント不存在と通常の404を区別する
  ことで、主催者が「URLを間違えた」のか「期限切れ」なのかを誤解しないようにする)。

## 3. 結果ページ側の実装方針

- 結果ページの表示ロジックは、`one_time_draft/{draft_id}`取得結果に応じて以下の3状態
  に分岐する(mvp-flow-draft.mdのstatus分岐〈generated/out_of_scope/insufficient_input〉
  とは別軸の、ページ自体の表示状態)。
  1. ドキュメントが存在し生成完了(`status: generated`等): 通常の結果表示。
  2. ドキュメントが存在するが生成中・失敗: フェーズ12で設計済みの「生成中」表示
     またはttl-expiry-result-delivery-refund-design.md 3-2節の返金済み案内を表示。
  3. ドキュメントが存在しない(TTL失効済み、または`draft_id`自体が無効): 「このURLの
     結果の保存期間(24時間)が終了したため閲覧できません。再度ご利用いただく場合は
     お手数ですが最初からお申し込みください」という案内文を表示する。決済自体は
     既に完了しているはずの画面であるため、誤って「お申し込みください」の文言だけが
     目に入り二重決済を誘発しないよう、案内文には「既にお支払い済みの場合、結果を
     再度確認したい旨をメール完了通知の返信等でご連絡いただければ個別対応します」
     という問い合わせ導線も合わせて記載する(本venture自体の個別問い合わせ対応フロー
     は未設計、次回候補とする)。
- 3節(3)の「個別対応」に該当する問い合わせが実際に発生した場合、オーナー自身による
  確認・対応(結果データの再送等)が必要になる可能性があるが、これは本フェーズでは
  想定シナリオの整理のみに留め、実際の問い合わせ対応フロー自体の設計は次回候補とする。

## 4. 未検証・残課題

- 3節(3)の「個別対応」の具体的な対応フロー(オーナー自身がFirestoreの旧データを
  遡って確認する手段がTTL削除後は存在しないため、実質的には「結果データの再生成」
  または「返金」のいずれかになる可能性が高い)の設計は未着手。
- 「このURLの結果の保存期間が終了しました」表示自体の多言語対応・文言の最終調整は
  未検討。
- 実際のFirestore TTLポリシー設定・結果ページの実装自体はGCPプロジェクト作成後の
  話であり、オーナー承認待ちの範囲(pending-approval.md参照)。今回は表示方針の
  机上設計のみに留める。
