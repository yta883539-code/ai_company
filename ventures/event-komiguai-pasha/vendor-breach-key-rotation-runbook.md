# 外部ベンダー侵害発覚時の自社キー緊急ローテーション手順(設計)

## 1. 背景

ノーコードWeb制作サービス「Studio」(Studio株式会社)は2026年10月16日、クラウド環境内の
脆弱性を悪用した第三者による不正アクセスを公表した(不正アクセス確認期間は2026年9月30日
〜10月1日、同社は10月14日までに脆弱性修正・経路遮断を完了)。対象は全登録顧客のアカウント
情報に加え、各社サイトのフォーム送信内容、**外部サービス連携用のAPIキー**にまで及んだ
(piyolog・internet.watch.impress.co.jp・cybersecurity-jp.com・rocket-boys.co.jp各報道で
確認)。デジタル庁も2026年10月22日、同社サービスを一部ホームページ運営に利用していたことを
理由に問い合わせフォーム最大13,323件の漏えい可能性を公表し、LUUP(21,368件)・Link-U
(7,663件)・ラクスル(6,412件)等、業種を問わず多数の組織に波及した。

本件は個人情報保護法上の報告・本人通知義務の一次整理が主題の既存「パシャっと」系漏えい対応
アイデア群とは異なり、漏えいした情報に**個人情報だけでなく自社が外部サービスと連携するために
使っていたAPIキー・復号鍵そのものが含まれる**ケースを扱う。この場合、個人情報保護法上の対応
に加えて、漏えいしたキーを使って第三者が自社の決済代行・LLM API・データベース等の外部
サービスへ不正アクセスできる状態が生じている可能性があり、通常の漏えい対応とは別に「自社が
保有するキー群を総点検し、影響範囲が確定する前に予防的に失効・再発行する」という技術的な
緊急対応が別途必要になる。

kura-pasha(フェーズ262)・aircon-pasha・course-set-pasha・forklift-pasha・
line-reservation-aiの5venture既に同種の設計ドキュメントを横展開済みであり、本ventureが
cross-venture横展開の対象として最後に残っていた。本ドキュメントはevent-komiguai-pasha
自体がこの種の被害を受けた場合に備え、本venture固有の依存先キー群を洗い出し、緊急
ローテーションの手順を設計のみ先行して整理するもの。実際の不正アクセス発生・キー漏えいは
本ventureには生じていない。

## 2. event-komiguai-pashaが保有する外部連携キー・シークレットの一覧

tech-stack.mdの構成を前提に、本venture固有の依存先を整理する。他venture(kura-pasha等)が
LINE Messaging APIを入力チャネルとするのに対し、本ventureは低頻度利用特性
(tech-stack.mdフェーズ7)に基づきLINE公式アカウントを採用せず、**Webフォーム**を入力
チャネルとしている点が本venture固有の差分である。

| 依存先 | 保有するシークレット | 用途 |
| --- | --- | --- |
| Stripe | シークレットキー(`sk_live_...`)・Webhook署名シークレット(`whsec_...`) | one-time-checkout-no-account-design.md(フェーズ10)のStripe Checkout one-time payment mode発行・Webhook受信、ttl-expiry-result-delivery-refund-design.md(フェーズ12)のRefund API呼び出し |
| LLM APIプロバイダ | APIキー | 4出力生成(llm-system-prompt-draft.md)、prototype/mock_llm_client.pyと差し替える実LLM呼び出し |
| GCP(Cloud Run functions・Firestore) | サービスアカウント鍵・Secret Managerアクセス権 | Webフォーム受信処理(prototype/form_submission_intake.py)の実行環境、`one_time_draft`・`inquiry`コレクション(result-page-ttl-access-design.md・inquiry-handling-design.md)の接続 |

本ventureは**LINEチャネルアクセストークン・チャネルシークレットを保有しない**ため、
他venture(kura-pasha等)の一覧表にあるLINE関連行は該当しない。これはLINE公式アカウントを
採用しないという設計方針(tech-stack.mdフェーズ7)に起因する意図的な差異であり、是正を
要する不整合ではない。

いずれも実アカウント開設自体がオーナー承認待ち(pending-approval.md参照)のため、現時点では
上記は「開設後に保有することになる」想定の一覧である。Studio社の事案のように、これらのキー
を直接保管するのが上記ベンダー自身ではなく、その先に利用するさらに別のSaaS(例: Webフォーム
ホスティングサービス自体)である場合、依存の層が一段深くなる点にも注意する(tech-stack.md
フェーズ7で検討した静的ホスティング無料枠の具体的なベンダー選定は未確定のため、選定後は
本表を更新する)。

## 3. 緊急ローテーション手順(ドラフト)

1. **検知**: 上記いずれかのベンダー(またはそのベンダーがさらに利用する委託先)が
   不正アクセス・情報漏えいを公表し、自社が保有するAPIキー・シークレットが対象に
   含まれる可能性があるとの連絡・報道を確認した時点を起点とする。
2. **一次切断**: 対象ベンダーの管理画面から影響範囲が確定する前に、該当するキー・
   シークレットを予防的に失効させ、新しいキーを再発行する(「疑わしきは即時失効」を
   原則とし、公式な影響範囲の確定を待たない)。
3. **再配線**: 新しいキーをCloud Run functionsの環境変数・Secret Managerへ反映し、
   旧キーでの呼び出しが拒否されることを確認する(例: Stripe Webhook署名検証で旧
   `whsec_...`が失敗することを確認)。
4. **不正利用の痕跡確認**: 各ベンダーの管理画面・Cloud Loggingで、キー失効までの間に
   想定外の呼び出し(決済・LLM API呼び出し等)が発生していないかを確認する。本venture
   は単発決済(1決済=1生成)のため、`one_time_draft`コレクションの決済済みフラグと
   実際のLLM呼び出し回数の不整合(決済なしにLLMが呼ばれた形跡等)も確認観点に加える。
5. **個人情報保護法上の対応との併走**: キー漏えい自体とは別に、当該ベンダーが保持して
   いた顧客データ(フォーム送信内容等、本venture経由の個人情報)が対象に含まれる場合は、
   既存の漏えい対応系「パシャっと」群と同じ一次整理(報告・本人通知の要否判定)を
   並行して行う。

## 4. 未検証・残課題

  のUI・キー失効手順の詳細は各ベンダーの実アカウント開設後に確認・更新する。
- Webフォームホスティングサービスの具体的な選定(tech-stack.mdフェーズ7で未確定)が
  決まった時点で、依存先一覧(本ドキュメント2節)に当該ベンダーを追加する。
- 他venture(aircon-pasha・course-set-pasha・forklift-pasha・kura-pasha・
  line-reservation-ai)への横展開は本フェーズで完了し、全6venture共通の対応方針が
  整った。
- 実際のキーローテーション実行・ベンダーへの問い合わせ自体は、各ベンダーの実アカウント
  開設(オーナー承認待ち)後でなければ発生しない。本フェーズはコード変更を行わない。
