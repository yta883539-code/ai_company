# draft_id生成方式の確定と末尾4文字衝突可能性の確認(フェーズ53)

inquiry-form-ui-draft.md(フェーズ52)6節の残課題、および one-time-checkout-no-account-
design.md(フェーズ10)2節で「入力内容のハッシュ値またはUUID」のまま未確定だった
`draft_id`の生成方式を本フェーズで確定し、問い合わせメール本文に記載する末尾4文字の
衝突可能性を確認する。

## 1. `draft_id`生成方式をUUID4に確定

- ハッシュ値方式は採用しない。(1)5入力要素(`capacity`等)が同一の入力を送った別の
  主催者同士で`draft_id`が重複し得る、(2)入力内容からの一方向ハッシュは原理的に入力の
  推測・突合に使われ得り、`draft_id`がTTL内の結果アクセスキーを兼ねる(result-page-
  ttl-access-design.md)という前提(推測不能なランダムトークンであること)と相性が悪い。
- 以上より、ランダムUUID(UUID version4、RFC 4122)を採用する。128bit中122bitが
  完全にランダムで、残り6bitがversion/variantの固定ビットである。

## 2. 「末尾4文字」の位置とランダム性の確認

UUID4の文字列表現は`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`の5群構成であり、固定ビットは
3群目先頭1文字(`4`固定、version)と4群目先頭1文字(`8`/`9`/`a`/`b`の4通りのみ、
variant)に位置する。inquiry-form-ui-draft.md・README.mdで言及している「末尾4文字」は
文字列末尾=5群目(12文字)の末尾4文字であり、version/variantの固定ビットを含まない
完全にランダムな16進4文字である。したがって16^4=65,536通りがほぼ均等に分布し、
現行の「メール本文には末尾4文字のみ記載する」運用はそのまま有効と確認した。

## 3. 衝突確率の試算

衝突が実害になるのは、オーナーが`inquiry`対応時に末尾4文字から`one_time_draft`を
検索した際に複数件ヒットする状況であり、これはTTL(24時間)で失効していない
(=直近24時間以内に発行された)`draft_id`の件数に依存する。誕生日問題の近似式
p≈1-e^(-n(n-1)/(2N))(N=65,536)で試算すると、

| 24時間以内の発行件数n | 衝突確率(近似) |
|---|---|
| 10 | 約0.07% |
| 50 | 約1.87% |
| 100 | 約7.56% |

本venture立ち上げ初期(個人主催の小規模イベント運営者向け、500円/回の単発利用)の
想定発生件数は一桁〜十数件/日程度と見込まれ、この規模では実務上無視できる水準だが、
利用が伸びて同時発行件数が増えると無視できない水準になるため、末尾4文字だけを
一意キーとして運用しない設計を4節で確定する。

## 4. 衝突時のオーナー側照合手順の確定

- inquiry-form-ui-draft.md(フェーズ52)3節で、問い合わせフォームの`customer_email`は
  決済時にStripe Checkoutへ入力したものと同一を主催者が入力する前提の必須項目として
  既に設計済みである。
- `one_time_draft/{draft_id}`に`customer_email`フィールドを追加する(Webhook受信時、
  決済完了メール送信に使う`customer_email`をそのままレコードへ書き込む。ttl-expiry-
  result-delivery-refund-design.md〈フェーズ12〉2節で既にStripe Checkout Session作成時
  の`customer_email`必須化は確定済みのため、追加の決定事項はこのフィールドをFirestore
  レコードへ保存する点のみ)。
- オーナー側の検索手順を「(1)末尾4文字で`one_time_draft`を絞り込み→(2)複数件ヒットした
  場合は問い合わせフォームの`customer_email`と一致するものを採用」という二段階照合に
  確定する。末尾4文字は検索の初期フィルタ(ヒント)、`customer_email`が一意性を保証する
  実質的な照合キーという役割分担とする。
- 末尾4文字・`customer_email`の両方が一致してしまう極めて低い確率の事象は、
  問い合わせ本文(`category`・`detail`)と結果ページの生成内容をオーナーが目視で
  照合する手動対応に委ねる(本venture低頻度運用の前提上、これ以上の自動化は
  コストに見合わないと判断)。
