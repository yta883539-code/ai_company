# LLM API利用コスト試算(生成1回あたりの原価 vs pricing-plan.mdの従量単価・基本料実質単価)

作成日: 2026-10-19

## 背景

pricing-plan.md(フェーズ4)で料金プラン(月額+従量課金+単発利用)を仮決めしたが、原価構造の
主要素であるLLM API呼び出し自体のコスト(Claude API利用料)は本ventureで未試算だった。
course-set-pasha/llm-api-cost-estimate.md・aircon-pasha/llm-api-cost-estimate.mdの構成・前提を
踏襲しつつ、本venture固有の入出力規模(llm-system-prompt-draft.md・schema/output.schema.json・
mvp-flow-draft.md)に置き換えて試算する。claude-apiスキル記載の公開料金表(2026年10月時点、
Claude 5.5世代)を使用した机上試算であり、実LLM API呼び出し自体は行わない
(オーナー承認待ちの範囲、pending-approval.md参照)。

## 前提(入出力トークン数の概算)

- **入力(1)システムプロンプト+構造化出力スキーマ**: llm-system-prompt-draft.md(9,847文字)・
  schema/output.schema.json(7,886文字)の現行ドラフト合計17,733文字。他venture同様、実際にAPIへ
  送信するシステムプロンプトは設計根拠の説明等のメタ記述を除いた凝縮版になる見込みが高いため、
  以下2シナリオで幅を持たせる。
  - シナリオA(圧縮後の想定・保守的な小規模プロンプト): 2,300トークン
  - シナリオB(現行ドラフトの文字数からの概算・上限側): 日本語・英語混在のMarkdownを
    1トークン≒2文字と仮定し、約8,900トークン
- **入力(2)主催者の入力メモ**: mvp-flow-draft.mdの入力例(「会場キャパ800人、入場口2箇所・
  退場口1箇所、開場16:30/開演18:00、自由入場(整理番号なし)、警備員は会場スタッフ4名のみ、
  過去にヒヤリハット無し」等、80〜120文字程度)に基づき、日本語1文字≒1トークンで150〜300トークン
  (シナリオAは200トークン、シナリオBは300トークンを採用)。

- **出力(4出力)**: (1)入退場時混雑確認セルフチェックリスト、(2)警備員重点配置案・分散入場誘導
  アナウンス文案、(3)来場者向け掲示文案(`outdoor_queue`に応じた道路使用許可注記を含む)、
  (4)ヒヤリハット記録フォーマット例。course-set-pasha(3出力)より出力数が1つ多く、(2)は
  アナウンス文案を含むため、600〜1,300トークン(シナリオAは900トークン、シナリオBは1,300
  トークンを採用)。

正確なトークン数は、実LLM接続後に`count_tokens`(無料・課金なしの計測専用エンドポイント)で
確認する必要がある(接続自体はオーナー承認待ちのため未実施)。本試算は上記の概算値に基づく
机上の上限見積もりである。

## プロンプトキャッシュ適用時の試算(シナリオB、Sonnet 5.5)

システムプロンプト+スキーマ部分(約8,900トークン)は入力メモの都度変化しない固定部分のため、
プロンプトキャッシュ(cache_control)の対象にできる。2回目以降の生成でキャッシュ読み取り
(Sonnet 5.5はキャッシュ読み取り$0.20/100万トークン)が効く前提で試算すると:

- システムプロンプト部分: 8,900トークン × $0.20/100万 × 150円 ≒ 0.27円
- 入力メモ部分(キャッシュ対象外): 300トークン × $2/100万 × 150円 ≒ 0.09円
- 出力: 1,300トークン × $10/100万 × 150円 ≒ 1.95円
- 合計: 約2.31円(キャッシュなしの約4.71円から約51%削減)

pricing-plan.mdが想定する利用頻度(個人経営の小規模ライブハウスで月数件〜十数件、単発主催者は
月1〜2件程度)はcourse-set-pasha(週2〜3回)より利用間隔が長く、デフォルトのキャッシュ有効期限
(5分)では生成のたびにキャッシュ書き込みが再発生する見込みが高い。1時間〜それ以上のTTLの検討
余地があるが、月数件程度の頻度ではTTL延長でも毎回書き込みが発生するケースが残るため、
キャッシュ効果は他venture(line-reservation-ai・course-set-pasha等、週次以上の利用頻度)より
限定的である可能性が高いことを前提として残す(実装時の要検証事項)。

## pricing-plan.mdの従量単価・基本料実質単価との比較

| 比較対象 | 金額(1回あたり) | Sonnet 5.5・シナリオB・キャッシュ利用時との比率 |
|---|---|---|
| 単発利用(都度課金) | 500円 | 約0.5% |
| ライトプラン従量単価 | 250円 | 約0.9% |
| スタンダードプラン従量単価 | 200円 | 約1.2% |
| ライトプラン基本料実質単価(780円÷3件) | 約260.0円 | 約0.9% |
| スタンダードプラン基本料実質単価(1,980円÷10件) | 約198.0円 | 約1.2% |

最も保守的な組み合わせ(Opus 5.5・シナリオB・キャッシュなし、約9.42円)で比較しても、
最安の単価(スタンダード従量単価200円)に対して約4.7%にとどまり、十分な粗利が残る計算になる。
Sonnet 5.5・キャッシュ利用時であれば約1%程度とさらに小さい。本ventureはcourse-set-pasha等と
同様、LLM API原価が事業性を圧迫する主要因にはならないという結論が成り立つ。

## 結論・次のステップ候補

- 本venture(4種類の短い日本語下書きを生成する単方向バッチ処理)の用途であれば、他
  「パシャっと」シリーズの結論と同様にClaude Sonnet 5.5で十分な品質が見込め、Opus 5.5ほどの
  高価格帯モデルは必須ではない可能性が高い。実LLM接続後、schema/validate_test_cases.pyが
  検証した厳守事項(道路使用許可注記・ヒヤリハット記録5項目固定等)の通過率を踏まえたモデル
  選定の比較検証が必要。
- 正確なトークン数は`count_tokens`エンドポイント(無料)で実測できるため、実LLM接続の承認が
  得られた際は、まずcount_tokensのみで正確な入出力トークン数を確認し、本試算のシナリオA/Bの
  どちらに近いかを特定してから実際の生成呼び出しに進む順序が望ましい。
- プロンプトキャッシュの導入(システムプロンプト+スキーマ部分への`cache_control`付与)は
  コスト削減効果があるが、本venture想定顧客の利用頻度(月数件程度)では他venture以上に
  キャッシュ書き込みの再発生が見込まれるため、原価試算上の必須前提とはしない(導入自体は
  実装時の優先事項として残す)。
- 実際のLLM API呼び出し・APIキー取得はオーナー承認が必要なアクションであり、本ドキュメントは
  あくまで契約前の判断材料整理にとどまる(pending-approval.md記載の既存の承認待ち事項の範囲内、
  新たな承認待ち事項は発生しない)。
