# MVP入出力フォーマット草案(フェーズ2)

## 対象

専任の警備計画・安全管理担当者を置かない個人〜小規模のライブハウス運営者・屋内音楽イベント
(ライブ・トークイベント等、数百〜数千人規模)主催者。

## 入力

主催者がチャット/Webフォームに入力する簡単なメモ。例:

- 「会場キャパ800人、入場口2箇所・退場口1箇所、開場16:30/開演18:00、自由入場(整理番号なし)、
  警備員は会場スタッフ4名のみ、過去にヒヤリハット無し」
- 「会場キャパ300人、入場口1箇所(入退場共用)、全席指定、警備員は外部委託3名+自社スタッフ2名」

market-research.mdフェーズ1での確認を踏まえ、入力メモから以下の要素を抽出する。

1. `capacity`(会場キャパシティ)
2. `entry_exit_points`(入場口・退場口の数、共用か分離か)
3. `admission_type`(自由入場/指定席/事前予約制〈先着・抽選〉等)
4. `staffing`(自社スタッフ数・外部委託警備員数)
5. `outdoor_queue`(入場待機列が屋内に収まるか、屋外・公道に及ぶ可能性があるか)

`outdoor_queue`が未入力または「屋外に及ぶ可能性あり」の場合、出力(3)の掲示文案に加えて
「待機列が公道に及ぶ場合は所轄警察署への道路使用許可の要否を主催者自身で確認してください」
という注記を必ず付す(market-research.mdフェーズ1で次回候補として挙げた論点への対応)。

### admission_typeへの「事前予約制(先着・抽選)」追加について(フェーズ21)

event-komiguai-pashaフェーズ20の候補探索中、東京藝術大学のギャラリートーク等、入場を
時間枠単位の事前予約(先着・抽選)で管理する屋内イベント事例が見られたため、
`admission_type`の選択肢に「事前予約制(先着/抽選)」を追加した。既存の2値
(自由入場=focus:entry、指定席=focus:exit、G3_mixed_admission_typeテストケースの
混在=focus:both)との関係は次の通り:

- 事前予約制は来場時刻が予約枠で分散されるため自由入場のような開場直後の入場集中は
  起きにくい一方、来場者側が予約枠の到着時刻を厳密に守らない場合(早めに並ぶ等)や、
  予約枠が1回(全員同時刻)しかないイベントでは自由入場と同様の入場集中が生じ得る。
  また退場は同時刻に集中しやすく指定席と同様の傾向を持つ。
- このため事前予約制は入力のみからどちらに重点を置くべきか一意に決まらず、
  混在(admission_type混在)と同様に`focus:both`を既定値とし、出力2の文案内に
  「予約枠が複数時間帯に分かれているか、入場時も混雑し得るかを主催者自身で確認してください」
  という注記を付す方針とする(既存のG3_mixed_admission_typeの扱いを転用)。
- スキーマ(output.schema.json)・テストケース(validate_test_cases.py)への反映は
  フェーズ22で完了した。output.schema.jsonの`staffing_plan.focus`descriptionに
  事前予約制の場合もbothを既定とする旨を追記し、validate_test_cases.pyに
  `G4_advance_reservation_admission_type`(focus:both、予約枠の集中有無が一意に
  決まらない旨の判断委任記載あり)を追加、全12件(既存11件+1件)パスを確認した。

## 出力

1. 入退場時混雑確認セルフチェックリスト: `capacity`・`entry_exit_points`・`admission_type`から、
   消費者安全調査委員会の経過報告(csic_cms201_260930_01.pdf)が指摘する確認項目(入退場口数が
   キャパシティに対し十分か、開場から開演までの導線上に合流・ボトルネックが生じないか等)に基づく
   チェックリストを生成。
2. 警備員重点配置案・分散入場誘導アナウンス文案: `staffing`と`entry_exit_points`から、混雑が
   見込まれる時間帯(開場直後等)・エリア(入場口付近等)に応じた重点配置の一次案、および
   分散入場を促すアナウンス文案の下書きを生成。
3. 来場者向け整列・分散入場案内の掲示文案: 入場口付近に掲示する簡潔な案内文の下書き
   (`outdoor_queue`に応じた道路使用許可注記を含む)。
4. ヒヤリハット記録フォーマット例: 発生日時・場所・状況・対応・再発防止策を記載する記録簿の
   テンプレート(将棋倒し等の未然事例を想定)。

## 出力スキーマ方針(次回フェーズで実装)

course-set-pasha/kura-pasha等の既存「パシャッと」シリーズと同型のstatus分岐
(`generated` / `out_of_scope` / `insufficient_input`)を踏襲する。`insufficient_input`は
`capacity`・`entry_exit_points`・`admission_type`のいずれかが欠落している場合。`out_of_scope`は
警備計画の最終確定・入場制限の実施判断・外部警備会社への発注契約・所轄警察署への届出代行等、
主催者・警備責任者自身の判断権限に属する要求が来た場合。

## 範囲外(厳守事項の方向性)

- 警備計画の最終確定・入場制限の実施判断はしない(market-research.mdフェーズ1の整理の通り、
  生成物はあくまで主催者自身が最終決定する一次案)。
- 外部警備会社への発注・警備業法上の委託契約自体は代行しない。
- 所轄警察署への道路使用許可申請・届出代行はしない(注記により確認を促すのみ)。
- 興行場法・都道府県興行場条例が定める施設の構造基準(避難経路の設置等)の適否判断はしない。

## capacityの定義方針(複数の情報源で収容人数の記載が食い違う場合、フェーズ42追記)

interview-rehearsal-script.md(フェーズ37)「確認ポイント」で、層1候補1(奈良NEVER LAND)の
収容人数がサイトごとに230人(livefans.jp)/250人(ticketjam.jp)と食い違い、
「`capacity`入力値を消防法上の定員か運用上の実質人数のどちらで記録するかの判断基準を
別途整理する必要がある」という未確定事項が残されていたため、本フェーズで机上の方針を
整理する。

- `capacity`は、主催者が入力メモに記載した1つの数値をそのまま採用し、本サービス側で
  複数の情報源(消防法上の定員・座席表上の数値・過去の実績動員数等)を突き合わせて
  「正しい」数値に補正することはしない(本サービスはあくまで主催者自身の入力を一次案の
  生成に用いる設計であり、入力値の真正性確認は主催者自身の責任範囲という既存の厳守事項の
  方針〈mvp-flow-draft.md「範囲外」節〉と整合させるため)。
- ただし、入力メモ内に「定員(消防法上)」「実質収容人数」等、複数の数値が異なる名目で
  併記されている場合は、`insufficient_input`とはせず、出力1(入退場時混雑確認セルフ
  チェックリスト)の冒頭に「複数の収容人数の記載がある場合は、入退場口数に対する比率算出に
  用いた数値を明示し、他の数値も参考値として併記する」という注記を付す方針とする。これは
  厳守事項1(警備計画の最終確定への不介入)と同様、どの数値を基準に使うかの最終判断は
  主催者自身に委ねる考え方を踏襲したものである。
- この方針は、実在候補(層1候補1等)の収容人数の食い違いという個別事例を一般化したもので、
  schema/output.schema.json・validate_test_cases.pyへの反映(複数収容人数併記ケースの
  テストケース追加)は次回候補とする(現時点ではコード変更は行っていない)。
