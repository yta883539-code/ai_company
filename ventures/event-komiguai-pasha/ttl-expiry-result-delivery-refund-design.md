# TTL失効・結果返却方式・返金/決済失敗時の挙動 設計(フェーズ12)

one-time-checkout-no-account-design.md(フェーズ10)「未検証・残課題」の3点
(TTL失効の実装方式、結果返却方式の決定、返金・決済失敗時の挙動)に対応する。

## 1. `one_time_draft`のTTL失効の実装方式

- Firestoreのネイティブ機能である「TTLポリシー」を採用する。定期バッチ(Cloud Scheduler
  +Cloud Functions)による削除は、本ventureが他venture比で志向する「低頻度利用に対して
  固定費・常時稼働コンポーネントを増やさない」という設計方針(tech-stack.mdフェーズ7)に
  反するため不採用とする。
- `one_time_draft/{draft_id}`に`expires_at`フィールド(作成時刻+24時間のタイムスタンプ)を
  追加し、FirestoreのTTLポリシーで`expires_at`を指定する。TTLポリシーの実際の設定(GCP
  プロジェクト側の操作)自体はGCPプロジェクト作成後に行うため、現時点ではフィールド設計
  のみを確定する。
- TTL削除は保証はされるが即時ではない(Firestoreの仕様上、数時間程度のタイムラグが生じ
  得る)ため、`expires_at`を過ぎたレコードへの決済完了通知(Webhook)が万一到達した場合に
  備え、Webhook処理側でも`expires_at`を過ぎた`draft_id`への`checkout.session.completed`
  受信時は生成を行わず「期限切れ」エラーとして処理し、後述2節の返金フローに回す防御的
  チェックをステータス遷移ロジックに追加する(TTL自体に処理の正しさを依存させない)。

## 2. 決済完了後の結果返却方式

- one-time-checkout-no-account-design.md(フェーズ10)で未決定だった(a)リダイレクトURL方式・
  (b)メールリンク方式について、「(a)を主経路、(b)を取りこぼし防止の併用経路とする」
  ハイブリッド方式を採用する(いずれか一方の選択ではなく併用する点が今回の決定)。
  1. Stripe Checkout Session作成時に`customer_email`の入力を必須項目として求める
     (継続課金モデルのようなアカウント登録は発生させないが、結果到達性の確保のために
     メールアドレスのみ取得する)。
  2. 決済完了後、Stripeの`success_url`で主催者を`/result/{draft_id}`(結果表示ページ)へ
     リダイレクトする(a方式)。生成処理は2節後述のとおりWebhook受信をトリガーに非同期で
     実行されるため、リダイレクト直後は「生成中」表示とし、クライアント側でポーリングまたは
     結果ページ自体の再読み込みにより生成完了を確認する設計とする。
  3. Webhook(`checkout.session.completed`)受信・生成処理完了時に、`customer_email`宛て
     に結果ページ`/result/{draft_id}`への直接リンクを記載した完了メールを送信する(b方式)。
     ブラウザを閉じる等でリダイレクト画面を失った場合でも、このメールのリンクから同じ
     結果ページに再アクセスできる。
  4. 結果ページ`/result/{draft_id}`自体は`expires_at`後も一定期間(残課題、次回検討)は
     閲覧可能とするか、TTL失効と同時に閲覧不可とするかは未決定のまま残す。
- メール送信手段(SMTP/メールAPI)の選定自体は実装時の課題として残し、他venture
  (forklift-pasha trial-end-notification-design.md等)と同様、実際の送信はメール連携
  接続後にオーナー確認を経て行う前提(pending-approval.mdの既存範囲を踏襲、本ventureに
  固有の新規承認事項は発生しない)。

## 3. 返金・決済失敗時の挙動

決済失敗時と生成失敗時を明確に区別する。

### 3-1. 決済自体が失敗する場合(カード拒否等)

- Stripe Checkoutページ上でのカード拒否等は、Stripe側の標準フロー内で主催者が再入力・
  再試行する(Stripeの標準機能の範囲内で、本サービス側の追加実装は不要)。
- `checkout.session.completed`が発火しない限り`one_time_draft`のステータスは
  `awaiting_payment`のまま変化せず、実際の課金は発生していないため返金の概念自体が
  生じない。TTL失効(1節)によりそのまま期限切れとなる。

### 3-2. 決済完了後に生成処理(LLM API呼び出し)が失敗する場合

- 継続課金モデルの解約系設計(stripe-cancellation-deletion-candidate-trigger-design.md等)
  に相当する、単発決済モデル固有の「決済は成功したがサービス提供(生成)ができなかった」
  ケースへの対応を新規に整理する。
- 処理フロー:
  1. Webhook受信後、生成処理を最大2回まで自動リトライする(一時的なLLM API障害を想定)。
  2. 2回失敗した場合、`one_time_draft/{draft_id}`のステータスを`generation_failed`に
     更新する。
  3. Stripe Refund API(`refunds.create`、対象`payment_intent`)により全額自動返金する
     (主催者側の過失によらない不具合のため、オーナーによる個別判断を待たず全額返金を
     既定動作とする設計方針とする。他venture同様、実際のAPIキーでの返金実行自体は
     Stripeアカウント接続後の話であり現時点では机上設計)。
  4. 返金完了後、`customer_email`宛てに「生成処理に失敗したため全額返金した」旨と
     再度入力し直す場合の案内を記載したメールを送信する(2節のメール送信経路を再利用)。
- 本フローは課金・利用回数カウンタを持たない単発決済モデル特有の簡潔さ(継続課金モデル
  のような按分計算が不要)を活かした設計である。

  で解消済み。TTL失効(ドキュメント削除)と同時に閲覧不可とし、専用の「保存期間終了」
  案内を表示する方針を確定している(フェーズ46でこの残課題欄の記載漏れを是正)。
- Stripe Refund APIの返金可能期間(Stripeの制約、通常180日以内)を超えた場合の例外処理
  は、フェーズ46で以下の通り整理し解消する。本venture(単発決済・TTL24時間)では、
  3-2節の自動返金はWebhook受信直後(決済完了から数分〜数時間以内)に実行され、
  inquiry-handling-design.md(フェーズ15)の個別問い合わせ対応フローも問い合わせ発生から
  相応の期間内にオーナーが判断する前提であり、決済から180日を跨いで返金判断が
  持ち越される運用上のシナリオは想定されない。したがって本exception処理は設計不要と
  判断し、万一180日を超過した個別問い合わせ(フェーズ15の類型3等)が発生した場合のみ、
  Stripe側がRefund APIエラーを返すため、その時点でオーナーに「Stripe側の返金期限超過
  のため返金不可、他手段(銀行振込等)での個別対応が必要」と案内する例外ハンドリングを
  inquiry-handling-design.mdの対応フロー実装時に追加すれば十分とする(机上設計のみ)。
- Firestore TTLポリシーの実際の設定(GCPプロジェクト側の操作)自体は、実GCPプロジェクト
  作成後に行うため、オーナー承認待ちの範囲(pending-approval.md参照)として残る。
- 実際のStripeアカウント接続・Webhookエンドポイント登録・GCPプロジェクト作成・メール
  送信手段の接続はいずれもアカウント作成・支払いが発生するためオーナー承認待ちの範囲
  (pending-approval.md参照)。今回は実装方式の机上設計のみに留める。
